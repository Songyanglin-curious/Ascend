## 问题定义

- 问题一句话描述：先实现“处理逻辑如何定义、如何被编排、如何在控制台循环跑起来”的最小工作流内核。
- 背景：Ascend 原先容易被理解成多 Agent 系统，导致抽象过高、实现容易跑偏；现已收敛为“多处理逻辑 + 工作流编排 + 有限 AI 调度”的方向，具体的操作是Node接受一个问题或者统一抽象为输入  然后交给场景 场景呢目前定义为 多个处理逻辑 组成的工作流（定义不同任务如何组织模式。
    例如：

    * 思考场景：Explore → Select → Freeze
    * 写作场景：Structure / Write → Review → Revise
    * 学习场景：Explore → Summarize → Review
    * 需求文档场景：Explore → Select → Structure → Write → Review → Freeze
    场景层回答的是：
    一类任务通常如何组合推进模式
    备注：
        真正的工作流不是这样单项推进，而是可循环可判断选择分支。
    ）

场景由 Mode（也可以叫做处理逻辑） 组成的  目前最新的我们抽象为 处理逻辑  暂时就是一份提示词来控制AI的功能（
        定义不同类型的具体的推进方式。
        例如：
        * Explore：探索
        * Select：选择
        * Write：写作
        * Review：评审
        * Revise：修订
        * Summarize：提炼
        * Freeze：冻结

        模式层是：
        这一步到底是以什么方式推进  
    ）

场景的工作流 不是单一的推进 而是可循环 可判断选择分支

- 触发原因：当前最核心的不是完整恢复体系，而是先把处理逻辑、提示词输入、上下文拼装、切换编排、NodeRaw 记录、切换回调这条主链跑通，并且能接入 DeepSeek 真正测试。
- 目标：
  1. 定义处理逻辑的数据结构与最小契约
  2. 实现处理逻辑注册与工作流编排
  3. 让控制台能够将工作流循环跑起来
  4. 工作流要可编辑
  5. 使用 `deepseek-reasoner`因为后续的工作都是思考性的为主，所以需要推理能力强的模型 ，但是这个最好做统一的抽象，AI模型的统一抽象(你可以根据情况自己决定，你这块比我更熟悉)
  6. 每次调用 AI 时，正确传入当前逻辑的提示词和上下文
  7. 每次 AI 交互向 NodeRaw 写入记录
  8. 每次工作流切换时，通过回调向外暴露下一次建议模型及切换信息 （便于后续添加节点运行状态记录后向其记录）
  9. 工作流可以有出口通过分支逻辑判断 也可以允许人强行中断 退出
  10. 自然退出和人为强行中断退出 执行相同的后续逻辑
  11. 工作流目前要有cach机制 当无法正常正确流转进入cach 目前先放TODO占位（后续在这里使用调度AI进行调度处理接续工作流）
- 非目标：
  1. 不实现完整恢复工作流
  2. 不实现复杂异常处理，只用 TODO 占位
  3. 不实现前端界面
  4. 不实现 Agent 调度

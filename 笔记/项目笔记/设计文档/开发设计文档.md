# Ascend 1.0 开发设计文档

## 1. 文档定位

本文档不是理念说明，不是方案摘要，而是：

**面向实际开发落地的系统设计文档。**

它回答的问题是：

1. 系统需要拆成哪些模块
2. 每个模块负责什么
3. 模块之间如何交互
4. 哪些是同步链路，哪些是异步链路
5. 第一版应该按什么顺序实现
6. 每个模块采用什么技术和实现方式

本文档默认以下内容已经成立：

- Ascend 1.0 的统一推进契约已确定
- Node / StepRecord / Scheduler / Rescan 的职责边界已确定
- 1.0 只做单人、单工作台、单项目范围内的最小闭环

---

## 2. 开发目标

Ascend 1.0 的开发目标不是做一个“看起来很完整”的平台，而是做出一套真正可跑通的最小推进系统。

第一版只要求做到：

1. 可以创建推进对象
2. 可以把对象组织成树/图关系
3. 可以选出当前应该推进的 Node
4. 可以执行一轮最小推进
5. 可以生成 StepRecord
6. 可以回写 Node 当前态
7. 可以在关键变化后同步重新纳管受影响节点
8. 可以在前端工作台上看到当前树图和 Node 信息

---

## 3. 总体开发原则

### 3.1 分层优先

系统必须按层拆，不允许把“领域语义”“编排框架”“数据库结构”“前端展示”混在同一层。

### 3.2 业务真相优先

所有正式状态、正式留痕、正式关系，都以数据库为唯一业务真相。

### 3.3 运行断面与业务真相分离

运行时 checkpoint、mode 断点、waitHuman 等信息，只属于执行断面，不属于业务真相模型。

### 3.4 同步主链极简

主链只保留必要同步动作：

- Node 初始化
- Scheduler 选择
- 单轮执行
- StepRecord 生成
- Node 回写
- Rescan 重新纳管

### 3.5 异步任务后置

摘要重算、embedding、评测、导出都放在异步层，不进入主链。

---

## 4. 模块总览

Ascend 1.0 建议拆成 8 个模块：

1. Domain 模块
2. Rule 模块
3. Persistence 模块
4. Runtime 模块
5. Application 模块
6. API 模块
7. Web 模块
8. Worker 模块

其中：

- Domain / Rule 是系统核心
- Persistence / Runtime 是承载层
- Application / API / Web / Worker 是交付层

---

## 5. 模块说明

## 5.1 Domain 模块

### 5.1.1 职责

Domain 模块负责定义 Ascend 的核心业务对象与领域服务。

它承载：

- Node
- Edge
- StepRecord
- Round
- Project
- Scheduler
- Rescan
- 推进契约

### 5.1.2 必须包含的子内容

- 实体（Entity）
- 值对象（Value Object）
- 领域契约（Contract）
- 领域服务（Domain Service）

### 5.1.3 不负责的内容

Domain 模块不负责：

- 数据库存取
- HTTP 接口
- 前端展示
- LangGraph 编排实现
- 队列消费

### 5.1.4 建议目录

```text
packages/domain/
  src/
    entities/
    value-objects/
    contracts/
    services/
    index.ts
```

### 5.1.5 核心实体

#### Node

Node 承载当前推进对象的内容状态。

建议最小字段：

- id
- projectId
- parentId
- title
- raw
- summary
- conclusion
- next
- scenario
- status
- activeStatus
- order
- createdAt
- updatedAt

#### Edge

Edge 承载 Node 间关系。

建议最小字段：

- id
- projectId
- sourceNodeId
- targetNodeId
- type
- label
- createdAt

#### StepRecord

StepRecord 承载单轮完成后的正式留痕。

建议最小字段：

- id
- nodeId
- roundId
- mode
- input
- output
- change
- next
- createdAt

#### Round

Round 承载一轮变化范围。

建议最小字段：

- id
- projectId
- title
- goal
- status
- createdAt
- updatedAt

#### Project

Project 承载一个独立推进空间。

建议最小字段：

- id
- title
- description
- defaultScenario
- createdAt
- updatedAt

### 5.1.6 核心领域服务

#### SchedulerService

负责：

- 过滤候选节点
- 选择当前 Node
- 计算 mode 入口
- 判断是否需要 waitHuman

#### RescanService

负责：

- 根据变化输入识别受影响节点
- 将这些节点重新纳入推进范围

#### NodeTransitionService

负责：

- 校验合法状态流转
- 应用状态变化
- 封装 reopen / freeze / complete 等迁移

#### StepRecordService

负责：

- 根据单轮结果生成 StepRecord
- 组织输入/输出/change/next

## 5.2 Rule 模块

### 5.2.1 职责

Rule 模块负责把业务边界写成明确规则函数。

它不做状态机 runtime，只做：

- 规则判断
- 迁移校验
- 候选过滤规则
- 重开规则
- Rescan 触发规则

### 5.2.2 为什么单独拆出

原因有两个：

1. 防止规则散落在 service 和 controller 里
2. 让规则可以被单元测试直接覆盖

### 5.2.3 建议目录

```text
packages/rules/
  src/
    node/
    scheduler/
    rescan/
    round/
    common/
    index.ts
```

### 5.2.4 建议函数

#### Node 规则

- canTransition(oldStatus, newStatus)
- canEnterCandidatePool(node)
- canReopen(node)
- shouldFreeze(node)
- shouldComplete(node)

#### Scheduler 规则

- filterCandidateNodes(nodes)
- rankCandidateNodes(nodes, context)
- resolveModeEntry(node, runtimeState)
- shouldWaitHuman(context)

#### Rescan 规则

- shouldTriggerRescan(changeSet)
- collectImpactedNodes(changeSet, graph)
- shouldReactivateNode(node)

---

## 5.3 Persistence 模块

### 5.3.1 职责

Persistence 模块负责：

- schema 定义
- 数据库存取
- 领域对象与数据库对象转换
- 查询与写入事务管理

### 5.3.2 技术选型

- PostgreSQL
- Prisma

### 5.3.3 为什么用关系库

因为 1.0 的关系模型本质上是：

**以树为主，允许少量引用和回跳的图。**

它不需要图数据库。

### 5.3.4 必须提供的 Repository

- ProjectRepository
- NodeRepository
- EdgeRepository
- StepRecordRepository
- RoundRepository

### 5.3.5 必须提供的查询能力

#### Node 查询

- 按 id 查 Node
- 查某项目全部 Node
- 查某节点子节点
- 查某节点父节点
- 查启用节点
- 查当前候选节点

#### Edge 查询

- 查某项目全部 Edge
- 查某节点出边/入边
- 查父子关系边
- 查引用边

#### StepRecord 查询

- 查某节点全部 StepRecord
- 查某 Round 下全部 StepRecord
- 查最新 StepRecord

### 5.3.6 必须支持的事务

以下动作必须在同一事务里完成：

1. 单轮完成后的 StepRecord 生成
2. Node 当前态回写
3. 如有必要，Rescan 重新纳管

这是主链事务。

### 5.3.7 事务边界补充

* 主链事务只覆盖“正式落账阶段”，不覆盖 Runtime 执行阶段。
* 也就是说，LangGraph 执行、LLM 调用、外部网络请求必须发生在事务外；事务开启时点应在单轮结果已经返回之后。
* 事务内只做三类动作：

1. 写 StepRecord
2. 回写 Node 当前态
3. 如有必要，同步执行 Rescan 重新纳管

* 涉及 Rescan 的领域服务不得自行持有全局 prisma 实例，而必须接收当前事务上下文 `tx` 并在同一事务中完成。

## 5.4 Runtime 模块

### 5.4.1 职责

Runtime 模块负责承载实际单轮执行过程。

它负责：

- ScenarioRunner
- graph 组装
- 中断恢复
- mode 执行断点
- 运行态 checkpoint

### 5.4.2 技术选型

- LangGraph.js

### 5.4.3 设计边界

Runtime 只承载执行过程，不存业务真相。

换句话说：

- currentMode 在 Runtime
- isWaitingHuman 在 Runtime
- checkpoint 在 Runtime
- Node / StepRecord / Round 真相不在 Runtime

### 5.4.4 thread_id 绑定规则

* Runtime 必须为每条“可恢复执行链”分配稳定的 `thread_id`。
* `thread_id` 不建议直接等同于 `node.id`，更稳的做法是显式绑定到执行链粒度，例如：
* `nodeId:roundId`
* 或独立 `executionId`
* 数据库中应显式保存 `nodeId`、`roundId`、`threadId` 的对应关系。
* Resume 时，应以 `threadId` 恢复 Runtime 断面，而不是仅凭 Node 当前态猜测恢复位置。

补充理由：LangGraph 的 checkpointer 以 thread 为单位保存和恢复状态，执行时需要传入 `thread_id` 作为恢复指针。

### 5.4.5 建议目录

```text
packages/runtime/
  src/
    graph/
    scenarios/
    prompts/
    adapters/
    index.ts
```

### 5.4.6 核心组件

#### ScenarioRunner

统一入口。

负责：

- 接收当前 Node
- 根据 scenario 装配 graph
- 执行一轮
- 返回单轮结果

#### GraphFactory

负责：

- 根据 scenario 组装图
- 挂接 mode 节点
- 配置中断点

#### PromptAdapter

负责：

- 从领域对象提取执行输入
- 组装 prompt 输入物
- 清洗输出结果

#### InterruptAdapter

负责：

- 在需要人工介入时触发 waitHuman
- 恢复运行

### 5.4.7 Scenario 目录建议

```text
scenarios/
  think/
    graph.ts
    nodes/
    prompts/
  write/
    graph.ts
    nodes/
    prompts/
  review/
    graph.ts
    nodes/
    prompts/
```

### 5.4.8 1.0 的运行时只实现一条最小主线

优先实现：

**think: Explore -> Freeze**

原因：

它最短，最能验证：

- Node 初始化
- Scheduler 选择
- 单轮执行
- StepRecord 生成
- Node 回写
- Rescan 触发

## 5.5 Application 模块

### 5.5.1 职责

Application 模块负责组织用例，不承载领域规则本身。

它负责把：

- Repository
- Domain Service
- Runtime
- 事务管理

组合成可调用的业务用例。

### 5.5.2 建议用例

- CreateProjectUseCase
- CreateNodeUseCase
- CreateChildNodeUseCase
- RunSchedulerOnceUseCase
- RunSingleRoundUseCase
- ResumeNodeUseCase
- ReopenNodeUseCase
- TriggerRescanUseCase
- GetWorkbenchViewUseCase

### 5.5.3 为什么需要这层

因为：

- Controller 不应直接碰 Domain Service
- Domain Service 不应直接知道 HTTP
- Runtime 不应直接管理数据库事务

### 5.5.4 主链最关键用例

#### RunSingleRoundUseCase

它是系统主链中心。

建议流程：

1. 获取当前 Node
2. 调用 Runtime 执行一轮
3. 生成 StepRecord
4. 回写 Node
5. 同步执行 Rescan
6. 提交事务
7. 返回结果

---

## 5.6 API 模块

### 5.6.1 职责

API 模块负责：

- 对外暴露 HTTP 接口
- 做参数校验
- 调用 Application UseCase
- 返回 DTO

### 5.6.2 不负责的内容

API 模块不负责：

- 业务规则判断
- 领域状态迁移
- prompt 组装
- 数据库直接操作

### 5.6.3 建议接口组

#### Project 接口

- POST /projects
- GET /projects/:id

#### Node 接口

- POST /nodes
- PATCH /nodes/:id
- GET /nodes/:id
- POST /nodes/:id/activate
- POST /nodes/:id/deactivate
- POST /nodes/:id/reopen
- POST /nodes/:id/create-child

#### Scheduler 接口

- POST /scheduler/pick
- POST /scheduler/run-once
- POST /scheduler/resume

#### StepRecord 接口

- GET /nodes/:id/step-records

#### Round 接口

- POST /rounds
- GET /rounds/:id

#### Workbench 接口

- GET /projects/:id/workbench

### 5.6.4 Workbench 接口返回什么

Workbench 不是直接返回原始表数据，而应返回：

- 画布节点数组
- 画布边数组
- 当前选中 Node 详情
- StepRecord 摘要
- 当前候选信息

也就是：

**返回前端工作台所需的 read model。**

## 5.7 Web 模块

### 5.7.1 职责

Web 模块负责：

- 展示树/图
- 展示 Node 详情
- 展示 StepRecord
- 发起命令
- 切换工作台视图

### 5.7.2 技术选型

- Next.js
- React
- TypeScript
- React Flow

### 5.7.3 最重要的设计边界

前端不能直接修改业务真相。

也就是说：

- 前端不能自己改 Node.parentId
- 前端不能自己改 Edge 真相
- 前端不能自己改 Node.status

前端只能：

1. 发命令
2. 等后端更新 DB
3. 重新拉取 workbench read model

### 5.7.4 为什么必须加 Adapter

因为：

- 后端存的是业务 Node / Edge
- React Flow 要的是画布 Node / Edge

两者不是同一种结构。

因此必须存在：

- NodeToFlowNodeAdapter
- EdgeToFlowEdgeAdapter

### 5.7.5 命令边界补充

* Web 层对图的修改必须走“命令模式”，不能直接把 React Flow 结构回写为业务真相。
* 前端允许做的事情只有：

1. 拉取 workbench read model
2. 发起命令（如 CreateChildNode、ActivateNode、RunSingleRound、ResumeNode）
3. 等后端完成持久化后重新刷新图

* 前端本地可以维护展示态，例如选中状态、展开折叠、局部拖拽位置；但父子层级、业务关系、正式状态只能由后端修改。
* Adapter 至少应包含：
* `Node -> FlowNode`
* `Edge -> FlowEdge`
* `WorkbenchReadModel -> GraphViewModel`

补充理由：React Flow 消费的是画布节点/边模型，不是你的业务 Node 真相；其节点类型核心是 `id`、`position`、`data` 这类展示字段。

### 5.7.6 建议目录

```text
apps/web/
  src/
    components/
      graph/
      node-panel/
      step-record/
    adapters/
    commands/
    queries/
    pages/
```

### 5.7.7 第一版页面

- ProjectListPage
- WorkbenchPage
- NodeDetailPanel
- StepRecordPanel
- RoundPanel

### 5.7.8 第一版图工作台只做哪些能力

- 展示图
- 选中节点
- 展示节点详情
- 展示 StepRecord
- 通过按钮发命令

第一版不做：

- 大规模拖拽编排
- 实时协同
- 复杂布局编辑
- 前端本地真相编辑

Worker 模块只负责异步重任务。

例如：

- eval

### 5.8.2 技术选型

- BullMQ
- Redis

Worker 不承接主链同步动作。

以下内容不能进 Worker：

- StepRecord 生成
- Node 回写
- Rescan 重新纳管
- 候选池更新

## 6. 模块交互关系

## 6.1 总体交互图

系统按以下方向流动：

**Web -> API -> Application -> Domain / Runtime / Persistence -> DB**

异步支线为：

**Application -> Queue -> Worker**

### 6.1.1 同步主链交互

```text
Web
  -> API
  -> Application UseCase
  -> Domain Service
  -> Runtime 执行单轮
  -> Domain 生成 StepRecord
  -> Persistence 事务写入
  -> Domain 执行 Rescan
  -> Persistence 更新候选范围
  -> 返回 API
  -> Web 刷新 workbench
```

### 6.1.2 异步支线交互

```text
Application
  -> Queue Producer
  -> Worker Consumer
  -> Persistence
```

---

## 6.2 各模块依赖方向

### 6.2.1 允许依赖

- API 依赖 Application
- Application 依赖 Domain / Runtime / Persistence / Queue
- Runtime 依赖 PromptAdapter / 外部模型适配器
- Web 依赖 API
- Worker 依赖 Queue / Persistence

### 6.2.2 禁止依赖

- Domain 不能依赖 API
- Domain 不能依赖 Web
- Domain 不能依赖具体 HTTP 框架
- Persistence 不能反向依赖 Web
- Runtime 不能反向直接修改前端状态

---

## 6.3 核心交互一：创建 Node

### 流程

1. Web 发起 CreateNode 命令
2. API 调用 CreateNodeUseCase
3. Application 组织参数
4. Domain 创建 Node
5. Persistence 写库
6. 返回 Node DTO
7. Web 刷新工作台

### 特点

- 不经过 Runtime
- 不经过 Worker
- 是纯业务对象创建链路

---

## 6.4 核心交互二：运行一轮

### 流程

1. Web 发起 RunSingleRound 命令
2. API 调用 RunSingleRoundUseCase
3. UseCase 读取当前 Node
4. UseCase 调用 Runtime 执行单轮
5. Runtime 返回单轮结果后，Application 才进入数据库事务阶段；事务不应先于 Runtime 执行开始。
6. Runtime 返回单轮结果
7. Domain 生成 StepRecord
8. Domain 计算 Node 回写结果
9. Domain 判断是否触发 Rescan
10. Persistence 在同一事务中完成：
    - 写 StepRecord
    - 回写 Node
    - 更新重新纳管节点
11. 返回最新结果
12. Web 重新拉取 workbench

### 特点

- 这是系统最重要的同步主链
- StepRecord / Node / Rescan 必须处于同一事务语义内
- `RunSingleRoundUseCase` 的事务边界应以后置落账为准，而不是以“开始运行一轮”为准。
- 该用例应把 `tx` 显式传入需要参与同事务的 Repository / Domain Service，避免在事务内部混入新的全局数据库连接。

---

## 6.5 核心交互三：恢复运行

### 流程

1. Runtime 在 waitHuman 处中断
2. Web 提交人工输入
3. API 调用 ResumeNodeUseCase
4. UseCase 交给 Runtime 恢复 checkpoint
5. Runtime 完成单轮
6. 后续仍按单轮主链沉淀

### 特点

- 恢复点在 Runtime
- 正式结果仍落到 Domain + Persistence

---

## 6.6 核心交互四：前端图刷新

### 流程

1. Web 请求 /workbench
2. API 调用 GetWorkbenchViewUseCase
3. Persistence 读取 Node / Edge / 当前状态
4. Application 组装 read model
5. Adapter 转成 React Flow 结构
6. 返回给前端

### 特点

- 前端只拿投影，不拿数据库真相对象直接乱改

---

## 7. 数据流与状态流

## 7.1 数据流

Ascend 1.0 有三类数据：

### 7.1.1 业务真相数据

存储在 DB 中：

- Node
- Edge
- StepRecord
- Round
- Project

### 7.1.2 运行断面数据

存储在 Runtime checkpoint 中：

- currentMode
- waitHuman
- 中间 prompt 输入输出
- graph 断点

### 7.1.3 前端投影数据

由后端临时组装返回：

- React Flow 节点数组
- React Flow 边数组
- 当前 Node 面板数据
- StepRecord 摘要

---

## 7.2 状态流

### Node.status 流转

最小流转：

- 未开始 -> 进行中
- 进行中 -> 已冻结
- 进行中 -> 已完成
- 已冻结 -> 进行中（重开）

### Node.activeStatus 流转

最小流转：

- 启用 -> 停用
- 停用 -> 启用

### waitHuman 流转

只属于 Runtime：

- false -> true
- true -> false

waitHuman 不直接改 Node.status。

---

## 8. 第一版实现顺序

Ascend 1.0 必须按顺序做，不能一开始就前后端齐飞。

---

## 8.1 第一步：Persistence + Domain 骨架

### 目标

先把业务真相和领域规则立住。

### 要做什么

1. 建 Prisma schema
2. 建 Repository
3. 实现 Node / Edge / StepRecord / Round / Project 实体
4. 实现 Rule 函数
5. 实现 SchedulerService / RescanService / StepRecordService

### 验收标准

- 可以创建 Node
- 可以创建 Edge
- 可以生成 StepRecord
- 可以校验状态流转

---

## 8.2 第二步：最小主链事务

### 目标

不接 Runtime，先手工模拟一轮完成。

### 要做什么

1. 写 RunSingleRoundUseCase 的骨架
2. 用 mock 结果代替 Runtime 输出
3. 跑通：
   - StepRecord 生成
   - Node 回写
   - Rescan 同步触发

### 验收标准

- 一次事务内能完成单轮正式落账
- Rescan 能同步更新受影响节点

---

## 8.3 第三步：接 Runtime

### 目标

把 mock 单轮换成真实 Runtime。

### 要做什么

1. 接入 LangGraph.js
2. 实现 ScenarioRunner
3. 实现 think: Explore -> Freeze
4. 实现 interrupt / resume

### 验收标准

- Node 能进入单轮执行
- waitHuman 可中断恢复
- 单轮完成后能回到主链沉淀

---

## 8.4 第四步：接 API

### 目标

把后端能力暴露成接口。

### 要做什么

1. 做 Node / Scheduler / Workbench 接口
2. 做 DTO 和参数校验
3. 做基础错误处理

### 验收标准

- 前端或 Postman 可以走通完整主链

---

## 8.5 第五步：接 Web 工作台

### 目标

先做读写最小工作台。

### 要做什么

1. 接 React Flow
2. 做 Adapter
3. 做 Node 面板
4. 做 StepRecord 面板
5. 做 run / resume / create-child 等命令按钮

### 验收标准

- 可以看到树/图
- 可以选 Node
- 可以发命令
- 可以看到最新 StepRecord

---

## 8.6 第六步：补 Worker

### 目标

把非主链重任务挪到异步层。

### 要做什么

1. 接 BullMQ
2. 做 summarize / embed / eval / export job

### 验收标准

- Worker 不影响主链正确性

---

## 9. 第一版模块优先级

### P0

必须先做：

- Domain
- Rule
- Persistence
- Application 主链

### P1

主链跑通后做：

- Runtime
- API

### P2

主链稳定后做：

- Web
- Worker

---

## 10. 每个模块的具体实现技术

## 10.1 Domain

- TypeScript
- 类或函数式都可以
- 倾向纯函数 + 轻量对象

## 10.2 Rule

- TypeScript 纯函数
- 配合 Vitest/Jest 单测

## 10.3 Persistence

- Prisma
- PostgreSQL
- Repository Pattern

## 10.4 Runtime

- LangGraph.js
- PromptAdapter
- LLM adapter

## 10.5 API

- Node.js + TypeScript
- 框架任意，优先选你最熟的

## 10.6 Web

- Next.js
- React
- React Flow
- 基础状态管理即可

## 10.7 Worker

- BullMQ
- Redis

## 12. 第一版明确不做的开发项

1. 不做 XState runtime 集成
2. 不做图数据库
3. 不做 Temporal
4. 不做前端本地真相编辑
5. 不做实时协同
6. 不做复杂权限
7. 不做多项目联动
8. 不做复杂 Agent 团队协作

---

## 13. 一句话总结

**Ascend 1.0 的开发骨架应以 Domain + Rule + Persistence 为核心，以 Runtime 承载单轮执行，以 Application 组织主链事务，以 API 暴露命令，以 Web 展示工作台，以 Worker 承担异步重任务。主链同步、边界清晰、真相落库，是第一版最重要的工程原则。**

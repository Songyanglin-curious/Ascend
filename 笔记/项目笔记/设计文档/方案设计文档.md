# Ascend 1.0 设计文档（规整版）

## 1. 文档定位

本文档只做一件事：

**把 Ascend 1.0 收成一份可继续细化的正式设计骨架。**

它不讨论：

- 具体代码实现
- 具体表字段细节
- 具体 prompt 内容
- UI 细节交互
- 后续高级能力

它只回答四类问题：

1. Ascend 1.0 要解决什么
2. Ascend 1.0 的系统边界是什么
3. Ascend 1.0 的核心结构如何组织
4. Ascend 1.0 第一版做到哪里为止

---

## 2. 版本定位

Ascend 1.0 是一套：

**以统一推进契约为底层骨架、用于承接复杂任务推进的探索性系统。**

它不是完整产品，不是全自动 Agent 平台，也不是图数据库项目，更不是通用工作流引擎。

Ascend 1.0 当前只验证一件事：

**复杂任务能否不再依赖平铺聊天和大段 prompt 硬控，而改为通过结构化对象、明确状态和可承接链路稳定推进。**

---

## 3. 设计目标

Ascend 1.0 的目标只有四个：

1. 让任务推进从“聊天堆积”变成“结构承接”
2. 让每次推进都能留下明确留痕，而不是只剩最后结果
3. 让系统能够形成清晰的下一步入口，而不是每次重新起头
4. 让上位变化发生后，相关节点可以重新纳入推进

---

## 4. 非目标

Ascend 1.0 不做以下内容：

1. 不追求完整自治
2. 不追求多用户实时协同
3. 不追求复杂多 Agent 编排
4. 不追求覆盖全部任务类型
5. 不追求把所有任务统一成一种内容流程
6. 不追求重型分布式工作流平台
7. 不追求一次性做成最终产品

---

## 5. 第一原则

Ascend 1.0 的统一基础不是任务内容，而是：

**一次最小推进必须满足的共同结构。**

一次推进至少包含五项：

1. 输入状态
2. 本轮动作
3. 输出结果
4. 状态变化
5. 下一步入口

这五项构成统一推进契约。

也就是说：

- 不同任务可以不同
- 不同模式可以不同
- 不同场景可以不同
- 但都必须能被表达为一次推进

---

## 6. 核心判断

Ascend 1.0 不是“思考框架”，而是：

**任务推进框架。**

它的共性不在“发散—收敛”这种内容过程里，而在：

- 当前对象如何被表示
- 当前推进如何被记录
- 当前结果如何被承接
- 下一步如何被继续

因此，Ascend 1.0 的重点不是规定任务“应该怎么思考”，而是规定任务“怎样才算一次有效推进”。

---

## 7. 总体架构

Ascend 1.0 采用五层结构。

### 7.1 领域层

领域层定义 Ascend 自己的核心语义。

包括：

- Node
- Edge / NodeTree 关系
- StepRecord
- Round
- Scheduler
- Rescan
- 推进契约
- 状态规则

领域层是系统核心资产。

这一层不应依赖具体编排框架。

### 7.2 规则层

规则层负责把领域边界压成明确规则。

包括：

- 状态流转规则
- 候选资格规则
- Scheduler 选择规则
- Rescan 触发规则
- 冻结重开规则
- 单轮结束后的沉淀规则

这层可以先用纯 TypeScript 规则函数表达，而不强依赖外部状态机库。

### 7.3 运行时层

运行时层负责承载具体执行过程。

包括：

- ScenarioRunner
- 模式编排
- 中断与恢复
- 单轮执行断面
- 子图 / 子流程承接

这一层使用现有编排工具承载，但不存放业务真相。

### 7.4 持久化层

持久化层负责保存业务真相。

包括：

- Project
- Node
- Edge
- StepRecord
- Round
- 规则相关配置

这里保存的是系统可追溯、可检索、可继续承接的正式状态。

### 7.5 展示层

展示层负责工作台和图形交互。

包括：

- 节点树 / 图视图
- Node 详情
- StepRecord 列表
- 当前轮次视图
- 命令发起入口

展示层只展示和发命令，不直接持有业务真相。

---

## 8. 核心对象

### 8.1 Project

Project 是一个独立推进空间。

它负责承载：

- 当前项目的 Node 集合
- 当前项目的关系结构
- 当前项目的默认场景配置

1.0 阶段一个 Project 就是一套独立树图空间。

### 8.2 Node

Node 是最核心的内容承载体。

它回答的是：

- 当前在推进什么
- 当前已经形成了什么内容承接
- 当前已经可以暂时成立什么判断
- 下一步从哪里继续

Node 至少承载：

- 原始内容
- 当前承接内容
- 当前结论
- 下一步入口
- 当前状态
- 当前场景

### 8.3 Edge / NodeTree

Edge / NodeTree 负责组织关系，不负责承载内容。

它解决的是：

- 父子关系
- 分支关系
- 引用关系
- 回跳关系
- 节点排序

### 8.4 StepRecord

StepRecord 记录的是：

**一个 Node 在一轮完成后留下的正式推进痕迹。**

它不是过程流水，而是轮次沉淀。

它至少承载：

- 本轮输入
- 本轮输出
- 本轮变化
- 本轮 next
- 所属 Node

### 8.5 Round

Round 是一轮变化的容器。

1.0 中它先作为轻量组织单位存在，用于承接：

- 本轮目标
- 本轮相关 StepRecord
- 本轮范围说明

Round 在 1.0 不做复杂跨项目协同。

### 8.6 Scheduler

Scheduler 是受约束选择器。

它不负责内容判断本体，只负责：

- 过滤候选节点
- 选当前 Node
- 决定进入哪个 mode
- 判断是否需要等待人工
- 接收重新纳管节点

### 8.7 Rescan

Rescan 负责：

**当上位关键变化发生后，找出受影响节点，并重新纳入推进范围。**

它不直接修内容，不替代后续推进。

---

## 9. 状态模型

Ascend 1.0 只保留最小状态集合。

### 9.1 Node.status

用于表达推进阶段：

- 未开始
- 进行中
- 已冻结
- 已完成

### 9.2 Node.activeStatus

用于表达当前是否纳入推进范围：

- 启用
- 停用

### 9.3 NodeRuntime

NodeRuntime 不属于业务真相状态集合。

它只承载运行断面，例如：

- currentMode
- isWaitingHuman

NodeRuntime 的职责是“这一轮跑到哪”，不是“节点现在正式是什么状态”。

---

## 10. 一轮的定义

Ascend 1.0 中，一轮的正式定义是：

**一个 Node 在其所属 Scenario 下走完，形成明确输入输出。**

这意味着：

- mode 切换不是新开一轮
- 人工介入不是新开一轮
- 单轮中可循环、回退、分支判断
- 只有本轮完成后，才生成 StepRecord
- 只有本轮完成后，才统一回写 Node

---

## 11. 主链

Ascend 1.0 的最小主链固定为：

1. 接收原始输入
2. 创建 Node
3. 轻量初始化
4. Scheduler 选当前 Node
5. 进入并执行本轮 mode
6. 单轮完成
7. 生成 StepRecord
8. 回写 Node
9. 必要时同步执行 Rescan
10. 回到 Scheduler

### 11.1 初始化阶段

初始化只做结构准备：

- 确定 scenario
- 设置初始状态
- 写入 NodeTree
- 初始化运行断面

初始化不做内容推进。

### 11.2 单轮执行阶段

单轮内部允许：

- mode 前进
- mode 回退
- mode 循环
- 分支判断
- 人工介入

但这些都属于同一轮内部过程。

### 11.3 沉淀阶段

沉淀顺序固定为：

1. 生成 StepRecord
2. 回写 Node

### 11.4 Rescan 阶段

Rescan 是沉淀后的同步领域动作。

它不应被放入异步队列主链中。

原因是：

如果 Rescan 还没完成，Scheduler 就不应该开始下一轮候选选择。

---

## 12. 模式层与场景层

Ascend 1.0 不统一任务内容，但统一推进骨架。

差异通过 Mode 和 Scenario 表达。

### 12.1 Mode

1.0 暂定最小集合：

- Explore
- Write
- Review
- Revise
- Freeze

### 12.2 Scenario

1.0 暂定最小集合：

- think
- write
- review

每个 Scenario 内部可组织自己的 mode 流程。

### 12.3 规则边界

- Scenario 先于 Mode
- Mode 必须受 Scenario 约束
- 一个 Node 不切换 Scenario
- 如需切换 Scenario，必须新建子节点

---

## 13. 技术承载原则

Ascend 1.0 采用“领域语义自己写，通用基础设施直接接”的原则。

### 13.1 该自己写的

只写三类内容：

1. 领域对象与推进契约
2. 规则函数与领域服务
3. 框架之间的胶水层

### 13.2 不该自己写的

不手搓以下能力：

- 编排框架
- 图形画布
- 自动布局
- ORM
- 队列系统
- 观测系统

---

## 14. 工具选型原则

1.0 只选“够用、成熟、可替换”的工具。

### 14.1 运行时编排

使用现有 graph orchestration 工具承载：

- 单轮执行
- 中断恢复
- 子图调用
- 运行断面持久化

但它只承载运行态，不承载业务真相。

### 14.2 数据存储

使用关系型数据库作为唯一业务真相库。

保存：

- Node
- Edge
- StepRecord
- Round
- Project

### 14.3 前端图工作台

使用现成图编辑 / 流程图组件做工作台。

但前端只展示和发命令，不直接改业务层级。

### 14.4 队列

异步队列只处理“可以脱离主链的重任务”，例如：

- 摘要重算
- embedding
- 评测
- 导出

不承接主链同步领域动作。

## 18. 设计约束

### 18.1 Postgres 是唯一业务真相库

正式状态、正式结果、正式留痕都必须落库。

### 18.2 运行时状态不是业务真相

checkpoint、currentMode、waitHuman 等只属于运行断面。

### 18.3 单轮后统一沉淀

StepRecord 与 Node 回写不能提前发生。

### 18.4 Rescan 是同步动作

Rescan 完成前，不应进入下一轮 Scheduler 选择。

### 18.5 前端不能直接改业务层级

前端只能发命令，不能直接修改后端关系真相。

---

## 19. 第一阶段实施建议

1. 先做纯后端骨架
2. 先写 schema 和领域规则
3. 先用测试跑通一条最小链路
4. 再接运行时编排
5. 最后再接前端工作台

第一条应跑通的最小主线建议是：

**think: Explore -> Freeze**

也就是：

- 创建 Node
- 初始化
- 进入 Explore
- 完成一轮
- 生成 StepRecord
- Node 进入已冻结
- 如有影响则同步 Rescan

## 20. 一句话总结

**Ascend 1.0 是一套以统一推进契约为底层骨架、以 Node 为内容承载、以 StepRecord 为轮次留痕、以 Scheduler / Rescan 维持推进秩序、以关系型数据库保存业务真相、以运行时承载单轮执行断面的任务推进系统。**

## 附录A：领域硬约束

本节不是对系统功能的补充，而是对实现边界的强约束。  
任何代码、流程、UI、运行时编排，只要与本节冲突，以本节为准。

### A.1 一轮的绝对定义

一轮的正式定义是：

**一个 Node 在其所属 Scenario 下走完，形成明确输入输出，并完成统一沉淀。**

由此推出：

- Mode 切换不等于新开一轮
- 单轮内部循环、回退、分支判断不等于新开一轮
- 人工中途介入不等于一轮结束
- 只有形成可统一沉淀的结果时，才算一轮完成

禁止把单轮内部的任一步骤误记为“已完成一轮”。

### A.2 初始化链不可跳跃

原始输入不得直接进入调度或直接进入 Mode。  
首次入场必须严格按以下顺序完成：

1. 对象化：创建首个 Node
2. 轻量初始化：确定 Scenario、写入初始状态、挂入关系结构、初始化运行断面
3. 完成初始化后，才允许进入 Scheduler

初始化阶段只做结构准备，不做内容推进。  
初始化阶段绝不进入任何 Mode。

### A.3 单轮内部禁止提前沉淀

单轮内部运行过程中，允许变化的是运行断面，不是正式业务沉淀。  
因此在单轮完成前，严禁提前写入高密度正式字段。

单轮内部允许更新的内容仅限：

- currentMode
- isWaitingHuman
- 原始上下文痕迹
- 为执行所必需的临时运行信息

单轮内部严禁提前更新的内容包括：

- Node.summary
- Node.conclusion
- Node.next
- Node.status 的完成性结论
- StepRecord

沉淀只能发生在单轮完成后的统一落账阶段。

### A.4 沉淀顺序必须固定

单轮完成后的正式落账顺序必须固定为：

1. 生成 StepRecord
2. 回写 Node

禁止先改 Node、再补 StepRecord。  
禁止部分字段边跑边写、最后再“补一条记录”。

StepRecord 是一轮完成后的结算单，不是对话流水账。

### A.5 Scenario 先于 Mode

Scenario 决定一类任务的推进语境，Mode 只是该语境内的推进方式。  
因此必须满足：

- Scenario 先于 Mode
- Mode 必须受 Scenario 约束
- Mode 不能脱离 Scenario 自由乱选

禁止把 Mode 当成独立的全局自由操作集。  
禁止在未确定 Scenario 的情况下直接进入 Mode 执行。

### A.6 Node 身份不可漂移

Node 的身份在其生命周期内必须稳定，尤其是 Scenario 不可漂移。  
一个 Node 一旦确定 Scenario，后续不得切换到另一种 Scenario。

如确需切换，唯一合法方式是：

- 创建新子节点承接
- 将新节点挂入关系结构
- 对新节点重新执行初始化链

禁止让原 Node 直接改 Scenario 继续跑。

### A.7 状态维度必须严格正交

节点状态必须拆成互不混写的三个维度：

#### 1. Node.status
只表达推进阶段，例如：

- 未开始
- 进行中
- 已冻结
- 已完成

它只回答：**推进到了哪。**

#### 2. Node.activeStatus
只表达是否纳入调度范围，例如：

- 启用
- 停用

它只回答：**当前要不要纳入推进。**

#### 3. NodeRuntime
只表达单轮内部运行断面，例如：

- currentMode
- isWaitingHuman

它只回答：**这一轮内部跑到哪。**

禁止把“等待人工”写成 Node.status。  
禁止把调度资格混进推进阶段。  
禁止让运行断面冒充正式业务状态。

### A.8 Scheduler 是受约束选择器，不是系统大脑

Scheduler 的职责只有：

- 过滤候选
- 选择当前 Node
- 决定进入哪个合法 Mode
- 判断是否需要等待人工
- 接收重新纳管节点

Scheduler 不负责：

- 替代内容生成
- 替代关系组织
- 替代正式沉淀
- 直接修复 Node 内容
- 直接改写最终结论

禁止把 Scheduler 实现成无边界的“中央智能体”。

### A.9 调度资格先于调度优先级

调度时必须先判断“有没有资格进入候选池”，再判断“先选谁”。

候选门槛至少满足：

- activeStatus = 启用
- status != 已完成

`已冻结` 默认不进入候选池。  
只有被显式重开，或被 Rescan 重新纳管后，才允许再次进入调度范围。

### A.10 调度优先原则固定为“先收口，再开新口”

在合法候选中，调度优先级必须遵守：

1. `进行中` 优先于 `未开始`
2. `next` 明确的优先于 `next` 不明确的
3. 人工显式关注 / 外部明确触发拥有最高覆盖权

禁止在已有明确断面未收口时，无限制地不断新开节点。

### A.11 Rescan 只负责重新纳管，不负责直接修内容

Rescan 的职责只有一个：

**当上位关键变化发生后，识别受影响节点，并将其重新纳入推进范围。**

Rescan 不负责：

- 直接修改 Node 内容
- 直接修正结论
- 跳过正常推进流程替代后续处理

Rescan 只能把节点送回系统，不能替系统完成后续推进。

### A.12 Rescan 在主链中属于同步领域动作

Rescan 若被定义为单轮沉淀后的必要后续动作，则在该主链内必须同步完成。  
在 Rescan 完成前，不应开始下一轮 Scheduler 候选选择。

禁止把本应影响候选池正确性的 Rescan 随意丢进异步队列后立即继续调度。

### A.13 人机协作的控制粒度是“阶段受控”，不是“动作级审批”

系统的人机协作模型应遵守：

- 人负责高信息密度收敛与定标
- AI 负责边界内的大体量展开与执行

控制点应落在阶段性产物上，例如：

- 问题是否稳定
- 规范是否可执行
- 结果是否通过验收

禁止把系统设计成“AI 每走一步都申请一次”。  
也禁止在问题对象未稳定时，放任 AI 长距离盲跑。

### A.14 未稳定对象必须等待人工，不得盲目展开

当出现以下情况时，应进入等待人工状态：

- 当前问题对象未稳定
- 核心边界未明确
- 候选池尚未形成但继续展开会明显放大噪音
- 上位约束缺失，AI 无法合法判断下一步

此时系统应表现为 `isWaitingHuman = true`，而不是伪装成“继续自动推进”。

### A.15 前端与运行时都不得绕过领域硬约束

前端只能发命令，不能直接篡改业务真相。  
运行时框架只承载执行过程，不能用运行时习惯覆盖领域规则。

因此：

- 前端不得直接改写正式关系真相
- 运行时 checkpoint 不得冒充正式业务状态
- 任何框架默认行为若与本节冲突，必须被领域规则覆盖

### A.16 约束优先级

本节优先级高于：

- 代码实现便利
- 前端交互便利
- 编排框架默认机制
- 临时调试需求
- AI 自动生成的局部实现习惯

凡违反本节约束的实现，即使“能跑通”，也视为错误实现。

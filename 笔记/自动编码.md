# 环境搭建好后，如何进行自动编码与自动测试

## 1. 启动前提

只有在下面三类前提都成立后，才应该让 Codex 开始真正编码：

1. **环境前提成立**

   WSL / Ubuntu / Node / Codex CLI 已可用

1. **规则前提成立**

   至少已经有：

* `51-最小实现范围.md`
* `52-实现计划.md`
* `53-AI编码输入物.md`
* `54-验证用例.md`

1. **仓库前提成立**

   仓库里已经有最小骨架：

* `docs/`
* `skills/`
* `src/`
* `tests/`

如果这三类前提没齐，

那不叫“自动编码”，

那只是让 AI 在半空中乱长。

## 2. 自动编码的核心原则

Codex 自动编码时，不能按“一个大 prompt 一次写完”来跑。

官方对长任务的建议本质上是一个循环：

 **Plan → Edit code → Run tools（tests/build/lint）→ Observe → Repair → Update status → Repeat** 。([developers.openai.com](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex/?utm_source=chatgpt.com))

所以你的自动编码过程，也必须被组织成这个循环，

而不是自由发挥。

同时，Codex 官方工作流文档也强调：它更适合在**显式上下文 + 明确定义 done** 的情况下工作。([developers.openai.com](https://developers.openai.com/codex/workflows/?utm_source=chatgpt.com))

## 3. 自动编码的正确实施方式

当前项目最稳的自动编码方式是：

### 第一步：锁定当前批次

一次只允许 Codex 做一个批次。

例如：

* 批次 1：Node / Tree / StepRecord
* 批次 2：Solution / Workspace / Project
* 批次 3：Round
* 批次 4：顺序协同 / 升格
* 批次 5：生命周期

这里不要让它“顺手把后面也写了”。

### 第二步：把当前批次规则喂给 Codex

当前批次必须只拿：

* 当前批次 skill
* `53` 中当前阶段要求
* `54` 中当前批次验收项

而不是整套所有文档一起灌。

这样上下文最稳，跑偏最少。

### 第三步：让 Codex 真正写代码

这时才让它改 `src/` 或 `tests/`。

当前目标不是“完整系统”，而是：

**当前批次的最小实现。**

### 第四步：立即运行测试

自动编码之后，立刻进入自动测试。

这一步不能省。

因为官方长任务循环里，“Run tools → Observe → Repair”本来就是核心环节。([developers.openai.com](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex/?utm_source=chatgpt.com))

### 第五步：失败就让它自修

如果当前批次测试失败，

不要立刻换批次。

应该让 Codex：

* 读取失败结果
* 修复当前批次
* 重新跑测试

直到：

* 当前批次通过
* 或你判定它已经卡住

### 第六步：通过后才进入下一批

当前批次不通过，

不允许进入下一批。

## 4. 自动测试怎么组织

自动测试不要写成“最后统一测”。

当前最稳的方式是：

### 4.1 一批一验

每个批次完成后，只跑当前批次相关测试。

例如：

* 批次 1 就主要跑内核最小测试
* 批次 3 再补 Round 相关测试
* 批次 4 再补协同 / 升格测试

### 4.2 测试必须映射 54

测试不是自己随便写。

它要尽量直接映射到 `54-验证用例.md`：

* 正向闭环测试
* 边界测试
* 反向验证测试

这样测试通过，才有真实意义。

### 4.3 自动测试的目标不是“覆盖率好看”

当前阶段，测试只服务一件事：

**证明最小正确形态成立。**

所以比起追求大而全的测试覆盖，

更重要的是：

* 核心闭环有没有过
* 边界有没有混
* 不实现项有没有偷偷被做进去

## 5. 这套流程里 App 和 Skills 怎么配合

### Skills 的作用

Skills 负责把“当前批次该怎么做”固化下来。

官方对 skills 的定位就是：把 instructions、resources、scripts 这些东西打包成可复用工作流，让 Codex 更稳定地跟流程走。([developers.openai.com](https://developers.openai.com/codex/skills/?utm_source=chatgpt.com))

所以在你的项目里，skills 的作用不是装饰，

而是：

**把自动编码从 prompt 驱动，变成 workflow 驱动。**

### Codex App 的作用

Codex App 更适合做并行监督。

它的价值不在于代替 CLI 主施工，

而在于：

* 开一个线程做主实现
* 开一个线程做 `54` 验收复核
* 开一个线程做边界检查

因为 App 天然就适合并行线程和长任务监督。([openai.com](https://openai.com/index/introducing-the-codex-app/?utm_source=chatgpt.com))

## 6. 当前最推荐的自动编码工作流

如果压成一条最简流程，就是：

1. 进入仓库根目录
2. 启动 Codex CLI
3. 调用当前批次 skill
4. 只让它实现当前批次
5. 改完立即跑当前批次测试
6. 失败则让它修复并重测
7. 通过后交给 App 中的审查线程复核
8. 人做最后“通过 / 不通过”裁决
9. 再进入下一批

这套流程的关键不是“全自动”，

而是：

**高自动施工 + 低频人工裁决。**

## 7. 当前结论

环境搭好以后，正确的自动编码方式不是：

* 一次性全写
* 不分批次
* 先写代码后想验收
* 只靠一个大 prompt

而是：

**按批次驱动，让 Codex 在 skill 约束下编码，在测试循环里自修，在 54 的验收框架里被裁决。**

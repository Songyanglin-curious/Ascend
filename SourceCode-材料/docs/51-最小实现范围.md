## 0. 文档用途

### 0.1 本文档的定位

本文档是  **Ascend 1.0 当前阶段的最小实现范围约束文档** 。

它的作用不是解释方案，不是继续讨论架构，也不是扩展未来方向。

它只用于一件事：

**约束本次 1.0 最小实现的边界。**

也就是说，本文档回答的是：

* 这次到底要实现什么
* 这次明确不实现什么
* 本次最小对象模型是什么
* 本次必须跑通哪条最小闭环
* 本次实现做到什么算完成

### 0.2 本文档的适用对象

本文档主要用于：

* AI 执行实现任务
* 人检查 AI 是否跑偏
* 人确认这次实现范围是否被守住

因此本文档应被理解为：

**施工范围单，而不是概念说明书。**

### 0.3 本文档不负责什么

本文档不负责以下内容：

1. 不重写方案总览
2. 不重新讨论 Solution / Workspace / Project / Round 的为什么
3. 不重新讨论生命周期、协同、派生产物的理论边界
4. 不展开未来版本的可能性
5. 不展开完整对象模型、完整状态机、完整自动化机制
6. 不输出实现细节之外的长篇解释

也就是说：

**前面的文档负责把系统想清楚，本文档负责把这次施工边界压清楚。**

### 0.4 本文档的使用方式

阅读和执行本文档时，遵守以下规则：

1. 以本文档中的“必须实现”和“明确不实现”为最高约束
2. 若前序文档存在更宽泛表述，以本文档范围为准
3. 本文档未明确要求的能力，不自动补做
4. 本文档未明确冻结的复杂机制，不提前实现
5. 本文档中的“最小闭环”优先级高于“概念上也许可以支持的能力”

### 0.5 本文档的目标

本文档当前目标只有一个：

**让 Ascend 1.0 先以最小正确形态进入可实现状态。**

这里的“最小正确形态”指的是：

* 上层组织结构已经成立
* Project 内部推进内核已经成立
* 至少一条完整最小闭环可以跑通
* 但不提前扩展成完整产品或完整平台

### 0.6 本章结论

第 0 章到这里正式冻结以下内容：

1. 本文档是当前 1.0 的最小实现范围约束文档
2. 本文档服务于 AI 执行与人校验，不服务于概念讨论
3. 本文档只定义本次施工边界，不重讲理论
4. 本文档未明确要求的能力，不自动补做
5. 本文档的目标，是让 Ascend 1.0 先以最小正确形态进入可实现状态

## 1. 当前冻结术语

### 1.1 术语冻结的目的

本章用于冻结当前版本的核心术语。

从本章开始，这些词在当前 1.0 实现范围内统一使用，不再切换。

如果后续历史文档中存在更早的叫法，例如：

* Tree 曾被当作一级单位
* 某些上层对象口径曾未稳定

一律以本章为准。

### 1.2 Problem

**Problem = 我要达成的最终目标。**

说明：

* 它不是某次操作
* 不是某个节点
* 不是某个 Project
* 不是某个 Round
* 它是跨时间、跨阶段的目标性存在

当前实现要求：

* Problem 作为上层语义前提被承认
* 当前版本不要求单独做成复杂对象系统

### 1.3 Solution

**Solution = 围绕同一个最终目标而存在的最上层组织容器。**

说明：

* 它承接的是问题空间
* 它组织多个 Project
* 它不是更大的 Project
* 它不是 Round
* 它不是 Workspace

当前实现要求：

* 当前版本必须承认 Solution 存在
* Solution 是上层最小容器对象之一

### 1.4 Workspace

**Workspace = 人进入某个 Solution 后，当前干活时的工作上下文。**

说明：

* 它不是新的组织层单位
* 它不是 Project 本身
* 它不是 Round 本身
* 它承接当前焦点、当前入口、当前相关对象与必要附加信息

当前实现要求：

* 当前版本必须承认 Workspace 存在
* Workspace 只先承接最小上下文语义
* 当前版本不要求完整 UI

### 1.5 Project

**Project = Solution 内部一级独立工作对象。**

说明：

* 它承接的是独立工作面
* 它不是普通文件夹项
* 它不是 Node
* 它不是 Round
* 它不是 Tree 的同义词

当前实现要求：

* 当前版本统一使用 Project 作为一级单位
* 不再使用 Tree 作为 Solution 内一级单位名词

### 1.6 Tree

**Tree = Project 当前默认可采用的一种内部组织结构。**

说明：

* Tree 不是 Solution 内一级单位
* Tree 只处理 Project 内部结构组织
* 当前 1.0 已明确的大量运行规则，默认建立在“Project 采用 Tree 结构”的前提上

当前实现要求：

* 当前版本允许 Project 默认采用 Tree 结构
* 当前版本不展开其他完整结构类型体系

### 1.7 Node

**Node = 最小推进对象。**

说明：

* 它承接最小内容单元
* 它是 Project 内部推进的基础对象
* 它不是 Project
* 它不是 Round

当前实现要求：

* 当前版本必须实现 Node 的最小承接能力
* Node 是 Project 内部运行闭环的一部分

### 1.8 StepRecord

**StepRecord = 某个 Node 在某个场景下完成一轮推进后的局部沉淀记录。**

说明：

* 它记录局部推进
* 它不是 Round
* 它不承接跨 Project 变化
* 它是局部推进留痕对象

当前实现要求：

* 当前版本必须承认并实现 StepRecord 的最小留痕能力

### 1.9 Round

**Round = 围绕同一个最终目标而存在的一次跨 Project 变化组织单位。**

说明：

* 它承接一次变化
* 它不是 Solution
* 它不是 Workspace
* 它不是 Project
* 它不是 StepRecord 的集合

当前实现要求：

* 当前版本必须承认 Round 存在
* 当前版本只要求最小骨架与最小流程
* 当前版本不展开完整状态机与自动机制

### 1.10 Scheduler

**Scheduler = Project 内部局部推进秩序控制器。**

说明：

* 它决定局部推进如何继续
* 它不直接承担 Solution 级组织职责
* 它不替代 Round
* 它不替代 Workspace

当前实现要求：

* 当前版本只需保留最小推进秩序语义
* 当前版本不展开全局自动调度系统

### 1.11 Rescan

**Rescan = 在上位变化后识别受影响内容并将其重新纳入推进的机制。**

说明：

* 它主要作用于 Project 内部默认 Tree 结构下的再纳管
* 它不等于多 Project 自动协同
* 它不等于 Round

当前实现要求：

* 当前版本只承认最小再纳管能力
* 当前版本不展开复杂全局影响分析系统

### 1.12 生命周期

**生命周期 = Project 作为工作对象的整体存续过程。**

说明：

* 它不是 Node.status
* 它不是 Round 状态
* 它不是 Workspace 当前焦点
* 当前最小阶段冻结为：
* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档

当前实现要求：

* 当前版本只承认最小生命周期语义
* 当前版本不展开完整状态机与自动迁移

### 1.13 派生产物

**派生产物 = 某个 Project 推进过程中形成、并可能继续被单独承接的结果。**

说明：

* 它不天然自动升格为新 Project
* 是否升格取决于它是否形成新的独立工作面
* 它可能是文档、规则、AI 指令或其他结果

当前实现要求：

* 当前版本只承认“可升格”这一判断
* 当前版本不展开完整派生产物分类学

### 1.14 当前冻结术语之间的最小关系

当前 1.0 中，这些术语之间的最小关系冻结如下：

* Problem：最终目标
* Solution：目标空间容器
* Workspace：当前工作上下文
* Project：一级独立工作对象
* Tree：Project 默认内部结构
* Node：最小推进对象
* StepRecord：局部推进留痕
* Round：跨 Project 变化单位
* Scheduler：局部推进秩序控制器
* Rescan：局部再纳管机制

### 1.15 本章结论

第 1 章到这里正式冻结以下内容：

1. 当前版本统一使用本章术语，不再切换叫法
2. Project 是 Solution 内一级单位，Tree 不再是一级单位
3. Workspace 是当前工作上下文，不是组织层对象
4. Round 是跨 Project 变化单位，不是 StepRecord 或 Workspace 的别名
5. 生命周期是 Project 的独立状态轴，不属于 Node / Round / Workspace
6. 当前实现范围必须以本章术语口径为准

## 2. 本次必须实现的范围

### 2.1 总原则

本次 1.0 实现只做一件事：

**把 Ascend 当前已经冻结的最小上层组织结构与最小 Project 内部推进闭环，做成可运行的最小系统。**

这里的“可运行”指的是：

* 不是只定义对象
* 不是只写类型
* 不是只写空壳类
* 而是至少有一条最小闭环可以真正串起来

### 2.2 本次必须实现的上层组织对象

本次必须实现以下上层对象的最小版本：

#### 2.2.1 Solution

必须具备最小承接能力：

* 承接一个最终目标对应的问题空间
* 能容纳多个 Project
* 能作为 Workspace 与 Round 的上层容器

当前要求：

* 只做最小对象，不做复杂管理能力

#### 2.2.2 Workspace

必须具备最小承接能力：

* 承接当前 Solution
* 承接当前焦点 Project
* 承接当前焦点入口
* 承接当前相关 Project 的最小背景信息

当前要求：

* 只做语义层最小承接
* 不做完整 UI

#### 2.2.3 Project

必须具备最小承接能力：

* 作为一级独立工作对象存在
* 可挂载到某个 Solution 下
* 可被 Workspace 选为当前焦点
* 当前默认采用 Tree 作为内部组织结构

当前要求：

* 只做当前默认结构版本
* 不做多结构类型支持

#### 2.2.4 Round

必须具备最小承接能力：

* 承接一次跨 Project 的变化
* 至少包含：
* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮下一步入口

当前要求：

* 只做最小骨架和最小流程
* 不做完整状态机

### 2.3 本次必须实现的 Project 内部对象

本次必须实现以下 Project 内部对象的最小版本：

#### 2.3.1 Tree

必须具备最小承接能力：

* 作为 Project 默认内部组织结构存在
* 能组织 Node 之间的基本关系

当前要求：

* 只支持当前最小组织能力
* 不做复杂多结构兼容

#### 2.3.2 Node

必须具备最小承接能力：

* 承接原始内容
* 承接总结内容
* 承接当前结论
* 承接下一步入口
* 承接当前状态

当前要求：

* 只做当前最小内容模型
* 不扩展额外复杂字段

#### 2.3.3 StepRecord

必须具备最小承接能力：

* 记录一次局部推进
* 能挂到某个 Node 上
* 能表达这轮做了什么、产出了什么、下一步从哪里继续

当前要求：

* 只做局部留痕
* 不做完整历史系统

#### 2.3.4 Scheduler

必须具备最小承接能力：

* 能在当前 Project 内部继续推进
* 能基于当前状态选择下一步推进对象或继续入口

当前要求：

* 只做最小局部推进秩序
* 不做全局调度

#### 2.3.5 Rescan

必须具备最小承接能力：

* 在上位变化后，能把受影响内容重新纳入推进

当前要求：

* 只做最小再纳管语义
* 不做复杂全局影响分析

### 2.4 本次必须实现的最小行为能力

本次除了对象存在，还必须实现以下最小行为能力：

#### 2.4.1 创建 Solution

必须能创建一个最小 Solution。

#### 2.4.2 在 Solution 下创建 Project

必须能在一个 Solution 下挂接至少一个 Project。

#### 2.4.3 进入 Workspace

必须能让 Workspace 承接：

* 当前 Solution
* 当前焦点 Project
* 当前入口

#### 2.4.4 完成一次 Project 内部最小推进

必须能在当前焦点 Project 内：

* 进入某个 Node
* 完成一次最小推进
* 形成 StepRecord
* 更新 Node

#### 2.4.5 形成一个最小 Round

当变化超出单个 Project 内部时，必须能创建并承接一个最小 Round。

#### 2.4.6 显式切换到另一个 Project

必须能在当前形成明确断点后，显式切换当前焦点 Project。

#### 2.4.7 形成下一步入口

无论是 Node、Project 还是 Round 层，当前实现都必须留下可继续的入口。

### 2.5 本次必须跑通的最小闭环

本次最少必须跑通下面这条闭环：

1. 创建一个 Solution
2. 在 Solution 下创建至少一个 Project
3. 建立 Workspace
4. 让 Workspace 选中当前焦点 Project
5. 在该 Project 内创建或进入一个 Node
6. 完成一次最小推进
7. 生成 StepRecord
8. 更新 Node / Tree / Project
9. 必要时创建最小 Round
10. 必要时显式切换到另一个 Project
11. 留下下一步入口

如果这条链路不能跑通，

则本次实现不算完成。

### 2.6 本次必须实现的升格能力（最小版）

本次不要求完整派生系统，

但必须承认最小升格能力：

* 某个结果在满足“形成独立工作面”的判断后
* 可以被作为新的 Project 创建出来

当前要求：

* 只做“可升格”的最小语义
* 不做自动判定
* 不做完整来源关系系统

### 2.7 本次必须实现的生命周期能力（最小版）

本次不要求完整生命周期系统，

但必须承认最小生命周期语义：

* Project 至少有：
* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档

当前要求：

* 只做最小阶段表达
* 不做自动迁移
* 不做完整状态机

### 2.8 本章结论

第 2 章到这里正式冻结以下内容：

1. 本次必须实现最小上层组织对象：

* Solution
* Workspace
* Project
* Round

1. 本次必须实现最小 Project 内部对象：

* Tree
* Node
* StepRecord
* Scheduler
* Rescan

1. 本次必须实现最小行为能力：

* 创建 Solution
* 创建 Project
* 进入 Workspace
* 完成一次 Project 内部推进
* 形成 StepRecord
* 形成最小 Round
* 显式切换 Project
* 留下下一步入口

1. 本次必须跑通一条完整最小闭环
2. 本次必须承认最小升格能力与最小生命周期语义

## 3. 本次明确不实现的内容

### 3.1 总原则

凡是不属于“最小闭环成立”所必需的能力，

本次一律不实现。

当前阶段不追求：

* 完整
* 自动
* 智能
* 美观
* 高扩展性

当前阶段只追求：

**最小正确形态能够跑通。**

### 3.2 本次明确不实现的上层复杂能力

本次明确不实现以下上层复杂能力：

#### 3.2.1 跨 Solution 关系

不实现：

* 多个 Solution 之间的引用
* 跨 Solution 协同
* 跨 Solution 的统一工作区

#### 3.2.2 多 Round 并发

不实现：

* 同一 Workspace 下多个活跃 Round 并行推进
* Round 并发优先级处理

#### 3.2.3 Round 嵌套

不实现：

* 大 Round 下再拆子 Round 的正式机制

### 3.3 本次明确不实现的 Round 高级能力

本次明确不实现以下 Round 高级能力：

#### 3.3.1 完整状态机

不实现：

* Round 全量状态表

* 回退 / 重开机制

#### 3.3.2 自动创建 / 自动结束 / 自动拆分

不实现：

* 自动识别 Round 开始
* 自动识别 Round 结束
* 自动拆分 Round

#### 3.3.3 完整字段体系

不实现：

* Round 的完整对象字段表
* 完整事件日志模型
* 完整存储模型

### 3.4 本次明确不实现的协同复杂能力

本次明确不实现以下协同复杂能力：

#### 3.4.1 自动协同编排

本次明确不实现以下生命周期复杂能力：

## 5. 本次必须跑通的最小闭环

### 5.1 总原则

本次实现不是“对象都定义了就算完成”，

而是必须跑通一条完整最小链路。

这条链路的目标是：

**证明 Ascend 1.0 当前最小上层组织结构 + 最小 Project 内部推进闭环 已经可以共同工作。**

如果对象存在，但链路跑不通，

则本次实现不算完成。

---

### 5.2 本次必须跑通的最小链路

本次最小闭环固定为下面 11 步：

1. 创建一个 Solution
2. 在 Solution 下创建至少一个 Project
3. 建立一个 Workspace
4. 让 Workspace 选中当前焦点 Project
5. 在该 Project 内创建或进入一个 Node
6. 完成一次最小推进
7. 生成一条 StepRecord
8. 更新 Node / Tree / Project
9. 当变化超出单 Project 内部时，创建一个最小 Round
10. 必要时显式切换到另一个 Project
11. 留下下一步入口

这 11 步必须能串成一条完整可继续的链路。

---

### 5.3 第一步：创建 Solution

必须能创建一个最小 Solution。

当前要求只承认：

* 它承接一个最终目标空间
* 它可以容纳多个 Project

当前不要求：

* 复杂元数据
* 复杂管理能力

**验收要求：**

* 系统中能明确存在一个 Solution 实体

---

### 5.4 第二步：在 Solution 下创建至少一个 Project

必须能在某个 Solution 下创建至少一个 Project。

当前要求只承认：

* Project 是一级独立工作对象
* 它挂在某个 Solution 下
* 它当前默认采用 Tree 结构

**验收要求：**

* Solution 中至少存在一个可工作的 Project

---

### 5.5 第三步：建立 Workspace

必须能建立 Workspace，

并让它进入当前 Solution 的工作上下文。

当前要求只承认：

* 当前 Solution
* 当前焦点 Project
* 当前入口
* 当前最小背景信息

**验收要求：**

* 当前 Workspace 能明确知道自己处于哪个 Solution 中

---

### 5.6 第四步：选中当前焦点 Project

Workspace 必须能选中一个当前焦点 Project。

当前实现不允许：

* 多焦点并行推进
* 焦点模糊

**验收要求：**

* 在任意时刻，Workspace 中只有一个正式焦点 Project

---

### 5.7 第五步：在当前 Project 内创建或进入一个 Node

必须能在当前焦点 Project 内：

* 创建一个 Node
* 或进入一个已有 Node

这个 Node 必须能够承接最小内容语义：

* 原始内容
* 总结
* 当前结论
* 下一步入口
* 当前状态

**验收要求：**

* 焦点 Project 内至少存在一个可推进的 Node

---

### 5.8 第六步：完成一次最小推进

必须能在当前 Node 上完成一次最小推进。

这里的“最小推进”只要求成立最小推进契约：

* 有输入状态
* 有本轮动作
* 有输出结果
* 有状态变化
* 有下一步入口

当前不要求：

* 完整模式体系
* 完整场景体系
* 复杂多轮演化

**验收要求：**

* 当前 Node 能完成一轮最小推进，并生成结果

---

### 5.9 第七步：生成 StepRecord

每次最小推进之后，必须生成一条 StepRecord。

当前要求：

* StepRecord 能挂到当前 Node
* 能记录本轮动作
* 能记录本轮结果
* 能记录本轮下一步入口

**验收要求：**

* 每次局部推进后，系统中存在对应 StepRecord

---

### 5.10 第八步：更新 Node / Tree / Project

局部推进结束后，系统必须完成最小回写。

至少要发生：

* Node 更新
* Tree 中相关结构保持可承接
* Project 仍然处于可继续状态

当前不要求复杂一致性系统，

但最小回写必须存在。

**验收要求：**

* 推进之后，Node / Tree / Project 三层仍然保持可继续

---

### 5.11 第九步：必要时创建最小 Round

当变化不再只是单个 Project 内部局部推进时，

系统必须能够创建一个最小 Round。

这个 Round 至少能承接：

* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮下一步入口

注意：

* 这里是“必要时”
* 不是要求每次局部推进都自动创建 Round

**验收要求：**

* 系统能显式创建并承接一个最小 Round

---

### 5.12 第十步：必要时显式切换到另一个 Project

如果当前变化涉及多个 Project，

系统必须允许：

* 在当前 Project 形成明确断点后
* 显式切换当前焦点 Project
* 继续下一段推进

当前不允许：

* 多 Project 并发推进
* 隐式漂移焦点

**验收要求：**

* 系统能显式切换当前焦点 Project
* 切换后仍然保持 Workspace、Round、Project 三层语义清楚

---

### 5.13 第十一步：留下下一步入口

这是整个闭环成立的最后条件。

无论是：

* Node 层
* Project 层
* 还是 Round 层

最终都必须留下：

**下一步从哪里继续。**

如果系统只能完成一次推进，

但不能形成后续入口，

那它还不算真正的可继续系统。

**验收要求：**

* 完成这一轮之后，系统能明确指出下一步入口

---

### 5.14 这条闭环为什么是当前最小闭环

这条链路之所以是当前最小闭环，是因为它已经同时覆盖了：

#### 上层组织层

* Solution
* Workspace
* Project
* Round

#### Project 内部推进层

* Tree
* Node
* StepRecord
* Scheduler / Rescan 的最小语义

#### 接续能力

* 当前焦点
* 显式切换
* 下一步入口

也就是说，

这条链路虽然不大，

但已经足以验证：

**Ascend 1.0 当前最小结构是否真的能共同工作。**

---

### 5.15 本次最小闭环的验收句

当前实现完成的最低验收句，固定为：

> 系统能够创建一个 Solution，并在其中创建至少一个 Project；人能够通过 Workspace 进入当前工作上下文，在焦点 Project 中对某个 Node 完成一次最小推进并生成 StepRecord；当变化超出单 Project 内部时，系统能够显式创建一个最小 Round，并在必要时显式切换到另一个 Project，最终留下下一步入口。

如果这句话不能成立，

则本次实现不算完成。

---

### 5.16 本章结论

第 5 章到这里正式冻结以下内容：

1. 本次实现必须跑通一条完整最小闭环
2. 最小闭环固定为 11 步：

* 创建 Solution
* 创建 Project
* 建立 Workspace
* 选中焦点 Project
* 创建或进入 Node
* 完成一次最小推进
* 生成 StepRecord
* 更新 Node / Tree / Project
* 必要时创建 Round
* 必要时显式切换 Project
* 留下下一步入口

1. 当前实现不是只做对象定义，而是必须让这条链跑通
2. StepRecord 是局部推进验收点
3. Round 是跨 Project 变化验收点
4. 显式切换 Project 和留下下一步入口，是闭环是否真正成立的关键判断点

## 6. 推荐实现顺序

### 6.1 总原则

本次实现顺序不按文档顺序排，

只按一条原则排：

**先实现最小依赖，再实现最小闭环，再补上跨 Project 变化承接。**

也就是说，顺序必须服务于“先跑通”，

而不是服务于“先看起来完整”。

当前推荐顺序固定为 5 个阶段：

1. Project 内部最小内核
2. 上层组织外壳
3. Round 最小承接
4. 最小协同与升格
5. 生命周期最小语义补齐

---

### 6.2 第一阶段：先实现 Project 内部最小内核

这一阶段先实现：

* Tree
* Node
* StepRecord
* Scheduler（最小版）
* Rescan（最小语义）

这一阶段的目标不是做完整 Project 系统，

而是先让下面这件事成立：

**一个 Project 内部，至少能承接一个 Node，并完成一次最小推进。**

也就是说，这一阶段优先解决：

* Node 怎么存
* Tree 怎么挂 Node
* 一次推进怎么形成 StepRecord
* 如何留下下一步入口

#### 为什么第一阶段先做这个

因为如果 Project 内部推进最小内核都不成立，

后面的：

* Workspace
* Round
* 协同
* 升格

都只是空壳。

所以第一阶段必须先把：

**最小推进单位** 立住。

---

### 6.3 第二阶段：再实现上层组织外壳

这一阶段实现：

* Solution
* Workspace
* Project（最小上层对象）

这一阶段的目标是：

**让 Project 内部最小推进闭环，有一个正式的上层容器和上下文入口。**

也就是说，这一阶段优先解决：

* Solution 怎么承接目标空间
* Project 怎么挂到 Solution 下
* Workspace 怎么承接当前焦点与当前入口

#### 为什么第二阶段才做这个

因为上层组织对象本身不产生推进，

它们的意义建立在“内部已经能推进”的基础上。

所以应该先有：

* Project 内部推进内核

再有：

* Solution / Workspace / Project 的正式组织外壳

---

### 6.4 第三阶段：再实现 Round 最小承接

这一阶段实现：

* Round 最小对象
* Round 最小骨架
* Round 最小流程
* Round 与 Workspace / Project 的最小挂接

这一阶段的目标是：

**让跨 Project 的变化获得正式承接。**

也就是说，这一阶段优先解决：

* 一次变化怎么形成 Round
* Round 怎么承接目标、范围、状态、下一步入口
* Round 怎么和当前 Workspace / Project 发生联系

#### 为什么第三阶段才做这个

因为 Round 的前提是：

* 已经有 Solution
* 已经有 Workspace
* 已经有 Project
* 已经有 Project 内部最小推进

这些不先成立，Round 就没有落点。

---

### 6.5 第四阶段：再实现最小协同与升格

这一阶段实现：

* 显式切换当前焦点 Project
* 顺序推进多个 Project
* 最小派生升格语义
* 在必要时把结果创建为新的 Project

这一阶段的目标是：

**让一个 Solution 中的多个 Project 开始形成最小协同关系。**

也就是说，这一阶段优先解决：

* 当前 Project 到明确断点后如何切换
* 另一个 Project 如何接上继续
* 某个结果满足条件后如何被升格成新 Project

#### 为什么第四阶段才做这个

因为协同和升格都依赖前面三层已经存在：

* Project 内部推进能跑
* 上层容器已成立
* Round 已能承接变化

没有这些，协同与升格就只会变成概念表演。

---

### 6.6 第五阶段：最后补最小生命周期语义

这一阶段补上：

* Project 创建
* Project 活跃
* Project 暂停 / 封存
* Project 结束 / 归档

这一阶段的目标是：

**让 Project 不再只是“创建后一直挂着”的对象，而是有最小存续语义。**

注意：

* 这里只补最小阶段表达
* 不补完整生命周期状态机
* 不补自动迁移

#### 为什么把生命周期放到后面

因为当前阶段的第一优先级是：

* 先让对象能工作
* 再让对象能变化
* 最后再让对象整体有更完整的存续表达

如果一开始就把生命周期做重，

很容易压住整个推进节奏。

---

### 6.7 当前实现顺序的压缩版

如果把实现顺序再压成一句话，可以固定为：

> 先做 Project 内部最小推进内核，再做 Solution / Workspace / Project 的上层组织外壳，再做 Round 最小承接，然后补最小协同与升格，最后补 Project 生命周期最小语义。

这句话就是当前实现顺序的总规则。

---

### 6.8 当前阶段不允许颠倒的顺序

为了防止 AI 跑偏，当前明确不允许下面这些顺序：

#### 6.8.1 不允许先做完整 UI

Workspace 还没成立前，不做完整界面。

#### 6.8.2 不允许先做复杂 Round 状态机

Round 最小骨架没跑通前，不做复杂状态机。

#### 6.8.3 不允许先做自动协同

显式顺序协同没跑通前，不做自动协同。

#### 6.8.4 不允许先做完整生命周期系统

最小闭环没跑通前，不做自动迁移 / 自动归档。

#### 6.8.5 不允许先补未来能力

当前最小闭环没成立前，不补未来可能的结构类型、复杂关系系统或自治能力。

2. 推荐实现顺序固定为五阶段：

## 7. 验收标准

### 7.1 总原则

本次验收标准只接受：

**可判断、可观察、可验证的完成条件。**

不接受以下表述作为验收标准：

* 差不多可用
* 基本成立
* 大体正确
* 看起来像这样
* 后面再补一下就行

当前验收必须写成：

**能 / 不能**

**有 / 没有**

**成立 / 不成立**

的判断句。

---

### 7.2 上层组织层验收标准

本次必须通过以下上层组织层验收：

#### 7.2.1 Solution 验收

必须满足：

* 能创建一个 Solution
* Solution 能承接至少一个最终目标语义
* Solution 下能挂接多个 Project

#### 7.2.2 Workspace 验收

必须满足：

* 能建立一个 Workspace
* Workspace 能绑定当前 Solution
* Workspace 能承接当前焦点 Project
* Workspace 能承接当前焦点入口

#### 7.2.3 Project 验收

必须满足：

* 能在 Solution 下创建 Project
* Project 能被 Workspace 选中为当前焦点
* Project 当前默认采用 Tree 结构

#### 7.2.4 Round 验收

必须满足：

* 能创建一个最小 Round
* Round 至少承接：
* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮下一步入口

---

### 7.3 Project 内部推进层验收标准

本次必须通过以下 Project 内部推进层验收：

#### 7.3.1 Tree 验收

必须满足：

* Project 内部能存在 Tree
* Tree 能组织至少一个 Node

#### 7.3.2 Node 验收

必须满足：

* Node 能承接原始内容
* Node 能承接总结内容
* Node 能承接当前结论
* Node 能承接下一步入口
* Node 能表达当前状态

#### 7.3.3 StepRecord 验收

必须满足：

* 每次最小推进后都能生成一条 StepRecord
* StepRecord 能挂到对应 Node
* StepRecord 能表达本轮动作、本轮结果、本轮下一步入口

#### 7.3.4 Scheduler 验收

必须满足：

* 在当前 Project 内，系统能基于当前状态给出下一步继续对象或继续入口

#### 7.3.5 Rescan 验收

必须满足：

* 当上位变化发生后，系统能将受影响内容重新纳入推进

---

### 7.4 最小闭环验收标准

本次最核心验收是：

**最小闭环必须跑通。**

必须满足下面 11 条全部成立：

1. 能创建 Solution
2. 能在 Solution 下创建至少一个 Project
3. 能建立 Workspace
4. Workspace 能选中当前焦点 Project
5. 能在当前 Project 内创建或进入 Node
6. 能完成一次最小推进
7. 能生成 StepRecord
8. 能更新 Node / Tree / Project
9. 当变化超出单 Project 内部时，能创建最小 Round
10. 能显式切换到另一个 Project
11. 能留下下一步入口

这 11 条有任意一条不成立，

本次实现都不算完成。

---

### 7.5 协同与升格验收标准

本次虽然不做完整协同系统，

但必须通过以下最小协同与升格验收：

#### 7.5.1 协同验收

必须满足：

* 一个 Round 可以涉及多个 Project
* 但任意一个实际推进时刻，Workspace 中只能有一个焦点 Project
* Project 切换必须是显式动作
* 协同通过顺序推进实现，不通过交错并发推进实现

#### 7.5.2 升格验收

必须满足：

* 某个结果在满足“形成独立工作面”判断后，可以被创建为新的 Project
* 新 Project 能被挂入当前 Solution
* 新 Project 后续能被 Workspace 选中

注意：

* 当前验收只要求“可以升格”
* 不要求自动判定
* 不要求完整来源关系系统

---

### 7.6 生命周期最小语义验收标准

本次虽然不做完整生命周期系统，

但必须通过以下最小语义验收：

必须满足：

* Project 至少能表达：
* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档
* 生命周期语义独立于：
* Node.status
* Round 状态
* Workspace 当前焦点

这条验收的意义是：

**Project 不再只是“创建了就一直挂着”的对象。**

---

### 7.7 明确不作为本次验收条件的内容

以下内容即使没有实现，也不影响本次通过：

* 完整 UI
* 完整 Round 状态机
* 多 Round 并发
* 自动协同
* 自动升格
* 完整生命周期自动迁移
* 多结构类型支持
* 完整字段体系
* 跨 Solution 关系

这些内容当前都不属于本次验收范围。

---

### 7.8 本次总验收句

本次实现完成的总验收句固定为：

> 系统能够创建一个 Solution，并在其中创建至少一个 Project；人能够通过 Workspace 进入当前工作上下文，在焦点 Project 中对某个 Node 完成一次最小推进并生成 StepRecord；当变化超出单 Project 内部时，系统能够显式创建一个最小 Round，并在必要时显式切换到另一个 Project，最终留下下一步入口；同时，Project 至少具备最小生命周期语义，且结果在满足独立工作面条件时可被升格为新的 Project。

只要这句话成立，

本次实现就算通过。

### 7.9 本章结论

第 7 章到这里正式冻结以下内容：

1. 本次验收标准必须全部写成可判断句
2. 上层组织层必须通过：

例如：

* Project 是一级单位
* Tree 是内部结构
* Workspace 是工作上下文
* Round 是变化单位

#### 9.4.2 用来确认对象职责

例如：

* Solution 承接目标空间
* Project 承接独立工作面
* StepRecord 承接局部推进留痕

#### 9.4.3 用来确认边界

例如：

* 生命周期不等于 Node.status
* Round 不等于 Workspace
* 协同不等于并发推进

#### 9.4.4 不用来继续扩设计

例如不能因为文档里提到：

* 未来结构类型
* 自动协同
* 自动升格
* 完整 UI
* 跨 Solution 关系

## 0. 文档目标与边界

### 0.1 文档目标

本文档用于定义：

**Project 作为一级独立工作对象，在整个问题解决过程中如何存在、持续、暂停、结束与保留。**

这份文档关心的不是：

* 某个 Node 当前怎么推进
* 某个 Round 当前怎么变化
* 当前 Workspace 聚焦在哪里

它关心的是：

**一个 Project 作为工作对象，整体上怎么活下去。**

也就是说，这份文档要解决的是：

* Project 如何被建立
* Project 如何持续存在
* Project 什么时候只是暂时停住
* Project 什么时候真正结束
* 不同 Project 为什么生命周期不一样

### 0.2 本文档要解决的问题

本文档只解决以下问题：

1. 为什么 Project 不能只被理解成“创建了就一直存在”
2. 什么叫 Project 生命周期
3. Project 生命周期和 Node 状态、Round 状态、Workspace 焦点之间的边界是什么
4. Project 最少应该经历哪些生命周期阶段
5. 为什么不同类型的 Project 生命周期不一样
6. 当前 1.0 先冻结哪些生命周期内容，暂不展开哪些内容

也就是说，这份文档关注的是：

**Project 作为工作对象的存续过程。**

### 0.3 本文档不解决的问题

本文档不负责以下内容：

1. 不重新定义 Project 内部的运行规则
2. 不重写 Node 的状态流转
3. 不定义 Round 的完整状态机
4. 不定义 Workspace 的当前焦点切换机制
5. 不完整展开多 Project 协同规则
6. 不完整展开派生产物系统
7. 不展开生命周期的自动化实现机制

这些问题分别属于其他文档：

* Project 内部运行 → `运行规则.md`
* 变化组织单位 → `43-轮次.md`
* 工作上下文 → `41-解决方案层与工作区.md`
* 多 Project 协同与派生产物 → `45-多Project协同与派生产物.md`

### 0.4 本文档与其他文档的边界

#### 0.4.1 与《运行规则》的边界

《运行规则》回答的是：

* Node 怎么推进
* 一轮怎么完成
* StepRecord 怎么生成
* 条件动作怎么触发

这些都是 **Project 内部运行层** 的问题。

而本文档回答的是：

**Project 这个工作对象本身，整体上如何存在。**

所以：

* `运行规则` 讨论的是推进过程
* `生命周期` 讨论的是对象存续过程

#### 0.4.2 与《轮次》的边界

《轮次》回答的是：

**这次变化如何被组织。**

它承接的是变化单位。

而本文档承接的是工作对象单位。

所以：

* `Round` 关心的是某次变化
* `Project 生命周期` 关心的是这个工作对象在多次变化中怎么存在

#### 0.4.3 与《解决方案层与工作区》的边界

《解决方案层与工作区》回答的是：

* Solution 是什么
* Workspace 是什么
* Project 在 Solution 中是什么
* 当前如何在多个 Project 并存时工作

而本文档进一步回答的是：

**这些 Project 作为工作对象，会不会一直活着，怎么活，什么时候停。**

#### 0.4.4 与《多Project协同与派生产物》的边界

协同文档会讨论：

* Project 之间如何顺序协作
* 派生产物如何出现
* 长期关系与当前变化怎么理解

而本文档不负责说明“怎么协同”，

只负责说明：

**作为协同对象的 Project，本身是长期的、临时的，还是派生的。**

### 0.5 当前文档的最小任务

在当前阶段，这份文档的最小任务只有四个：

1. 定义什么叫 Project 生命周期
2. 把它和 Node / Round / Workspace 的状态层边界拆开
3. 定义 Project 的最小生命周期阶段
4. 承认不同 Project 生命周期存在差异

只要这四件事写清，后面的协同、派生和实现设计就有了稳定的上游输入。

### 0.6 当前文档的写作原则

本文档遵守以下原则：

1. **先定义存续过程，不定义完整状态机**

   当前先让生命周期概念成立，不把它立刻写成复杂自动系统。
2. **先拆边界，再谈阶段**

   不先拆清楚和 Node / Round / Workspace 的边界，后面所有“暂停 / 结束 / 归档”都会混层。
3. **先承认差异，不先做完整分类学**

   当前先承认长期、临时、派生这类差异存在，但不急着把所有类型一次写死。
4. **先解决“Project 怎么活”，不解决“系统怎么自动管它”**

   生命周期先是概念层问题，后面才是自动化问题。

### 0.7 本章结论

第 0 章到这里正式冻结以下内容：

1. 本文档是 **Project 生命周期定义文档**
2. 它只解决“Project 作为工作对象如何存在”
3. 它不负责 Project 内部运行、不负责 Round 变化组织、不负责 Workspace 当前焦点
4. 它的核心任务是定义：Project 的存续过程、最小阶段与类型差异
5. 当前阶段，这份文档先以最小正确形态成立，不展开完整状态机与自动化机制

## 1. 为什么需要 Project 生命周期

### 1.1 Project 不能只被理解成“建立了就一直在那里”

当前你已经正式承认：

* Solution 内部有多个 Project
* 这些 Project 围绕同一个最终目标服务
* 一个 Project 是一个独立工作面
* 不同 Project 可以是分析、文档、规则、AI 指令、实现规划等不同工作对象

一旦 Project 成立为一级单位，

一个问题就自然会出现：

**这些 Project 会一直存在吗？**

如果答案默认是“会”，

那后面你会遇到很多麻烦：

* 临时工作对象是不是也要一直保留
* 派生产物是否和主工作对象一样长期存在
* 一个已经完成使命的 Project 是不是还和活跃 Project 一样
* 一个暂时停止的 Project 和真正结束的 Project 有什么区别

这说明，Project 不能只被理解成“有了就一直在那”。

它必须有自己的存续逻辑。

### 1.2 一旦 Solution 层成立，生命周期问题就不再是可选问题

如果你还停留在“单树 / 单 Project 推进”阶段，

生命周期问题可以暂时被弱化。

因为这时你大概率只在处理一个持续推进对象。

但一旦 Solution 层成立，

并且你已经承认：

* 一个最终目标会有多个 Project
* Project 有不同角色
* 有些是主工作对象
* 有些是派生对象
* 有些可能只是临时存在

那么生命周期问题就不再是“以后再说”的附加话题，

而是会立刻变成一个必须回答的问题：

**这些 Project 为什么有的该长期存在，有的只该短期存在。**

所以生命周期问题并不是后期优化问题，

而是 Solution 层成立后的自然结果。

### 1.3 不同 Project 的存在方式天然不同

这是你最早提出这个问题时最核心的直觉，我认为是对的。

例如：

* 一个围绕主问题持续推进的 Project

  往往需要长期承接
* 一个为了某一轮变化临时开的 Project

  可能只需要短期存在
* 一个由主工作结果派生出来的文档 / 规则 / AI 指令 Project

  它的存在方式也未必和主 Project 一样

这说明：

**Project 虽然同属一级单位，但它们的生命周期天然不一样。**

也就是说，Project 不是“同一种对象在不同内容上的重复”，

而是“同一层级下存在方式可能不同的工作对象”。

如果不承认这一点，

后面你会被迫把所有 Project 都按同一套方式理解，

那一定会失真。

### 1.4 生命周期不清，会导致“暂停”“结束”“归档”全部混掉

如果没有生命周期层，

你后面所有与“Project 还在不在”有关的判断都会打架。

例如：

* 一个 Project 当前不做了，是暂停还是结束？
* 一个 Project 当前只是保留着，是活跃还是归档？
* 一个派生 Project 当前已经产出完了，它还算活着吗？
* 一个临时 Project 后面又要继续用，算重开还是一直没结束？

这些问题如果没有生命周期层承接，

你最后只能用很模糊的话去描述：

* 先放着
* 暂时不用
* 好像完成了
* 以后可能还会用
* 先别删

这种模糊状态在讨论时还能撑一下，

但一旦要继续实现、继续协同、继续让 AI 稳定理解，

就会立刻变成问题。

所以，生命周期最核心的价值之一，就是把：

* 暂停
* 封存
* 结束
* 归档
* 重开

这些概念正式拆开。

### 1.5 生命周期问题本质上也是“问题如何被持续解决”的一部分

这里要再往上提一层。

你前面已经明确了：

**核心不是对象怎么组织得更漂亮，而是问题如何被解决。**

那么 Project 生命周期为什么重要？

因为它本质上回答的是：

**为了持续解决这个问题，哪些工作对象需要一直保留，哪些只需要阶段性存在。**

也就是说，生命周期不是单纯的对象管理问题，

它其实也是问题解决过程的一部分。

例如：

* 主问题 Project 如果过早结束，问题可能还没真正解决
* 临时辅助 Project 如果一直不结束，工作空间会越来越重
* 派生 Project 如果不区分长期还是临时，后面会越来越混

所以，Project 生命周期不是“整理对象时顺手考虑一下”的问题，

而是：

**问题解决过程如何持续、如何收束、如何保留必要工作面的正式问题。**

### 1.6 生命周期和记忆策略天然相连

你前面最早提到“持久树 / 一次性树”的时候，

其实已经不是单纯在说“树”，

而是在说：

**不同工作对象，应该保留多少历史、保留到什么程度。**

这其实就是生命周期和记忆策略的耦合问题。

例如：

* 长期 Project

  往往要保留更多历史和上下文
* 临时 Project

  可能只需要保留关键结果，不需要保留全部细节
* 派生 Project

  可能更重视最终产物，而不是全过程痕迹

所以，一旦生命周期不明确，

后面“记忆保留多少”“归档到哪里”“还值不值得继续承接”都会跟着混乱。

这也是为什么生命周期必须单独写一份文档，

而不是塞进别的地方随便一句带过。

### 1.7 生命周期不是运行状态

这里要提前钉死一个边界。

之所以要单独写生命周期文档，

还有一个很重要的原因：

**生命周期不是运行状态。**

也就是说：

* `Node.status` 不是 Project 生命周期
* `Round 当前状态` 不是 Project 生命周期
* `Workspace 当前焦点` 也不是 Project 生命周期

这些都只是当前状态。

而生命周期讨论的是：

**这个 Project 作为工作对象，整体上处于什么存续阶段。**

如果这两层不拆开，

后面你会很容易把：

* 当前没在推进
* 当前没被焦点选中
* 当前这一轮没涉及
* 当前已经结束

全部混成一回事。

### 1.8 当前阶段为什么必须先承认 Project 生命周期

如果你现在不承认 Project 生命周期，

后面会立刻出现一个结构缺口：

你已经有了：

* Solution：目标空间
* Workspace：当前工作上下文
* Project：独立工作面
* Round：变化单位

但你还没有一层来回答：

**这些工作面整体上怎么存在。**

这意味着系统会有：

* 目标空间
* 工作上下文
* 变化单位
* 局部推进规则

却没有：

* 工作对象本身的存续过程

这会让上层结构缺一层非常关键的稳定性。

所以当前阶段必须先承认：

**Project 有生命周期。**

即使现在还不展开完整状态机、完整字段和自动化机制，

这个概念层也必须先成立。

### 1.9 本章结论

第 1 章到这里正式冻结以下内容：

1. Project 不能只被理解成“建立了就一直存在”的对象
2. 一旦 Solution 层成立，Project 生命周期问题就不再是可选问题
3. 不同 Project 的存在方式天然不同，至少会出现长期型、临时型、派生型等差异
4. 如果没有生命周期层，“暂停 / 结束 / 归档 / 重开”这些概念会全部混掉
5. 生命周期问题本质上也是“问题如何被持续解决”的一部分
6. 生命周期与记忆 / 保留策略天然相连
7. 生命周期不是运行状态，不能和 Node.status、Round 状态、Workspace 焦点混为一谈
8. 当前阶段必须先承认：Project 有生命周期，即使暂不展开完整状态机与自动化机制


# 2. Project 生命周期的最小定义与边界

## 2.1 Project 生命周期不是“当前状态”，而是“整体存续过程”

在当前阶段，Project 生命周期首先应被理解为：

**一个 Project 作为一级独立工作对象，从被建立、被持续承接、被暂时停止，到最终结束或归档的整体存续过程。**

这里最关键的是：

* 它描述的是整体过程
* 不是某个时刻的局部状态
* 不是某一轮变化的状态
* 不是当前工作焦点

也就是说，生命周期回答的是：

**这个 Project 作为工作对象，现在总体上处于怎样的存在阶段。**

而不是回答：

* 这个 Node 现在是什么状态
* 这轮 Round 现在推进到哪
* 当前 Workspace 正聚焦哪个 Project

## 2.2 Project 生命周期的最小定义

在当前阶段，我建议把 Project 生命周期的最小定义冻结成下面这句话：

> **Project 生命周期，是 Project 作为一级独立工作对象，在整个问题解决过程中从创建、持续承接、暂停或封存，到最终结束或归档的整体存续过程。**

这里有四个关键词：

### 2.2.1 一级独立工作对象

生命周期不是给 Node 用的，也不是给 Round 用的。

它只服务于 Project 这一层。

### 2.2.2 整个问题解决过程

它不是描述某一轮，而是描述这个工作对象在更长时段内如何存在。

### 2.2.3 整体存续过程

它讨论的是“活多久、怎么活、何时停”，不是局部运行结果。

### 2.2.4 结束或归档

生命周期天然要求你承认：Project 不会永远都停留在“正在活跃”。

它必须有收束方式。

## 2.3 生命周期为什么必须和其他状态层拆开

如果不把 Project 生命周期和别的状态层拆开，

后面所有判断都会互相污染。

你现在至少已经有这些层：

* Node 的推进状态
* Round 的变化状态
* Workspace 的当前焦点状态
* Project 的生命周期状态

如果这些层不拆开，

你很快会把下面这些问题混成一回事：

* 当前没推进
* 当前没被焦点选中
* 当前这一轮没涉及
* 当前已经暂停
* 当前已经结束
* 当前只是归档但还保留

所以，生命周期这层的成立，本质上就是为了：

**把“工作对象整体怎么存在”从“当前正在发生什么”里拆出来。**

## 2.4 生命周期与 Node.status 的边界

这一组边界必须先钉死。

### 2.4.1 Node.status 解决的是局部推进阶段

Node.status 讨论的是：

* 未开始
* 进行中
* 已冻结
* 已完成

它回答的是：

**这个 Node 当前推进到了哪里。**

这属于最小推进对象层。

### 2.4.2 Project 生命周期解决的是工作对象整体存续

Project 生命周期回答的是：

**这个 Project 作为工作对象，现在处于整体上的什么存续阶段。**

例如：

* 这个 Project 是否仍然活跃
* 是否只是暂时停住
* 是否已经结束
* 是否已经归档

### 2.4.3 边界结论

因此：

* `Node.status` 不是 Project 生命周期
* 某个 Node 完成，不等于整个 Project 生命周期结束
* 某个 Node 冻结，也不等于 Project 进入暂停或归档

一句话：

**Node.status 是局部推进状态，Project 生命周期是工作对象存续状态。**

## 2.5 生命周期与 Round 状态的边界

这一组边界同样重要。

### 2.5.1 Round 状态解决的是“这次变化走到哪”

Round 讨论的是：

* 这次变化当前进行到什么位置
* 这次变化是否形成断点
* 这次变化是否结束

它回答的是：

**这一轮变化现在怎么样。**

### 2.5.2 Project 生命周期解决的是“这个工作对象整体怎么样”

Project 生命周期讨论的是：

* 这个 Project 是否仍然活跃
* 这个 Project 是否暂时停住
* 这个 Project 是否结束
* 这个 Project 是否归档

它回答的是：

**这个工作对象整体现在怎么样。**

### 2.5.3 边界结论

因此：

* Round 状态不是 Project 生命周期
* 一个 Round 结束，不等于某个 Project 生命周期结束
* 一个 Project 暂停，也不等于当前 Round 必然结束

一句话：

**Round 状态是变化状态，Project 生命周期是工作对象存续状态。**

## 2.6 生命周期与 Workspace 焦点的边界

这一组边界是为了防止“当前没在看”被误认为“这个 Project 已经不活了”。

### 2.6.1 Workspace 焦点解决的是“当前在看什么”

Workspace 关注的是：

* 当前焦点 Project 是哪个
* 当前从哪个入口继续
* 当前有哪些背景信息

它回答的是：

**现在我正在处理哪个 Project。**

### 2.6.2 生命周期解决的是“这个 Project 还活着吗”

Project 生命周期关注的是：

* 它是否仍是活跃工作对象
* 是否只是当前没被焦点选中
* 是否已经暂停 / 封存
* 是否已经结束 / 归档

### 2.6.3 边界结论

因此：

* 当前没被 Workspace 选中，不等于生命周期结束
* 当前不是焦点，不等于 Project 已暂停
* 当前只是背景，也不等于它已归档

一句话：

**Workspace 焦点是当前使用状态，Project 生命周期是对象存续状态。**

## 2.7 生命周期与“是否存在”也不是一回事

还有一个常见误区：

“只要这个 Project 还存在文件或记录，它是不是就还活着？”

这个理解也不够准。

因为：

* 一个 Project 可以已经结束，但仍被保留
* 一个 Project 可以已归档，但仍可追溯
* 一个 Project 可以暂停，但还未重新激活
* 一个 Project 可以只是作为历史存在，而不是当前活跃对象

所以：

**生命周期不是简单的“存在 / 不存在”。**

它解决的是：

**这个 Project 以什么方式存在。**

这点非常重要，

因为它直接决定你后面如何处理：

* 暂停
* 封存
* 归档
* 结束
* 重开

## 2.8 当前阶段 Project 生命周期最少要回答的四个问题

如果把定义再压一层，

当前阶段，Project 生命周期至少要回答下面四个问题：

1. 这个 Project 现在是正在承接工作，还是只是被保留着
2. 这个 Project 现在是暂时停住，还是已经真正结束
3. 这个 Project 结束后，是彻底消失，还是以归档形式保留
4. 这个 Project 后续还能不能被重新激活或重新引用

只要这四个问题回答不清，

生命周期层就还没有真正成立。

## 2.9 当前 1.0 对生命周期定义的最小冻结版本

如果把这一章压成一段正式冻结语句，可以写成：

> Project 生命周期，是 Project 作为一级独立工作对象，在整个问题解决过程中从创建、持续承接、暂停或封存，到最终结束或归档的整体存续过程。
>
> 它不等于 Node 的推进状态，不等于 Round 的变化状态，也不等于 Workspace 的当前焦点状态。
>
> 生命周期关注的是“这个工作对象整体如何存在”，而不是“当前某一轮发生了什么”或“当前正在看什么”。

## 2.10 本章结论

第 2 章到这里正式冻结以下内容：

1. Project 生命周期描述的是 Project 作为一级独立工作对象的整体存续过程
2. 生命周期不是某个时刻的局部状态，而是更长时段内的整体存在状态
3. `Node.status` 不是 Project 生命周期
4. Round 状态不是 Project 生命周期
5. Workspace 当前焦点不是 Project 生命周期
6. 生命周期也不等于简单的“存在 / 不存在”
7. 生命周期最少要回答：是否仍在承接工作、是暂停还是结束、结束后如何保留、后续能否重新激活
8. 当前阶段，Project 生命周期作为独立概念已经正式成立

# 3. Project 的最小生命周期阶段

## 3.1 为什么当前阶段只适合先冻结最小阶段

既然生命周期已经成立，

下一步自然会问：

**一个 Project 最少会经历哪些阶段。**

这里最容易走偏的地方，就是一上来就把生命周期写成非常复杂的状态机。

那样会立刻引入：

* 过多状态
* 过多转移条件
* 过多例外情况
* 过早的自动化想象

这不符合当前阶段。

所以在 1.0 当前边界下，更稳的做法是：

**先冻结最小阶段骨架。**

也就是说，先回答：

* 最少分哪几段就够用

而不是先回答：

* 所有可能状态是什么

## 3.2 当前阶段建议冻结为四段

我建议当前阶段把 Project 生命周期先冻结为 4 个最小阶段：

1. 创建
2. 活跃
3. 暂停 / 封存
4. 结束 / 归档

这是当前最克制、也最够用的一版。

原因是：

* 足够表达主要存续差异
* 足够和运行状态层区分
* 足够支撑后续协同与实现讨论
* 不会一开始就长成复杂状态机

## 3.3 第一阶段：创建

### 3.3.1 含义

创建表示：

**这个 Project 已经被正式承认为一个独立工作对象。**

它不再只是：

* 一个想法
* 一段补充
* 一个局部节点
* 一句顺手记下的话

而是已经升格成：

**一个值得被单独承接的工作面。**

### 3.3.2 这一阶段的重点

创建阶段最关键的不是“已经推进了多少”，

而是：

**它已经获得了作为 Project 被组织、被承接、被切换的资格。**

### 3.3.3 和活跃的区别

创建不等于已经进入持续工作状态。

有些 Project 被创建出来后，还未进入真正活跃推进。

所以：

* 创建 = 正式成立
* 活跃 = 正在承接工作

这两者不能混。

## 3.4 第二阶段：活跃

### 3.4.1 含义

活跃表示：

**这个 Project 当前仍然是一个正在承接工作的有效工作对象。**

它可能：

* 正在被焦点选中
* 当前没被选中但仍属于活跃工作面
* 正在等待后续 Round 继续涉及
* 正在持续为最终目标提供工作承接

### 3.4.2 这一阶段的重点

活跃不是说它“此刻必须正在被操作”，

而是说：

**它仍然属于当前问题解决过程中有效的工作对象。**

所以要特别区分：

* 当前不在焦点 ≠ 不活跃
* 当前没在这一轮里 ≠ 不活跃

### 3.4.3 活跃的价值

这一阶段让你可以承认很多 Project 处于“仍然有效，但此刻不一定正在操作”的状态。

这对于多 Project 并存非常关键。

## 3.5 第三阶段：暂停 / 封存

当前阶段我建议先把这两者暂时放在同一段中理解，

后面如果有必要再拆细。

### 3.5.1 含义

暂停 / 封存表示：

**这个 Project 当前不再作为活跃工作对象继续推进，但仍保留着后续可能被重新引用、重新激活或被追溯的意义。**

它不等于彻底结束。

它强调的是：

* 当前先停住
* 当前不再活跃推进
* 但还值得保留

### 3.5.2 为什么当前先合并处理

“暂停”和“封存”严格来说并不完全一样。

但在当前阶段，如果过早拆开，

你会马上进入：

* 两者边界是什么
* 哪个可恢复、哪个不可恢复
* 哪个更像归档、哪个更像冻结

这些都太细了。

所以当前阶段先收成一个中间阶段更稳。

也就是：

**当前不活跃，但仍保留意义。**

### 3.5.3 这一阶段的价值

这一阶段存在的意义，就是防止你把下面两种完全不同的情况混成一回事：

* 暂时不做了
* 已经彻底结束了

它让“停着但还留着”这类状态有了正式位置。

## 3.6 第四阶段：结束 / 归档

当前阶段我也建议先把这两者放在同一段理解，

后面再决定是否细拆。

### 3.6.1 含义

结束 / 归档表示：

**这个 Project 已经完成其作为独立工作对象的主要使命，不再被视为当前问题解决过程中的活跃工作面。**

它强调的是：

* 当前使命已完成或已终止
* 不再作为继续推进对象存在
* 其后更多以结果保留、历史追溯或归档保留的方式存在

### 3.6.2 为什么当前先合并处理

“结束”和“归档”在严格意义上也不完全相同：

* 结束更偏工作意义上的完成
* 归档更偏保留方式

但当前阶段如果过早拆开，

生命周期体系会立刻开始长复杂。

所以当前先把它们收成一个终态段更稳：

**不再作为当前活跃工作面存在。**

### 3.6.3 这一阶段的重点

这一阶段的关键不是“消失”，

而是：

**不再承担当前活跃承接职责。**

这也呼应了前面说的：

生命周期不是“存在 / 不存在”，

而是“以什么方式存在”。

## 3.7 四个阶段之间的最小关系

当前阶段先不要写完整状态机，

但四个阶段之间最小的逻辑关系可以先冻结为：

* `创建` 之后，Project 才有资格进入后续存在阶段
* `活跃` 表示当前仍在问题解决过程中承担工作
* `暂停 / 封存` 表示当前不活跃，但仍保留意义
* `结束 / 归档` 表示当前已不再作为活跃工作面存在

也就是说，这四段天然表达的是：

**成立 → 承担工作 → 暂停保留 → 结束保留**

这已经足够支撑当前阶段的理解。

## 3.8 为什么当前不继续细分更多阶段

你当然还可以继续细分，例如：

* 准备中
* 待激活
* 冻结中
* 已完成未归档
* 已归档可重开
* 已归档不可重开

这些都有道理。

但当前阶段不适合继续细分，原因有三点：

### 3.8.1 当前目标不是做完整状态机

你现在需要的是：

* 生命周期概念成立
* 和其他状态层拆清
* 至少有最小阶段可用

而不是一次性把所有状态写完。

### 3.8.2 当前边界还在概念冻结阶段

如果现在细分，

后面：

* 协同
* Round
* 派生产物
* 记忆策略

一变，生命周期分法也会跟着变。

### 3.8.3 过早细分会压垮文档节奏

你现在的节奏是：

* 先把上层形态立住
* 再决定怎么实现

如果在这里就把生命周期系统写得很细，

后面很容易又被它卡住。

## 3.9 当前阶段不同 Project 对这四段的落点会不同

这里要先提醒一句：

虽然当前统一冻结为四段，

但不同类型 Project 在这四段中的表现会不同。

例如：

* 长期 Project

  往往会在“活跃”停留更久，暂停后也更可能被重开

* 临时 Project

  往往很快从“创建 / 活跃”走向“暂停 / 结束”

* 派生 Project

  可能更快进入“结束 / 归档”，但仍保留产物价值

也就是说，当前冻结的是共同骨架，

不是说所有 Project 都会以同样节奏走完这四段。

## 3.10 当前 1.0 对最小阶段的冻结版本

如果把这一章压成一段正式冻结语句，可以写成：

> 当前 1.0 阶段，Project 生命周期先冻结为四个最小阶段：创建、活跃、暂停 / 封存、结束 / 归档。
>
> 这四个阶段分别用于承接：Project 的正式成立、Project 作为有效工作对象持续承接、Project 当前不活跃但仍保留意义、Project 不再作为当前活跃工作面存在。
>
> 当前阶段先不展开完整状态机，只冻结这一最小阶段骨架。

## 3.11 本章结论

第 3 章到这里正式冻结以下内容：

1. 当前阶段，Project 生命周期先冻结为四个最小阶段：

* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档

1. 创建表示 Project 已被正式承认为一级独立工作对象
2. 活跃表示 Project 当前仍然是有效工作对象，即使此刻不一定正在被焦点选中
3. 暂停 / 封存表示 Project 当前不活跃，但仍保留后续意义
4. 结束 / 归档表示 Project 已不再作为当前活跃工作面存在
5. 当前阶段先不把暂停和封存、结束和归档继续细拆
6. 当前阶段先不展开完整状态机
7. 这四段已经足以构成 Project 生命周期的最小骨架
8. 不同类型的 Project 会在这四段中表现出不同节奏，但当前冻结的是共同阶段骨架
9. 当前 1.0 已经可以正式承认：Project 生命周期最少需要这四段来承接


# 4. 不同 Project 的生命周期差异

## 4.1 为什么必须单独讨论差异

前面第 3 章已经把 Project 生命周期先冻结成了四个最小阶段：

* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档

这四段已经足够构成共同骨架。

但如果只停在这里，还会残留一个很大的误解：

**好像所有 Project 只是内容不同，但生命周期方式应该一样。**

这恰恰是不对的。

因为你前面之所以会意识到“需要 Project 生命周期”，根本原因不是：

* 有没有生命周期

而是：

* **不同 Project 的存在方式不一样。**

所以这一章的任务，不是推翻共同骨架，

而是要正式承认：

**同样的四段骨架，不同类型的 Project 会以不同方式经历。**

## 4.2 当前阶段不先做完整类型学，只先承认最小差异

这里要先收一下。

这一章不准备把 Project 一次性分成很多正式类型，

例如：

* 主问题 Project
* 临时协助 Project
* 文档 Project
* 规则 Project
* AI 指令 Project
* 验证 Project
* 归档 Project

这样分会迅速膨胀。

当前阶段更稳的做法是先承认三种最小差异来源：

1. **长期承接型**
2. **临时型**
3. **派生型**

也就是说，当前不是先做完整分类学，

而是先回答：

**什么样的 Project 天然更长期，什么样的天然更短期，什么样的是由别的工作面派生出来的。**

## 4.3 长期承接型 Project

### 4.3.1 含义

长期承接型 Project，是指：

**围绕最终目标长期持续存在、反复被继续承接、不会因为某一轮变化结束就自然消失的 Project。**

它往往承接的是：

* 主问题本身
* 核心设计面
* 长期维护的核心规则面
* 持续演进的主体工作面

### 4.3.2 生命周期特征

这类 Project 的特点通常是：

* 更容易长期停留在“活跃”
* 即使进入“暂停 / 封存”，也更可能被重新激活
* 很少因为一轮变化结束就彻底进入“结束 / 归档”
* 对历史、上下文和前序演化的依赖更强

也就是说，这类 Project 的生命周期更像：

**持续存在，间歇推进。**

### 4.3.3 为什么要承认这一类

如果不承认长期承接型 Project，

后面你会被迫把主问题工作面和临时辅助工作面用同一套方式理解，

这会造成两个问题：

* 主问题 Project 容易被误判成“已经结束”
* 历史上下文和持续演化的重要性会被低估

所以，长期承接型是必须承认的一类。

## 4.4 临时型 Project

### 4.4.1 含义

临时型 Project，是指：

**为了某一阶段、某一轮变化、某个局部问题而临时成立的工作面。**

它存在的意义不是长期承接，而是：

* 为某次变化服务
* 为某个局部目标服务
* 为某个暂时性问题提供独立工作面

### 4.4.2 生命周期特征

这类 Project 的特点通常是：

* 创建后很快进入活跃
* 活跃期往往较短
* 更容易在较短时间内进入“暂停 / 封存”或“结束 / 归档”
* 对长期历史的依赖通常较弱
* 更强调“做完就停、停了就收”

也就是说，这类 Project 的生命周期更像：

**短促成立，完成即收。**

### 4.4.3 为什么要承认这一类

如果不承认临时型 Project，

后面你会倾向于把所有 Project 都当成长线工作对象，

结果会导致：

* 临时工作面在 Solution 里越积越多
* 本该快速结束的对象长期挂着
* Workspace 背景越来越重
* “暂停 / 结束 / 归档”的判断越来越乱

所以，临时型也是必须承认的一类。

## 4.5 派生型 Project

### 4.5.1 含义

派生型 Project，是指：

**不是直接围绕主问题原生建立，而是由其他 Project 的稳定结果进一步派生出来的独立工作面。**

例如：

* 文档 Project
* 规则 Project
* AI 指令 Project
* 某些实现拆项 Project

它们虽然仍然围绕同一个最终目标服务，

但它们的直接来源往往不是目标本身，

而是：

**另一个 Project 已经形成了可继续派生的结果。**

### 4.5.2 生命周期特征

这类 Project 的特点通常是：

* 往往在某个主 Project 达到一定稳定度后才出现
* 生命周期更受来源 Project 的状态影响
* 更容易在形成产物后进入“结束 / 归档”
* 是否长期保留，往往取决于该产物是否仍需持续维护

所以它的生命周期既不像长期型那样天然持续，

也不像临时型那样纯粹短促，

而是更像：

**由来源工作面激发出来，并围绕产物价值决定存续。**

### 4.5.3 为什么要承认这一类

如果不承认派生型 Project，

后面你会被迫把：

* 文档
* 规则
* AI 指令
* 其他产物面

要么继续塞回主 Project，

要么错误地当成和主 Project 完全同类的长期对象。

这两种都不对。

所以派生型 Project 必须单独承认。

## 4.6 三类差异不是“正式类型表”，而是当前最小差异轴

这里要再强调一次边界。

当前这三类：

* 长期承接型
* 临时型
* 派生型

并不是最终完整分类体系。

它们只是当前阶段最小必须承认的差异轴。

也就是说，这一章当前做的不是：

* 给所有 Project 下最终类型定义

而是在正式承认：

**不同 Project 的生命周期不会一样。**

这一步已经够大，也已经够有价值。

## 4.7 差异主要体现在哪里

当前阶段，我建议先把生命周期差异主要理解为体现在下面三件事上：

### 4.7.1 活跃时长不同

* 长期型更可能长时间处于活跃
* 临时型更可能短期活跃后快速收束
* 派生型则取决于来源与产物价值

### 4.7.2 暂停后的命运不同

* 长期型暂停后更可能被重新激活
* 临时型暂停后更可能直接走向结束
* 派生型暂停后是否重开，取决于其产物是否仍需维护

### 4.7.3 结束后的保留意义不同

* 长期型即使结束，往往仍有较高历史价值
* 临时型结束后，通常只需要保留关键结果
* 派生型结束后，保留重点往往在产物，而不是全过程

这说明，同样的四段生命周期骨架，在不同 Project 上并不是“同样地走一遍”。

## 4.8 生命周期差异与记忆 / 保留策略的关系

这一点必须在这一章落下来，

因为这是你最早提出这个问题时最有价值的直觉之一。

不同 Project 的生命周期差异，会直接影响：

* 要保留多少历史
* 要保留多久
* 保留重点是什么
* 结束后保留的是过程还是结果

例如：

### 4.8.1 长期承接型

更应保留：

* 历史演化
* 关键前提变化
* 长期上下文
* 结构性结论

### 4.8.2 临时型

更应保留：

* 关键结论
* 最终结果
* 为什么开过这次工作面
* 为什么停掉

但不一定要长期保留所有细节过程。

### 4.8.3 派生型

更应保留：

* 产物本身
* 产物来源
* 产物和来源 Project 的关系
* 必要时保留关键生成脉络

所以，生命周期差异不仅仅是“停多久”的问题，

它还天然决定了：

**怎么记、保留什么、保留到什么程度。**

## 4.9 当前阶段不处理哪些差异

这一章也要收边界，

否则你很快会继续追问：

* 长期型是不是还能细分
* 临时型和派生型会不会交叉
* 一个 Project 会不会从临时变长期
* 长期型是否还能降级
* 派生型是否会反过来变主工作面

这些都是真问题，

但当前阶段不展开。

因为一旦展开，就会进入：

* 生命周期迁移机制
* 类型转换机制
* 自动升格 / 降格机制

这都太早了。

所以当前只冻结：

**差异存在。**

不冻结：

* 差异之间的完整迁移规则

## 4.10 当前 1.0 对生命周期差异的最小冻结版本

如果把这一章压成一段正式冻结语句，可以写成：

> 当前 1.0 阶段，正式承认不同 Project 的生命周期存在差异。
>
> 当前先以长期承接型、临时型、派生型三类作为最小差异轴，用于说明不同 Project 在活跃时长、暂停后的命运、结束后的保留意义上天然不同。
>
> 当前阶段先承认差异，不展开完整分类体系，也不展开类型转换与自动迁移机制。

## 4.11 本章结论

第 4 章到这里正式冻结以下内容：

1. 不同 Project 的生命周期不会一样
2. 当前阶段先承认三类最小差异轴：

* 长期承接型
* 临时型
* 派生型

1. 长期承接型更偏持续存在、间歇推进
2. 临时型更偏短促成立、完成即收
3. 派生型更偏由来源工作面激发，并围绕产物价值决定存续
4. 当前阶段这三类不是最终完整类型表，而是最小差异轴
5. 生命周期差异主要体现在：活跃时长、暂停后的命运、结束后的保留意义
6. 生命周期差异与记忆 / 保留策略天然相关
7. 当前阶段先承认差异，不展开完整分类体系与类型迁移机制

# 5. 当前 1.0 先冻结什么 / 暂不展开什么

## 5.1 这一章的目标

到这里为止，你已经把下面这些东西都碰到了：

* Project 生命周期是什么
* 它和 Node / Round / Workspace 的边界
* 最小生命周期阶段
* 不同 Project 的生命周期差异
* 生命周期和记忆 / 保留策略的关系

如果这时不做一次收口，

生命周期文档会立刻继续自然膨胀，

最后很容易变成：

* 完整状态机文档
* 完整对象建模文档
* 自动归档系统文档
* 智能记忆裁剪策略文档

这不符合当前阶段。

所以这一章的任务是：

**明确当前 1.0 到底先冻结什么，又暂不展开什么。**

## 5.2 当前 1.0 先冻结的第一件事：正式承认 Project 生命周期存在

这一条必须先钉死。

当前阶段，1.0 正式承认：

**Project 作为一级独立工作对象，具有生命周期。**

这意味着，从现在开始，Project 不再被理解成：

* 只要创建了就一直挂着
* 只看当前焦点，不看整体存续
* 只看局部推进，不看整体存在方式

而是正式承认：

**Project 作为工作对象，整体上会经历存续阶段。**

这条冻结，是整份文档成立的前提。

## 5.3 当前 1.0 先冻结的第二件事：生命周期是独立于运行状态层的

当前阶段，正式冻结以下边界：

* `Node.status` 不是 Project 生命周期
* Round 状态不是 Project 生命周期
* Workspace 焦点不是 Project 生命周期

也就是说，

生命周期是一条独立状态轴，

它描述的是：

**这个工作对象整体怎么存在。**

这条边界如果不冻结，

后面所有“暂停 / 结束 / 归档 / 重开”都会继续打架。

## 5.4 当前 1.0 先冻结的第三件事：最小四段生命周期骨架

当前阶段，正式冻结 Project 的最小生命周期阶段为：

1. 创建
2. 活跃
3. 暂停 / 封存
4. 结束 / 归档

这条冻结已经足够支撑：

* Project 是否正式成立
* Project 是否仍然承担工作
* Project 是否只是停住但保留
* Project 是否已不再作为活跃工作面存在

当前先不进一步拆细。

## 5.5 当前 1.0 先冻结的第四件事：生命周期差异存在

当前阶段，正式承认：

**不同 Project 的生命周期不会一样。**

并且先以三类最小差异轴冻结：

* 长期承接型
* 临时型
* 派生型

这一步的意义，不是做完整分类学，

而是防止你后面默认：

**所有 Project 都应该以同一种方式存在。**

## 5.6 当前 1.0 先冻结的第五件事：生命周期差异会影响保留策略

当前阶段虽然不展开完整记忆系统，

但可以先正式冻结一条很重要的判断：

**生命周期差异天然会影响历史保留与记忆策略。**

也就是说：

* 长期型更应保留长期演化脉络
* 临时型更偏保留关键结果
* 派生型更偏保留产物与来源关系

当前先冻结这个方向判断，

但不展开完整实现模型。

## 5.7 当前 1.0 暂不展开：完整生命周期状态机

当前阶段，Project 生命周期已经有了四段最小骨架，

这已经足够。

当前不展开：

* 更细的阶段拆分
* 严格状态转移表
* 何时允许回退
* 何时允许重开
* 哪些阶段可以跳转

也就是说：

**先冻结阶段，不展开完整状态机。**

## 5.8 当前 1.0 暂不展开：自动迁移与自动归档

这也是一个非常自然会继续长的问题。

例如：

* 活跃多久后自动转暂停
* 暂停多久后自动归档
* 派生型 Project 是否自动结束
* 长期型 Project 是否自动保持活跃

这些都属于更高一层自动化机制。

当前阶段不展开：

* 自动迁移
* 自动归档
* 自动升格 / 降级

只先承认：

* 生命周期阶段存在
* 差异存在

### 5.9 当前 1.0 暂不展开：完整记忆 / 保留策略

虽然已经承认生命周期与记忆策略相关，

但当前不展开完整体系，例如：

* 每类 Project 要保留哪些字段
* 保留多久
* 保留到哪一层
* 何时裁剪
* 何时归档只留摘要
* 何时仅留产物不留过程

这些都太细。

当前只先冻结方向判断，不展开完整策略。

## 5.10 当前 1.0 暂不展开：生命周期与协同的自动联动

你后面一定会自然继续问：

* 一个 Project 生命周期变化，是否自动影响协同关系
* 派生型结束后，主 Project 是否自动更新
* 某个长期型暂停后，相关 Round 是否自动调整

这些问题都很真实，

但当前阶段不适合展开。

因为一旦展开，就会把生命周期文档和协同文档绑死。

所以当前阶段：

**不展开生命周期与协同的自动联动机制。**

## 5.11 当前 1.0 暂不展开：完整字段设计

当前阶段也不适合继续写：

* Project 生命周期字段表
* 生命周期标记位
* 生命周期日志模型
* 生命周期和保留策略的字段关系

原因很简单：

你现在还在冻结概念边界，

不是做最终数据模型。

所以当前阶段：

**先冻结概念层，不冻结完整字段层。**

## 5.12 为什么这些内容当前不展开

这一节也必须单独写。

不展开，不是因为这些问题不重要，

而是因为当前阶段的任务不是“做完生命周期系统”，而是：

**先让 Project 生命周期以最小正确形态成立。**

当前不展开这些内容，有三个原因：

### 5.12.1 防止生命周期文档膨胀成完整状态系统

一旦把所有迁移、自动化、字段、裁剪都写进来，

你现在好不容易把：

* Node.status
* Round 状态
* Workspace 焦点
* 生命周期

拆开了。

如果现在继续深入自动机制，边界会再次混掉。

### 5.12.3 保住当前推进节奏

你现在真正需要的是：

* 先让生命周期概念成立
* 再去补协同和实现设计

而不是在这里一次性把系统全做完。

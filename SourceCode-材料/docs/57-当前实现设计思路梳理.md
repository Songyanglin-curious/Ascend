# 当前实现设计思路梳理

## 1. 文档目的

这份文档不是重新定义 Ascend 1.0，而是把 **当前仓库里的实际实现** 讲清楚。

它主要服务两个目标：

1. 让还没通读代码的人，先看懂现在这套代码是怎么组织起来的
2. 让后续纠偏时，能明确区分：
   - 哪些是当前实现已经存在的承接方式
   - 哪些是与 docs 冻结规则仍然存在偏差的地方

因此，本文档讲的是“现状实现”，不是“理想设计”。

---

## 2. 当前实现的整体定位

当前仓库更接近一个 **树形节点推进 demo + CLI 状态外壳**。

它已经具备这些最小能力：

1. 有 Solution / Workspace / Project / Round / Node / Tree / StepRecord 这些对象外壳
2. 可以在 Project 内维护一棵树
3. 可以聚焦当前节点并推进一步
4. 可以把一步的结果写成 StepRecord
5. 可以把最新 StepRecord 回写到 Tree
6. 可以通过 CLI 查看状态、列节点、看节点详情、创建新节点、推进当前节点
7. 可以通过 DeepSeek 先生成 step 草稿或 finish 草稿，再走现有 CLI 流程

它还不等于 docs 中那套完整运行主链，原因是：

1. 没有真正的 NodeRuntime
2. 没有 mode 流转
3. 没有“单轮内部过程”这层运行态
4. AI 只拿到轻量上下文，不是完整树级上下文
5. finish 不是完整留痕闭环

---

## 3. 当前实现里的对象分工

### 3.1 Solution

`src/Solution.ts` 里的 Solution 很薄，只负责：

1. 承接方案 ID
2. 承接方案目标
3. 承接 Project 列表

它当前不负责复杂的跨 Project 编排。

### 3.2 Workspace

`src/Workspace.ts` 里的 Workspace 负责：

1. 记录当前在哪个 Solution 里
2. 记录当前 focus 的 Project
3. 记录一个 `currentEntry`

这里最大的现状问题是：

`currentEntry` 在当前实现里是混用的。

它有两种来源：

1. `focusWorkspaceProject()` 会把它写成 `project.currentNodeId`
2. 真正执行一步后，又会把它写成 `kernel.updatedNode.next`

所以它目前同时被当成：

1. 当前焦点位置
2. 下一步文本入口

这也是后续必须纠偏的关键点之一。

### 3.3 Project

`src/Project.ts` 里的 Project 是当前最重要的上层容器，负责承接：

1. `nodes`
2. `tree`
3. `currentNodeId`
4. `lifecycleStage`

它内部目前默认就是：

**一个 Project = 一组节点快照 + 一棵节点关系树 + 一个当前焦点节点。**

### 3.4 Node

`src/Node.ts` 里的 Node 当前是一个“内容快照体”。

它主要保存：

1. `raw`
2. `summary`
3. `conclusion`
4. `next`
5. `status`
6. `activeStatus`

当前实现对 Node 的理解更接近：

**节点当前快照**

而不是：

**节点完整多轮运行面**

这就是为什么你会看到：

1. `raw` 只是一个字符串
2. 多轮历史主要散落在全局 `stepRecords`
3. Node 自己并不拥有完整的多轮原始对话承接结构

### 3.5 Tree

`src/NodeTree.ts` 与 `src/Tree.ts` 提供的是节点关系结构。

当前 Tree 主要负责：

1. 父子关系
2. 同级顺序
3. 最近一次 StepRecord 的回写挂点

当前 Tree 不负责承接完整历史，只挂一个 `currentStepRecordId`。

### 3.6 StepRecord

`src/StepRecord.ts` 里的 StepRecord 是当前最小留痕体。

它只保留：

1. `input`
2. `output`
3. `change`
4. `next`

当前实现里它更像：

**某一步完成后的结果快照**

而不是：

**一个节点完整一轮运行日志**

### 3.7 Scheduler

`src/Scheduler.ts` 当前只实现了最小调度器：

1. 过滤候选节点
2. 给候选打分
3. 选出当前节点

评分主要看：

1. 节点状态
2. `next` 是否明确
3. `scenario` 与当前场景是否贴近
4. 与当前焦点节点的树距离
5. 同级顺序

它还没有实现：

1. mode 入口选择
2. 人工介入判断
3. 真正的回流主链控制

### 3.8 Rescan

`src/Rescan.ts` 当前只是一个最小工具：

1. 找变化源的直接子节点
2. 把这些节点重新设为 `启用`

它目前没有正式接回 CLI 主链。

### 3.9 Round

`src/Round.ts` 当前只是一个最小数据壳。

CLI 在展示状态时，还会临时构造一个 `round-current`。

所以当前 Round 的现状更像：

**当前上下文快照壳**

而不是严格意义上的：

**跨 Project 变化组织单位**

## 4. 当前实际推进主链

当前最常走的是 CLI 主链，而不是 docs 中更完整的运行主链。

### 4.1 初始化

`npm run cli -- init` 或 `reset` 会创建一个 demo 状态：

1. 一个 Solution
2. 一个 Project
3. 一个默认 Node
4. 一个默认 Tree
5. 一个 Workspace

这一步是 demo 初始化，不是“真实原始输入入场”。

### 4.2 聚焦节点

运行时主要依赖 `currentNodeId` 来表达当前聚焦节点。

CLI 也提供 `focus-node` 命令来手工切换焦点。

### 4.3 推进一步

执行 `step` 或 `step-ai` 时，主链是：

1. 读取当前状态文件
2. 找到当前 Project
3. 找到当前焦点 Node
4. 构造一个 step draft
5. 调 `runProjectWorkflowKernel()`
6. 生成一条新的 StepRecord
7. 回写 Tree 的 `currentStepRecordId`
8. 回写 Workspace 的 `currentEntry`
9. 落盘回 `runtime/.ascend-cli-state.json`

当前这里最关键的实现选择是：

CLI 使用的是 `runProjectWorkflowKernel()`，不是 `runProjectMinimalKernel()`。

这意味着默认行为是：

1. 生成新的 StepRecord
2. 更新 Node 的 `next`
3. 保留既有 `summary / conclusion`

所以当前 step 更像：

**给当前节点追加一步结果，并更新下一入口**

而不是：

**重新生成节点当前完整快照**

### 4.4 AI 推进一步

`step-ai` 会先调 DeepSeek 生成草稿，再复用现有 step 流程。

模型拿到的上下文目前包括：

1. project 的简化信息
2. workspace 的简化信息
3. 当前 node 的快照
4. 最近几条 stepRecords

这里没有把整棵树结构、父子节点、完整多轮原始记录一起送给模型。

所以当前 AI 推进更像：

**当前焦点节点的轻量草稿生成**

而不是：

**整棵问题树上的完整上下文推理**

### 4.5 finish

`finish` / `finish-ai` 当前走的是另一条更短的链：

1. 找到目标节点
2. 生成人工或 AI 的 `summary / conclusion`
3. 直接调用 `finishProjectNode()`
4. 把节点状态改成 `已完成`
5. 落盘

这里不会新增 StepRecord。

这就是现状实现里最明显的非对称点：

1. `step` 会留痕
2. `finish` 不留痕

## 5. 当前实现里的两条“推进语义”

这是理解当前代码时最容易混的地方。

### 5.1 最小内核语义

`runProjectMinimalKernel()` 的语义更接近：

1. 选中当前节点
2. 生成 StepRecord
3. 用这一步结果直接更新节点的 `summary / conclusion / next`
4. 回写 Tree

### 5.2 工作流语义

`runProjectWorkflowStep()` 的语义更接近：

1. 选中当前节点
2. 生成 StepRecord
3. 默认只更新 `next`
4. 保留节点既有的 `summary / conclusion`
5. 回写 Tree

当前 CLI 主要走第二条。

所以如果只看 CLI，你看到的系统行为更接近：

**追加一步历史，而不是重写节点当前结论。**

---

## 6. 当前实现里最重要的已知偏差

这里只收最关键、最影响介入判断的偏差。

### 6.1 Node 还不是完整多轮承接体

`raw` 只是字符串。

这意味着：

1. 当前问题原文
2. 当前 AI 回复
3. 多轮原始问答
4. 中间过程原文

并没有在 Node 本体里形成稳定承接。

### 6.2 缺少 NodeRuntime

docs 中很重要的：

1. `currentMode`
2. `isWaitingHuman`

在实现层还不存在。

所以“单轮内部过程”这条线现在基本是空的。

### 6.3 currentEntry 语义混用

当前代码同时把它当成：

1. 节点位置
2. 下一步文本入口

这会直接影响 Workspace 的边界稳定性。

### 6.4 Round 被 demo 化

当前状态查看时会临时造一个 `round-current`。

这会让 Round 从“必要时成立的跨 Project 单位”滑向“当前上下文的展示壳”。

### 6.5 finish 没有留痕闭环

这使得：

1. step 是有历史的
2. finish 是直接改结果的

运行链路不对称。

### 6.6 树推进仍主要靠人工驱动

当前系统还没有形成：

1. 完整的自动选点
2. 自动拆子节点
3. 自动回流
4. 自动继续下一节点

所以它现在更像：

**人工操作一棵树**

而不是：

**系统稳定推进一棵树**

## 7. 你现在介入时最值得先看的地方

如果你暂时不想通读全部代码，建议优先看这几类文件：

1. `src/Node.ts`
   - 先看 Node 当前到底承接了什么
2. `src/Progress.ts`
   - 先看“一步推进”现在到底怎么定义
3. `src/Project.ts`
   - 先看 Project 内部当前怎么挂节点和树
4. `src/Workspace.ts`
   - 先看 `currentEntry` 为什么会混
5. `runtime/cli.mjs`
   - 先看真实运行入口到底怎么串起来
6. `runtime/llm.mjs`
   - 先看 AI 实际拿到的上下文有多薄

---

## 8. 一句话总结

**当前实现已经把“树、节点、一步留痕、CLI 运行入口”搭出来了，但它仍然主要是一个演示级的最小运行外壳；真正与你原始设计冲突最大的地方，是 Node 还没有成为完整多轮运行面，运行态也还没有独立成 NodeRuntime。**

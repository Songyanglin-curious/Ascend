
**你要找的不是“思考框架”，而是“任务推进框架”。**
单纯思考，prompt 已经够了；你现在要解决的是：

* 思考
* 写作
* 改写
* 评审
* 归档
* 回扫
* 调度

这些怎么放进同一套系统里，还不互相打架。

所以关键不在于继续强化“发散-收敛”，而在于找到**更高一层的共性**。

这个共性我建议你这样定：

## 不要把共性定成“步骤内容”

而要定成“推进单元的统一契约”

也就是说，写文章和发散收敛当然不一样，但它们都可以被统一成：

**一个节点在当前状态下，经过一次推进，产出新的状态、结果和下一步入口。**

这才是共性。

不是都要发散收敛。
也不是都要先想再写。
而是都要满足同一个运行骨架：

1. 有输入状态
2. 有本轮动作
3. 有输出结果
4. 有状态变化
5. 有下一步入口

这就是你要找的“框架级共性”。

## 所以你的系统别围绕“思考循环”建

要围绕“推进单元”建

你可以把最底层收成一个统一对象：

### Step / Unit

表示一次最小推进。

它不关心自己是不是思考、写作、评审，只关心：

* 当前处理对象是什么
* 这一步的目标是什么
* 用哪种模式推进
* 产出了什么
* 下一步是什么

然后“思考”“写作”“评审”都只是不同的推进模式。

## 这样一来，你的框架可以分成三层

### 1. 运行骨架层

这个层只定义统一契约，不定义具体任务内容。

统一契约就是：

* 输入
* 动作
* 输出
* 状态
* 下一步

这是最核心的一层。

### 2. 模式层

这里放不同类型的推进模式。

例如：

* Explore：探索
* Select：选择
* Write：写作
* Review：评审
* Revise：修订
* Summarize：提炼
* Freeze：冻结

注意，这些是“模式”，不是全系统唯一流程。

### 3. 场景层

这里才是具体组合。

比如：

#### 思考场景

Explore → Select → Freeze

#### 写文章场景

Clarify topic → Structure → Write → Review → Revise

#### 学习场景

Explore material → Summarize → Review understanding → Freeze

#### 需求文档场景

Explore → Select → Structure → Write → Review → Freeze

这样就通了。

## 你之前为什么会难受

因为你试图让“发散收敛”成为全系统底层共性。

但实际上它只适合一类任务：
**对象还不清晰、需要探索和收敛的任务。**

而写文章很多时候不是这个状态。

写文章更像：

* 已有目标
* 已有材料
* 需要组织
* 需要表达
* 需要评审修改

它的核心矛盾不是“发散收敛”，而是“组织-生成-校验”。

所以你现在的突破点是：

**承认不同任务的底层推进模式不同，但它们共享同一个运行骨架。**

这就既有共性，又保留扩展性。

## 你真正该统一的有三样

### 1. 统一对象

都挂在节点树上。

无论是思考节点、写作节点、评审节点，都是节点。

### 2. 统一推进记录

每一步都留下：

* 原始输入
* 精炼内容
* 本轮结果
* 下一步入口

### 3. 统一调度方式

调度不关心你这一步是发散还是写作，只关心：

* 当前节点状态
* 当前适合哪种模式
* 下一步该推进什么

## 所以现在最实用的判断

你别再问：

**“所有任务能不能都归到发散收敛？”**

答案是不行，也不该。

你该问的是：

**“所有任务能不能都归到统一推进骨架，然后由不同模式组合完成？”**

答案是可以，这就是你要找的框架方向。

## 最后压成一句

**共性不在任务内容里，共性在推进契约里。**
**框架负责统一推进方式，模式负责处理任务差异，场景负责做具体组合。**

你现在最值得先定的，不是四层还是三层，而是这一条统一契约。

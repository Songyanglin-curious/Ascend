# Ascend 1.0 方案

## 1. 版本定位

Ascend 1.0 是  **探索性编码 Agent 阶段** 。

它不是完整产品，也不是最终架构。
它要验证的是：

**复杂任务能否脱离大段 prompt 的人工硬控，转而通过统一推进骨架来稳定推进。**

Ascend 1.0 关注的不是“怎么把所有任务都变成同一种思考循环”，而是：

**怎么让思考、写作、改写、评审、归档、回扫、调度进入同一套系统，又不互相打架。**

## 2. 核心判断

Ascend 1.0 不是思考框架，而是  **任务推进框架** 。

它的共性不在任务内容里，而在推进契约里。

也就是说：

* 写文章和发散收敛不一样
* 评审和写作不一样
* 学习和需求分析也不一样

但它们都可以被统一成同一种运行骨架：

1. 有输入状态
2. 有本轮动作
3. 有输出结果
4. 有状态变化
5. 有下一步入口

这就是 Ascend 1.0 的底层共性。

## 3. 1.0 要解决的核心问题

Ascend 1.0 主要解决五件事：

1. 上下文不再依赖平铺聊天历史，而是可承接
2. 不同任务不再混在同一次输出里，而是按模式推进
3. 每次推进都有记录，而不是只留下最后结果
4. 任务可以形成清晰的下一步入口，而不是每次重新起头
5. 上位变化后，相关内容可以重新纳入推进

## 4. 1.0 的主骨架

Ascend 1.0 的真正主结构，不是 Node/Step 本身，而是三层推进框架：

### 4.1 运行骨架层

这是最底层、最核心的一层。

它不定义具体任务内容，只定义统一推进契约：

* 输入状态
* 本轮动作
* 输出结果
* 状态变化
* 下一步入口

这一层回答的是：

**任何任务在系统里，最小一次推进应该长什么样。**

### 4.2 模式层

这一层定义不同类型的推进方式。

例如：

* Explore：探索
* Select：选择
* Write：写作
* Review：评审
* Revise：修订
* Summarize：提炼
* Freeze：冻结

模式层回答的是：

**这一步到底是以什么方式推进。**

这里承认不同任务的底层推进模式不同，不强行统一成“发散—收敛”。

### 4.3 场景层

这一层定义不同任务如何组合模式。

例如：

* 思考场景：Explore → Select → Freeze
* 写作场景：Structure / Write → Review → Revise
* 学习场景：Explore → Summarize → Review
* 需求文档场景：Explore → Select → Structure → Write → Review → Freeze

场景层回答的是：

**一类任务通常如何组织模式。**

## 5. 1.0 的支撑结构

在三层推进框架之外，Ascend 1.0 还需要一组支撑结构，使统一推进骨架能够真正落地运行。

这些支撑结构不构成系统的主骨架，但它们共同承担了 **上下文承接、过程留痕、关系组织与推进控制** 的职责。

### 5.1 Node Tree

Node Tree 负责维护节点之间的组织关系。

它的职责不是保存节点内容，而是描述节点如何形成整体结构。

它主要解决的问题是：

* 节点之间如何形成树状组织
* 父节点与子节点如何关联
* 平级分支、主分支、保留分支如何挂接
* 节点在整体上下文中的位置如何确定

可以理解为：

**Node Tree 管关系，不管内容。**

### 5.2 Node

Node 是推进对象的内容承载体。

它不是系统主骨架，但它是系统中最核心的上下文单元之一。

它主要负责承载某一推进对象当前的内容状态，主要解决的问题是：

* 当前在推进什么
* 原始内容如何保留
* 总结内容如何承接
* 当前结论如何挂住
* 下一步入口如何保留
* 当前状态如何表达

可以理解为：

**Node 管内容，不管关系。**

### 5.3 Step Record

Step Record 负责记录最近一次具体推进。

它不是骨架本身，而是统一推进契约在系统中的一次实际留痕。

它主要解决的问题是：

* 这一步围绕哪个对象展开
* 这一步做了什么
* 这一步采用了什么模式
* 这一步产出了什么结果
* 这一步让对象发生了什么变化

可以理解为：

**Step Record 管过程，不管长期承载。**

### 5.4 Scheduler / Rescan

Scheduler 和 Rescan 负责维持系统的推进秩序。

它们不直接承载内容，也不直接构成关系结构，而是承担推进控制职责。

其中：

* **Scheduler** 负责决定当前推进哪个对象、采用什么模式、是否需要人工介入
* **Rescan** 负责在上位变化后识别受影响内容，并将其重新纳入推进流程

它们主要解决的问题是：

* 系统下一步应如何继续推进
* 推进优先级如何安排
* 变化发生后哪些内容需要重新处理
* 系统如何在动态变化中保持可继续性

可以理解为：

**Scheduler / Rescan 管推进秩序，不管内容本体。**

## 5.5 支撑结构之间的关系

这四类支撑结构分别承担不同职责：

* **Node Tree** 负责组织关系
* **Node** 负责承载内容
* **Step Record** 负责记录推进
* **Scheduler / Rescan** 负责控制推进

它们共同服务于三层推进框架，使 Ascend 1.0 不只是一个抽象骨架，而是一套可以持续承接、持续推进、持续调整的运行结构。

Ascend 1.0 的运行方式可以压成一句话：

**对象挂在上下文中，通过某种模式完成一次推进，留下记录，更新状态，并形成下一步入口。**

展开就是：

1. 当前存在一个推进对象
2. 该对象有当前状态
3. 系统根据当前状态选择模式
4. 执行一次推进
5. 生成结果与记录
6. 更新对象状态
7. 形成下一步入口
8. 必要时触发人工决策
9. 上位变化时触发回扫，再进入下一轮推进

## 7. 1.0 对任务差异的处理方式

Ascend 1.0 不要求所有任务共享同一种步骤内容。
它要求的是：

* **共享同一种推进骨架**
* **通过 Mode 处理任务差异**
* **通过 Scenario 做具体组合**

因此：

* 思考任务可以偏探索与冻结
* 写作任务可以偏组织、生成、修订
* 评审任务可以偏检查与反馈
* 学习任务可以偏理解、提炼、校验

这样系统既有共性，又保留扩展性。

## 8. 1.0 的边界

Ascend 1.0 不做这些事：

1. 不追求完整自治
2. 不追求覆盖所有任务类型
3. 不追求复杂多 Agent 协同
4. 不追求把所有任务统一成同一种循环模板
5. 不追求一次性做成最终产品

Ascend 1.0 只验证一件事：

**统一推进骨架，是否足以把复杂任务从纯 prompt 阶段推进到可持续承接的编码阶段。**

## 9. 1.0 的阶段目标

### 阶段一：推进骨架成立

确认输入状态、本轮动作、输出结果、状态变化、下一步入口这 5 项能够成为统一契约。

### 阶段二：任务差异纳入模式层

确认不同任务不再混在一起，而是通过不同 Mode 处理。

### 阶段三：任务组合纳入场景层

确认不同场景可以通过 Mode 组合形成自己的推进路径。

### 阶段四：上下文与记录能承接推进

确认推进对象可以持续承接，且每次推进都有记录。

### 阶段五：调度与回扫开始发挥作用

确认系统能够根据状态继续推进，并在上位变化后重新纳入受影响内容。

## 10. 一句话定义

**Ascend 1.0 是一套以统一推进契约为底层骨架、以 Mode 处理任务差异、以 Scenario 做任务组合、以 Node Tree 承接上下文、以 Step Record 留下推进痕迹、以 Scheduler / Rescan 维持推进秩序的探索性编码方案。**

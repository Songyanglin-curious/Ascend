可以。
我按我们现在已经定下来的模型，把 **从“只有原始输入”到“一轮结束”** 的完整过程顺一遍。

先压一句总定义：

**一轮 = 一个 Node 在其所属 Scenario 下走完，形成明确输入输出；中间的 mode 流转、循环、回退都属于这一轮内部过程。**

下面是完整主链。

## 一、起点：只有原始输入，还没有 Node

系统最开始拿到的是一份原始输入，例如：

* 一个问题
* 一段想法
* 一个任务
* 一段草稿
* 一次用户输入

这时还没有 Node，也谈不上调度、mode、StepRecord。

---

## 二、创建首个 Node

先把原始输入转成系统里的第一个可承载对象。

这一步至少形成：

* `id`
* `title`
* `raw`

这时：

* `summary`
* `conclusion`
* `next`

都允许为空，因为还没经过真正推进。

---

## 三、轻量初始化处理

这一步只做结构准备，不做内容推进。

它负责：

1. 确定 `scenario`
   * 输入倾向明显时，可由 AI 判定
   * 倾向不明显时，由人判定
2. 设置 Node 初始运行状态
   * `status = 未开始`
   * `activeStatus = 启用`
3. 挂入 NodeTree
   * 首个 Node 作为根节点进入树结构
4. 初始化 NodeRuntime
   * `nodeId`
   * `currentMode = null`
   * `isWaitingHuman = false`

到这里为止，这个 Node 才算真正进入系统。

---

## 四、Scheduler 选定当前 Node

现在系统里已经有了一个可运行 Node。
Scheduler 开始工作。

它先做候选过滤，再选当前推进对象。

当前第一轮通常很简单，因为一般只有一个首节点。
以后如果节点多了，Scheduler 再根据：

* `activeStatus`
* `status`
* `next`
* `scenario`
* NodeTree 位置

去做选择。

这一步的结果是：

**当前轮到哪个 Node 进入推进。**

---

## 五、Scheduler 为当前 Node 确定 mode 入口

这一步不是自由乱猜，而是受 scenario 约束。

规则是：

### 1. 如果 `NodeRuntime.currentMode = null`

说明这个 Node 还没真正进入场景工作流。

这时：

* 根据 `scenario`
* 找到该场景的入口 mode

### 2. 如果 `currentMode` 不为空

说明这个 Node 已经在一轮内部推进过。

这时：

* 不重新猜入口
* 直接从当前断面继续

但按我们当前主链推演，第一次通常是 `currentMode = null`。

---

## 六、进入并执行这一轮内部的 mode 流程

这里有一个很重要的边界：

**进入 mode 和执行 mode 合并为同一步。**

也就是说，一旦确定当前 mode，就直接开始这一轮内部推进。
不会再拆成：

* 先记当前位置
* 再单独执行

### 这一轮内部可能发生什么

一个 Scenario 内部可以有多个 mode 流转，例如：

* Explore
* Review
* Revise
* Freeze

这些 mode 可以：

* 线性前进
* 循环
* 回退
* 分支判断

但这些都还属于  **同一个 Node 的同一轮内部过程** 。

---

## 七、这一轮内部运行时，更新什么

这一点我们已经定得比较清楚了：

### 1. 过程中的细粒度变化

只更新：

* `NodeRuntime`
* 原始上下文存储

也就是说，过程中可以不断积累：

* 当前跑到哪个 mode
* 是否等待人工
* 本轮对话过程
* 本轮中间原始输入输出

### 2. 过程中不立即更新什么

这一轮内部过程里，不频繁更新：

* `Node.summary`
* `Node.conclusion`
* `Node.next`
* `StepRecord`

因为这些是 **一轮结束后才统一沉淀** 的东西。

---

## 八、必要时人工介入

如果运行到某一步时，出现这些情况：

* 场景方向不清
* 分支判断无法自动确定
* 是否冻结无法拍板
* 用户意图明显不足

那么系统会进入：

* `NodeRuntime.isWaitingHuman = true`

此时本轮不算完成，只是进入等待人工的中间态。
人工给出选择后，再继续这一轮内部流程。

---

## 九、一轮完成

当这个 Node 在其所属 Scenario 下完成时，这一轮才真正结束。

这里的“完成”不是全系统问题解决了，
而是：

**这个 Node 在这个 Scenario 下，该走的流程走完了，已经形成了本节点这一轮的明确输入输出。**

这时才进入统一沉淀。

---

## 十、生成 StepRecord

一轮结束后，生成一条 StepRecord。

它记录的是这一整轮的沉淀结果，而不是中间每个 mode。

当前最小版本是：

* `id`
* `nodeId`
* `input`
* `output`
* `change`
* `next`

这里的含义是：

* `input`：这一轮的输入
* `output`：这一轮的最终输出
* `change`：这一轮让 Node 发生了什么整体变化
* `next`：这一轮之后，下一步入口是什么

---

## 十一、统一回写 Node

StepRecord 生成后，再统一更新 Node。

主要更新：

* `summary`
* `conclusion`
* `next`
* `status`

这里要注意：

### `status` 怎么变

这一点按你们后续可再细化，但当前可以这样理解：

* 如果这个 Node 这一轮完成后已完全结束，可设为 `已完成`
* 如果这一轮已经形成稳定结果，但仍保留后续重开可能，可设为 `已冻结`

你们后续实现时可以再明确哪种场景进哪个状态。

---

## 十二、必要时创建子节点

如果这一轮的结果带来了新的可推进对象，就在这里创建新的子 Node。

例如：

* 当前节点完成后，拆出几个新的子问题
* 需要切换场景，则不在原 Node 上切换，而是创建新的子节点

然后：

* 新子节点写入 Node
* 关系写入 NodeTree
* 子节点再各自初始化进入系统

这一步非常关键，因为你们已经定了：

**一个 Node 不切换 scenario；若需切换场景，拆成新的子节点。**

---

## 十三、必要时触发 Rescan

如果这一轮完成后带来了上位关键变化，例如：

* `conclusion` 被根本性修正
* 原有冻结结论被推翻
* 后续节点前提发生变化

这时触发 Rescan。

Rescan 只做两件事：

1. 找出受影响节点
2. 让这些节点重新纳入推进流程

它不直接修内容，最后还是交回 Scheduler。

---

## 十四、回到 Scheduler，开始下一轮

当这一轮的：

* StepRecord 已生成
* Node 已回写
* NodeTree 已更新（如有）
* Rescan 已触发（如有）

系统就回到 Scheduler。

然后：

* 从当前启用节点里
* 选择下一个要推进的 Node

进入下一轮。

---

# 压成最短主链

如果只保留主干，就是：

**原始输入 → 创建首个 Node → 轻量初始化 → Scheduler 选当前 Node → 按 scenario 进入并执行本轮 mode 流程 → 过程中更新 NodeRuntime 与原始上下文 → 一轮完成后生成 StepRecord → 统一回写 Node → 必要时创建子节点 / 触发 Rescan → 回到 Scheduler**

---

# 这条链里每个结构的职责

再压一句，防止混：

* **Node** ：承载这个对象当前的内容状态
* **NodeTree** ：承载它与其他节点的关系
* **NodeRuntime** ：承载这一轮内部运行到哪
* **Scheduler** ：决定当前轮到谁
* **StepRecord** ：记录这一轮最终留下了什么
* **Rescan** ：在关键变化后把受影响节点重新送回流程

---

这一步如果你认可，下一步最值得做的不是再扩概念，而是：

 **把这条主链压成“明确的阶段清单”** ，也就是分成 1、2、3、4 这样的正式步骤，方便后面直接喂给 AI 去实现。

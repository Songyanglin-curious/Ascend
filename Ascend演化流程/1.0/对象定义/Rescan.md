
# Rescan 的定位

**Rescan 不是重新思考一切，也不是自动修正文档。**
它只是一个“变化后的重新纳管器”。

它存在的原因只有一个：

**当上位节点发生关键变化时，系统需要知道哪些旧节点不再完全可信，应该重新进入推进流程。**

所以它的核心作用不是“处理内容”，而是：

**发现受影响节点，并把它们交回调度系统。**

# Rescan 1.0 的最小功能

我建议 1.0 里，Rescan 只承担 4 个功能。

## 1. 接收变化源

先明确：

**哪个节点发生了关键变化。**

这里的“变化源”通常是一个 Node。
例如：

* `conclusion` 被改了
* `summary` 被大幅重写了
* `next` 被改成了完全不同的方向
* 节点从“已冻结”重新打开

Rescan 的第一步不是分析全局，而是先拿到一个明确的变化起点。

## 2. 定位直接受影响节点

Rescan 先只看 **直接下游** ，不要一开始做全图传播。

也就是：

* 这个节点的子节点
* 明确挂在它下面继续展开的节点
* 明确以它为前提的节点

这一层的目标不是“找全所有可能受影响内容”，而是：

**先找到最明显、最直接需要重看的节点。**

这很重要，因为 1.0 要克制。
如果一上来就做深度传播，很容易失控。

## 3. 重新标记节点

找到受影响节点后，Rescan 不负责重写内容。
它只负责把这些节点的“运行资格”改掉，让它们重新回到系统视野里。

也就是说，它要做的更像是：

* 把原本停用的节点重新启用
* 或把原本冻结的节点标记为需要重新审视
* 或增加一个“待重新检查”的信号

这里的本质是：

**让旧节点重新进入可推进范围。**

## 4. 交回 Scheduler

这是边界最重要的一点。

Rescan 找完节点之后，不继续往下做。
它不负责：

* 先处理哪个
* 用什么 Mode
* 是否立即执行

这些都交回 Scheduler。

所以完整链路是：

**上位变化 → Rescan 找到受影响节点 → 这些节点重新进入候选池 → Scheduler 决定先处理谁**

# Rescan 不负责什么

为了防止它长歪，1.0 里必须明确它不负责下面这些事。

## 1. 不负责自动改内容

它不直接改 `summary`、`conclusion`、`next`。
它只负责把节点重新送回流程。

## 2. 不负责决定优先级

它不决定先回扫哪个节点。
那是 Scheduler 的事。

## 3. 不负责复杂因果推理

1.0 里先不做：

* 跨多层复杂影响传播
* 网状依赖分析
* 高级语义推断式回扫

这些以后再说。

## 4. 不负责替代人工判断

Rescan 可以提示“这些节点可能受影响”，
但不替人拍板“这些节点一定要全面重做”。

# Rescan 1.0 的触发条件

我建议 1.0 先只认少量触发条件，不要太多。

## 1. 当前结论被修改

这是最核心的触发条件。
因为 `conclusion` 代表节点当前已成立判断，一旦改了，下游最容易受影响。

## 2. 节点从已冻结重新打开

这表示原本稳定的东西被重新讨论了，下游应重新纳管。

## 3. 上位节点方向发生明显切换

比如 `next` 不再是原来的推进方向，而是切到另一条路。
这时候原来的下游节点可能就需要重看。

先这三类就够了。

# Rescan 1.0 的输出

Rescan 最终输出的东西应该很简单，不要复杂化。

它至少输出：

* 变化源节点是谁
* 哪些节点被判定为受影响
* 这些节点需要被重新纳入推进

也就是说，它的输出不是“修复结果”，而是：

**待重新处理的节点列表。**

# 一句话定义

**Rescan 是在上位节点发生关键变化时，识别直接受影响节点，并将其重新纳入推进流程的能力。**

# 和整体框架的关系

最后再压一句它在整体里的位置：

* **NodeTree** 提供关系
* **Rescan** 利用关系找受影响节点
* **Scheduler** 决定重新纳入后的处理顺序

所以：

**Rescan 是变化后的发现器，不是执行器。**

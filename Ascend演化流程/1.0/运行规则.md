# Ascend 1.0 运行规则冻结稿

## 0. 文档定位与适用范围

### 0.1 文档定位

《Ascend 1.0 运行规则冻结稿》用于定义 **Ascend 1.0 在运行时如何发生一次有效推进** 的正式规则。

它服务的对象不是“概念理解”，而是“运行约束”。
它要把 Ascend 1.0 已确定的统一推进契约，落实为可执行、可判断、可编码的运行规则，使系统中的一次推进能够稳定地被表示、被记录、被承接。Ascend 1.0 的统一基础不是任务内容，而是一次最小推进共同必须满足的结构：输入状态、本轮动作、输出结果、状态变化、下一步入口。

这份文档面向的是  **1.0 的探索性编码阶段** 。
它不承担完整产品说明职责，也不承担最终架构定稿职责；它只负责把 1.0 当前已经形成的运行骨架，压成可以继续实现设计和编码落地的规则文本。Ascend 1.0 当前的版本定位是“探索性编码 Agent 阶段”，目标是验证统一推进骨架是否足以支撑复杂任务从纯 prompt 阶段进入可持续承接的编码阶段。

### 0.2 本文档要解决的问题

本文档只回答以下问题：

1. 原始输入进入系统后，何时算真正进入运行范围
2. 一个 Node 如何开始、进行、暂停、完成一轮推进
3. 哪些状态会变化，哪些信息只在一轮结束后统一沉淀
4. Scheduler 在运行中可以做什么，不可以做什么
5. 人工介入在什么位置发生，发生后意味着什么
6. 子节点与 Rescan 在什么条件下触发，以及它们如何影响后续推进

也就是说，这份文档关心的是  **运行中的规则顺序与约束边界** ，而不是抽象介绍对象本身。Ascend 1.0 的最短主链已经明确为：原始输入 → 创建首个 Node → 轻量初始化 → Scheduler 选当前 Node → 确定并执行本轮 mode 流程 → 过程更新 NodeRuntime 与原始上下文 → 一轮完成 → 生成 StepRecord → 回写 Node → 必要时创建子节点 / 触发 Rescan → 回到 Scheduler。运行规则文档就是对这条主链及其条件分支进行正式约束。

### 0.3 本文档不解决的问题

本文档不负责以下内容：

1. 不重新论证 Ascend 1.0 的版本定位、主骨架与理念来源
2. 不重新解释 Node、NodeTree、StepRecord、Scheduler、Rescan 的概念价值
3. 不定义完整类型字段设计细节
4. 不给出具体代码实现、类划分、接口设计或存储方案
5. 不扩展 1.0 之外的场景、模式与产品能力
6. 不讨论最终 UI、交互层或完整产品形态

原因是这些内容分别属于方案文档、类型定义文档和实现设计文档的职责范围。Ascend 1.0 当前也明确不追求完整自治、不追求覆盖所有任务类型、不追求复杂多 Agent 协同、不追求一次性做成最终产品。

### 0.4 与其他文档的边界

本文档与其他文档的边界如下：

**1. 与《方案》文档的边界**
《方案》负责回答“Ascend 1.0 是什么、为什么这样设计、主骨架是什么、支撑结构承担什么职责”。
《运行规则冻结稿》不再重讲这些内容，只在这些前提已经成立的基础上，继续回答“系统在运行时到底按什么规则推进”。方案文档已经明确：共性在推进契约，不在任务内容；三层主骨架是运行骨架层、模式层、场景层；支撑结构负责内容承载、关系组织、推进留痕与推进控制。

**2. 与类型定义文档的边界**
类型定义文档负责回答“系统里有哪些核心对象、每个对象至少有哪些字段”。
《运行规则冻结稿》不负责新增对象，也不负责展开字段设计，只规定这些对象在运行中如何被使用、何时更新、在什么条件下发生状态变化。当前已基本稳定的对象最小集合包括 Node、NodeTree、StepRecord、Scheduler、Rescan，以及相关状态字段。

**3. 与协作链路文档的边界**
协作链路文档负责回答“谁先做、谁后做、谁产出给谁”。
《运行规则冻结稿》则在既有链路基础上补上“每一步按什么规则成立、哪些可以自动推进、哪些必须等待人工、哪些条件会重开节点或触发回扫”。也就是说，链路文档描述顺序，运行规则文档补充约束。

**4. 与实现设计文档的边界**
实现设计文档负责回答“这些规则最终如何落成代码、模块、接口、存储与执行流程”。
《运行规则冻结稿》在它之前，作为实现设计的上游约束输入存在。没有这份规则冻结，AI 在实现时就容易脑补状态流转、人工触发条件和重开规则。现有材料也已经明确，状态流转规则、Freeze 后重开、Rescan 入池、人工介入触发条件都还需要正式收口。

### 0.5 适用范围

本冻结稿的适用范围限定在  **Ascend 1.0 的运行骨架层及其直接相关支撑结构交互** ，具体包括：

* Node 进入系统运行范围前后的规则
* Node 在单轮推进中的运行规则
* Node.status、activeStatus、NodeRuntime 等运行相关状态的使用规则
* Scheduler 对候选选择、推进进入、人工等待、继续推进的规则
* StepRecord 的生成时机与 Node 的统一回写规则
* 子节点创建与 Rescan 重新纳管的触发规则

本文档默认以上对象和主链已经成立，因此不再回头讨论是否需要这些对象，而只讨论它们在 1.0 中如何运作。Ascend 1.0 当前已经基本完成版本定位、主骨架、支撑结构职责边界和对象最小定义，正在进入把协作链路和运行规则压成可编码设计的阶段。

### 0.6 使用原则

阅读和使用本文档时，应遵守以下原则：

1. 以运行约束优先，不以概念解释优先
2. 以 1.0 当前边界优先，不提前为后续版本预埋复杂扩展
3. 以最小可编码为目标，不把规则写成抽象口号
4. 以统一推进契约为总前提，不把某一类任务的内容流程误写成系统共性
5. 规则冲突时，以“是否有利于稳定表示、稳定记录、稳定承接一次推进”为最终判断标准

这与 Ascend 1.0 的第一原则一致：系统真正统一的不是任务内容，而是一次推进必须满足的共同结构。

## 1. 运行规则的基本约束

### 1.1 统一前提：Ascend 1.0 以推进契约作为运行骨架

Ascend 1.0 的运行规则，不以某一种任务内容流程作为基础，而以统一推进契约作为基础。
也就是说，系统中任何一次被承认为“有效推进”的过程，都必须至少能够被表示为以下五项：

* 当前输入状态
* 本轮动作
* 输出结果
* 状态变化
* 下一步入口

这五项不是某个具体场景的写法，而是 Ascend 1.0 所有运行规则的共同前提。后续所有章节中的初始化、调度、单轮执行、结果沉淀、条件触发，都必须能够落回这五项之中。

### 1.2 Ascend 1.0 是任务推进框架，不是内容流程框架

Ascend 1.0 的共性不在任务内容本身，而在任务如何被表示、被记录、被承接。
因此，系统不要求所有任务共享同一种内容步骤，也不要求所有任务都服从同一种“思考循环”。它真正统一的是运行骨架，而不是内容过程。不同任务的差异，由 mode 表达；不同任务的组织方式，由 scenario 表达。

这一约束的直接含义是：

* 运行规则只规定“推进必须怎样成立”
* 不规定所有任务“具体应该怎么做”
* 不把某个场景内部的内容习惯误写成系统共性

### 1.3 一轮的定义是 Node 级、Scenario 级完成

在 Ascend 1.0 中，“一轮”不是一次对话，不是一次消息往返，也不是某个 mode 的单步执行。
一轮的正式定义是：

**一个 Node 在其所属 Scenario 下走完，形成明确输入输出；中间的 mode 流转、循环、回退都属于这一轮内部过程。**

因此，后续所有运行判断都应以这个口径为准：

* 进入一个 mode，不等于一轮开始完成
* mode 间切换，不等于新开一轮
* 人工中途介入，不等于一轮结束
* 只有当该 Node 在当前 Scenario 下形成了本轮明确输入输出，才算一轮完成

### 1.4 Scenario 先于 Mode，Mode 受 Scenario 约束

Ascend 1.0 的三层主骨架已经明确为：运行骨架层、模式层、场景层。场景层定义一类任务如何组织 mode，模式层定义某一步以什么方式推进。由此，运行规则中的顺序必须固定为：

**先确定 scenario，再由 scenario 约束 mode 的进入与流转。**

这意味着：

* mode 不是自由乱选
* mode 入口不能脱离 scenario 单独决定
* 当 `NodeRuntime.currentMode = null` 时，应按当前 scenario 找入口 mode
* 当 `currentMode` 已存在时，应从当前断面继续，而不是重新猜入口

本章只冻结这一上层顺序，不展开不同 scenario 的具体 mode 映射；映射细则属于后续章节。

### 1.5 一个 Node 不切换 Scenario

一个 Node 在进入系统并完成轻量初始化后，应当在其既定 scenario 下推进。
如果后续运行过程中发现需要切换场景，不应直接修改原 Node 的 scenario，而应创建新的子节点承接新的场景推进。

这一约束的作用是防止一个 Node 的运行身份在中途漂移，导致：

* 同一 Node 的历史记录无法解释
* StepRecord 的轮次边界被破坏
* 原有结论与后续推进混在一起
* Scheduler 难以判断当前对象到底处于哪类推进路径

因此，本冻结稿将其视为硬规则，而不是实现建议。

### 1.6 单轮内部允许多次 Mode 流转，但这些都不单独构成 StepRecord

在一个 Node 的一轮内部，允许发生多个 mode 的线性前进、循环、回退与分支判断。
这些过程都属于同一轮内部运行，而不单独生成 StepRecord。StepRecord 只记录该 Node 在该 Scenario 下完成一轮后的最终沉淀结果，不记录中间每个 mode 的细过程。

因此，系统必须遵守以下边界：

* 中间 mode 流转属于运行态，不属于最终留痕
* 过程中可更新 `NodeRuntime` 与原始上下文
* `Node.summary / conclusion / next` 不应在每个 mode 后频繁回写
* StepRecord 只能在一轮完成后生成

这一约束是后续“单轮运行规则”和“沉淀规则”的共同前提。

### 1.7 Scheduler 只做受约束选择，不承担内容判断本体

Scheduler 属于推进秩序控制结构，不属于内容承载结构。
它的职责是决定当前推进哪个对象、采用什么模式、是否需要人工介入，以及在变化发生后系统如何继续推进；它不直接承载内容，也不直接构成关系结构。

因此，本冻结稿对 Scheduler 的基本约束是：

* 它可以做“受约束选择”
* 它不能替代内容生成与内容判断本体
* 它不能把自己扩张成系统“大脑”
* 它的判断必须建立在已有状态、scenario、运行断面和规则约束之上

后续章节可以展开 Scheduler 的候选过滤、当前节点选择、mode 入口选择和人工介入判断，但这些都不能突破本条边界。

### 1.8 Rescan 只负责重新纳管，不直接修复内容

Rescan 的职责是：当上位关键变化发生后，识别受影响节点，并让这些节点重新纳入推进流程。
它不直接修改节点内容，不直接替代后续一轮推进，也不直接生成新的结论。

因此，本冻结稿对 Rescan 的基本约束是：

* Rescan 只负责识别影响范围
* Rescan 只负责把相关节点送回推进范围
* 被重新纳管的节点，后续仍应交回 Scheduler
* 内容修复、结论更新、重新冻结，都必须通过后续正常推进完成

这条边界的意义是防止 Rescan 演化成“隐式修复器”，破坏系统的显式留痕与运行可解释性。

### 1.9 人工介入属于单轮中途等待，不属于新开一轮

当运行过程中出现方向不清、分支无法自动判定、是否冻结无法自动拍板、用户意图明显不足等情况时，系统可以进入等待人工状态，例如 `NodeRuntime.isWaitingHuman = true`。
但这种等待只表示本轮中途暂停，不表示一轮已经结束，也不表示系统要另开一轮。人工输入补入后，应继续原有单轮内部流程。

因此，本章冻结如下边界：

* 人工介入是运行中断面，不是轮次边界
* 等待人工不自动生成 StepRecord
* 等待人工不直接触发 Node 统一回写
* 人工返回后应继续当前单轮，而不是默认新建 Node 或新起一轮

### 1.10 主干闭环必须成立，条件动作按需插入

Ascend 1.0 的最短主链已经基本明确：

**原始输入 → 创建首个 Node → 轻量初始化 → Scheduler 选当前 Node → 按 scenario 进入并执行本轮 mode 流程 → 过程中更新 NodeRuntime 与原始上下文 → 一轮完成后生成 StepRecord → 统一回写 Node → 必要时创建子节点 / 触发 Rescan → 回到 Scheduler。**

这条链路说明两个基本事实：

第一，主干闭环必须成立。
也就是从“进入一轮推进”到“生成记录并回到调度”的最小闭环必须可解释、可承接、可继续。

第二，条件动作不是主干必经项。
人工介入、创建子节点、触发 Rescan 都是按条件插入，不是每轮必发生。系统规则应保证主干稳定，条件动作按需出现，而不是把所有可能情况都强行塞进每一轮。

### 1.11 本章结论

第 1 章冻结的不是状态细节，而是后续所有规则都必须服从的上层前提：

* Ascend 1.0 以推进契约作为运行基础
* 一轮是 Node 级、Scenario 级完成
* scenario 先于 mode，mode 受 scenario 约束
* 一个 Node 不切换 scenario
* 中间 mode 流转不单独生成 StepRecord
* Scheduler 只做受约束选择
* Rescan 只做重新纳管
* 人工介入只是单轮中途等待
* 主干闭环必须成立，条件动作按需插入

## 2. 进入系统前后的初始化规则

### 2.1 原始输入不等于系统内对象

系统最开始接收到的只是原始输入。它可能是一个问题、一段想法、一份任务描述、一段草稿，或者一次用户输入。此时还没有 Node，也还没有调度、mode 或 StepRecord，因此这类输入只能算“系统外原始材料”，还不能直接进入运行主链。

因此，本冻结稿先明确一条边界：

**Ascend 1.0 不直接对原始输入做调度；原始输入必须先对象化，才能进入运行范围。**
这也符合 Ascend 1.0 的统一推进方式：系统处理的不是散乱聊天片段，而是具有当前状态、可被推进、可被记录、可形成下一步入口的推进对象。

### 2.2 首次进入系统的链路不能跳

当外部新输入第一次进入系统时，首次输入链必须经过三个阶段：

1. 接收原始输入
2. 创建首个 Node
3. 轻量初始化

这三个阶段属于首次入场链，不能跳步。链路清单已经明确：当外部新输入第一次进入系统时，`1 → 2 → 3` 不能跳；也就是说，不能跳过对象化直接初始化，也不能跳过初始化直接交给 Scheduler。

因此，本章冻结如下规则：

**首次输入只有在完成“创建 Node + 轻量初始化”之后，才允许被视为系统内可运行对象。**
在这之前，它只是待处理输入，不属于调度范围。

### 2.3 创建首个 Node 的目标是“对象化”，不是“开始推进”

创建首个 Node 的目标，是把原始输入转成系统内可承载的对象。
这一步至少形成三个字段：

* `id`
* `title`
* `raw`

与此同时，以下字段允许为空：

* `summary`
* `conclusion`
* `next`

原因很直接：在这一时刻，系统只是把输入对象化，还没有进入真正推进，因此不应假装已经有中高密度沉淀结果。相关链路材料已经明确，这一步“只是把输入对象化，还不算开始推进”。

由此冻结两条规则：

第一，创建 Node 时必须有最小承载字段，使原始输入获得系统内唯一身份与可引用性。

第二，创建 Node 时不得提前写入本应在一轮完成后才统一沉淀的结果字段，例如 `summary / conclusion / next`。这些字段允许为空，并应留待后续真实推进后再回写。

### 2.4 轻量初始化的职责是“让 Node 真正进入系统”

创建完 Node 之后，还不能立刻视为它已经进入了系统运行主链。
轻量初始化阶段的职责，是把这个刚对象化的 Node 变成一个真正可被调度、可被推进、可被承接的运行对象。现有链路文档已经明确：这一步“只做结构准备，不做内容推进”；并且“到这里为止，这个 Node 才算真正进入系统”。

因此，本冻结稿正式定义：

**Node 的“进入系统”时点，不是创建对象时，而是轻量初始化完成时。**
在初始化之前，Node 只是系统内的裸承载体；初始化完成后，它才具备运行身份。

### 2.5 轻量初始化必须完成的四项内容

轻量初始化阶段必须完成四项内容，缺一不可。

#### 2.5.1 确定 scenario

初始化时必须先确定该 Node 所属的 scenario。规则已明确：

* 输入倾向明显时，可由 AI 判定
* 倾向不明显时，应由人工判定

这里的 scenario 判定，不是内容推进的一部分，而是为了让这个 Node 获得后续 mode 入口和运行身份。因为在 Ascend 1.0 中，scenario 先于 mode，mode 受 scenario 约束；没有 scenario，就没有合法的入口 mode。

因此，本章冻结：

**轻量初始化必须给出 scenario；若当前无法可靠判定，则不得跳过，而应等待人工给定。**
系统不能让一个“scenario 未定”的 Node 进入后续调度。

#### 2.5.2 设定 Node 初始运行状态

初始化时必须为 Node 设定初始运行状态：

* `status = 未开始`
* `activeStatus = 启用`

这说明两个事实。
第一，Node 已经进入系统，但尚未真正开始一轮推进，所以状态应是“未开始”，而不是“进行中”。
第二，它在初始化完成后默认应进入候选范围，因此 `activeStatus` 设为“启用”。链路文档已经把这一组初始状态写得很明确。

因此，本章冻结：

**初始化阶段只能把 Node 放到“已入场但未开始”的位置，不能在此阶段直接推进到“进行中”。**
真正进入一轮推进，要等 Scheduler 选中并进入 mode 之后才成立。

#### 2.5.3 写入 NodeTree

初始化时必须把 Node 写入 NodeTree。
对于首次输入形成的首个 Node，它应作为根节点进入树结构。现有链路材料已经把这一步写清：首节点作为根节点挂入树；到此之后，这个对象才不只是单独存在，而是正式进入可承接的上下文结构。

因此，本章冻结：

**任何进入系统运行范围的 Node，都必须处于 NodeTree 中。**
首次输入形成的首 Node 必须作为根节点挂入；后续新节点则按其来源关系挂入。初始化阶段不要求展开全部关系语义，但要求至少完成“进入树”的动作。

#### 2.5.4 初始化 NodeRuntime

初始化时必须为该 Node 建立运行态，并至少写入：

* `nodeId`
* `currentMode = null`
* `isWaitingHuman = false`

相关链路文档已经明确把这三项列为初始化内容：`currentMode` 初始为空，`isWaitingHuman` 初始为否。其含义是：该 Node 已拥有运行时承接位，但尚未真正进入具体 mode，也尚未处于等待人工状态。

这里也顺带暴露出一个实现层要对齐的小口径：当前 `NodeRuntime.ts` 中的 `currentMode` 仍被写成普通 `string` 字段，而初始化链路口径已经明确要求首轮是 `currentMode = null`。这说明实现定义后续需要和运行规则对齐，否则初始化规则无法被类型系统准确表达。

### 2.6 轻量初始化只做结构准备，不做内容推进

轻量初始化阶段的核心边界是：**只做结构准备，不做内容推进。**
这一点在“链路清单”和“一个 Node 的链路”里都被直接写明。初始化阶段负责的是 scenario、初始状态、入树、运行态，而不是生成结论、形成下一步、做候选池、进入 Review 或 Write。

因此，本章冻结以下禁止项：

* 初始化阶段不进入任何 mode
* 初始化阶段不生成 StepRecord
* 初始化阶段不回写 `summary / conclusion / next`
* 初始化阶段不把 Node 标记为“已开始一轮”
* 初始化阶段不替代 Scheduler 做后续选择

这样做的目的，是保住主链分工：初始化只负责“让对象进入可运行范围”，真正的推进从 Scheduler 选定当前 Node 并为其确定 mode 入口时开始。

### 2.7 什么时点算“真正进入系统”

结合前面各条，本章把“真正进入系统”的判定正式压成一个明确标准：

一个 Node 只有同时满足以下条件，才算真正进入系统运行范围：

1. 已由原始输入创建为 Node
2. 已确定 scenario
3. 已设定初始状态为 `status = 未开始`、`activeStatus = 启用`
4. 已写入 NodeTree
5. 已初始化 NodeRuntime，且 `currentMode = null`、`isWaitingHuman = false`

只要上述条件有任何一项未完成，该对象都不应被 Scheduler 当作可调度对象。链路材料已经明确指出：到轻量初始化完成为止，这个 Node 才算真正进入系统；而 Scheduler 的工作发生在这之后。

因此，本章冻结一句总规则：

**“进入系统”不是一个模糊感觉，而是初始化完成后的正式状态切换。**
只有在这个切换发生后，Ascend 1.0 的运行主链才真正开始。

### 2.8 首次输入完成初始化后的直接后果

当首个 Node 完成初始化之后，系统就进入下一个阶段：Scheduler 开始工作。
此时它才有资格从启用节点中选出当前推进对象。第一轮通常比较简单，因为一般只有一个首节点；后续节点增多后，Scheduler 才会根据 `activeStatus / status / next / scenario / NodeTree 位置` 等因素做进一步筛选和排序。

所以，初始化完成的直接后果不是“内容已经推进”，而是：

**系统获得了一个合法的可调度起点。**
这是初始化阶段唯一应该交付给后续主链的结果。

### 2.9 本章结论

第 2 章冻结的是“Node 如何进入系统”的规则，而不是“Node 如何完成一轮推进”的规则。到本章为止，可以正式压下以下几点：

* 原始输入不直接参与调度，必须先对象化
* 首次输入链 `接收原始输入 → 创建 Node → 轻量初始化` 不能跳
* 创建 Node 只完成最小承载，不提前写沉淀结果
* 轻量初始化的职责是让 Node 真正进入系统
* 初始化必须完成：确定 scenario、设定初始状态、写入 NodeTree、初始化 NodeRuntime
* 初始化只做结构准备，不做内容推进
* 初始化完成后，Node 才获得可调度资格
* Scheduler 的工作从初始化完成之后才开始

## 3. 节点状态与候选资格规则

### 3.1 节点状态只表达“推进阶段”，不表达“是否纳入调度”

在 Ascend 1.0 中，`Node.status` 只负责表达这个节点当前处于什么推进阶段。
它不直接表达该节点当前是否应该进入候选池，也不承担“主线 / 保留”“当前要不要碰”的语义。Node 当前的最小推进状态集合已经基本冻结为：

* `未开始`
* `进行中`
* `已冻结`
* `已完成`

因此，本章先冻结一条总边界：

**`status` 是推进阶段状态，不是调度资格状态。**
这也是前面“对象最小定义”里已经修正过的口径：`NodeStatus` 承接的是推进状态，而不是宽泛的运行语义。

### 3.2 activeStatus 只表达“是否纳入当前推进范围”

与 `status` 不同，`activeStatus` 的职责是表达该节点当前是否纳入系统的推进范围。
当前最小定义已经明确为两种：

* `启用`
* `停用`

并且在前面的整理里，这个字段已经被明确用来承接“保留分支 / 暂不跟进”的运行语义，而不是把这些语义塞进 NodeTree 或 `status`。

因此，本章冻结第二条总边界：

**`activeStatus` 只管当前要不要把该节点纳入推进范围，不管这个节点本身推进到了哪一步。**

由此可以推出两点：

* `status = 进行中` 的节点，也可能因为某种原因被 `停用`
* `status = 未开始` 的节点，只要 `activeStatus = 启用`，就仍然可能进入候选池

也就是说，推进阶段和是否纳入当前候选，不是同一个维度。

### 3.3 NodeRuntime 不属于节点状态集合

除了 `status` 和 `activeStatus` 之外，系统里还有 `NodeRuntime`。
它承接的是单轮运行中的临时断面，例如：

* `currentMode`
* `isWaitingHuman`

在前面的主链与初始化规则里已经明确：`NodeRuntime` 在初始化时被创建，过程中持续更新；人工介入时体现在 `isWaitingHuman = true`，而这并不等于一轮结束，也不等于 Node 出现了一个新的正式状态。

因此，本章冻结：

**等待人工、当前 mode、运行断点，都属于 `NodeRuntime`，不属于 `Node.status`。**

换句话说：

* 不额外引入“等待中”这种 Node 状态
* 不把 `currentMode` 混写进 `status`
* 不把“一轮内部暂停”误当成“节点推进阶段改变”

这条边界非常重要，否则后面状态规则会把“中途等待”和“阶段完成”混为一谈。

### 3.4 四种 Node.status 的正式含义

#### 3.4.1 `未开始`

`未开始` 表示该节点已经完成对象化和初始化，已经真正进入系统运行范围，但还没有被正式带入一轮推进。
前一章已经冻结：初始化完成后，Node 的初始状态是 `status = 未开始`、`activeStatus = 启用`；真正进入一轮推进，要等到 Scheduler 选中它并进入 mode 之后。

因此，`未开始` 的正式含义是：

**已入场，未开轮。**

它说明这个节点已经具备系统内身份和可承接性，但尚未发生本轮推进。

#### 3.4.2 `进行中`

`进行中` 表示该节点已经被带入推进主链，当前仍处在可继续推进、尚未结束的状态。
结合主链定义，这类节点已经进入过 `选 Node → 定 mode → 执行一轮内部流程` 这一段，但还没有落到“这一轮完全结束并完成沉淀”的最终状态。

因此，`进行中` 的正式含义是：

**已开轮，仍可继续。**

它是最典型的“应优先收口”的状态。前面的 Scheduler 讨论也已经明确，在有资格的节点里，`进行中` 优先于 `未开始`，核心原则是“先收口，再开新口”。

#### 3.4.3 `已冻结`

`已冻结` 表示该节点已经形成阶段性稳定结果，当前默认不继续向前推进，但它不是绝对终态。
前面的链路和 Rescan 讨论已经明确：冻结结果可能在上位变化、人工操作或重新纳管后被重新打开，因此 `已冻结` 不应等同于“永远结束”。

因此，`已冻结` 的正式含义是：

**阶段性收住，默认不继续，但保留被重新打开的可能。**

这也是为什么在候选资格上，`已冻结` 默认不进入候选池，但在被重新打开或被重新纳管时可以重新进入。前面的 Scheduler 材料已经直接给出了这一口径。

#### 3.4.4 `已完成`

`已完成` 表示该节点在 1.0 当前边界下已经结束，不再作为继续推进对象进入调度。
Scheduler 的候选过滤规则已经明确：`status != 已完成` 是候选门槛之一。

因此，`已完成` 的正式含义是：

**该节点在当前版本边界下视为终态。**

后续如仍需继续，不应直接把它当普通候选重新推进；通常应通过新子节点承接，或者在更高版本里定义更细的 reopen 机制。就 1.0 而言，本章先把它冻结成默认终态。

### 3.5 两种 activeStatus 的正式含义

#### 3.5.1 `启用`

`启用` 表示该节点当前被纳入系统推进范围。
但它不自动等于“本轮一定会被选中”，因为进入候选池之后还要继续受 `status`、`next`、`scenario`、NodeTree 位置和人工指定等因素影响。Scheduler 的讨论已经明确：`activeStatus = 启用` 只是候选门槛之一，不是最终选中结果。

因此，`启用` 的正式含义是：

**允许参与当前调度。**

#### 3.5.2 `停用`

`停用` 表示该节点当前不纳入系统推进范围。
它不代表内容作废，不代表树关系失效，也不必然代表这个节点已经完成；它只表示当前不把它送进候选池。前面的对象边界已经把“保留分支”的运行语义主要压到 `activeStatus` 上，而不是压到 NodeTree。

因此，`停用` 的正式含义是：

**当前保留，不进入调度。**

这也意味着：

* 一个节点可以内容上仍然有效，但运行上暂时停用
* 停用节点后续可以被人工重新启用
* Rescan 或人工操作也可以让停用节点重新回到推进范围，只是那属于后续条件触发规则，不在本章展开细则。

### 3.6 status 与 activeStatus 的边界关系

到这里为止，本章把两者的边界正式压成一句话：

**`status` 说明“推进到了哪里”，`activeStatus` 说明“当前要不要纳入推进”。**

由此可得四条直接规则：

1. 不能用 `status` 表达“保留分支”
2. 不能用 `activeStatus` 表达“已经冻结”或“已经完成”
3. 不能把两者合并成一个字段
4. Scheduler 做候选过滤时，必须先同时看这两个维度，而不是只看其中之一

这也是当前 1.0 运行边界里最值得保住的一条结构清晰性。

### 3.7 候选资格的最小门槛

在 Ascend 1.0 里，Scheduler 的第一件事不是“选谁”，而是先做候选过滤。前面的材料已经直接写明，最小门槛至少包括：

* `activeStatus = 启用`
* `status != 已完成`
* 必要时排除 `已冻结`

结合当前链路与状态口径，本章将候选资格正式冻结为：

一个 Node 只有同时满足以下条件，才有资格进入当前候选池：

1. `activeStatus = 启用`
2. `status != 已完成`
3. `status != 已冻结`，除非它已被明确重新打开或重新纳管

这三条是 **门槛** ，不是排序。
也就是说，它们先决定“能不能进池”，之后才谈“进池后先选谁”。

### 3.8 各状态对候选资格的直接影响

为了后续实现更稳定，本章把四种 `status` 对候选资格的影响直接写死如下。

#### 3.8.1 `未开始`

* 若 `activeStatus = 启用`，可进入候选池
* 若 `activeStatus = 停用`，不可进入候选池

理由是：它虽然尚未开轮，但已经是合法的系统内对象。初始化完成后，首个 Node 就是以这种状态获得可调度资格的。

#### 3.8.2 `进行中`

* 若 `activeStatus = 启用`，可进入候选池
* 并且在后续排序上通常优先于 `未开始`

理由是：它是典型的“已开轮未收口”对象，前面的 Scheduler 讨论已经明确“进行中 > 未开始”，原则是先收口，再开新口。

#### 3.8.3 `已冻结`

* 默认不进入候选池
* 只有在被明确重新打开、被 Rescan 重新纳管、或被人工操作重新送回推进范围时，才重新具备候选资格

这和前面的 Scheduler 与 Rescan 口径一致：冻结默认排除，但在被重新送回来后可以重新纳入候选。

#### 3.8.4 `已完成`

* 不进入候选池

这是最硬的一条。候选过滤已经把 `status != 已完成` 写成门槛；1.0 当前边界下不把已完成节点当普通候选重新推进。

### 3.9 候选资格不等于最终选中

即使一个节点已经进入候选池，也不等于它一定会成为“当前 Node”。
前面的材料已经明确：Scheduler 在候选过滤之后，还会继续参考至少这些信息来做选择：

* `status`
* `next`
* `scenario`
* NodeTree 位置
* 人工指定 / 外部触发

因此，本章再冻结一条边界：

**候选资格只解决“有没有资格被选”，不解决“此刻先选谁”。**

“先选谁”属于下一章 Scheduler 运行规则的内容；本章只把门槛钉死。

### 3.10 本章结论

第 3 章到这里正式冻结以下内容：

* `Node.status` 只表达推进阶段
* `activeStatus` 只表达是否纳入当前推进范围
* `NodeRuntime` 只承接单轮内部运行断面，不进入 Node 状态集合
* Node 的正式推进状态集合为：`未开始 / 进行中 / 已冻结 / 已完成`
* Node 的正式启用状态集合为：`启用 / 停用`
* 候选资格的最小门槛为：`activeStatus = 启用`、`status != 已完成`、`已冻结` 默认不进池
* `未开始` 与 `进行中` 在启用时可进入候选池
* `已冻结` 默认不进池，重新打开或重新纳管后才可重新进入
* `已完成` 不进入候选池
* 候选资格不等于最终选中，排序与人工覆盖属于 Scheduler 规则范围

## 4. Scheduler 运行规则

### 4.1 Scheduler 的定位

在 Ascend 1.0 中，Scheduler 是推进秩序控制器。
它不承载内容，不组织树关系，不记录推进结果，也不直接执行内容生成；它的职责是基于既有状态和约束，决定系统当前如何继续推进。现有材料已经把它压成五项职责：过滤候选节点、选择当前推进对象、选择本轮 mode、判断是否需要人工介入、接收重新纳管的节点。

因此，本章先冻结一句总定义：

**Scheduler 在 1.0 中是受约束选择器，不是内容大脑。**
它负责“选谁、怎么推进、什么时候别自动选”，但不负责替代 Node、NodeTree、StepRecord、Mode 或 Scenario 各自的职责。

### 4.2 Scheduler 的进入时机

Scheduler 的工作起点，不在原始输入阶段，也不在 Node 刚创建时。
前面的主链已经明确：只有当首个 Node 完成轻量初始化，真正进入系统运行范围后，Scheduler 才开始工作。此时系统中已经存在一个可运行 Node，Scheduler 再先做候选过滤，再选当前推进对象。

因此，本章冻结：

**Scheduler 的前提是：节点已经完成初始化并具备可调度资格。**
它不负责把原始输入对象化，也不负责补做初始化。初始化之前的对象，不进入 Scheduler 的工作范围。

### 4.3 Scheduler 的运行顺序

Scheduler 在一轮中的工作顺序应固定，不应自由打乱。
结合现有链路和讨论，1.0 应按以下顺序运行：

1. 候选过滤
2. 当前 Node 选择
3. 本轮 mode 确定
4. 是否需要人工介入判断
5. 若无需人工，则把当前 Node 送入本轮内部流程
6. 若存在重新纳管节点，则把其接回候选范围后再按上述顺序处理

这里有一个很重要的边界：

**Scheduler 只负责把节点送到正确入口，不负责替节点完成这一轮内容推进。**
节点真正进入 mode 并执行内部流程，是后续主链阶段；Scheduler 到“确定当前 Node + 确定当前 mode + 判断是否需要人工”为止。

### 4.4 候选过滤规则

Scheduler 的第一件事不是“选谁”，而是先过滤掉本轮不该碰的节点。
现有材料已经把最小门槛写清楚：

* `activeStatus = 启用`
* `status != 已完成`
* `已冻结` 默认不进入，除非被重新打开或重新纳管

因此，本章正式冻结：

**Scheduler 必须先做候选过滤，只有通过门槛的节点才允许进入后续排序。**

这一步是门槛判断，不是优先级排序。
也就是说，在这里先回答“有没有资格被选”，而不是“谁更优先”。这也和前一章“候选资格不等于最终选中”的边界一致。

### 4.5 当前 Node 选择规则

在候选池形成后，Scheduler 才进入“当前 Node 选择”。
现有材料已经把 1.0 的优先依据压成六类，并给出了主次顺序。第一层仍然是资格门槛；在通过门槛后，再依据推进状态、`next`、`scenario`、NodeTree 位置和人工指定来做首选判断。

#### 4.5.1 第一优先级：推进状态

在有资格的节点中，先看 `status`。
当前建议顺序已经基本收住为：

1. `进行中`
2. `未开始`
3. `已冻结`（仅在被重新纳管时）
4. `已完成`（不选）

这条规则背后的原则也已经明确：

**先收口，再开新口。**
已经在推进中的节点，通常比新开的节点更适合优先处理。

#### 4.5.2 第二优先级：`next` 是否明确

在推进状态之后，再看当前节点的 `next` 是否明确。
现有讨论已经明确：

* `next` 明确，说明节点有更低摩擦的承接入口
* `next` 不明确，说明还缺继续推进条件，或者需要先人工判断

因此，本章冻结：

**有明确 `next` 的节点，优先于没有明确 `next` 的节点。**

这条规则的意义不是把 `next` 当成绝对命令，而是把它当成“当前是否更容易继续推进”的信号。

#### 4.5.3 第三优先级：`scenario` 与当前任务是否同路

在 `next` 之后，再看节点所属 `scenario` 是否贴近当前系统上下文或当前会话主线。
现有材料已经明确，`scenario` 在这里的作用不是做永久高低排序，而是判断“这个节点和当前任务是不是同路”。正在处理什么类型的任务，就优先同类或相邻场景的节点。

因此，本章冻结：

**`scenario` 的优先级作用，是上下文贴近度，而不是固定等级。**

#### 4.5.4 第四优先级：NodeTree 位置

再之后，看节点在 NodeTree 中的位置。
现有材料已经把 NodeTree 在 Scheduler 这里的作用压成两点：

* 节点离当前焦点远不远
* 同级中的 `order` 如何排列

因此，本章冻结：

**NodeTree 为 Scheduler 提供位置与顺序信息，用于做最后一层排序。**
朴素原则是：当前焦点附近的节点优先；同级冲突时按 `order`。

#### 4.5.5 第五优先级：人工指定 / 外部触发

如果存在人工显式关注或外部触发，Scheduler 可以提高相应节点优先级。
现有材料已经直接列出这类情形：

* 用户刚点了某个节点
* 某个节点刚被人工启用
* Rescan 刚把某个节点重新送回候选池

因此，本章冻结：

**人工显式关注高于普通自动排序。**
但这种覆盖只作用于“当前优先级”，不改写底层状态定义。

### 4.6 当前 Node 选择的最小顺序

综合前面各条，Scheduler 选择当前 Node 时，1.0 的最小顺序冻结为：

1. 先判断能不能进入候选池
2. 在候选池中优先 `进行中` 节点
3. 再看 `next` 是否明确
4. 再看 `scenario` 是否贴近当前任务
5. 再看它在树中离当前焦点是否更近
6. 同级并列时按 `order`
7. 有人工指定或外部触发时，优先人工指定

这条顺序是 1.0 的 **最小可实现规则** ，不是永久最优算法。
它的目的不是做复杂全局调度，而是让系统在多节点条件下仍能稳定给出“现在先推进谁”。

### 4.7 mode 选择规则

在当前 Node 选定后，Scheduler 还要为它确定本轮 mode。
这一点在链路文档里已经写得很清楚：如果 `NodeRuntime.currentMode = null`，说明该节点还没真正进入场景工作流，此时应根据 `scenario` 找到该场景的入口 mode；如果 `currentMode` 不为空，则说明该节点已经在一轮内部推进过，应直接从当前断面继续，而不是重新猜入口。

因此，本章冻结如下规则：

**mode 选择必须受 scenario 约束，并且优先沿着已有运行断面继续。**

具体来说：

* `currentMode = null`：进入该 `scenario` 的入口 mode
* `currentMode != null`：从当前 mode 继续推进，不重置入口

这里再补一条边界：

**Scheduler 决定“进入哪个 mode”，但不在本章负责定义 mode 的语义内容。**
mode 本身意味着什么，属于模式层定义；Scheduler 这里只做选择。

### 4.8 人工介入判断规则

Scheduler 还承担一个很关键的职责：判断这一轮能不能自动继续，还是必须交给人。
现有材料已经把几类典型触发条件列出来：

* 候选节点并列，规则无法明显区分
* 当前 Node 的 `next` 不明确
* 当前场景下可选 mode 不止一个，而且差异很大
* 涉及冻结、切换方向、重新激活停用节点

因此，本章冻结：

**Scheduler 不只负责自动选，还负责判断什么时候不该自动选。**

一旦判定必须人工介入，本轮应进入等待人工状态，而不是伪装成系统已经可以继续推进。等待人工在运行态上表现为 `NodeRuntime.isWaitingHuman = true`；它表示单轮中途暂停，不表示一轮结束。

### 4.9 重新纳管入口规则

当 Rescan 或人工操作把某些节点重新送回运行范围时，Scheduler 还承担一个很轻但必要的职责：把这些节点重新接回当前候选流程。
现有材料已经直接把这一点列为它的五项职责之一。

因此，本章冻结：

**Scheduler 是重新纳管节点进入推进流的入口，不是重新修复内容的执行者。**

也就是说，重新纳管只意味着：

* 某些节点重新具备被过滤、被排序、被选中的资格
* 后续仍按正常候选过滤、当前节点选择、mode 选择和人工判断继续

它不意味着 Scheduler 直接帮这些节点生成新结论。

### 4.10 Scheduler 不负责的事

为了避免后面实现漂移，这一章还必须把它的非职责边界写死。
现有材料已经明确，Scheduler 不负责：

* 承载内容，那是 Node
* 关系组织，那是 NodeTree
* 记录推进，那是 StepRecord
* 定义 mode 语义，那是 Mode
* 定义 scenario 语义，那是 Scenario
* 真正执行内容生成，它只是选，不是做

因此，本章正式冻结一句：

**只要某个功能开始承担“内容本体生成或内容本体判断”，它就已经越过了 Scheduler 的边界。**

### 4.11 Scheduler 这一阶段的输出

Scheduler 这一阶段结束后，系统至少应获得三个结果：

1. 当前轮到哪个 Node 进入推进
2. 该 Node 当前从哪个 mode 进入或继续
3. 当前是否允许自动继续，还是应转入等待人工

也就是说，Scheduler 的交付物不是内容结论，而是 **推进入口决策** 。
后续真正的一轮内部执行，才从这里开始接手。

### 4.12 本章结论

第 4 章到这里正式冻结以下内容：

* Scheduler 是受约束选择器，不是内容大脑
* 它的五项职责是：候选过滤、当前 Node 选择、mode 选择、人工介入判断、重新纳管入口
* 它只在节点完成初始化并真正进入系统后开始工作
* 运行顺序固定为：先过滤，再选当前，再定 mode，再判断是否人工介入
* 当前 Node 的最小选择顺序为：候选资格 → 推进状态 → `next` → `scenario` 贴近度 → NodeTree 位置 → 人工指定
* mode 选择遵循：`currentMode = null` 时按 `scenario` 进入入口 mode；否则从当前断面继续
* Scheduler 负责判断什么时候不该自动选
* Scheduler 负责把重新纳管节点接回推进流
* Scheduler 不承载内容、不组织关系、不记录推进、不定义模式与场景语义、不执行内容生成

## 5. 单轮推进中的运行规则

### 5.1 本章讨论范围

本章讨论的起点是：

**某个 Node 已经完成初始化，并被 Scheduler 选定为当前推进对象。**

本章讨论的终点是：

**该 Node 在其所属 Scenario 下，本轮已经形成明确输入输出，可以进入统一沉淀。**

也就是说，本章只覆盖主链中的这几段：

* Scheduler 为当前 Node 确定 mode 入口
* 进入并执行本轮内部流程
* 过程中更新运行态与原始过程
* 必要时等待人工
* 判定一轮完成

### 5.2 单轮的正式定义再次固定

为了避免把一次消息、一段 mode、一次人工回复误当成“一轮”，本章先再次固定单轮定义：

**一轮 = 一个 Node 在其所属 Scenario 下走完，形成明确输入输出；中间的 mode 流转、循环、回退都属于这一轮内部过程。**

因此，本章的所有规则都以这个口径为准：

* mode 前进不等于新开一轮
* mode 回退不等于上一轮失败
* 人工介入不等于一轮结束
* 只有当该 Node 在该 Scenario 下已经形成本轮明确输入输出时，才算一轮完成

### 5.3 单轮的进入条件

一个 Node 只有在满足以下前提时，才允许进入单轮推进：

1. 已完成初始化并真正进入系统
2. 已被 Scheduler 选定为当前 Node
3. 已确定本轮从哪个 mode 进入或继续

这三步不能混写。前面的链路已经明确，一轮推进主链是：选 Node → 定 mode → 执行内部流程 → 一轮完成；其中“进入 mode 与执行 mode 合并”，但“选 Node”和“定 mode”仍然先于单轮内部执行本体。

### 5.4 单轮从 mode 入口进入，不从内容结果进入

单轮开始时，系统不是先猜结果，而是先确定当前从哪个 mode 进入。规则已经在链路中写清：

* 若 `NodeRuntime.currentMode = null`，进入该 `scenario` 的入口 mode
* 若 `currentMode` 不为空，从当前 mode 继续推进，不重新猜入口

因此，本章冻结：

**单轮的进入点是 mode 入口或 mode 断点，而不是结果字段。**

也就是说，系统进入单轮时不以 `summary / conclusion / next` 为入口判断；这些字段属于一轮结束后的统一沉淀，而不是单轮开始时的运行起点。

### 5.5 “进入 mode”和“执行 mode”合并为同一步

这一条是单轮规则里非常关键的硬边界。现有链路已经明确：

**进入 mode 与执行 mode 合并，不单独拆开。**

它的含义是：

* 系统不需要先做一个“进入某 mode 但还没执行”的空阶段
* 一旦当前 mode 已确定，就直接进入该 mode 对应的本轮内部推进
* `currentMode` 的存在是为了标记运行断面，不是为了制造额外阶段

因此，本章冻结：

**单轮内部不再额外拆一个“静态占位的 mode 阶段”。**
mode 是运行位，不是展示位。

### 5.6 单轮内部允许发生的动作

在一个 Node 的同一轮内部，允许发生以下动作：

* mode 前进
* mode 循环
* mode 回退
* 分支判断
* 人工介入

这说明一轮内部不是一条僵直直线，而是允许在当前 Scenario 的工作流里进行必要的反复、校正和选择。前面的“一个 Node 的链路”也已经明确，不同 mode 可以在线性前进、循环、回退、分支判断之间切换，但这些仍属于同一个 Node 的同一轮内部过程。

因此，本章冻结：

**单轮内部允许有局部来回，但这些局部来回不构成新的轮次。**

### 5.7 单轮内部的边界：允许变化什么

单轮执行过程中，允许持续更新的是：

* `NodeRuntime`
* 原始上下文存储 / 原始过程痕迹

更具体地说，过程中可以不断积累这些信息：

* 当前跑到哪个 mode
* 是否正在等待人工
* 本轮对话过程
* 本轮中间原始输入输出

因此，本章冻结：

**单轮内部允许累积运行信息与原始痕迹，但这些变化先停留在运行层，不提前上升为最终沉淀。**

这条规则的核心目的是：
让系统在单轮内部保持可追踪、可继续，而不把每一步中间态都误当成已经稳定的结果。

### 5.8 单轮内部的边界：不立即更新什么

与上一条对应，现有链路也已经明确写出，单轮内部过程中**不立即更新**这些内容：

* `Node.summary`
* `Node.conclusion`
* `Node.next`
* `StepRecord`

因此，本章冻结：

**在单轮尚未完成之前，不频繁回写 Node 的中高密度结果字段，也不提前生成 StepRecord。**

原因很直接：

* `summary / conclusion / next` 属于一轮后的统一沉淀
* StepRecord 记录的是“一整轮留下了什么”，不是“中间每个 mode 发生了什么”

这条边界必须保住，否则系统会很快退化成“每一步都像在假装完成”。

### 5.9 NodeRuntime 在单轮中的职责

到这里为止，可以把 `NodeRuntime` 在单轮中的职责压成一句：

**NodeRuntime 承载的是这一轮内部运行到哪，而不是节点最终沉淀了什么。**

在 1.0 当前最小定义下，它至少承载：

* `nodeId`
* `currentMode`
* `isWaitingHuman`

在单轮里，这三个字段分别承担：

* `nodeId`：把运行态绑到正确 Node 上
* `currentMode`：表示当前运行断面停在哪个 mode
* `isWaitingHuman`：表示当前是否进入人工等待中断面

这里也顺手保留一个实现对齐提醒：链路口径已经明确首轮初始化时 `currentMode = null`，但当前 `NodeRuntime.ts` 仍写成普通 `string`，后续实现需要和运行规则对齐，否则单轮入口规则无法被类型精确表达。

### 5.10 人工介入属于单轮内部条件动作

现有链路已经明确把人工介入放在单轮内部，并且把它视为条件插入链，而不是主干必经链。人工介入的典型触发时机包括：

* 场景方向不清
* 分支判断无法自动确定
* 是否冻结无法拍板
* 用户意图明显不足

因此，本章冻结：

**人工介入是单轮内部的条件动作，不是主干轮次边界。**

它出现时，系统的运行表现为：

* `NodeRuntime.isWaitingHuman = true`
* 当前单轮暂停在中间断面
* 等待人工输入后，再继续这一轮内部流程

### 5.11 等待人工时，单轮没有结束

这一条必须单独钉死。现有材料已经多次写明：

**人工介入不代表一轮结束，只是中途等待。**

因此，本章冻结以下硬规则：

* `isWaitingHuman = true` 不等于一轮完成
* 等待人工时不生成 StepRecord
* 等待人工时不统一回写 `summary / conclusion / next / status`
* 人工返回后，继续当前单轮，而不是默认新建 Node 或新开一轮

这条边界的意义在于：
人工输入是单轮推进的补全条件，不是单轮推进的替代物。

### 5.12 单轮完成的判定标准

单轮什么时候算真正完成，现有链路也已经压得很清楚。判定标准至少包括：

1. 当前 Scenario 在该 Node 上已经形成明确输入输出
2. 本轮已经可以统一沉淀结果
3. 本轮不再继续内部 mode 流转

“一个 Node 的链路”对这点也给了更直白的解释：
这里的完成，不是全系统问题解决了，而是“这个 Node 在这个 Scenario 下，该走的流程走完了，已经形成了本节点这一轮的明确输入输出”。

因此，本章冻结：

**单轮完成是 Node 级、Scenario 级完成，不是全局任务级完成。**

这也意味着：

* 一个 Node 的一轮结束后，系统仍然可能继续推进其他 Node
* 一个复杂任务在全局上尚未解决，不影响某个 Node 的本轮已经完成

### 5.13 单轮完成前，不允许跳到沉淀阶段

前面的链路分类已经把一轮推进主链压成：
选 Node → 定 mode → 执行内部流程（内含运行态更新）→ 一轮完成 → 生成 StepRecord → 回写 Node → 回到 Scheduler。

因此，本章再冻结一条顺序规则：

**在单轮尚未满足完成判定之前，不允许跳过完成判定直接进入 StepRecord 或 Node 回写。**

否则会破坏两条关键边界：

* StepRecord 记录的是一轮完成后的沉淀结果
* Node 的中高密度结果字段是一轮后统一回写，而不是过程中频繁更新

### 5.14 单轮阶段的输出是什么

单轮阶段结束时，系统应交付的不是最终产品结论，而是：

1. 该 Node 在该 Scenario 下本轮已经完成
2. 本轮已形成明确输入输出
3. 本轮已到达可以统一沉淀的时点
4. 当前运行态已停在正确断面，等待后续沉淀步骤接手

也就是说，本章所定义的“单轮推进”本质上交付的是：

**一个可被沉淀的完成轮次。**

真正把它写成 StepRecord、回写进 Node，则是下一章的职责。

### 5.15 本章结论

第 5 章到这里正式冻结以下内容：

* 单轮讨论范围是：当前 Node 被选中后，到一轮真正完成前
* 一轮的定义是：一个 Node 在其所属 Scenario 下走完，形成明确输入输出
* 单轮从 mode 入口或 mode 断点进入，不从结果字段进入
* “进入 mode”和“执行 mode”合并为同一步
* 单轮内部允许：mode 前进、循环、回退、分支判断、人工介入
* 单轮内部只更新 `NodeRuntime` 与原始上下文存储
* 单轮内部不立即更新 `Node.summary / conclusion / next`，也不提前生成 StepRecord
* `NodeRuntime` 承载本轮运行断面，不承载最终沉淀结果
* 人工介入是单轮内部条件动作，等待人工不代表一轮结束
* 单轮完成的标准是：该 Node 在该 Scenario 下已形成明确输入输出，且本轮可统一沉淀、不再继续内部 mode 流转
* 单轮完成前，不允许跳到 StepRecord 生成和 Node 统一回写阶段


## 第 6 章 一轮完成后的沉淀规则

### 6.1 本章讨论范围

本章讨论的是：当某个 Node 在其所属 `scenario` 下完成一轮推进后，系统如何把这一轮正式落账，并把结果折叠回 Node 本体。

本章只处理三件事：

1. 什么时候允许进入沉淀阶段
2. `StepRecord` 在什么时点生成、记录什么
3. `Node` 在什么时点统一回写、回写什么

本章不处理：

* 单轮内部如何推进
* 子节点何时创建
* `Rescan` 何时触发
* `Scheduler` 如何继续选择下一节点

### 6.2 沉淀只能发生在“一轮完成”之后

沉淀不是单轮内部动作，而是一轮完成后的后置动作。

只有当以下条件同时成立时，才允许进入沉淀阶段：

1. 当前 Node 在当前 `scenario` 下已经形成明确输入输出
2. 本轮内部不再继续 mode 流转
3. 本轮已经具备统一落账条件

因此：

* 不能在 mode 中途生成 `StepRecord`
* 不能在等待人工时提前沉淀
* 不能在本轮尚未完成时先回写 `Node`

### 6.3 沉淀顺序固定：先 StepRecord，后 Node 回写

一轮完成后的沉淀顺序固定为：

1. 生成 `StepRecord`
2. 统一回写 `Node`

这条顺序不能颠倒。

原因是：

* `StepRecord` 负责记录“这一轮发生了什么、留下了什么”
* `Node` 回写负责把“这一轮的结果”折叠成该节点当前可继续被使用的状态

因此，`StepRecord` 面向 **轮次留痕** ，`Node` 回写面向 **当前态更新** 。

### 6.4 StepRecord 的定位

`StepRecord` 记录的是：

**一个 Node 在某个 `scenario` 下完成一轮后的结果。**

它不是过程流水，不是 mode 日志，也不是中间每一步判断的堆叠。

`StepRecord` 的职责是保留这一轮的完整推进留痕，使系统能够回答：

* 这一轮以什么为输入
* 这一轮产出了什么输出
* 这一轮让节点发生了什么变化
* 这一轮结束后，下一步入口是什么

### 6.5 StepRecord 的生成时机

`StepRecord` 只在一个时点生成：

**一轮已经完成，但 Node 还没有被统一回写之前。**

因此：

* 初始化阶段不生成 `StepRecord`
* 单轮内部 mode 流转时不生成 `StepRecord`
* 等待人工时不生成 `StepRecord`
* 只有在“本轮结束，准备正式落账”时才生成 `StepRecord`

### 6.6 StepRecord 的最小记录范围

在 1.0 当前边界下，`StepRecord` 至少应记录以下信息：

* `input`
* `output`
* `change`
* `next`

它们分别表示：

* `input`：这一轮直接承接和处理的输入
* `output`：这一轮最终产出的结果
* `change`：这一轮让该 Node 发生了什么关键变化
* `next`：这一轮结束后形成的下一步入口

`StepRecord` 的重点不是把过程写全，而是把 **这一轮最终沉淀下来的东西写清** 。

### 6.7 StepRecord 与 Node 各字段的关系

这一部分必须单独钉死，否则后面最容易混。

#### 6.7.1 `StepRecord.input` 与 `Node.raw`

`StepRecord.input` 不等于 `Node.raw`。

* `Node.raw` 是节点层面的原始材料承载体，强调完整、可追溯、保真
* `StepRecord.input` 是这**一轮**真正进入推进的输入

因此：

* `raw` 是节点级原始底稿
* `input` 是轮次级实际输入

一个 Node 可以长期保留同一份 `raw`，但不同轮次的 `input` 可能不同。

#### 6.7.2 `StepRecord.output` 与 `Node.summary / conclusion`

`StepRecord.output` 不直接等于 `Node.summary`，也不直接等于 `Node.conclusion`。

* `output` 是这一轮产出的整体结果
* `summary` 是本节点当前的高信息密度承接内容
* `conclusion` 是本节点当前已经可以暂时成立的判断

因此，关系应理解为：

**本轮 `output` 经过折叠后，才更新为节点当前的 `summary / conclusion`。**

也就是说：

* `output` 面向这一轮
* `summary / conclusion` 面向节点当前态

#### 6.7.3 `StepRecord.change` 与 `Node.status / conclusion`

`StepRecord.change` 也不等于 `Node.status`，也不等于 `Node.conclusion`。

* `change` 记录的是：这轮相对于上一轮，节点发生了什么变化
* `conclusion` 记录的是：当前已经成立了什么判断
* `status` 记录的是：这一轮结束后，节点当前落在哪个推进阶段

因此：

* `change` 是变化说明
* `conclusion` 是结果判断
* `status` 是推进落点

三者不能混写成一个东西。

#### 6.7.4 `StepRecord.next` 与 `Node.next`

`StepRecord.next` 和 `Node.next` 语义相近，但职责不同。

* `StepRecord.next`：记录这一轮结束时形成了什么下一步
* `Node.next`：作为节点当前态，供后续调度和继续推进使用

因此：

* 前者是历史留痕
* 后者是当前有效入口

### 6.8 StepRecord 不记录中间细过程

单轮内部允许出现：

* mode 前进
* mode 回退
* mode 循环
* 分支判断
* 人工介入

但这些属于运行过程，不属于 `StepRecord` 的直接记录对象。

因此，`StepRecord` 不负责记录：

* 每个 mode 经过了哪些细步骤
* 中间对话流水
* 所有临时判断与局部尝试
* `NodeRuntime` 的全部中间变化

这些过程信息应停留在运行层或原始过程层，而不是被误写成轮次沉淀。

### 6.9 Node 回写的定位

`Node` 回写的目标不是重复描述这一轮，而是把这一轮的结果折叠成节点当前态，使该节点能够被继续阅读、继续使用、继续推进。

因此，`Node` 回写回答的是：

**经过这一轮后，这个节点现在变成什么样了。**

`Node` 回写面向的是节点当前整体状态，而不是单轮过程本身。

### 6.10 Node 回写的主要字段

一轮完成后，`Node` 统一回写的核心字段为：

* `summary`
* `conclusion`
* `next`
* `status`

其中：

* `summary` 承接节点当前高信息密度内容
* `conclusion` 承接当前已经可以暂时成立的判断
* `next` 承接下一轮最小推进入口
* `status` 承接这一轮结束后的正式推进落点

### 6.11 各字段的沉淀边界

#### 6.11.1 `raw`

`raw` 是节点最完整、可追溯的原始材料。

它的职责是保真，不承担主要沉淀压缩职责。
一轮完成后的沉淀，不应把 `raw` 当成主要承接面来频繁覆盖。

因此：

* `raw` 不是本轮摘要
* `raw` 不是当前结论
* `raw` 不是下一步入口
* `raw` 的核心职责是原始信息保留与可追溯性

#### 6.11.2 `summary`

`summary` 用于承接：

**本节点当前高信息密度、较高信息完整性的承接内容。**

它虽然经过压缩，但压缩的目标只是剔除噪音、重复、无价值、无意义的信息，而不是主动降低信息密度。

因此：

* 它不是低信息密度摘要
* 它不是“这一轮发生了什么”的轮次说明
* 它不是 `raw` 的缩写版
* 它不是 `conclusion` 的复述版

它真正承担的是：

**本节点当前最适合继续被人和 AI 直接使用的工作面。**

在继续写文档、写规则、写 AI 指令、继续展开节点内容时，优先使用的应当是 `summary`；需要看原始依据时回到 `raw`；需要看当前判断时看 `conclusion`。

更新时机上，`summary` 应在一轮完成后的统一回写阶段更新，而不是在单轮内部频繁改写。

#### 6.11.3 `conclusion`

`conclusion` 用于承接：

**本节点当前已经可以暂时成立的判断。**

它强调的是判断与结果，而不是资料承接面。

因此：

* `summary` 更偏承接与生产
* `conclusion` 更偏判断与结果

一个节点可以有非常丰富的 `summary`，但 `conclusion` 仍然较短；也可以在 `summary` 已相对稳定时，`conclusion` 继续变化。

#### 6.11.4 `next`

`next` 用于承接：

**下一轮最小推进入口。**

它不是宽泛建议，也不是长期路线图，而是“从当前节点继续往前推进时，最直接的下一个动作入口”。

它同时出现在 `StepRecord` 和 `Node` 中，但职责不同：

* `StepRecord.next`：记录这一轮结束时形成了什么下一步
* `Node.next`：作为节点当前态，供后续 `Scheduler` 和推进链路继续使用

#### 6.11.5 `status`

`status` 用于承接：

**这一轮完成后，节点在推进阶段上的正式落点。**

在 1.0 当前边界下，最小落点原则为：

* 若该节点本轮结束后已完全结束，则进入 `已完成`
* 若该节点本轮已形成阶段性稳定结果，但仍保留后续重开可能，则进入 `已冻结`
* 若该节点本轮结束后仍需继续推进，则保持为可继续推进状态，由后续规则决定如何继续进入下一轮

这里冻结的是落点原则，不在本章展开更细的场景化判定。

### 6.12 `summary / conclusion / next / status` 只在沉淀阶段统一回写

这四类字段不应在单轮内部频繁改写。

因此，本章冻结：

* 单轮内部不提前写稳定版 `summary`
* 单轮内部不提前写正式 `conclusion`
* 单轮内部不提前写正式 `next`
* 单轮内部不提前给出最终 `status` 落点

它们都应在一轮完成后，作为一次统一落账动作被回写到 `Node` 中。

### 6.13 沉淀阶段是“统一落账”，不是“局部补丁”

沉淀阶段的本质不是零散修改几个字段，而是：

**把这一轮已经形成的结果，统一折叠进 Node 当前态。**

因此，沉淀阶段应整体看待这几个字段之间的关系：

* `summary`：当前节点如何被继续承接和继续生产
* `conclusion`：当前节点已经成立什么判断
* `next`：当前节点从哪里继续推进
* `status`：当前节点处于什么推进阶段

这四者应在同一轮沉淀中保持一致，而不是各自零散漂移。

### 6.14 `status` 的正式落点发生在沉淀阶段

节点推进状态的正式落点，只能发生在一轮完成后的统一回写阶段，而不能在过程中提前拍板。

因此：

* 不能在 mode 中途把节点直接改成 `已冻结`
* 不能在等待人工时把节点直接改成 `已完成`
* 不能在单轮尚未收束时提前写死最终状态

只有当本轮已经真正结束，并进入统一落账阶段时，`status` 才能正式落点。

### 6.15 沉淀主干不能跳过

只要一个 Node 真正完成了一轮推进，就不应跳过沉淀主干直接返回 `Scheduler`。

也就是说，不应出现这种情况：

* 本轮结束了
* 但没有生成 `StepRecord`
* 也没有统一回写 `Node`
* 直接回到调度

这样会导致两个问题：

1. 这一轮没有正式留痕
2. `Node` 当前态和真实推进历史脱节

因此，一轮真正完成后，沉淀主干必须走完。

### 6.16 沉淀完成后的直接后果

当这一轮已经：

1. 生成了 `StepRecord`
2. 完成了 `Node` 统一回写

系统才算完成了这轮的正式落账。

此时的直接后果是：

* 该轮推进已经被记录
* 该 Node 当前态已经被更新
* 系统具备进入后续条件阶段或回到 `Scheduler` 的资格

也就是说，沉淀完成并不等于全局任务结束，它只表示：

**这个 Node 的这一轮已经被正式记账。**

### 6.17 本章结论

第 6 章最终冻结如下：

* 沉淀只能发生在一轮完成之后
* 沉淀顺序固定为：先 `StepRecord`，后 `Node` 回写
* `StepRecord` 是轮次级留痕，不是过程流水
* `StepRecord` 记录的是本轮输入、输出、变化和下一步入口
* `StepRecord` 与 `Node` 字段不是一一等值关系，而是“本轮结果 → 节点当前态”的折叠关系
* `raw` 是原始材料层，保真优先，不是沉淀主承接面
* `summary` 是本节点当前高信息密度、较高信息完整性的承接内容，适合继续复用、整理资料和继续生产
* `conclusion` 是本节点当前已经可以暂时成立的判断
* `next` 是下一轮最小推进入口
* `status` 是一轮结束后的正式推进落点
* `summary / conclusion / next / status` 都应在沉淀阶段统一回写，而不是在单轮内部频繁改写
* 一轮真正完成后，不应跳过沉淀主干直接返回 `Scheduler`

## 7. 条件触发规则

### 7.1 本章讨论范围

本章讨论的起点是：

**某个 Node 已完成一轮推进，并已经完成本轮沉淀。**

本章讨论的终点是：

**条件动作处理完毕，系统具备回到 Scheduler、进入下一轮选择的资格。**

因此，本章只处理以下问题：

* 什么时候创建子节点
* 哪些情况必须新建子节点，而不能直接修改原 Node
* 什么时候触发 Rescan
* Rescan 触发后系统如何把受影响节点重新送回推进范围
* 已冻结节点在什么条件下允许重开

这些都属于主干闭环之后的条件动作，而不是主干必经链。

### 7.2 条件动作不是每轮必有，但出现后必须显式处理

Ascend 1.0 的最短主链已经明确为：原始输入 → 创建首个 Node → 初始化 → Scheduler → 单轮推进 → StepRecord → 回写 Node → 必要时创建子节点 / 触发 Rescan → 回到 Scheduler。这里“必要时”本身就说明：子节点与 Rescan 都是条件动作，不是每轮必须执行；但一旦触发，就必须作为显式阶段处理，而不能隐式混进主干过程。

因此，本章先冻结一条总规则：

**条件动作可以不出现，但不能偷偷发生。**

也就是说：

* 没触发时可以完全不执行
* 一旦触发，就必须有明确的动作边界和后续影响
* 条件动作处理完后，再回到 Scheduler

### 7.3 条件动作的基本分类

在 1.0 当前边界下，条件动作先收成三类：

1. 创建子节点
2. 触发 Rescan
3. 重开冻结节点

其中前两类在现有阶段清单和主链说明里已经明确出现；第三类虽然没有单独列成一个阶段，但现有口径已经反复出现“冻结结果被重新打开”“已冻结默认不进入候选，除非被重新打开”这一类表述，因此应在本章中单独冻结为显式规则，而不是继续放在暗处。

### 7.4 创建子节点的触发条件

创建子节点的目的，是把**本轮新产生的可推进对象**正式挂入系统，而不是把所有新想法都硬塞回原 Node。现有材料已经把几类典型触发条件写得比较清楚：

* 当前节点完成后，拆出新的子问题
* 需要切换场景
* 产生新的独立推进对象

这些都说明：当本轮结果不再只是“更新原 Node 当前态”，而是形成了新的推进对象时，应创建子节点。

因此，本章冻结：

**只有当本轮结果形成新的独立推进对象时，才创建子节点。**

反过来说：

* 只是补充原 Node 内容，不创建子节点
* 只是修正原 Node 结论，不创建子节点
* 只是为原 Node 明确了 `next`，不创建子节点
* 只有出现“可独立继续推进的新对象”时，才创建子节点

### 7.5 哪些情况必须新建子节点，而不能改原 Node

这一条必须写成硬规则。现有材料已经明确：

**一个 Node 不切换 scenario；如果需要切换场景，拆成新的子节点。**

因此，本章冻结以下必须建子节点的情形：

第一， **需要切换 scenario** 。
原 Node 继续保留其原场景下的历史、沉淀和状态；新场景由新子节点承接。

第二， **本轮结果已经拆出新的独立子问题** 。
这类对象不再只是原 Node 的局部补充，而是新的推进单元。

第三， **本轮产生了新的独立推进对象** 。
无论这个对象来自拆解、转向还是上位结论延伸，只要它具备“可以作为单独 Node 被继续推进”的条件，就不应继续混在原 Node 里。

由此再压一句总规则：

**凡是会改变对象身份的变化，不在原 Node 内硬改，而是拆成新子节点。**

### 7.6 创建子节点后的最小动作

创建子节点不是一句“生一个节点”就结束了。现有链路已经给出最小动作：

* 创建新 Node
* 写入 NodeTree
* 后续再走初始化流程

也就是说，新子节点一旦出现，就不是悬空对象，而应立刻被挂入系统关系中，并按正常规则进入初始化链，而不是绕过初始化直接进调度。

因此，本章冻结：

**子节点创建完成，至少意味着三件事同时成立：**

1. 新对象已经作为 Node 被创建
2. 它与原节点的关系已经写入 NodeTree
3. 它还需要像普通新节点一样再走初始化流程

这里也顺手钉死一个边界：

**子节点创建，不等于子节点立即开始推进。**
它只是获得了“进入系统”的资格，是否进入当前轮次仍由初始化和 Scheduler 决定。这个顺序与首次输入链一致，不能跳。

### 7.7 Rescan 的触发条件

Rescan 的作用不是“做第二轮内容处理”，而是当本轮带来关键变化时，把受影响的旧节点重新送回推进流。现有材料已经给出了最典型的三类触发条件：

* 核心结论被修正
* 冻结结果被重新打开
* 上位前提变化影响下游节点

另一份链路材料也给了几乎同义的表达：`conclusion` 被根本性修正、原有冻结结论被推翻、后续节点前提发生变化。两份材料口径是一致的。

因此，本章冻结：

**只有当本轮结果对其他既有节点的前提条件产生影响时，才触发 Rescan。**

反过来说：

* 只是原 Node 内部的小修，不触发 Rescan
* 只是新增了一个互不影响的子节点，不必触发 Rescan
* 只有出现“旧节点可能因此失效、偏移或需要重看”的情况，才触发 Rescan

### 7.8 Rescan 的职责边界

Rescan 的边界在现有材料里已经非常清楚：

* 找出受影响节点
* 将其重新纳入推进范围
* 不直接修内容
* 最后交回 Scheduler

并且方案文档也明确：Scheduler / Rescan 负责推进秩序，不负责内容本体。

因此，本章正式冻结：

**Rescan 只做重新纳管，不做内容修复。**

也就是说，Rescan 不负责：

* 直接改写受影响节点的 `summary`
* 直接改写受影响节点的 `conclusion`
* 直接替这些节点生成新 StepRecord
* 直接替这些节点进入具体 mode 流程

它只负责把“本来已离开当前推进流、但现在应重新处理”的节点送回运行范围。后续真正修内容，仍通过正常推进完成。

### 7.9 Rescan 触发后的最小状态效果

现有材料已经明确两件事：

* Scheduler 负责接收被重新纳管的节点
* 已冻结节点默认不进入候选池，除非被重新打开

虽然现有文本没有把所有状态动作逐条写死，但基于这两条已冻结口径，本章可以把 1.0 的最小效果正式压成如下规则：

第一，**被 Rescan 识别为受影响的节点，应重新具备进入候选流程的资格。**

第二，**如果该节点原本是“停用”，则需要被重新纳入推进范围；如果原本是“已冻结”，则需要被视为已被重新打开。**

第三，**Rescan 不直接决定它下一步做什么，只负责让它重新回到“可被 Scheduler 处理”的状态。**

这里用更操作化的话说，就是：

* Rescan 解决“把谁送回来”
* Scheduler 解决“现在先轮到谁”
* 单轮推进解决“回来之后具体怎么修”

这三层不能混。

### 7.10 已冻结节点的重开条件

结合现有材料，已冻结节点的重开至少有三类明确来源：

第一，**冻结结果被重新打开。**
这是 Rescan 触发条件里已经直接出现的表述。

第二，**上位关键变化使其原前提失效。**
例如核心结论被修正、上位前提变化影响下游节点。这类情况虽然可能不是直接点名“这个冻结节点重开”，但实质上会导致相关冻结节点必须重新纳管。

第三，**人工显式要求重开。**
现有 Scheduler 口径已经把“涉及冻结、切换方向、重新激活停用节点”列为必须人工介入的典型场景。这说明冻结状态的打开，在 1.0 中本来就不应被视为完全自动的日常动作；人工显式操作应被视为合法重开来源。

因此，本章冻结：

**已冻结节点默认不进入候选池；只有在被重新打开、被 Rescan 重新纳管，或被人工显式重开时，才重新进入推进范围。**

### 7.11 “创建子节点”和“触发 Rescan”不是同一件事

这两个动作很容易混，但在 1.0 里必须严格区分。

创建子节点，解决的是：

**本轮新产生了什么新的推进对象。**

Rescan，解决的是：

**哪些旧节点因为本轮变化而需要重新处理。**

一个是“生新对象”，一个是“把旧对象送回来”。它们可以在同一轮后同时出现，但不能互相替代。

因此：

* 不能用创建子节点代替对旧节点的回扫
* 不能用 Rescan 代替新对象入树
* 两者同时触发时，分别处理，各自留边界

### 7.12 条件动作完成后的回流规则

现有链路已经明确：当这一轮的 StepRecord 已生成、Node 已回写、NodeTree 已更新（如有）、Rescan 已触发（如有）之后，系统回到 Scheduler，开始下一轮选择。

因此，本章冻结：

**条件动作的终点不是“自己把事情做完”，而是把系统送回 Scheduler。**

也就是说：

* 子节点创建后，子节点后续仍通过初始化与 Scheduler 进入系统
* Rescan 完成后，受影响节点后续仍通过 Scheduler 进入候选
* 冻结节点被重开后，也仍然由 Scheduler 决定何时被推进

条件动作负责“改变可推进对象集合”，不负责替代后续推进本体。

### 7.13 本章结论

第 7 章到这里正式冻结如下：

* 条件动作不是每轮必有，但一旦触发必须显式处理
* 1.0 当前的条件动作先收为三类：创建子节点、触发 Rescan、重开冻结节点
* 只有当本轮结果形成新的独立推进对象时，才创建子节点
* 需要切换 `scenario` 时，必须创建新子节点，不能直接改原 Node
* 子节点创建后，至少要完成：创建 Node、写入 NodeTree、后续进入初始化流程
* 只有当本轮变化影响到既有节点前提时，才触发 Rescan
* Rescan 只负责找出受影响节点并重新纳入推进范围，不直接修内容
* 已冻结节点默认不进入候选池；只有在被重新打开、被 Rescan 重新纳管或被人工显式重开时，才重新进入推进范围
* 创建子节点解决“新对象入场”，Rescan 解决“旧对象回流”，两者不能混
* 条件动作完成后，系统回到 Scheduler，再进入下一轮推进

#### A.2.4 候选资格门槛表

| 条件                                          | 结果             |

### A.3 Scheduler 运行规则总表

#### A.3.1 Scheduler 职责表

| 职责         | 说明                               |
| ------------ | ---------------------------------- |
| 候选过滤     | 先排除不该碰的节点                 |
| 当前节点选择 | 选出当前要推进的 Node              |
| 模式选择     | 在已知 `scenario`下确定本轮 mode |
| 人工介入判断 | 判断什么时候不该自动选             |
| 重新纳管入口 | 接收被 Rescan 或人工送回的节点     |

Scheduler 不负责承载内容、组织关系、记录推进、定义模式语义、定义场景语义，也不负责真正执行内容生成。

#### A.3.2 当前 Node 选择顺序表

| 顺位 | 依据                | 规则                                                                     |
| ---- | ------------------- | ------------------------------------------------------------------------ |
| 1    | 是否可进入候选      | 先看 `activeStatus=启用`、`status!=已完成`、必要时排除 `已冻结`    |
| 2    | 节点推进状态        | `进行中`优先于 `未开始`；被重新纳管的 `已冻结`其后；`已完成`不选 |
| 3    | `next`是否明确    | `next`明确者优先                                                       |
| 4    | `scenario`贴近度  | 与当前任务主线更同路的优先                                               |
| 5    | NodeTree 位置       | 离当前焦点更近者优先；同级按 `order`                                   |
| 6    | 人工指定 / 外部触发 | 人工显式关注高于普通自动排序                                             |

核心原则是：**先收口，再开新口。**

#### A.3.3 mode 选择表

| 当前运行态              | 处理规则                         |
| ----------------------- | -------------------------------- |
| `currentMode = null`  | 根据 `scenario`找到入口 mode   |

#### A.3.4 人工介入判断表

| 触发情况                               | 是否应人工介入 |
| -------------------------------------- | -------------: |
| 候选节点并列，规则无法明显区分         |             是 |

#### A.5.1 沉淀顺序表

#### A.5.2 StepRecord 最小字段表

| ---------- | ---------------------------- |

| `next`       | 下一轮最小推进入口                             | 供后续 Scheduler 与推进链路使用                    |
| `status`     | 一轮结束后的正式推进落点                       | 在沉淀阶段统一确定                                 |

#### A.5.4 StepRecord 与 Node 字段关系表

| 对照项                                                | 关系                                                     |
| ----------------------------------------------------- | -------------------------------------------------------- |
| `StepRecord.input`vs `Node.raw`                   | 前者是轮次级实际输入，后者是节点级原始材料               |
| `StepRecord.output`vs `Node.summary / conclusion` | 前者是本轮产出，后者是折叠后的节点当前态                 |
| `StepRecord.change`vs `Node.status / conclusion`  | 前者写“这轮改了什么”，后两者写“当前成立什么、落在哪” |
| `StepRecord.next`vs `Node.next`                   | 前者是历史留痕，后者是当前有效入口                       |

### A.6 条件触发规则总表

#### A.6.1 条件动作分类表

| 类别         | 解决的问题                           |
| ------------ | ------------------------------------ |
| 创建子节点   | 本轮新产生了什么新的推进对象         |
| Rescan       | 哪些旧节点因为本轮变化而需要重新处理 |
| 重开冻结节点 | 哪些冻结对象重新具备推进资格         |

条件动作不是每轮必有，但一旦触发必须显式处理。

#### A.6.2 子节点创建触发表

| 触发情况                    | 是否创建子节点 |
| --------------------------- | -------------: |
| 当前节点拆出新的子问题      |             是 |
| 需要切换场景                |             是 |
| 产生新的独立推进对象        |             是 |
| 只是补充原 Node 内容        |             否 |
| 只是修正原 Node 结论        |             否 |
| 只是为原 Node 明确 `next` |             否 |

一个 Node 不切换 scenario；若需切换场景，拆成新的子节点。

#### A.6.3 子节点创建后动作表

| 动作                       | 是否必须 |
| -------------------------- | -------: |
| 创建新 Node                |       是 |
| 写入 NodeTree              |       是 |
| 后续再走初始化流程         |       是 |
| 立即绕过初始化直接进入调度 |       否 |

子节点创建不等于子节点立即开始推进。

#### A.6.4 Rescan 触发表

| 触发情况                 | 是否触发 Rescan |
| ------------------------ | --------------: |
| 核心结论被修正           |              是 |
| 冻结结果被重新打开       |              是 |
| 上位前提变化影响下游节点 |              是 |
| 原 Node 内部小修         |              否 |
| 新增互不影响的子节点     |              否 |

只有当本轮变化影响到既有节点前提时，才触发 Rescan。

#### A.6.5 Rescan 职责边界表

| Rescan 负责               | Rescan 不负责                     |
| ------------------------- | --------------------------------- |
| 找出受影响节点            | 直接修内容                        |
| 将其重新纳入推进范围      | 直接改写 `summary / conclusion` |
| 把节点送回 Scheduler 流程 | 直接生成新 StepRecord             |
| —                        | 直接替节点进入具体 mode 流程      |

Rescan 只负责重新纳管，不直接修内容。

#### A.6.6 冻结节点重开表

| 情况                       |         是否允许重开 |
| -------------------------- | -------------------: |
| 冻结结果被重新打开         |                   是 |
| 上位关键变化使其原前提失效 |                   是 |
| 人工显式要求重开           |                   是 |
| 无触发条件的普通冻结节点   | 否，默认不进入候选池 |

已冻结节点默认不进入候选池；只有在被重新打开、被 Rescan 重新纳管或被人工显式重开时，才重新进入推进范围。

### A.7 回流规则总表

| 条件动作完成后             | 后续处理                                       |
| -------------------------- | ---------------------------------------------- |
| 子节点已创建               | 子节点进入初始化链，初始化完成后才具备调度资格 |
| Rescan 已完成              | 受影响节点重新进入候选过滤范围                 |
| 冻结节点已重开             | 重新具备被 Scheduler 处理的资格                |
| 主干与条件动作全部处理完毕 | 回到 Scheduler，开始下一轮选择                 |

条件动作的终点不是“自己把事情做完”，而是把系统送回 Scheduler。

### A.8 一页压缩版

| 主题     | 一句话规则                                                                          |
| -------- | ----------------------------------------------------------------------------------- |
| 统一前提 | Ascend 1.0 以推进契约为骨架，不以某种任务内容流程为骨架                             |
| 首次入场 | 原始输入必须先对象化并初始化，Node 才真正进入系统                                   |
| 状态边界 | `status`管推进阶段，`activeStatus`管是否纳入推进范围，`NodeRuntime`管运行断面 |
| 调度边界 | Scheduler 负责选谁、怎么推进、什么时候别自动选                                      |
| 单轮边界 | 一轮是 Node 级、Scenario 级完成；中间 mode 流转和人工介入都不构成新一轮             |
| 沉淀边界 | 一轮完成后，先 StepRecord，再统一回写 Node                                          |
| 结构变化 | 新对象用子节点承接，不在原 Node 内硬改对象身份                                      |
| 变化回流 | 旧对象受影响时用 Rescan 重新纳管，不直接修内容                                      |
| 系统回流 | 主干和条件动作处理完后，一律回到 Scheduler                                          |

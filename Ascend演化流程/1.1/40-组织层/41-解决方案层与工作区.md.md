## 0. 文档目标与边界

### 0.1 文档目标

本文档用于定义  **Ascend 在单个 Project 运行内核之上的最小解决方案容器与最小使用视图** 。

更具体地说，这份文档只回答两个问题：

1. **什么是解决方案层（Solution）**
2. **人如何通过工作区（Workspace）进入、看到并使用其中的多个 Project**

它的作用不是重新定义 Node 内部如何推进，也不是直接展开多 Project 协同细节，而是先把“多个 Project 被什么组织起来”“人在这个组织层里如何工作”这两个上层问题正式收住。

### 0.2 本文档要解决的问题

本文档只解决以下问题：

1. 为什么单个 Project 不足以承接真实问题的完整解决过程
2. 为什么需要一个比 Project 更高一层的组织容器
3. Solution 最小承担什么职责
4. Workspace 最小承担什么职责
5. Project 在 Solution 中是什么地位
6. 当前工作区如何承接“多个 Project 存在，但一次只推进一个 Project”这一使用原则
7. Solution 与 Project、Node、Round、运行规则之间的边界是什么

也就是说，这份文档关心的是：

**多个 Project 如何被组织，以及人如何在这个组织层中工作。**

### 0.3 本文档不解决的问题

本文档不负责以下内容：

1. 不重新定义单个 Project 内部的运行规则
2. 不展开 Node、StepRecord、Scheduler、Rescan 的内部实现
3. 不详细展开 Round 的生命周期与字段设计
4. 不详细展开多 Project 协同的完整流程
5. 不详细展开 Project 内部结构类型的完整分类
6. 不详细展开派生产物 Project 的完整分类
7. 不讨论 UI 设计、页面布局、交互细节

这些内容分别属于其他文档：

* 单个 Project 内核运行规则 → `运行规则.md`
* 协作主链 → `协作链路.md`
* 轮次 → `43-轮次.md`
* Project 内部结构与生命周期 → `44-Project的生命周期.md` 或后续相关文档
* 多 Project 协同与派生产物 → `45-多Project协同与派生产物.md`

### 0.4 本文档与其他文档的边界

#### 0.4.1 与《方案总览》的边界

《方案总览》回答的是 Ascend 整体是什么、为什么要这样设计。
本文档不再重讲整体方案，只在此基础上，专门收束“解决方案层”与“工作区”这两个上层组织问题。

#### 0.4.2 与《运行规则》的边界

《运行规则》回答的是：当一个 Project 当前采用 Tree 作为内部结构时，一个 Node 如何进入系统、如何被调度、如何完成一轮推进、如何沉淀。
本文档不讨论 Project 内部推进规则，而只讨论：

**多个 Project 作为整体如何被组织，以及人如何进入这个整体。**

#### 0.4.3 与《轮次》的边界

《轮次》回答的是：一次跨 Project 变化如何被组织、记录和承接。
本文档只先回答：

**这些轮次发生在什么容器里。**

也就是说：

* 本文档定义“空间”
* `43-轮次.md` 定义“变化单位”

#### 0.4.4 与《Project 内部结构 / 生命周期》相关文档的边界

相关文档回答的是：Project 当前采用什么内部结构、如何创建、活跃、冻结、归档、结束。
本文档只先承认 Project 在 Solution 中存在，不展开 Project 作为对象如何演化，也不展开其内部结构类型的完整讨论。

#### 0.4.5 与《多Project协同与派生产物》的边界

相关文档回答的是：多个 Project 如何顺序协同、什么时候产生派生产物 Project。
本文档不展开协同细节，只先定义：

**这些协同关系发生在同一个 Solution / Workspace 中。**

### 0.5 当前文档的最小任务

在 1.0 当前阶段，这份文档的最小任务只有四个：

1. 定义 Solution 是什么
2. 定义 Workspace 是什么
3. 定义 Project 在 Solution 中的最小地位
4. 定义工作区的最小使用原则

只要这四件事写清，后面的 `轮次`、`Project生命周期`、`多Project协同` 三份文档就有了稳定的上游输入。

### 0.6 当前文档的写作原则

本文档遵守以下原则：

1. **先定义容器，再定义协同**
   不先把 Solution / Workspace 讲清，后面的多 Project 协同一定会飘。
2. **先定义最小职责，不定义完整产品形态**
   当前目标不是做完整产品蓝图，而是为后续实现提供足够稳定的组织层定义。
3. **先保住 Project 作为当前一级单位，不急于定义更多内部结构类型**
   当前阶段先使用 `Project` 作为 Solution 内部一级组织单位；Project 的内部结构暂不被 Tree 一词绑死，只冻结“当前默认可采用 Tree 结构”。
4. **只解决“如何组织”和“如何使用”，不回到 Project 内核细节**
   本文档不重复运行规则，不重新讨论 Node 内部推进。

### 0.7 当前冻结的关键名词口径

本章同时冻结以下名词口径：

* **Solution** ：组织多个 Project 的最上层容器
* **Workspace** ：人进入并使用 Solution 的当前工作视图
* **Project** ：Solution 内部一级独立工作对象
* **Tree** ：Project 当前默认的内部组织结构之一
* **Node** ：最小推进对象

这意味着：

* 后续不再把 Tree 当作 Solution 内部一级单位来使用
* Tree 退回为 Project 的一种内部结构形态
* 当前 1.0 已有的大量单树运行规则，可被解释为：
  **Project 采用 Tree 结构时的运行规则**

### 0.8 本章结论

第 0 章到这里正式冻结以下内容：

1. 本文档是 **Ascend 解决方案层与工作区定义文档**
2. 它只解决“多个 Project 如何被组织起来”以及“人如何在其中工作”
3. 它不负责 Project 内部运行规则，不负责轮次细节，不负责多 Project 协同细节
4. 它是 `43-轮次.md`、相关生命周期文档、`45-多Project协同与派生产物.md` 的上游输入
5. 当前阶段，Solution 内部一级单位统一称为 **Project**
6. `Tree` 不再作为一级单位名词，而作为 Project 当前默认的内部组织结构之一

## 1. 为什么需要解决方案层

### 1.1 单个 Project 只能稳定承接局部工作，不能自然承接完整解决过程

Ascend 当前已经把“一个 Project 内部如何稳定推进”压得比较清楚了。
更准确地说，当前已经细化的，是：

**当一个 Project 当前采用 Tree 作为内部结构时，Node 如何进入系统、如何被调度、如何完成一轮推进、如何沉淀。**

这说明 Project 内部的推进基座是成立的。
也就是说，局部工作对象的承接能力并不是现在的主要问题。

真正的问题在于：

**真实解决问题时，往往不只有一个局部工作对象。**

所以，单个 Project 适合承接一类独立工作的持续推进，却不天然适合承接“一个真实问题的全部解决过程”。

### 1.2 真实问题天然会同时涉及多个工作对象

当问题进入真实解决阶段时，实际发生的通常不只是“继续推进一个核心对象”。
往往会同时出现：

* 对问题本身的分析与拆解
* 对本次变化集合的组织
* 文档产出或文档修改
* 规则产出或规则修改
* AI 指令产出或指令调整
* 执行结果与轮次痕迹沉淀

这些东西不是同一层级的对象，也不是同一种工作形态。

如果全部硬塞进同一个 Project，表面上看像是“统一管理”，但实际会逐步变成：

* 主问题对象和派生产物混在一起
* 长期承接对象和本轮变化混在一起
* 工作对象和交付结果混在一起
* 分析、组织、产出三类动作混在一起

一旦混到这一步，Project 内部再好的运行规则也会逐渐失真。

### 1.3 “一个 Project 解决所有问题”在复杂场景下会失真

单 Project 模型最大的问题，不是完全不能工作，而是 **复杂度上来之后会失真** 。

一开始，你可能只是围绕一个问题在持续推进。
但当真实变化出现时，一次需求收敛、一次小版本演进、一次问题修复，往往会：

* 影响多个局部对象
* 新增很多节点
* 修改很多节点
* 派生很多结果
* 引出多个后续工作面

这时候如果仍然坚持“一切都放进一个 Project”，最终结果通常不是更统一，而是：

* Project 越来越重
* 内部对象层级越来越混
* 当前焦点越来越不清
* 后续产物越来越难承接

所以问题不是 Project 不能用，而是：

**单个 Project 不足以成为完整解决方案的唯一组织单位。**

### 1.4 解决方案层的作用，不是替代 Project，而是组织多个 Project

一旦承认“单个 Project 不够”，就必须进一步承认：

**Project 负责承接独立工作对象，Solution 负责组织这些工作对象。**

也就是说：

* Project 负责局部工作的持续推进
* Solution 负责组织多个 Project 及其关系
* Workspace 负责让人能够进入这个组织层并使用它

这三者不是替代关系，而是分层关系。

所以引入 Solution，不是在否定 Project，恰恰相反：

**是为了保护 Project，让 Project 不必承担本不属于它的全局组织职责。**

### 1.5 引入 Solution 不是为了让系统更乱，而是为了让多 Project 存在变得可控

这里有一个很重要的澄清。

引入解决方案层，不代表系统要在同一轮里交错推进多个 Project。
相反，正因为多个 Project 会同时存在，才更需要一个上层容器来明确：

* 当前 Solution 里有哪些 Project
* 哪个 Project 是当前焦点
* 一次只推进哪个 Project
* 其他 Project 如何作为“存在但暂不推进”的对象被保留

也就是说：

**Solution 的价值，不是让系统更复杂，而是让“多个 Project 并存”获得明确秩序。**

如果没有 Solution，这些 Project 不会因为你不命名它们就消失；
它们只会以更隐蔽、更临时、更难维护的方式存在。

### 1.6 真实解决过程除了主工作对象，还会产生派生工作对象

引入解决方案层的另一个原因，是主工作 Project 的结果往往不会停留在主工作 Project 内部。

一个围绕问题本身推进的 Project，在推进过程中，可能进一步派生出：

* 文档 Project
* 规则 Project
* AI 指令 Project
* 其他围绕当前问题继续工作的产物 Project

这些对象不是主 Project 的几个字段，也不是简单附属说明。
一旦它们形成了独立工作面，就应当作为独立 Project 被承接，而不是继续混在原 Project 内部。

这意味着：

**真实解决过程不只是“推进一个对象”，而是“围绕一个问题不断产生并组织多个工作对象”。**

而这正是 Solution 层存在的必要性。

### 1.7 解决方案层的引入，不违背统一推进契约

这里还要再压一条非常关键的判断。

引入 Solution 层，并不违背统一推进契约。
因为推进契约统一的从来不是“Node 长什么样”或“Project 长什么样”，而是：

**任何一次有效推进都必须满足什么共同结构。**

所以：

* Node 层可以服从推进契约
* Project 层也可以服从推进契约
* Round 层也可以服从推进契约
* Solution 层在一定条件下也可以被视为组织性推进对象

也就是说：

**统一推进契约不是被 Solution 打破了，而是被提升成了跨层级的最小通用接口。**

这反而是一个好迹象，说明你前面建立的推进基座没有被推翻，而是有了更高层的承接可能。

### 1.8 Solution 的引入，不是为了做大系统，而是为了防止上层混乱

这一点必须明确。

现在引入 Solution，不是为了立刻把 Ascend 扩成一个巨大系统，
也不是为了马上定义完整产品形态、复杂多 Project 编排或完整工作区界面。

当前引入它的目的只有一个：

**让已经出现的“多个独立工作对象并存”这一事实，获得正式、清晰、可继续实现的上层组织定义。**

换句话说，如果现在不引入 Solution，后面的问题不会消失；
它们只会继续以“临时文件夹约定”“口头默认主线”“记忆中的关系”这种方式存在。

正式引入 Solution，反而是为了让系统更克制、更清晰。

### 1.9 Solution 的出现，意味着 Ascend 正在从“围绕单一对象推进”走向“围绕真实问题组织解决过程”

如果说前面的 Project 内核解决的是：

**一个局部工作对象如何被稳定推进**

那么 Solution 层要解决的就是：

**围绕一个真实问题，如何把多个必要工作对象组织起来，使问题能够被持续推进并最终解决。**

这里的重点不是“对象被组织”本身，
而是：

**问题如何被解决。**

多个 Project、Round、协同关系、派生产物，都不是目的，
它们只是为了让一个真实问题在复杂情况下仍然能够：

* 被持续承接
* 被分层推进
* 被产出支撑物
* 被回扫和修正
* 最终走向解决

所以，Ascend 上层形态的变化，不应简单表述为：

“从推进某一个对象，走向组织多个对象共同解决问题”

而应表述为：

**从“围绕单一工作对象推进”，走向“围绕真实问题组织多个工作对象，使问题能够被系统性解决”。**

这意味着，后面讨论的重点虽然会从 Node / Tree 内部规则，逐步扩展到 Project、Round、多 Project 协同和派生产物，
但这些讨论始终都应受一个总目标约束：

**不是把对象组织得更漂亮，而是让问题更稳定地被解决。**

### 1.10 本章结论

第 1 章到这里正式冻结以下内容：

1. 单个 Project 可以稳定承接局部工作，但不足以承接完整解决过程
2. 真实问题天然会同时涉及多个工作对象与多个工作层级
3. 当复杂度上升时，“一个 Project 解决所有问题”会逐渐失真
4. Project 应被理解为独立工作对象，而不是完整解决方案的唯一组织单位
5. Solution 层的职责，不是为了组织对象而组织对象，而是为了让真实问题在多对象条件下仍然能够被持续推进并最终解决
6. Workspace 的职责，是让人能够进入、看到、选择并使用这些 Project
7. 引入 Solution 不会违背统一推进契约，反而使推进契约成为跨层级的最小通用接口
8. 当前引入 Solution 的目的，不是做大系统，而是防止多个工作对象继续无结构蔓延，并让问题解决过程获得正式的上层组织定义
9. Ascend 的上层形态，正在从“围绕单一对象推进”，走向“围绕真实问题组织解决过程”

# 第 2 章 Solution 的最小定义

## 2.1 Solution 不是新的推进单元，而是围绕最终目标存在的上层组织容器

在当前阶段，Solution 首先应被理解为：

**围绕同一个问题而存在的最上层组织容器。**

这里的“问题”，不是一次提问，不是一轮操作，也不是某一个节点或某一个 Project。
它指的是：

**我要达成的最终目标。**

这个目标往往跨越时间、阶段和多个独立工作面，因此无法自然地被单个 Project 完整承接。
Solution 的出现，就是为了给这个最终目标提供一个正式的上层承接层。

因此，Solution 不是更大的 Tree，也不是更复杂的 Project。
它是：

**多个独立工作对象围绕同一个最终目标被正式组织起来的地方。**

## 2.2 Solution 的核心职责不是管理对象，而是承接问题解决过程

这一点必须先钉死。

Solution 当然会组织多个 Project，
但它的核心职责不是为了“装下更多对象”，而是为了让一个真实问题的解决过程获得持续承接。

所以，Solution 真正承接的不是：

* 一堆文件
* 一堆树
* 一堆工作对象

而是：

**一个最终目标如何在多个阶段、多个工作对象、多个变化轮次中被持续推进并最终解决。**

也就是说，Solution 首先是 **问题解决的组织承接层** ，其次才是对象组织层。

## 2.3 Solution 解决的是“微软解决方案”那类上层组织问题

如果用更直观的话来讲，
Solution 可以理解为对“微软解决方案”那种上层组织抽象的借鉴。

它解决的是类似的问题：

* 多个独立工作对象为什么属于同一个目标
* 它们如何被归在一起
* 为什么它们不是散的，而是共同服务于同一个解决过程

所以，Solution 的价值不在于“它是一个更大的盒子”，
而在于：

**它为多个 Project 提供了共同目标与共同归属。**

## 2.4 Solution 内部的一级单位是 Project

在当前冻结口径下，Solution 内部的一级独立工作单位统一称为：

**Project**

这样处理的原因是：

* `Project` 是中性词，不预设内部一定是树形
* 它更适合承接不同类型的独立工作面
* 它可以兼容长期对象、临时对象、派生对象
* 它不会把上层组织层过早绑死在 Tree 这种内部结构上

因此，本章正式冻结：

**Solution 组织多个 Project，而不是组织多个 Tree。**

同时也要明确：

**Tree 不是 Solution 的一级单位，而是 Project 当前默认可采用的一种内部组织结构。**

## 2.5 Project 在 Solution 中的地位

Project 在 Solution 中，应被理解为：

**围绕当前最终目标而存在的一个独立工作面。**

它可能承接的是：

* 问题分析
* 文档编写或修改
* 规则生成或修改
* AI 指令生成或调整
* 其他围绕当前目标继续推进的独立工作

Project 的独立性，不在于它是不是完全脱离其他 Project，
而在于：

**它已经形成了一个可以被单独推进、单独承接、单独沉淀的工作面。**

所以，Project 不是普通文件夹项，也不是简单分类标签，
它是 Solution 内部真正可独立推进的一级对象。

## 2.6 Solution 的最小职责边界

在 1.0 当前阶段，Solution 的职责先收成下面这四条。

### 2.6.1 承接同一个最终目标

Solution 负责回答：

**这些 Project 为什么共同服务于同一个问题。**

没有这一层，多个 Project 只是并列存在；
有了这一层，它们才属于同一个问题的解决过程。

### 2.6.2 组织多个 Project 的并存

Solution 负责承认并维护：

* 当前有哪些 Project
* 这些 Project 都围绕同一个最终目标
* 它们不是偶然放在一起，而是同属一个解决过程

### 2.6.3 提供统一工作区的存在基础

Solution 不直接推进 Node，
但它必须提供 Workspace 得以存在的前提，也就是：

**人从哪里进入这个目标空间，并看到与这个目标有关的多个 Project。**

### 2.6.4 为 Round 和后续协同提供上层容器

Solution 当前不展开具体 Round 规则，
但它必须是 Round 能够成立的上层前提。

也就是说：

* 没有 Solution，就没有“跨多个 Project 的同一轮变化”这个说法
* 没有 Solution，多 Project 协同就只能靠临时默认

## 2.7 Solution 当前不承担的职责

为了防止把 Solution 写得过重，这一章还必须把它**不做什么**写清。

### 2.7.1 不替代 Project 内部推进

Project 内部如何推进，仍然由其内部结构和运行规则决定。
如果当前 Project 采用 Tree 结构，那就继续使用现有单树运行规则；
Solution 不替它做 Node 调度、StepRecord 生成或一轮沉淀。

### 2.7.2 不替代 Round

Solution 是问题空间，Round 是某一次跨 Project 变化的组织单位。
Solution 不是变化本身，而是变化发生的上层容器。

### 2.7.3 不直接做多 Project 编排细节

多个 Project 具体如何顺序协同，哪些先做、哪些后做，属于后续协同文档的问题。
本章只定义：它们处在同一个 Solution 中。

### 2.7.4 不等于 Workspace

Solution 和 Workspace 相关，但不是同一个概念。
Solution 是组织容器；Workspace 是人进入并使用这个容器时所处的当前工作上下文。

这一点必须分开，不然后面文档会把：

* 目标组织层
* 当前使用层

混成一个东西。

## 2.8 Solution 的最小成立条件

不是任何一组 Project 放在一起，都值得叫 Solution。
在当前阶段，我建议把 Solution 的最小成立条件冻结成下面三条：

### 2.8.1 围绕同一个最终目标

这些 Project 必须共同服务于同一个问题的解决，
而不是只是碰巧放在一起。

### 2.8.2 Project 之间具有目标相关性

它们不要求彼此完全依赖，
但必须在目标层面相关。
也就是说，它们之所以被组织在一起，不是因为分类方便，而是因为共同参与同一个目标的解决过程。

### 2.8.3 单个 Project 已不足以自然承接全部工作

如果全部内容都能自然落在同一个 Project 内，并且不会产生明显混层，那么此时未必必须升成 Solution。
只有当目标天然需要多个独立工作面时，Solution 才真正成立。

这一条很重要，因为它防止你把 Solution 变成“逢项目必套一层”的空壳。

## 2.9 Solution 的最小输出是什么

一个 Solution 最少应当向下提供三类东西：

### 2.9.1 目标级统一上下文

也就是：这些 Project 共同围绕的最终目标是什么。

### 2.9.2 当前 Project 集合

也就是：当前这个目标空间里，有哪些独立工作面存在。

### 2.9.3 当前工作入口

也就是：人和系统下一步从哪个 Project 或哪个工作区焦点进入。

注意，这里说的是“提供入口”，不是“自动完成推进”。
推进仍然发生在下层 Project 内部。

## 2.10 Solution 和 Project 的关系，不只是包含关系

表面上看，Solution 只是“包含多个 Project”。
但如果只把它写成包含关系，这层就会太弱。

更准确地说：

* Solution 为 Project 提供共同目标上下文
* Project 为 Solution 提供可独立推进的工作面
* Solution 让 Project 的并存获得上层意义
* Project 让 Solution 不停留在抽象目标层，而能真正进入解决过程

所以两者关系不只是“上层装下层”，而是：

**目标承接层 与 独立工作层 的配合关系。**

## 2.11 当前 1.0 对 Solution 的最小冻结版本

如果把这一章再压到最小，可以冻结成下面这段话：

> Solution 是围绕同一个最终目标而存在的最上层组织容器。
> 它的职责不是直接推进 Node，也不是替代 Project 内部运行，而是把多个围绕同一目标的独立工作对象（Project）组织在同一个目标空间中，并为 Workspace、Round 和后续多 Project 协同提供上层容器。
> 在当前阶段，Solution 内部一级单位统一称为 Project；Tree 退回为 Project 当前默认可采用的一种内部组织结构。

## 2.12 本章结论

第 2 章到这里正式冻结以下内容：

1. Solution 是围绕最终目标而存在的最上层组织容器
2. Solution 的核心职责，不是为了组织对象而组织对象，而是为了让同一目标在多工作对象条件下仍然被持续推进并最终解决
3. Solution 解决的是类似“微软解决方案”那种上层组织问题
4. Solution 内部一级单位统一称为 Project
5. Tree 不再作为 Solution 的一级单位，而是 Project 当前默认可采用的一种内部组织结构
6. Project 在 Solution 中的地位，是独立工作面，而不是普通文件夹项
7. Solution 的最小职责包括：承接同一目标、组织多个 Project 并存、提供统一工作区基础、为 Round 与后续协同提供上层容器
8. Solution 当前不负责 Project 内部推进、不替代 Round、不展开多 Project 编排细节，也不等于 Workspace 本身
9. 只有当多个独立工作面共同服务于同一个最终目标，并且单个 Project 已不足以自然消化时，Solution 才真正成立
10. Solution 与 Project 的关系，不只是包含关系，而是“目标承接层”和“独立工作层”的配合关系

# 第 3 章 工作区的最小定义

## 3.1 工作区不是另一个组织层对象，而是进入 Solution 的当前工作上下文

在当前阶段，Workspace 不应被理解为和 Solution、Project 平级的新对象。
它更合适的理解是：

**人进入某个 Solution 后，面向当前最终目标所处的工作上下文。**

也就是说：

* Solution 是组织容器
* Project 是一级独立工作对象
* Workspace 是人进入这个目标空间之后，当前干活所处的上下文承接面

因此，Workspace 首先是“使用层定义”，不是“新的组织层单位”。

## 3.2 工作区存在的原因，不是为了展示，而是为了稳定当前工作状态

如果只有 Solution 和多个 Project，而没有 Workspace 这个概念，
那么系统虽然在组织层上已经承认“这些 Project 属于同一个目标空间”，
但人在实际使用时仍然会遇到一个核心问题：

**我现在到底在哪个上下文里干活。**

所以 Workspace 的首要价值，不是页面展示，而是：

**为当前工作状态提供稳定承接。**

也就是说，Workspace 的本质不是“可视化面板”，而是：

* 当前在解决哪个目标
* 当前聚焦哪个 Project
* 当前从哪个入口继续
* 当前附着了哪些必要的背景信息

## 3.3 Workspace 承接的是“当前干活时的上下文”，不是“全部静态定义”

这一点必须和 Solution 分开。

Solution 承接的是：

* 当前最终目标是什么
* 为什么这些 Project 属于同一个目标空间
* 当前这个目标空间里有哪些独立工作面

而 Workspace 承接的是：

* 当前人正处在哪个目标空间中
* 当前焦点落在哪个 Project
* 当前从哪个入口继续工作
* 当前哪些其他 Project 和背景信息需要一起被看到

所以 Workspace 更接近：

**某个 Solution 在当前时刻的工作上下文。**

它不是替代 Solution 的静态定义，而是在 Solution 之上承接“现在怎么继续干活”。

## 3.4 Workspace 的核心职责

当前阶段，Workspace 的职责先收成四条。

### 3.4.1 提供当前 Solution 的工作入口

也就是：
当人进入一个 Solution 时，不是面对抽象容器，而是进入一个可继续工作的上下文。

### 3.4.2 承接当前焦点 Project

Workspace 必须承接一个关键问题：

**当前到底是哪一个 Project 正在被推进。**

这条非常重要。
因为你已经明确：虽然一个 Solution 里可以有多个 Project，但一次只推进一个 Project。
那 Workspace 就必须让这个“当前焦点 Project”清晰存在。

### 3.4.3 承接当前入口

Workspace 不只要知道“推进哪个 Project”，
还要知道：

**当前从哪里继续。**

这个入口可能是：

* 当前节点
* 当前分支
* 当前轮次入口
* 当前某个派生工作入口

这里先不细化字段，但概念上必须承认：

**Workspace 不只是知道现在在看什么，还要知道现在从哪继续。**

### 3.4.4 承接其他附加信息

你前面这句非常关键：

> Workspace 其实就是干活时状态的上下文还有其他附加信息等等

我建议正式冻结下来。
也就是说，Workspace 除了焦点 Project 和当前入口之外，还应承接：

* 当前相关的其他 Project
* 当前轮次背景
* 当前必要说明
* 当前工作需要参考的附加信息

因此，Workspace 不是单一焦点指针，而是：

**当前干活所需的上下文集合。**

## 3.5 工作区中的“当前焦点”是正式概念，不是临时感觉

在当前阶段，我建议把“当前焦点”正式写成 Workspace 的核心概念。

这个焦点至少包含两层：

### 3.5.1 当前焦点 Project

这是当前真正进入推进状态的一级工作对象。

### 3.5.2 当前焦点入口

也就是：
这个 Project 当前是从哪里继续工作的。

所以 Workspace 的焦点，不只是“选中了哪个 Project”，
而是：

**选中了哪个 Project，并且当前从哪个入口继续。**

## 3.6 工作区必须支持“多个 Project 并存，但一次只推进一个”

这条原则必须在这里正式落下来。

一个 Solution 中可以并存多个 Project，
但 Workspace 当前只能有一个正式推进焦点。
这意味着：

* 多个 Project 可以同时存在
* 多个 Project 可以同时可见
* 多个 Project 可以共同服务于同一个最终目标
* 但当前这一轮推进，只能有一个焦点 Project

所以，Workspace 的职责之一，就是把“多对象并存”和“单点推进”同时承接住。

也就是说：

**Workspace 不是并发工作台，而是有明确焦点的工作上下文。**

## 3.7 工作区中的其他 Project 不是噪音，而是背景工作面

如果 Workspace 只承接当前焦点 Project，
那它就会退化成“打开某个 Project 的详情页”。

但 Solution 层既然已经承认多个 Project 共同服务于同一个最终目标，
那么 Workspace 还必须承认：

**其他 Project 是当前工作上下文的一部分。**

所以，非焦点 Project 在 Workspace 中的意义不是“堆在旁边的列表”，而是：

* 说明当前目标还涉及哪些工作面
* 提供当前推进的背景信息
* 为后续切换、派生、回扫提供可见基础

这也是 Workspace 和单个 Project 视图的根本区别。

## 3.8 工作区不等于 Project 内部视图

这一条必须明确，否则后面很容易混。

Project 内部视图解决的是：

* 当前这个 Project 内部怎么推进
* 当前节点在哪里
* 当前结构怎么展开

而 Workspace 解决的是：

* 当前 Solution 中，哪个 Project 正在工作
* 其他 Project 如何同时被看见
* 人如何在目标空间层面继续工作

所以：

**Workspace 不是把某个 Project 展开后的页面，而是比 Project 更高一级的工作上下文视图。**

### 3.9 工作区当前不承担的职责

为了防止概念过重，这一章也要把 Workspace 的非职责写清。

#### 3.9.1 不替代 Solution 做组织定义

Workspace 不是用来决定“有哪些 Project”的，
它是在 Solution 已经存在的前提下，承接当前使用状态。

#### 3.9.2 不替代 Round 做跨 Project 变化承接

Workspace 可以显示当前与某轮变化相关的 Project，
但它不是 Round 本身，也不负责定义一轮变化怎么记录。

#### 3.9.3 不替代 Project 内核做推进

Workspace 可以承接当前焦点 Project，
但它不直接替代 Project 内部的 Scheduler、Node 推进和沉淀。

#### 3.9.4 不等于最终 UI 设计

当前讨论的是概念层工作区，不是页面方案。
所以这里不讨论：

* 左右布局
* 面板数量
* 标签页形式
* 具体交互动作

这些以后都可以变，但概念上的 Workspace 仍然成立。

## 3.10 Workspace 的最小成立条件

在 1.0 当前阶段，我建议把 Workspace 的最小成立条件冻结成下面四条：

1. 它依附于一个 Solution 存在
2. 它必须承接当前焦点 Project
3. 它必须承接当前入口
4. 它必须承接当前继续工作所需的其他附加信息

如果缺了这些，Workspace 就会退化成两种不够用的东西之一：

* 只是一份 Project 列表
* 只是某个 Project 的详情页

而真正的 Workspace，不是这两者中的任何一个。

## 3.11 Workspace 和 Solution 的关系，不是简单“容器和界面”的关系

表面看起来，好像可以把它们简单理解成：

* Solution = 组织容器
* Workspace = 工作界面

但这样还是太浅。

更准确地说：

* Solution 承接“当前最终目标为什么是同一个目标”
* Workspace 承接“人如何进入这个目标并继续工作”

所以两者关系不是简单技术分层，而是：

**目标承接层 与 工作上下文承接层 的关系。**

这很重要，因为它说明 Workspace 不是一个可以随便替换的外壳，而是 Ascend 上层形态的一部分。

## 3.12 当前 1.0 对 Workspace 的最小冻结版本

如果把这一章再压到最小，可以冻结成下面这段话：

> Workspace 是人进入某个 Solution 后所面对的当前工作上下文。
> 它不是新的组织层对象，也不是某个 Project 的内部详情页，而是承接“当前正在推进哪个 Project、当前从哪里继续、其他相关 Project 与附加信息如何同时存在”的使用层结构。
> 在当前阶段，Workspace 的最小职责是：承接当前焦点 Project、承接当前入口，并承接继续工作所需的其他附加信息。

## 3.13 本章结论

第 3 章到这里正式冻结以下内容：

1. Workspace 不是新的组织层单位，而是人进入 Solution 后的当前工作上下文
2. Workspace 的首要价值不是展示，而是稳定当前工作状态
3. Workspace 承接的是当前干活时的上下文，而不是全部静态定义
4. Workspace 的核心职责包括：提供当前 Solution 的工作入口、承接当前焦点 Project、承接当前入口、承接继续工作所需的其他附加信息
5. Workspace 中应同时存在“当前推进的焦点 Project”和“作为背景存在的其他相关 Project”
6. 一个 Solution 可以并存多个 Project，但 Workspace 当前只能承接一个正式推进焦点
7. Workspace 不是 Project 内部视图，而是比 Project 更高一级的工作上下文视图
8. Workspace 不替代 Solution 的组织定义，不替代 Round，不替代 Project 内核，也不等于最终 UI 设计
9. Workspace 的最小成立条件是：依附于一个 Solution、承接当前焦点 Project、承接当前入口、承接其他附加信息
10. Workspace 与 Solution 的关系，不只是容器与界面的关系，而是“目标承接层”与“工作上下文承接层”的关系


## 4. Solution 内部的最小组织单位

### 4.1 当前阶段，Solution 内部的一级单位统一称为 Project

在当前冻结口径下，Solution 内部的一级独立工作单位统一称为：

**Project**

这一点已经在前文出现，但这一章要把它正式压实。

也就是说，从 Solution 往下看，第一层不是 Tree，不是 Node，也不是 Round，而是：

**Project**

这是当前上层组织成立的关键锚点。

### 4.2 为什么一级单位不再叫 Tree

这一点必须明确写出来，否则后面文档会继续打架。

如果继续把 Solution 内部一级单位叫 `Tree`，那会天然带来两个问题：

#### 4.2.1 Tree 会过早绑定内部形状

`Tree` 这个词天然暗示的是：

* 层级分叉
* 父子关系
* 以树状方式展开
* 更适合问题分解与对象递进

但你现在已经明确看到，有些工作对象未必天然是树状的。
例如：

* 写文章
* 写规则
* 写提示词
* 做一组顺序修改
* 做一条线性推演

这些内容虽然有时可以被“退化成树”，
但那只是形式上能塞进去，不代表“Tree”就是最合适的一级命名。

#### 4.2.2 Tree 会把上层抽象绑死在某一种内部组织方式上

如果 Solution 直接组织 Tree，就等于默认：

**所有一级工作单位本质上都应该是树。**

而你现在恰恰已经意识到，这个前提未必成立。
所以继续用 Tree 作为一级单位，会让上层抽象被内部结构绑死。

因此，本章冻结：

**Tree 不再作为 Solution 内部一级单位名词。**

### 4.3 为什么当前用 Project 更合适

与 Tree 相比，`Project` 更适合作为当前阶段的一级单位，原因有三点。

#### 4.3.1 Project 是中性词

它不预设内部一定是树形。
这意味着它更适合作为上层组织层的一级单位。

#### 4.3.2 Project 更贴近“独立工作面”

你现在实际在组织的，不是抽象树，而是多个独立的工作对象。
这些对象可能承接：

* 分析
* 文档
* 规则
* AI 指令
* 其他围绕目标继续展开的工作

用 Project，能更自然地表达这种“独立工作面”的感觉。

#### 4.3.3 Project 能兼容后续结构演化

当前阶段你仍然可以让 Project 默认采用 Tree 结构；
以后如果发现某些 Project 更适合线性结构、章节结构或其他形态，也不需要推翻上层名词。

所以，Project 更像是：

**上层组织中的一级工作对象名词。**

### 4.4 Project 的最小定义

在当前阶段，我建议把 Project 的最小定义冻结成下面这句话：

> **Project 是 Solution 内部一级独立工作对象，用于承接围绕当前最终目标展开的一类独立工作面。**

这里有三个关键词：

#### 4.4.1 一级

Project 是 Solution 往下的第一层正式单位。

#### 4.4.2 独立

它必须能被单独推进、单独承接、单独沉淀。
如果某个内容根本不形成独立工作面，那它就还不够资格成为 Project。

#### 4.4.3 工作对象

Project 不是简单分类标签，也不是文件夹。
它必须是一个真实会被继续工作的对象。

### 4.5 Project 和 Node 的区别

这一节必须写清，不然后面会塌。

#### 4.5.1 Node 是最小推进对象

Node 解决的是：

* 一次推进怎么发生
* 一轮怎么沉淀
* 下一步从哪继续

它是微观运行层单位。

#### 4.5.2 Project 是一级工作对象

Project 解决的是：

* 哪一类独立工作面存在
* 这类工作如何被单独承接
* 它在 Solution 中和其他工作面如何并存

它是上层组织单位。

所以两者的关系不是“Project 只是大 Node”，也不是“Node 是小 Project”，而是：

**Project 承接独立工作面，Node 承接该工作面中的最小推进单元。**

### 4.6 Project 和 Tree 的关系

这一节也必须钉死。

当前最稳的理解是：

**Tree 是 Project 当前默认可采用的一种内部组织结构。**

也就是说：

* Project 是一级工作对象
* Tree 是这个工作对象内部怎么组织内容与推进的方式
* 当前 1.0 已经完成的大量细化，主要是：
  **Project 采用 Tree 结构时的运行规则**

这有一个很大的好处：

你前面已经完成的单树内核并没有作废，
它只是被重新定位为：

**Project 默认内部结构的一套运行细化。**

所以不是推翻，而是升层。

### 4.7 什么样的内容才有资格升格为 Project

不是所有东西都值得变成 Project。
否则 Solution 很快就会塞满碎片。

在当前阶段，我建议把 Project 的最小成立条件收成下面三条：

#### 4.7.1 它服务于当前最终目标

它必须和当前 Solution 所承接的最终目标有关。
如果完全无关，就不应进入这个 Solution。

#### 4.7.2 它已经形成独立工作面

也就是说，它不是某个 Node 的一句补充，不是临时想到的一句话，而是已经形成：

* 可以单独推进
* 可以单独承接
* 可以单独沉淀

的一类工作。

#### 4.7.3 它不再适合继续作为原 Project 内部局部内容存在

如果某个内容继续放在原 Project 内部，不会造成明显混层，那它就未必需要独立成 Project。
只有当它已经成为独立工作面时，才值得升格。

这条很重要，因为它直接决定你以后会不会无节制地产生 Project。

### 4.8 当前阶段 Project 的典型例子

为了避免这个概念过虚，这里给出几个典型例子。

一个围绕真实问题存在的 Solution 中，可能有：

* 一个分析 Project
  负责问题分析、理解、拆解、判断方向
* 一个文档 Project
  负责将问题解决过程沉淀成文档
* 一个规则 Project
  负责把稳定约束整理成规则
* 一个 AI 指令 Project
  负责把结果进一步翻译成可执行 AI 指令

这些都不是同一种工作，
但它们都共同服务于同一个最终目标。
所以它们作为多个 Project 被放进同一个 Solution 中，是自然的。

### 4.9 当前阶段 Project 的最小属性要求

这一章先不写完整字段设计，
但概念上，一个 Project 至少应具备以下属性：

1. 它属于哪个 Solution
2. 它承接哪一类工作面
3. 它当前是否仍然有效
4. 它当前是否是焦点 Project
5. 它当前采用什么内部组织方式（当前默认可以是 Tree）

这里不进入字段级设计，只是先说明：

**Project 必须是可被识别、可被承接、可被切换的对象。**

### 4.10 Project 当前不等于“最终结构类型”

这一节是为了防止你后面再次把名词写死。

当前引入 Project，不是说未来结构类型已经完全确定了。
恰恰相反，引入 Project 是为了给未来结构留余地。

所以本章要明确：

* 当前只冻结 `Project` 作为一级单位
* 当前只冻结 `Tree` 作为其默认内部结构之一
* 暂不完整定义其他内部结构类型
* 暂不展开 Project 的全部类型学

也就是说，Project 的冻结，解决的是**上层命名和边界问题**，不是一次性解决所有内部结构问题。

### 4.11 当前 1.0 对 Project 的最小冻结版本

如果把这一章再压到最小，可以冻结成下面这段话：

> Project 是 Solution 内部一级独立工作对象，用于承接围绕当前最终目标展开的一类独立工作面。
> 它不是简单文件夹项，也不是 Tree 的同义词。
> Tree 退回为 Project 当前默认可采用的一种内部组织结构。
> 当前 1.0 已完成的大量单树运行规则，应被理解为：Project 采用 Tree 结构时的运行细化。

### 4.12 本章结论

第 4 章到这里正式冻结以下内容：

1. 当前阶段，Solution 内部一级单位统一称为 Project
2. Tree 不再作为一级单位名词，而退回为 Project 当前默认可采用的一种内部组织结构
3. 之所以不用 Tree 作为一级单位，是因为 Tree 会过早绑定内部形状并限制上层抽象
4. Project 更适合作为一级单位，因为它是中性词，更贴近独立工作面，也更能兼容后续结构演化
5. Project 的最小定义是：Solution 内部一级独立工作对象，用于承接围绕当前最终目标展开的一类独立工作面
6. Project 与 Node 的关系，不是大小关系，而是“一级工作对象”与“最小推进对象”的关系
7. Project 与 Tree 的关系，是“工作对象”与“当前默认内部组织结构”的关系
8. 只有当某个内容已经形成独立工作面，并且不再适合继续作为原 Project 内部局部内容存在时，它才有资格升格为新的 Project
9. 当前引入 Project，不是一次性定义所有结构类型，而是先解决上层命名与边界问题
10. 当前 1.0 已完成的大量单树细化，应被重新理解为：Project 采用 Tree 结构时的运行细化


## 5. 工作区中的使用原则

### 5.1 工作区的第一原则：一次只推进一个 Project

这是整个工作区最核心的原则，必须放在第一条。

一个 Solution 中可以并存多个 Project，
Workspace 也可以同时让这些 Project 被看见，
但在任意一个实际推进时刻， **只能有一个正式推进焦点** 。

因此，本章先冻结一句总规则：

**一次只推进一个 Project。**

这条规则的意义非常大。
它意味着：

* 多个 Project 可以共存
* 多个 Project 可以同时可见
* 多个 Project 可以围绕同一个最终目标
* 但真正进入当前推进状态的，只能有一个

这条规则如果不钉死，后面所有关于 Workspace 的定义都会失去焦点。

### 5.2 “一次只推进一个 Project”不等于“其他 Project 不存在”

这条原则很容易被误解，所以要单独展开。

当说“一次只推进一个 Project”时，
不是说 Workspace 里只剩下一个 Project，
也不是说其他 Project 都被隐藏、冻结或失效了。

它真正的意思是：

**当前轮次的正式工作焦点只有一个。**

其他 Project 仍然可以：

* 被看见
* 被参考
* 被挂起
* 作为背景存在
* 在后续轮次继续推进

所以，Workspace 承接的是：

* 单点推进
* 多点共存

这两者必须同时成立。

### 5.3 工作区的第二原则：当前焦点必须明确

既然一次只推进一个 Project，
那么 Workspace 中就不能存在“模糊焦点”。

也就是说，人在任何时刻进入 Workspace，
都应该能回答下面两个问题：

1. **当前正在推进哪个 Project**
2. **当前从哪个入口继续推进**

如果这两个问题回答不出来，
那 Workspace 虽然表面上存在，但实际上并没有形成真正的工作上下文。

因此，本章冻结：

**Workspace 必须承接当前焦点。**

这个焦点至少包括：

* 当前焦点 Project
* 当前焦点入口

后面无论是继续写、继续分析、继续整理规则，
都必须从这个焦点继续，而不是重新猜当前工作点。

### 5.4 工作区的第三原则：切换 Project 必须是显式动作

在多 Project 并存的情况下，
最大风险之一就是：
人在思考中已经悄悄切到了另一个 Project，但系统没有明确记录这个切换。

这会导致：

* 当前上下文断裂
* 当前入口失效
* 轮次边界模糊
* 产物和来源对不上

所以，本章建议正式冻结：

**从一个 Project 切到另一个 Project，必须是显式动作。**

也就是说：

* 不能在一轮中途悄悄漂移焦点
* 不能在没有明确切换的情况下，把另一个 Project 的推进混进当前 Project
* 不能在“我好像顺手也处理了一下别的 Project”这种模糊状态下继续工作

这条规则的本质是保护工作区的上下文稳定性。

### 5.5 工作区的第四原则：Project 可以相关，但推进不能交错

多个 Project 当然可能高度相关。
例如：

* 一个分析 Project 推进后，影响文档 Project
* 一个规则 Project 的结果，需要驱动 AI 指令 Project
* 一个主工作 Project 的稳定结果，会派生出新的产物 Project

这些关系都成立。
但相关，不等于可以在同一轮里交错推进。

所以这里要压一条非常关键的原则：

**Project 之间可以相关，但当前推进不能交错。**

也就是说，正确的方式是：

* 先把当前焦点 Project 推进到一个明确断点
* 再显式切换到另一个 Project
* 而不是在一轮里来回穿插

这条规则对于后面的 Round 和多 Project 协同会非常重要。

### 5.6 工作区的第五原则：跨 Project 协作通过轮次组织，不通过并发推进实现

当前你已经明确了一个很好的约束：

* 多个 Project 作为独立工作区存在
* 每个 Project 内部是完整推进闭环
* 一次只推进一个 Project
* 跨 Project 协作通过 Round 组织
* 推进时按 Project 顺序处理，而不是同时交错

这条约束非常适合作为 Workspace 使用原则正式冻结下来。

所以本章建议写成：

**Workspace 中的多 Project 协作，依赖 Round 进行组织；
但在实际推进时，仍然按 Project 顺序处理，而不是并发交错推进。**

这条规则会让你后面很多复杂度自动下降。

### 5.7 工作区的第六原则：当前工作上下文必须承接必要背景，而不是只承接焦点本身

如果 Workspace 只承接“当前焦点 Project”，
那它会退化成一种非常窄的“打开一个对象”的状态。

但你已经明确：Workspace 不只是焦点，还包括附加信息和当前干活状态。

因此，这里建议正式冻结：

**Workspace 除了焦点，还必须承接继续工作所需的必要背景。**

这些背景可以包括：

* 当前相关的其他 Project
* 当前轮次背景
* 当前目标说明
* 当前约束或参考信息
* 当前已形成但尚未正式推进的相关线索

这条规则的意义是：

**Workspace 不是只知道“在干什么”，还要知道“带着什么背景在干”。**

### 5.8 工作区的第七原则：背景存在不等于背景自动进入本轮推进

这一条要单独强调。

即使其他 Project、当前轮次背景、其他附加信息都被挂在 Workspace 中，
也不意味着它们自动成为本轮正式推进对象。

否则，Workspace 又会退回成“所有东西一起推进”的状态。

所以本章冻结：

**背景信息可以存在于 Workspace 中，但不会自动进入当前轮次。**

只有当发生显式切换、显式派生、显式触发时，
背景中的其他 Project 或信息才进入后续正式推进流程。

### 5.9 工作区的第八原则：当前工作入口必须可恢复

如果 Workspace 要作为当前干活时的上下文承接面，
那它就不能只在“我正在盯着它看”的时候有效。

它还必须支持一种能力：

**我中断之后回来，仍然知道从哪里继续。**

所以，这里建议正式冻结：

**Workspace 必须承接当前工作入口，并使这一入口可恢复。**

也就是说，Workspace 至少要让人回来时能重新回答：

* 当前在推进哪个 Project
* 当前从哪个入口继续
* 当前轮次背景是什么
* 当前有哪些必要附加信息

这条原则对以后实现恢复、回扫、接续都非常关键。

### 5.10 工作区的第九原则：使用层可以先简，语义层不能含糊

这一条是为了防止后面过早掉进 UI 细节。

当前阶段，Workspace 不必一开始就设计得很复杂。
例如：

* 不必先做复杂界面
* 不必先做很多面板
* 不必先做完整切换体验

但即使使用层先做得很简，
Workspace 的语义层也不能含糊。

也就是说，哪怕未来 1.0 只是非常简单的实现，
下面这些概念仍然必须明确存在：

* 当前焦点 Project
* 当前焦点入口
* 当前背景信息
* 当前相关 Project
* 当前轮次背景

所以本章再压一句：

**实现可以先简，但语义不能先糊。**

### 5.11 工作区中的最小使用顺序

如果把前面的原则压成一个最小使用顺序，
我建议写成下面这样：

1. 进入某个 Solution
2. 进入该 Solution 的当前 Workspace
3. 确认当前焦点 Project
4. 确认当前入口与必要背景
5. 对该 Project 执行当前轮推进
6. 如需涉及其他 Project，先完成当前 Project 的明确断点
7. 再通过显式切换进入下一个 Project
8. 若需要跨 Project 组织变化，通过 Round 承接

这条最小顺序能直接帮助你以后思考实际使用流程。

### 5.12 当前 1.0 对工作区使用原则的最小冻结版本

如果把这一章再压到最小，可以冻结成下面这段话：

> 在一个 Solution 中，可以同时存在多个 Project，但在任意一个实际推进时刻，Workspace 只能承接一个正式推进焦点。
> 当前焦点必须明确，并且从一个 Project 切到另一个 Project 必须是显式动作。
> 多个 Project 可以相关，但推进不能交错；跨 Project 协作通过 Round 组织，而在实际执行时仍按 Project 顺序处理。
> Workspace 除了承接当前焦点 Project，还必须承接继续工作所需的必要背景与附加信息，并保证当前工作入口可恢复。

### 5.13 本章结论

第 5 章到这里正式冻结以下内容：

1. 工作区的第一原则是：一次只推进一个 Project
2. “一次只推进一个 Project”不等于其他 Project 不存在，而是指当前正式推进焦点只有一个
3. Workspace 中的当前焦点必须明确，包括当前焦点 Project 和当前焦点入口
4. 从一个 Project 切到另一个 Project，必须是显式动作
5. Project 之间可以相关，但推进不能交错
6. 多 Project 协作通过 Round 组织，而实际推进仍按 Project 顺序处理
7. Workspace 除了承接焦点 Project，还必须承接继续工作所需的必要背景与附加信息
8. 背景存在于 Workspace 中，不等于它们自动进入当前轮次
9. Workspace 必须使当前工作入口可恢复
10. 当前阶段实现可以先简，但工作区的语义层不能含糊
11. 工作区的最小使用顺序已经形成，可作为后续产品与实现设计的输入

## 6. Solution 与下层对象的边界

### 6.1 这一章的任务不是重新定义对象，而是防止层级打架

到了这一章，Node、Project、Tree、Round、Workspace、Solution 这些概念都已经出现了。
它们之间当然有关联，但如果关联不等于边界，后面一定会逐步混成一团。

所以这一章不再问：

* 它们是什么
* 为什么存在

而是专门回答：

* 谁负责什么
* 谁不负责什么
* 哪些职责不能跨层乱接

也就是说，这一章本质上是一章 **职责分界章** 。

### 6.2 Solution 与 Workspace 的边界

这两个概念最容易被误解成“一个东西的两种说法”，所以先拆它们。

#### 6.2.1 Solution 是目标承接层

Solution 承接的是：

* 当前最终目标
* 围绕这个目标存在的多个 Project
* 这些 Project 为什么属于同一个问题空间

所以，Solution 解决的是：

**这些东西为什么属于同一个解决过程。**

#### 6.2.2 Workspace 是使用承接层

Workspace 承接的是：

* 当前焦点 Project
* 当前焦点入口
* 当前轮次相关背景
* 当前需要一起存在的附加信息

所以，Workspace 解决的是：

**人在这个问题空间里，现在如何继续干活。**

#### 6.2.3 两者边界结论

因此可以正式压成一句：

**Solution 承接问题空间，Workspace 承接当前工作上下文。**

也就是说：

* Solution 不是当前工作状态
* Workspace 不是上层目标容器
* Solution 回答“这是什么问题空间”
* Workspace 回答“现在怎么继续工作”

### 6.3 Solution 与 Project 的边界

这是最核心的一组边界。

#### 6.3.1 Solution 不是更大的 Project

如果把 Solution 理解成“更大的 Project”，
那你后面一定会倾向于把所有工作继续塞进一个超大对象里，
这就又会回到原来单树 / 单对象承接一切的问题。

所以必须明确：

**Solution 不是更大的 Project。**

#### 6.3.2 Project 不是缩小版 Solution

反过来也一样。
Project 虽然是独立工作对象，但它不是一个微型 Solution。
Project 的职责不是去组织其他 Project，而是：

**承接一类独立工作面。**

#### 6.3.3 两者边界结论

因此：

* Solution 负责组织多个 Project 围绕同一个最终目标存在
* Project 负责承接某一类独立工作面
* Solution 不替代 Project 做内部推进
* Project 不替代 Solution 做上层组织

一句话：

**Solution 负责“问题空间”，Project 负责“独立工作面”。**

### 6.4 Solution 与 Tree 的边界

这一组边界是为了防止你后面又把一级单位写回 Tree。

#### 6.4.1 Tree 不是 Solution 的一级单位

当前口径已经冻结：

* Solution 内部一级单位是 Project
* Tree 退回为 Project 当前默认可采用的一种内部组织结构

所以 Tree 不再直接参与 Solution 这一层的命名体系。

#### 6.4.2 Tree 也不是 Solution 的替代物

Tree 能做的是：

* 承接局部内容
* 承接局部推进
* 承接结构展开

但它不适合直接承接：

* 多个独立工作面并存
* 多个 Project 之间的共同目标关系
* 上层问题空间组织

#### 6.4.3 边界结论

因此：

**Tree 属于 Project 的内部结构问题，不属于 Solution 的一级组织问题。**

这条边界一旦钉住，后面很多概念都会顺。

### 6.5 Solution 与 Node 的边界

这组边界是为了防止“Node 一路膨胀到上层”。

#### 6.5.1 Node 是最小推进对象

Node 承担的是：

* 一次推进怎么发生
* 一轮怎么沉淀
* 下一步如何继续

它是微观推进单元。

#### 6.5.2 Solution 不直接操作 Node 级语义

Solution 层不应该直接承接：

* 节点状态流转
* 节点是否冻结
* 节点一轮输入输出
* 节点 StepRecord

这些都属于 Node 所在的运行层和 Project 内部层。

#### 6.5.3 边界结论

因此：

**Node 解决“怎么推进最小内容单元”，Solution 解决“这些工作对象为什么属于同一个问题空间”。**

两者之间隔着 Project，而不是直接相连。

### 6.6 Solution 与 Round 的边界

这一组边界也非常重要，因为 Solution 很容易被误写成“所有变化都在里面直接发生”。

#### 6.6.1 Solution 不是变化本身

Solution 是围绕最终目标存在的问题空间。
它可以长期存在。
而 Round 是某一次变化、某一次批量修改、某一次跨 Project 推进组织。

因此：

**Solution 不是 Round。**

#### 6.6.2 Round 不是目标空间

Round 只能承接一次变化。
它不能承接整个问题的长期存在，也不能承接全部 Project 的长期归属。

所以：

**Round 不替代 Solution。**

#### 6.6.3 边界结论

因此：

* Solution 承接长期问题空间
* Round 承接一次跨 Project 变化
* Solution 是上层容器
* Round 是变化单位

一句话：

**Solution 解决“问题属于哪里”，Round 解决“这次变化怎么组织”。**

### 6.7 Solution 与 StepRecord 的边界

这一组边界是为了防止“轮次留痕”一路上浮。

#### 6.7.1 StepRecord 是局部推进留痕

StepRecord 记录的是：

* 某个 Node 在某个场景下完成一轮推进后的结果

它属于 Node / Project 内部推进层。

#### 6.7.2 Solution 不直接承接 StepRecord 语义

Solution 不负责：

* 描述某个 Node 这轮输入了什么
* 描述某个 Node 这轮输出了什么
* 描述某个 Node 这轮改了什么

这些东西太细，属于局部推进留痕。

#### 6.7.3 边界结论

因此：

**StepRecord 属于局部推进记录，Solution 属于问题空间组织。**

如果未来 Solution 需要看这些东西，也应通过下层聚合，而不是自己变成 StepRecord 的直接容器。

### 6.8 Solution 与 Scheduler 的边界

这一组边界决定了 Solution 会不会演化成“大脑”。

#### 6.8.1 Scheduler 负责局部推进秩序

Scheduler 的职责已经明确：

* 过滤候选
* 选择当前推进对象
* 选择 mode
* 判断是否人工介入
* 接收重新纳管对象

它面向的是局部推进秩序。

#### 6.8.2 Solution 不直接承担调度职责

Solution 当前不负责：

* 在 Node 级别选谁先推进
* 在 Project 内部定 mode
* 决定某个节点是否等待人工
* 替代局部运行规则

#### 6.8.3 边界结论

因此：

**Scheduler 解决“局部怎么推进”，Solution 解决“这些局部推进为什么属于同一个目标空间”。**

如果以后出现跨 Project 的选择机制，它也不能直接等同于现在的 Scheduler，至少概念上要分开。

### 6.9 Solution 与派生产物的边界

这里要防止 Solution 被写成“产物收纳箱”。

#### 6.9.1 派生产物不等于 Solution 本身

文档、规则、AI 指令等派生产物，
虽然都可能属于某个 Solution，
但它们不是 Solution 本身。

#### 6.9.2 Solution 负责承接归属，不负责吞并产物

更准确地说：

* Solution 负责承接这些派生产物为什么仍属于同一个最终目标
* 但具体产物应由相应的 Project 去承接
* Solution 不直接吞并它们成为自己的内部字段集合

#### 6.9.3 边界结论

因此：

**Solution 负责归属，派生产物 Project 负责工作。**

这会比“所有产物都挂在 Solution 下当静态附件”稳得多。

### 6.10 Solution 当前不该直接接住的职责

为了更彻底防打架，这里再反向列一次。

当前阶段，Solution 不应直接接住以下职责：

* 不直接接 Node 级运行规则
* 不直接接 Project 内部结构细节
* 不直接接 Round 的字段和生命周期
* 不直接接 StepRecord 留痕语义
* 不直接接 Scheduler 局部调度职责
* 不直接接派生产物的内部内容组织
* 不直接等同于 Workspace

也就是说，Solution 当前更像是：

**上层承接与组织定义，而不是一个把所有东西全包进去的超级对象。**

### 6.11 当前 1.0 的边界压缩版

如果把这一章再压到最小，可以冻结成下面这段话：

> Solution 是围绕同一个最终目标而存在的问题空间组织层。
> 它承接目标、归属与上层组织，但不直接承接 Project 内部推进、Node 级运行、Round 级变化、StepRecord 留痕与局部调度。
> Workspace 承接当前使用上下文，Project 承接独立工作面，Tree 承接 Project 的默认内部结构，Node 承接最小推进对象，Round 承接一次跨 Project 变化。
> Solution 与这些对象相关，但不替代这些对象各自的职责。

### 6.12 本章结论

第 6 章到这里正式冻结以下内容：

1. 本章的目标是防止层级职责打架，而不是重写对象定义
2. Solution 与 Workspace 的边界是：Solution 承接问题空间，Workspace 承接当前工作上下文
3. Solution 与 Project 的边界是：Solution 负责问题空间，Project 负责独立工作面
4. Tree 不再作为 Solution 一级单位，而属于 Project 的内部结构问题
5. Node 是最小推进对象，Solution 不直接承接 Node 级运行语义
6. Solution 是长期目标空间，Round 是某一次跨 Project 变化单位
7. StepRecord 属于局部推进留痕，不属于 Solution 的直接职责
8. Scheduler 属于局部推进秩序，不属于 Solution 的直接职责
9. 派生产物属于 Solution 的目标归属范围，但不应被 Solution 直接吞并为内部静态字段集合
10. 当前阶段，Solution 应保持为上层承接与组织定义，而不是包揽一切的超级对象

## 7. 当前 1.0 先冻结什么

### 7.1 这一章的目标

到目前为止，你已经把以下几层东西都碰到了：

* Solution
* Workspace
* Project
* Tree
* Node
* Round
* 多 Project 协同
* 派生产物
* 生命周期

如果这时不做一次收口，
后面文档会继续自然膨胀，最后你会同时讨论：

* 上层容器
* 中层协作
* 底层推进
* 生命周期
* UI
* 产物系统
* 自动化编排

结果就是一切都开始变得“有道理，但落不了地”。

所以这一章的目标只有一个：

**给 1.0 当前阶段的 Solution 层定义一个最小冻结边界。**

### 7.2 当前 1.0 先冻结的第一件事：承认 Solution 层存在

这一条必须先钉死。

在当前阶段，1.0 先正式承认：

**单个 Project 不足以自然承接一个真实问题的完整解决过程，因此需要 Solution 作为上层组织容器。**

这意味着，从现在开始，Ascend 1.0 不再只被理解为：

* 一个单树推进框架
* 一个 Project 内部推进系统

而是开始正式承认：

**存在围绕同一个最终目标组织多个 Project 的上层。**

这一条是整个 Solution 层成立的总前提。

### 7.3 当前 1.0 先冻结的第二件事：Solution 内部一级单位统一叫 Project

这一条也必须冻结，不然后面所有文档会来回切词。

当前阶段统一使用：

**Project = Solution 内部一级独立工作对象**

同时冻结：

* `Tree` 不再作为一级单位名词
* `Tree` 退回为 `Project` 当前默认可采用的一种内部组织结构

这样做的意义是：

* 上层命名不再被内部结构绑死
* 你前面已经完成的大量单树细化仍然可以保留
* 以后允许引入非树形内部结构，而不必推翻上层名词

这条冻结，本质上是一次 **升层而非推翻** 。

### 7.4 当前 1.0 先冻结的第三件事：Workspace 作为当前工作上下文正式成立

当前阶段，Workspace 也应被正式承认，但要控制在最小语义层，不扩成产品界面设计。

先冻结：

**Workspace = 人进入某个 Solution 后，当前干活所处的工作上下文。**

它至少承接：

* 当前焦点 Project
* 当前焦点入口
* 当前相关 Project
* 当前必要附加信息

当前 1.0 只冻结这个语义，
不展开具体 UI 布局、不展开交互细节、不展开多面板结构。

### 7.5 当前 1.0 先冻结的第四件事：一次只推进一个 Project

这一条是当前使用原则里最重要的硬约束，应直接冻结。

当前阶段正式冻结：

**一个 Solution 中可以存在多个 Project，但任意一个实际推进时刻，只能有一个正式推进焦点。**

这意味着：

* 多个 Project 可以共存
* 多个 Project 可以同时可见
* 多个 Project 可以共同服务于同一个最终目标
* 但不能在同一轮里交错推进多个 Project

这一条如果不冻结，后面 Workspace、Round、多 Project 协同都会立即变乱。

### 7.6 当前 1.0 先冻结的第五件事：多 Project 协同通过 Round 组织，但暂不展开完整机制

你现在已经很清楚地意识到：

* 多个 Project 会围绕同一个问题存在
* 它们之间会相互影响
* 它们不能并发乱跑
* 需要一个更高一级的单位来承接某次变化

所以当前阶段要正式承认：

**Round 是跨 Project 变化的组织单位。**

但这里先只冻结“存在与地位”，
不在当前文档里展开：

* Round 的完整字段
* Round 的状态机
* Round 的存储策略
* Round 的自动拆分逻辑

也就是说：

**先承认 Round，后细化 Round。**

### 7.7 当前 1.0 先冻结的第六件事：Project 可以有不同生命周期，但暂不细化完整类型体系

你前面已经明确看到：

* 有些工作对象是长期承接的
* 有些是一次性的
* 有些可能只是辅助性的

这说明 Project 的生命周期不应一刀切。
所以当前阶段应先冻结：

**Project 的生命周期允许不同。**

但这里先不要展开太多。
也就是说，当前只先承认：

* 持续承接型 Project
* 临时性 Project

至于更细的：

* 是否自动升格
* 是否自动归档
* 是否部分保留记忆
* 不同生命周期的精细策略

这些都先不进入 1.0 当前冻结范围。

### 7.8 当前 1.0 先冻结的第七件事：派生产物以“派生 Project”形式承认，但先不做完整分类学

你现在已经很明确地看到，真实问题解决过程中，
主工作对象往往会派生出：

* 文档
* 规则
* AI 指令
* 其他产物

所以当前阶段，应先正式承认：

**某些产物一旦形成独立工作面，就应以独立 Project 的形式被承接。**

但这里先不要做完整分类学。
也就是说，当前不急着正式定义：

* 文档 Project 的完整字段
* 规则 Project 的完整字段
* AI 指令 Project 的完整字段
* 所有派生产物 Project 的统一模型

先只冻结一句：

**派生产物可以升格为独立 Project。**

这就够了。

### 7.9 当前 1.0 不急着冻结的内容

这一章除了“先冻结什么”，也必须写“现在不冻结什么”。
这样边界才稳。

当前阶段，以下内容 **先不冻结为正式实现范围** ：

1. Project 内部全部可能的结构类型
2. 完整的多 Project 自动编排机制
3. Round 的完整状态机与存储设计
4. Project 间引用的完整模型
5. Project 生命周期的精细分类体系
6. 学习子树 / 辅助子树的正式实现机制
7. Workspace 的具体 UI 形态
8. Solution 层自动路由与自动分配逻辑
9. 跨 Solution 关系与协同

这些都已经出现了，也都值得讨论，
但它们不应在当前 1.0 冻结稿里被当作正式落地边界。

### 7.10 当前 1.0 的最小冻结范围

如果把这一章压成最小范围，我建议冻结成下面这组内容：

#### 组织层面冻结

* 1.0 正式承认 Solution 层存在
* Solution 围绕同一个最终目标组织多个 Project
* Solution 内部一级单位统一叫 Project
* Tree 退回为 Project 默认可采用的一种内部组织结构

#### 使用层面冻结

* Workspace 正式承接当前工作上下文
* 一次只推进一个 Project
* 当前焦点必须明确
* Project 切换必须显式发生

#### 协作层面冻结

* 多 Project 协同通过 Round 组织
* 但当前不展开 Round 全机制
* 派生产物可升格为独立 Project
* 但当前不展开完整产物分类学

#### 边界层面冻结

* 当前不细化全部结构类型
* 当前不实现完整生命周期系统
* 当前不实现复杂工作区 UI
* 当前不实现自动编排

### 7.11 当前 1.0 冻结这些内容的意义

这一步的意义，不是“保守”，而是：

**让 Solution 层先以最小正确形态成立。**

如果现在不收口，后面很容易出现两种坏情况：

#### 7.11.1 继续停留在单 Project / 单树心智里

那 Solution 层就始终只是一个概念补丁，
不会真正进入后续实现和文档体系。

#### 7.11.2 一次把 Solution 层膨胀成完整产品蓝图

那你会同时陷入：

* 多 Project 编排
* 生命周期系统
* 工作区界面
* 产物系统
* 自动化路由

最后反而什么都落不了。

所以当前 1.0 最好的策略就是：

**承认上层组织层，冻结其最小成立条件，但不提前吃掉全部复杂度。**

### 7.12 当前 1.0 的压缩版冻结结论

如果把这一章再压成一句正式冻结语句，可以写成：

> 当前 1.0 正式承认 Solution 作为围绕同一个最终目标组织多个 Project 的上层容器存在，正式承认 Workspace 作为当前工作上下文存在，并正式承认 Round 作为跨 Project 变化组织单位存在。
> 在当前阶段，Solution 内部一级单位统一称为 Project，Tree 退回为 Project 当前默认可采用的一种内部组织结构。
> 当前工作原则冻结为：一次只推进一个 Project，多 Project 协同通过 Round 组织，派生产物可以升格为独立 Project。
> 与此同时，完整的多 Project 编排、Round 细节、生命周期体系、结构类型体系与工作区 UI 暂不进入当前 1.0 冻结范围。

### 7.13 本章结论

第 7 章到这里正式冻结以下内容：

1. 当前 1.0 正式承认 Solution 层存在
2. 当前 1.0 正式承认 Solution 内部一级单位统一叫 Project
3. 当前 1.0 正式承认 Tree 退回为 Project 默认可采用的一种内部组织结构
4. 当前 1.0 正式承认 Workspace 作为当前工作上下文存在
5. 当前 1.0 正式冻结“一次只推进一个 Project”
6. 当前 1.0 正式承认 Round 作为跨 Project 变化组织单位，但暂不展开完整机制
7. 当前 1.0 正式承认派生产物可升格为独立 Project，但暂不展开完整分类学
8. 当前 1.0 暂不冻结完整结构类型体系、完整生命周期体系、复杂工作区 UI 与自动编排机制
9. 当前冻结这些内容的目的，是让 Solution 层先以最小正确形态成立，而不是一次性膨胀成完整产品蓝图


## 8. 当前 1.0 暂不展开什么

### 8.1 这一章的目标

当前阶段，Ascend 已经从单树推进内核，开始自然地长出：

* Solution
* Workspace
* Project
* Round
* 多 Project 协同
* 派生产物
* 生命周期差异

这些方向都是真的，
也都值得继续讨论。
但“值得讨论”不等于“现在就要正式展开并纳入 1.0 落地边界”。

所以这一章的目标不是否定这些问题，
而是正式声明：

**它们存在，但当前先不展开成完整定义或完整实现范围。**

### 8.2 暂不展开：Project 的完整结构类型体系

你已经明确意识到，Project 内部不一定只有 Tree。
有些内容可能是：

* 树状的
* 线性的
* 混合的
* 未来甚至可能出现别的结构

但当前 1.0 不适合正式展开完整的结构类型体系。
原因很简单：

* 一旦展开，你马上就要定义 Tree / Linear / Hybrid 的正式边界
* 还要定义它们之间如何切换、如何承接、如何统一推进
* 这会把当前讨论从“上层容器成立”迅速拉回“底层结构体系重做”

所以当前阶段只冻结：

* Project 是一级单位
* Tree 是当前默认可采用的一种内部组织结构

除此之外的结构类型，先承认存在可能，但 **不正式展开** 。

### 8.3 暂不展开：Round 的完整生命周期与字段设计

你已经明确看到 Round 的必要性，
也已经知道它不是树内概念，而是跨 Project 的变化组织单位。

但当前 1.0 不适合马上正式展开：

* Round 的字段集合
* Round 的状态流转
* Round 的开始 / 暂停 / 完成机制
* Round 的存储方式
* Round 和 StepRecord 的映射关系

这些问题都很重要，
但它们属于下一层落地问题。
当前 1.0 只需先承认：

**Round 存在，并且是跨 Project 变化的组织单位。**

其余细节，先不展开。

### 8.4 暂不展开：多 Project 的完整编排机制

当前你已经明确了一个非常好的使用约束：

* 多个 Project 可以共存
* 一次只推进一个 Project
* 跨 Project 协作通过 Round 组织
* 推进时仍按 Project 顺序处理，而不是交错并发

这个约束本身足够稳定。
但当前 1.0 不适合继续展开完整的多 Project 编排系统，例如：

* 哪些 Project 自动优先
* 哪些 Project 自动被拉起
* Project 之间的自动依赖调度
* 跨 Project 的自动切换策略
* 多 Project 的全局选择器

这些东西如果现在展开，会立刻让系统从“组织层成立”滑向“调度系统设计”。

所以当前阶段只冻结原则，不展开完整编排机制。

### 8.5 暂不展开：Project 生命周期的精细体系

你已经很清楚地意识到：

* 有长期 Project
* 有临时 Project
* 有派生 Project
* 有可能还有辅助 Project

这已经足够说明“生命周期不能一刀切”。
但当前 1.0 不适合继续展开成完整体系，例如：

* 生命周期完整类型表
* 生命周期自动迁移规则
* 自动归档条件
* 自动升格条件
* 不同生命周期的存储策略
* 不同生命周期的记忆裁剪策略

这些都可以保留到下一层讨论。
当前只先承认：

**Project 生命周期存在差异。**

但不继续细化。

### 8.6 暂不展开：学习子树 / 辅助子树的正式机制

你前面已经提出了一个很有价值的方向：

* 某个节点可能需要认知补足
* 可以开一棵学习树 / 辅助树
* 它为当前推进服务

这个方向是成立的。
但当前 1.0 不适合把它正式纳入主实现范围。
因为一旦展开，你马上就会面对：

* 子树和父对象怎么绑定
* 学习何时算够
* 学习结果怎么回填
* 学习树是临时还是持久
* 它属于 Project 还是 Project 内部结构的一部分

这些都是下一层复杂度。

所以当前阶段只保留一句：

**学习子树 / 辅助子树是后续可能方向，但当前 1.0 不正式展开。**

### 8.7 暂不展开：派生产物的完整分类体系

当前你已经明确看到，问题解决过程中会派生出：

* 文档
* 规则
* AI 指令
* 其他产物

也已经承认：

**这些产物一旦形成独立工作面，就可以升格为独立 Project。**

这一步已经足够。
但当前 1.0 不适合继续展开：

* 文档 Project 的完整模型
* 规则 Project 的完整模型
* AI 指令 Project 的完整模型
* 各类派生产物之间的统一关系
* 派生产物 Project 的完整类型学

因为一旦这样做，你会立刻进入“产品矩阵”式定义，
这会远远超过当前阶段所需。

所以当前阶段只冻结：

* 可派生
* 可独立承接

不冻结完整分类学。

### 8.8 暂不展开：Workspace 的 UI 形态

当前你已经把 Workspace 的语义压得比较清楚了：

* 它是当前工作上下文
* 它承接当前焦点
* 它承接当前入口
* 它承接背景与附加信息

这些语义已经足够。
但当前 1.0 不适合继续展开：

* Workspace 页面布局
* 面板划分
* 栏位设计
* 标签页设计
* 切换交互
* 折叠 / 展开策略

这些属于产品界面问题，
而当前你还处在概念层和实现边界层。

所以当前阶段：

**冻结语义，不展开 UI。**

### 8.9 暂不展开：跨 Solution 的关系

当前你已经在一个 Solution 内部开始讨论多个 Project。
这已经足够复杂了。

所以当前 1.0 不适合继续讨论：

* Solution 和 Solution 之间如何引用
* 一个 Project 是否能跨多个 Solution
* 跨 Solution 的全局工作区
* 跨 Solution 的迁移机制

这些问题一定会来，
但它们明显是下一层问题。

当前阶段先冻结：

**只讨论单个 Solution 内部的问题空间组织。**

### 8.10 暂不展开：自动路由与自动决策系统

当前你已经有：

* Scheduler 的局部调度能力
* Workspace 的当前焦点能力
* Round 的上层变化单位概念

这已经够了。
当前 1.0 不适合继续展开成：

* 全局自动路由系统
* 自动选择最佳 Project
* 自动创建新 Project
* 自动派生产物 Project
* 自动判定哪些 Project 应归档
* 自动重组问题空间

这些东西一旦进来，
Ascend 很快会从“可控的人机协作系统”变成“想做全局自治系统”。

这不符合你当前边界。

### 8.11 暂不展开：完整的组织层字段设计

到目前为止，Solution / Workspace / Project / Round 都已经有了概念层定义。
但当前 1.0 不适合马上进一步写成：

* 每个对象的完整字段表
* 每个字段的严格类型
* 字段之间的完整关系图
* 所有对象的最终存储模型

原因是：

* 现在你还处在组织层概念收口阶段
* 很多字段会被后续 Round、生命周期、多 Project 协同牵动
* 现在急着字段化，后面一定会反复推翻

所以当前阶段先冻结概念层和边界层，
字段层先不完整展开。

### 8.12 为什么这些内容现在不展开

这一节也必须明确。
不展开，不是因为它们不重要，
而是因为当前阶段的任务不是“把所有可能性都设计完”，而是：

**先让 Solution 层以最小正确形态成立。**

当前不展开这些内容，有三个原因：

#### 8.12.1 防止边界失控

一旦把这些都展开，
1.0 会立刻失去最小范围。

#### 8.12.2 防止概念层和实现层提前缠死

很多问题现在其实还属于“是否需要”阶段，
而不是“怎么精细实现”阶段。

#### 8.12.3 保住当前推进节奏

你现在最需要的是：

* 让组织层成立
* 让命名稳定
* 让边界清楚

而不是同时把所有下阶段问题都吃掉。

### 8.13 当前 1.0 暂不展开内容的压缩版

如果把这一章再压成一句正式冻结语句，可以写成：

> 当前 1.0 已正式承认 Solution、Workspace、Project、Round 等上层组织概念存在，但暂不展开 Project 的完整结构类型体系、Round 的完整生命周期与字段设计、多 Project 的完整编排机制、Project 生命周期的精细体系、学习子树 / 辅助子树的正式机制、派生产物的完整分类体系、Workspace 的 UI 形态、跨 Solution 关系、自动路由与自动决策系统，以及完整的组织层字段设计。
> 这些问题都已出现且重要，但当前阶段只做记录，不进入正式实现冻结范围。

### 8.14 本章结论

第 8 章到这里正式冻结以下内容：

1. 当前 1.0 暂不展开 Project 的完整结构类型体系
2. 当前 1.0 暂不展开 Round 的完整生命周期与字段设计

6. 当前 1.0 暂不展开派生产物的完整分类体系

## 9. 最小例子

### 9.1 为什么需要最小例子

前面几章已经冻结了这些概念：

* Solution
* Workspace
* Project
* Tree
* Round
* 一次只推进一个 Project
* 多 Project 协同通过 Round 组织
* 当前 1.0 暂不展开什么

但这些概念如果只停留在定义层，
很容易出现一种错觉：

“每个概念都好像说得通，但放在一起时不知道系统到底怎么工作。”

所以这一章的作用是：

**用一个最小、真实、可操作的场景，把 Solution 层的最小形态跑通。**

### 9.2 例子的目标

我们用这样一个最小目标来举例：

**我要把 Ascend 当前已冻结的一棵树运行规则，继续整理成一份可用于后续实现的正式文档体系。**

注意，这里的“问题”不是：

* 写一个节点
* 改一个状态
* 做一轮操作

而是：

**把“当前树内规则已经明确”这件事，进一步推进成可组织、可沉淀、可继续扩展的解决过程。**

这正好适合用来说明：

* 为什么要有 Solution
* 为什么会有多个 Project
* Workspace 承接的到底是什么
* Round 如何作为跨 Project 变化单位存在

### 9.3 这个例子里的 Solution

在这个例子里，可以有一个 Solution，名字暂时可以理解为：

**Ascend 1.0 设计整理**

它承接的最终目标不是：

* 只写运行规则
* 只整理某一棵树
* 只补某一个文档

而是：

**把 Ascend 1.0 当前已经形成的内容，整理成一套可继续实现、可继续扩展的正式设计基础。**

这个最终目标跨越多个阶段，也会涉及多个工作面，
所以它不是一个 Project 能自然吃下的东西，
因此需要一个 Solution。

### 9.4 这个例子里的 Project

在这个最小例子里，当前至少可能出现下面几个 Project。

#### 9.4.1 运行规则 Project

它承接的是：

* 单个 Project 当前采用 Tree 结构时
* Node 如何进入系统
* 如何调度
* 如何完成一轮
* 如何沉淀
* 条件动作如何触发

这对应你前面已经完成的大量细化。

#### 9.4.2 解决方案层 Project

它承接的是：

* Solution 是什么
* Workspace 是什么
* Project 是什么
* 这些上层概念之间的关系
* 当前 1.0 先冻结什么、暂不展开什么

也就是你现在正在写的这一份文档。

#### 9.4.3 实现规划 Project

它承接的是：

* 最小实现范围
* 类型冻结
* 实现顺序
* 验证用例
* AI 编码输入物

它不直接定义运行规则，也不直接定义 Solution 层，
但它围绕同一个最终目标继续向下承接实现问题。

这个例子里，这三个 Project 已经足够说明问题。
它们都服务于同一个最终目标，但显然不是同一类工作。

### 9.5 为什么这三个东西不该继续塞回一个 Project

这个例子最关键的价值，就在于能说明：

**为什么单个 Project 不够。**

如果把它们都塞进一个 Project，会发生什么？

* 运行规则会和上层组织定义混在一起
* 上层概念会和实现计划混在一起
* 当前已经冻结的内容和后续待实现内容混在一起
* 工作焦点会不断漂移

最后你会发现，看起来只是在“整理一个系统”，
实际上却在同一个工作面里不断切换：

* 规则层
* 组织层
* 实现层

这就是单 Project 会逐步失真的地方。

### 9.6 这个例子里的 Workspace

当人进入这个 Solution 时，面对的不是“抽象解决方案”本身，
而是一个当前工作上下文。

例如，当前 Workspace 里可能承接的是：

* 当前 Solution：Ascend 1.0 设计整理
* 当前焦点 Project：解决方案层 Project
* 当前焦点入口：正在写《41-解决方案层与工作区.md》第 9 章
* 当前相关 Project：
  * 运行规则 Project
  * 实现规划 Project
* 当前附加信息：
  * 已冻结的运行规则结论
  * 已决定的命名口径（Solution / Project / Tree / Workspace）
  * 当前 1.0 的边界

这时你就会发现，Workspace 不是“某个 Project 的详情页”，
而是：

**人当前干活时的整体上下文。**

### 9.7 这个例子里“一次只推进一个 Project”如何成立

虽然当前 Workspace 中能同时看到多个 Project，
但在这个例子里，当前真正推进的只有一个：

**解决方案层 Project**

也就是说，现在虽然：

* 运行规则 Project 存在
* 实现规划 Project 也存在

但它们此时只是背景工作面，
并不进入当前这一轮正式推进。

这一点非常重要。
因为它说明：

**多 Project 并存，不等于多 Project 同时推进。**

Workspace 承接的是：

* 当前焦点
* 其他背景对象

而不是把所有对象一起推进。

### 9.8 如果当前需要切到另一个 Project，会发生什么

假设此时你看完第 9 章之后，觉得：

“上层定义差不多了，我现在要去补《最小实现范围》。”

那会发生什么？

正确的做法不是在当前这一轮里，
直接把实现规划内容插进“解决方案层 Project”的当前推进里。

正确的做法应该是：

1. 先把当前 Project 推进到一个明确断点
2. 保存当前工作上下文
3. 显式切换焦点 Project
4. 进入“实现规划 Project”的当前入口
5. 再继续那边的推进

这个例子直接说明了：

**Project 切换必须是显式动作。**

否则 Workspace 的上下文会立刻混乱。

### 9.9 这个例子里 Round 如何存在

再往前走一步，假设现在出现这样一次变化：

“把当前单树内核整理成正式运行规则文档，并同步补出上层 Solution 层定义，最后输出下一步实现规划。”

这时，其实已经不是某一个 Project 内部的事了，
而是一轮跨 Project 变化。

那么这时就可以认为存在一个 Round，
它大致承接的是：

* 本轮目标：整理 Ascend 1.0 当前设计基础
* 涉及 Project：
  * 运行规则 Project
  * 解决方案层 Project
  * 实现规划 Project
* 本轮产出：
  * 运行规则冻结稿
  * 解决方案层文档
  * 下一步实现规划入口

这里 Round 的作用不是替代任何一个 Project，
而是把这次变化组织起来。

这个例子直接说明了：

**Round 不是 Project 内部概念，而是跨 Project 变化单位。**

### 9.10 这个例子里 Tree 处在什么位置

这个例子还可以顺手说明 Tree 的新位置。

在“运行规则 Project”内部，
你前面已经细化的那套 Node、StepRecord、Scheduler、Rescan、状态流转规则，
仍然完全成立。

所以在这个例子里：

* Solution 组织多个 Project
* Project 是一级独立工作对象
* Tree 仍然可以存在，但它已经退回到某个 Project 的内部组织结构

也就是说，Tree 没有消失，
只是它不再承担 Solution 一级单位的角色了。

### 9.11 这个例子里派生产物如何出现

再往后一步，
假设“解决方案层 Project”已经整理出稳定结果，
需要进一步产出一份：

* AI 可读的编码输入物
* 或正式实现任务拆项
* 或规则文档

那么这时，就可能出现新的独立工作面。

这时候正确的做法不是把这些全部当成当前 Project 的附录字段继续塞进去，
而是：

**如果它已经形成独立工作面，就升格为新的 Project。**

这正是“派生产物可以升格为独立 Project”的一个最小例子。

### 9.12 这个例子告诉我们的最小运行图景

如果把这个例子再压一下，可以得到一个非常清楚的最小图景：

* 有一个最终目标
  → “整理 Ascend 1.0 设计基础”
* 这个最终目标被一个 Solution 承接
  → `Ascend 1.0 设计整理`
* 这个 Solution 内有多个 Project
  → 运行规则 / 解决方案层 / 实现规划
* 人当前通过 Workspace 进入这个 Solution
  → 当前焦点是“解决方案层 Project”
* 当前只推进一个 Project
  → 其他 Project 作为背景存在
* 当一次变化跨多个 Project 时
  → 由 Round 来组织

这个最小图景，已经足以说明前面 1–8 章的主要定义并不是空概念。

### 9.13 当前 1.0 的最小例子冻结版

如果把这一章再压成一段话，可以冻结成下面这样：

> 例如，在“整理 Ascend 1.0 设计基础”这一最终目标下，可以存在一个 Solution，内部同时存在“运行规则 Project”“解决方案层 Project”“实现规划 Project”等多个独立工作面。
> 人通过 Workspace 进入该 Solution 时，当前可以聚焦其中一个 Project，例如正在编写解决方案层文档，而其他 Project 作为背景存在但不进入当前轮次。
> 如果当前变化同时影响多个 Project，则通过 Round 组织这次跨 Project 变化。
> 在每个 Project 内部，仍然可以继续采用 Tree 作为默认内部组织结构。
> 这个例子说明：Solution 承接最终目标，Project 承接独立工作面，Workspace 承接当前工作上下文，Round 承接跨 Project 变化，而 Tree 退回为 Project 的内部结构。

### 9.14 本章结论

第 9 章到这里正式冻结以下内容：

1. 最小例子的作用，是验证前面 1–8 章概念放在一起后是否仍然成立
2. 一个真实最终目标可以由一个 Solution 承接
3. 一个 Solution 内可以并存多个 Project，它们围绕同一个最终目标服务
4. Workspace 承接的是当前工作上下文，而不是某个 Project 的单独详情页
5. 在多 Project 并存的情况下，当前仍然只推进一个焦点 Project
6. Project 切换必须是显式动作
7. 当一次变化同时影响多个 Project 时，应通过 Round 组织
8. Tree 没有消失，而是退回为 Project 当前默认可采用的一种内部组织结构
9. 派生产物一旦形成独立工作面，就可以升格为新的 Project
10. 这个最小例子已经足以说明：Solution / Workspace / Project / Round / Tree 之间的当前定义可以共同成立


## 10. 本章结论

到这里为止，《解决方案层与工作区》这一份文档，正式冻结以下内容。

### 10.1 关于问题

1. 本文所说的“问题”，不是一次操作、一次提问、一个节点或一个 Project。
2. 问题指的是：**我要达成的最终目标。**
3. 这个最终目标通常跨越时间、阶段和多个独立工作面，因此不能天然被单个 Project 完整承接。

### 10.2 关于 Solution

4. Solution 是围绕同一个最终目标而存在的最上层组织容器。
5. Solution 的核心职责，不是为了组织对象而组织对象，而是为了让同一目标在多工作对象条件下仍然能够被持续推进并最终解决。
6. Solution 解决的是类似“微软解决方案”那种上层组织问题：多个独立工作对象为什么属于同一个解决过程。
7. Solution 不是更大的 Project，也不是更大的 Tree。
8. Solution 属于 **目标承接层** 。

### 10.3 关于 Project

9. Solution 内部一级单位统一称为  **Project** 。
10. Project 是围绕当前最终目标而存在的一级独立工作对象。
11. Project 的本质是独立工作面，而不是普通分类项或文件夹。
12. 只有当某项工作已经形成可单独推进、单独承接、单独沉淀的独立工作面时，它才有资格成为 Project。
13. 单个 Project 可以稳定承接局部工作，但不足以自然承接完整解决过程。

### 10.4 关于 Tree

14. Tree 不再作为 Solution 的一级单位。
15. Tree 退回为 **Project 当前默认可采用的一种内部组织结构。**
16. 当前 1.0 已经完成的大量单树运行细化，应被理解为：**Project 采用 Tree 结构时的运行规则。**
17. 当前阶段不正式展开完整的 Project 结构类型体系。

### 10.5 关于 Workspace

18. Workspace 不是新的组织层对象，而是人进入某个 Solution 后的当前工作上下文。
19. Workspace 属于 **工作上下文承接层** 。
20. Workspace 的职责不是展示，而是稳定当前干活状态。
21. Workspace 至少承接：

* 当前焦点 Project
* 当前焦点入口
* 当前相关 Project
* 当前必要附加信息

22. Workspace 不是某个 Project 的内部详情页，而是比 Project 更高一级的当前工作视图。
23. Workspace 不等于最终 UI 设计，当前只冻结语义，不展开界面。

### 10.6 关于使用原则

24. 一个 Solution 中可以并存多个 Project。
25. 但在任意一个实际推进时刻，**一次只推进一个 Project。**
26. 当前焦点必须明确，至少包括：

* 当前焦点 Project
* 当前焦点入口

27. 从一个 Project 切到另一个 Project，必须是显式动作。
28. 多个 Project 可以相关，但推进不能交错。
29. 跨 Project 协作通过 Round 组织，而实际推进仍按 Project 顺序处理。
30. Workspace 中的背景信息可以存在，但不会自动进入当前轮次。

### 10.7 关于 Round

31. Round 是跨 Project 的变化组织单位。
32. Solution 是问题空间，Round 是某一次变化。
33. Solution 不替代 Round，Round 也不替代 Solution。
34. 当前阶段只承认 Round 的存在与地位，不展开其完整生命周期、字段与实现机制。

### 10.8 关于边界

35. Solution 负责问题空间组织，不直接承接 Project 内部推进。
36. Project 负责独立工作面，不替代 Solution 做上层组织。
37. Node 是最小推进对象，仍属于 Project 内部运行层。
38. StepRecord 属于局部推进留痕，不上升为 Solution 的直接职责。
39. Scheduler 属于局部推进秩序，不属于 Solution 的直接职责。
40. 派生产物属于 Solution 的目标归属范围，但应由相应 Project 承接，而不是直接被 Solution 吞并为静态字段集合。

### 10.9 关于当前 1.0 先冻结什么

41. 当前 1.0 正式承认 Solution 层存在。

### 10.11 这一整份文档最终建立了什么

58. 它正式建立了 Ascend 从“单个 Project / 单树推进内核”向“围绕最终目标组织多个 Project 的上层结构”过渡的概念基础。

### 10.12 压缩版正式结论

如果把整份文档再压成一段正式结论，可以写成：

> Ascend 在当前阶段，已不再只被理解为单个 Project 内部的推进系统，而开始正式承认围绕同一个最终目标组织多个 Project 的 Solution 层存在。
> Solution 负责承接目标空间，Workspace 负责承接当前工作上下文，Project 负责承接独立工作面，Tree 退回为 Project 当前默认可采用的一种内部组织结构，Round 负责承接跨 Project 的变化。
> 当前 1.0 先冻结这一上层结构的最小成立条件与最小使用原则，而不提前展开完整的多 Project 编排、生命周期系统、结构类型体系与工作区 UI。
> 这样做的目的，不是为了扩张系统，而是为了让真实问题在多工作对象条件下，仍然能够被稳定组织并持续解决。

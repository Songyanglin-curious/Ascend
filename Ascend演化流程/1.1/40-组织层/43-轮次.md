## 0. 文档目标与边界

### 0.1 文档目标

本文档用于定义：**Ascend 在 Solution 层中，如何承接一次跨 Project 的变化。**

只回答两个问题：

1. 什么是 Round
2. Round 如何作为跨 Project 的变化组织单位存在

重点不是重写 Node 内部推进规则，也不是完整展开多 Project 协同，而是先正式收住：**当一个变化不再只是某个 Project 内部的事时，系统用什么单位来承接。**

### 0.2 本文档解决的问题

本文档只解决：

1. 为什么单个 Project 不足以承接真实变化
2. 为什么需要高于 Project 的变化单位
3. Round 的最小定义
4. Round 与 StepRecord 的边界
5. Round 与 Workspace 的边界
6. Round 最少应承接什么
7. Round 最少如何开始、推进、结束
8. Round 如何承接跨 Project 的顺序协同

核心关心的是：**一次跨 Project 变化如何被正式组织。**

### 0.3 本文档不解决的问题

本文档不负责：

1. Project 内部运行规则
2. Node、StepRecord、Scheduler、Rescan 的内部机制
3. 多 Project 协同的完整规则
4. Project 完整生命周期
5. Workspace 的完整 UI 与交互
6. Round 的最终字段表、完整状态机、最终存储模型
7. 自动拆 Round、并发 Round、嵌套 Round 等高级机制

### 0.4 与其他文档的边界

* 与《解决方案层与工作区》的边界：`41` 定义的是问题空间，本文定义的是变化单位。
* 与《运行规则》的边界：运行规则讨论单个 Project / Node 如何推进；本文讨论这些局部推进如何在更高层被组织成一次变化。
* 与 StepRecord 的边界：StepRecord 记录局部推进结果；Round 承接跨 Project 变化。
* 与 Workspace 的边界：Workspace 承接当前工作上下文；Round 承接当前变化本身。
* 与多 Project 协同文档的边界：本文只回答 Round 如何作为协同的最小承接单位，不展开全部协同规则。

### 0.5 当前文档的最小任务

当前阶段只做四件事：

1. 定义 Round
2. 定义 Round 与 StepRecord / Workspace / Project 的边界
3. 定义 Round 的最小组成
4. 定义 Round 的最小流程

### 0.6 写作原则

1. 先定义变化单位，再讨论变化机制
2. 先给最小可用边界，不给完整状态机
3. 先承认显式变化，不假设自动组织
4. 不回到 Node 层细节，不提前吞并协同文档

### 0.7 名词口径

* 问题：我要达成的最终目标
* Solution：围绕同一个最终目标存在的最上层组织容器
* Project：Solution 内部一级独立工作对象
* Workspace：当前干活时的工作上下文
* Round：一次跨 Project 的变化组织单位
* StepRecord：某个 Node 在某个场景下完成一轮推进后的局部沉淀记录

层级关系：

* Solution 承接目标空间
* Project 承接独立工作面
* Round 承接一次变化
* Workspace 承接当前工作上下文
* StepRecord 承接局部推进留痕

### 0.8 本章结论

本文正式冻结：本文档是 Round 的定义文档；它只解决“一次跨 Project 的变化如何被正式组织”；Round 与 StepRecord、Workspace、Project 的边界必须先成立；当前阶段先按“最小变化单位”来写，不按“完整系统”来写。

## 1. 为什么需要轮次

### 1.1 单个 Project 只能承接局部变化

Project 内部推进本身成立，但这不等于一次真实变化天然只发生在一个 Project 内。Project 解决的是某个工作面怎么继续，不天然解决：**这次变化整体影响了什么。**

### 1.2 真实变化天然跨多个 Project

更常见的情况是：

* 主 Project 结论变了
* 文档 Project 要同步调整
* 规则 Project 要同步补充
* AI 指令 Project 也要修改
* 甚至会新增派生 Project

也就是说，面对的常常不是“一个工作面继续推进”，而是：**一次变化同时影响多个工作面。**

### 1.3 没有 Round，变化会退化成散落修改

没有 Round 时，系统仍可继续改，但会逐渐说不清：

* 这次变化的边界是什么
* 哪些 Project 属于同一轮变化
* 这一轮到底产出了什么
* 下次应接哪一轮继续

结果是跨 Project 变化不会消失，只会退化成：**散落在各处、靠记忆串起来的一组修改。**

### 1.4 StepRecord 不能替代 Round

StepRecord 记录的是某个 Node 在某个场景下的一轮推进结果，足以支撑单个 Project 内部留痕，但不能回答：

* 这次变化整体影响了哪些 Project
* 这次变化整体是什么
* 这次变化当前状态是什么
* 这次变化之后从哪里继续

所以 StepRecord 解决的是更低层的问题。

### 1.5 Workspace 也不能替代 Round

Workspace 承接的是当前工作上下文，如：

* 当前焦点 Project
* 当前入口
* 当前相关 Project
* 当前附加信息

它回答的是：**我现在在什么上下文里干活。**

Round 回答的是：**这次变化作为正式变化，如何被承接。**

### 1.6 Round 的作用：让变化获得正式承接

当目标被拆成多个 Project 后，系统自然需要两种上层承接：

1. Solution：承接问题空间
2. Round：承接变化过程

Solution 回答“这些 Project 为什么属于同一个最终目标”，Round 回答“这次变化为什么属于同一轮变化”。

### 1.7 没有 Round，多 Project 协同只能依赖隐性顺序

你已经明确了一个关键原则：

* 一个 Solution 中可有多个 Project
* 一次只推进一个 Project
* 多 Project 协同通过顺序推进实现
* 不在同一轮中交错推进多个 Project

但若没有 Round，这种顺序协同会退化成隐性默认：事情在发生，但“这是一轮变化”没有被正式组织。

### 1.8 Round 的核心意义

Round 不是为了做批处理，而是为了让一次变化有边界。它至少回答：

1. 这次变化围绕什么目标发生
2. 涉及哪些 Project
3. 到哪里算结束
4. 结束后从哪里继续

### 1.9 Round 不破坏“一次只推进一个 Project”

引入 Round 并不意味着同一时刻推进多个 Project。更准确地说：

* Round 是上层组织单位
* Project 仍是当前正式推进焦点单位
* 一个 Round 中可先后涉及多个 Project
* 但任意时刻仍只有一个焦点 Project

### 1.10 当前阶段必须承认 Round

当前系统已经有：

* Solution
* Workspace
* Project
* 单点推进原则

但还没有正式概念来承接：**这次变化本身。**

所以即使暂不展开完整状态机和字段设计，Round 作为概念层也必须先成立。

### 1.11 本章结论

单个 Project 只能承接局部变化；真实变化往往跨多个 Project；没有 Round 时变化会退化成散落修改；StepRecord 和 Workspace 都不能替代变化单位；Solution 承接问题空间，Round 承接变化过程；Round 的核心意义是让变化获得明确边界；它不会破坏“一次只推进一个 Project”的原则，反而让这条原则更稳。

## 2. Round 的最小定义

### 2.1 Round 是高于 Project 的变化单位

Round 首先应被理解为：

**围绕同一个最终目标而发生的一次跨 Project 变化组织单位。**

它不是某个 Project 内部的一轮，也不是模糊的阶段感，而是一次正式变化单位。它承接的不是某个 Node 的本轮推进，也不是某个 Project 的单次局部修改，而是：**一组围绕同一目标、在本次变化中彼此相关的 Project 级变化。**

### 2.2 Round 回答“这次变化是什么”

* 问题回答：最终要达成什么
* Solution 回答：目标的问题空间是什么
* Project 回答：有哪些独立工作面
* Round 回答：**这一次变化本身是什么**

所以 Round 不是问题本身，也不是目标空间本身，而是推进过程中的某一次正式变化承接单位。

### 2.3 Round 的职责不是推进内容，而是组织变化

Round 不直接替代：

* Node 推进
* Project 内部运行
* Scheduler 选节点
* StepRecord 留痕

它真正承接的是：

* 本次变化的边界
* 涉及哪些 Project
* 当前处在哪个阶段
* 结束后下一步怎么继续

所以它首先是 **变化承接对象** ，不是内容执行对象。

### 2.4 最小定义

> **Round 是围绕同一个最终目标而存在的一次跨 Project 变化组织单位，用于承接本次变化涉及的工作面、变化边界、当前状态与后续入口。**

关键词有四个：

* 一次：它不是长期目标空间，而是某一次正式变化
* 跨 Project：它站在高于单个 Project 的层级
* 变化组织单位：它组织变化，而不替内容执行
* 后续入口：它不仅描述这次变化，还承接下一步从哪继续

### 2.5 Round 和 Project 的关系

两者不是包含或替代关系：

* Project 承接工作对象
* Round 承接本次变化如何作用于这些工作对象

Project 是对象维度，Round 是变化维度。

### 2.6 Round 和 StepRecord 的关系

* StepRecord 记录某个 Node 在某个场景下一轮推进后的结果
* Round 记录本次变化整体涉及哪些 Project、推动了什么、当前处在哪

所以：

* StepRecord 是局部推进留痕
* Round 是跨 Project 变化承接

一个 Round 可关联很多 StepRecord，但它不等于这些痕迹的堆叠。

### 2.7 Round 和 Workspace 的关系

* Workspace 承接当前干活的上下文
* Round 承接当前这次变化本身

所以：

* Workspace 让人知道“现在在哪个上下文里工作”
* Round 让系统知道“当前这次变化是什么”

Workspace 可承接当前 Round 的相关信息，但不等于 Round；Round 也不等于当前工作视图。

### 2.8 Round 的最小职责

当前阶段先收成四条：

1. 承接本次变化的目标边界
2. 承接本次变化涉及的 Project 范围
3. 承接本次变化的当前状态
4. 承接本次变化结束后的下一步入口

### 2.9 Round 的最小成立条件

不是任何修改集合都值得叫 Round。它至少应满足：

1. 围绕同一个当前变化目标
2. 涉及至少一个明确工作对象
3. 具有可继续承接的意义

否则它只是临时操作痕迹。

### 2.10 Round 的最小骨架

当前 1.0 先冻结为四块：

1. 本轮变化目标
2. 本轮涉及的 Project
3. 本轮当前状态
4. 本轮结束后的下一步入口

### 2.11 Round 当前不是什么

当前阶段，Round 不是：

* 最终目标本身
* Solution 本身
* Project 本身
* 某个 Node 的一轮推进
* StepRecord 的上位同义词
* Workspace 的别名
* 完整任务系统
* 自动调度器

一句话：**Round 是变化单位，不是万能容器。**

### 2.12 最小冻结版

> Round 是围绕同一个最终目标而存在的一次跨 Project 变化组织单位。它不替代 Project 内部推进，而是承接本次变化的目标边界、涉及的 Project 范围、当前状态与下一步入口。它不是问题、Solution、Project、StepRecord 或 Workspace 的同义词，而属于变化承接层。

### 2.13 本章结论

Round 是一次跨 Project 的变化组织单位；它承接的是“这次变化是什么”；核心职责不是推进内容，而是组织变化；其最小骨架是变化目标、涉及 Project、当前状态、下一步入口；它与 Project、StepRecord、Workspace 均为不同层级对象；当前已可作为正式概念成立。

## 3. Round 与 StepRecord 的边界

### 3.1 这一章解决什么

Round 和 StepRecord 都与“变化”和“记录”有关，因此容易混。但它们承接的不是同一层级的变化。这一章只回答：StepRecord 记录什么、Round 记录什么、为什么谁也不能替代谁。

### 3.2 StepRecord 记录局部推进沉淀

StepRecord 记录的是：**某个 Node 在某个场景下完成一轮推进后的结果。**

它的特征是：

* 依附于 Node
* 依附于某一轮局部推进
* 记录局部输入、输出、变化和下一步入口
* 属于局部推进留痕

它回答的是：**这个 Node 这一轮发生了什么。**

### 3.3 Round 记录跨 Project 变化整体

Round 记录的不是某个 Node 的一轮推进，而是：**一次跨 Project 变化整体是什么。**

它的特征是：

* 不依附于单个 Node
* 不依附于单个局部推进
* 承接本次变化涉及的 Project、边界、状态和下一步入口
* 属于变化组织层

它回答的是：**这次变化整体是什么。**

### 3.4 核心差异在层级，不在大小

与其说 StepRecord 小、Round 大，不如说：

* StepRecord 位于 Node 内部推进层、局部沉淀层
* Round 位于 Project 之上的变化组织层、跨 Project 承接层

Round 不是“大一点的 StepRecord”，StepRecord 也不是“小一点的 Round”。

### 3.5 一个回答“局部这轮”，一个回答“整体这次”

* StepRecord：这个 Node 这一轮怎么样了
* Round：这次变化整体怎么样了

某个分析 Project 中某个 Node 形成一条 StepRecord，只说明该 Node 的一轮推进成立，并不自动说明：

* 本次跨 Project 变化已经成立
* 变化已经结束
* 涉及哪些其他 Project
* 下一步应转向哪里

这些仍需要 Round 承接。

### 3.6 一个 Round 可关联多个 StepRecord，但不等于它们的集合

一个 Round 中当然可能出现很多局部推进，因此：

**一个 Round 可以关联多个 StepRecord。**

但不能推出：

**Round = 多个 StepRecord 的集合。**

因为 StepRecord 只告诉你各个局部推进分别发生了什么，而 Round 还要告诉你：

* 为什么这些局部推进属于同一轮变化
* 这次变化整体边界是什么
* 当前状态是什么
* 之后从哪里继续

Round 多出来的是：**变化整体的组织语义。**

### 3.7 StepRecord 为什么不能替代 Round

即使收集了很多 StepRecord，你仍可能说不清：

* 为什么这些记录属于同一次变化
* 这次变化的开始边界在哪里
* 结束边界在哪里
* 各记录在整体变化中处于什么位置

所以 StepRecord 有留痕能力，但没有变化组织能力。

### 3.8 Round 也不能替代 StepRecord

反过来也不能因为 StepRecord 不够，就让 Round 吞掉局部推进。否则 Round 会变成巨大的混合物，既要记局部输入输出，又要记整体变化，最终导致：

* Round 过重
* 局部粒度被污染
* Node 层沉淀失去独立性
* 已冻结的运行规则被反向破坏

所以局部推进留痕仍必须由 StepRecord 承接。

### 3.9 更准确的关系

* StepRecord = 局部沉淀
* Round = 变化承接

### 3.10 从记录对象看差异

* StepRecord 的对象：Node、场景、局部轮次
* Round 的对象：当前变化、涉及 Project、整体边界、后续入口

StepRecord 面对的是“推进对象的一轮”，Round 面对的是“变化本身”。

### 3.11 从恢复与继续看差异

* StepRecord 支持局部恢复：某个 Node 上一轮做到哪、留下了什么、局部下一步怎么接
* Round 支持整体变化恢复：当前变化在干什么、涉及了哪些 Project、边界是什么、下一次变化从哪里接

### 3.12 最小冻结版

> StepRecord 记录某个 Node 在某个场景下完成一轮推进后的局部沉淀；Round 记录围绕同一个最终目标而发生的一次跨 Project 变化的整体承接。一个 Round 可以关联多个 StepRecord，但不等于多个 StepRecord 的集合。StepRecord 负责局部推进留痕，Round 负责变化整体组织，两者相关但不可互相替代。

### 3.13 本章结论

StepRecord 记录局部推进沉淀，Round 记录整体变化承接；两者差异在层级，不只是大小；一个回答局部这轮，一个回答整体这次；一个 Round 可关联多个 StepRecord，但不等于它们的集合；StepRecord 不能替代 Round，Round 也不能吞并 StepRecord。

## 4. Round 的最小组成

### 4.1 本章目标

当前阶段不急着进入完整字段表、状态机和存储模型，但如果连最小组成都说不清，Round 仍只是抽象词。本章只回答：Round 最少必须承接什么。

### 4.2 最小组成是变化骨架，不是对象堆叠

Round 的最小组成不应先理解成“有几个字段”，而应理解成：**一轮变化至少要能回答哪几类问题。**

当前建议冻结为四块：

1. 本轮变化目标
2. 本轮涉及的 Project 范围
3. 本轮当前状态
4. 本轮结束后的下一步入口

### 4.3 本轮变化目标

Round 必须回答：**这次变化到底在干什么。**

这里承接的不是最终目标本身，而是最终目标在这一次变化中的具体推进目标。没有这一层，Round 会退化成模糊修改集合。

### 4.4 本轮涉及的 Project 范围

Round 还必须回答：**这次变化涉及哪些 Project。**

至少应能区分：

* 本轮正式涉及的 Project
* 当前存在但不属于本轮范围的其他 Project

这是 Round 高于单个 Project 的核心原因。

### 4.5 本轮当前状态

Round 不能只是变化标签，它还必须回答：**这次变化当前走到哪了。**

这里的状态不是 Node 的局部状态，也不是 Project 内部运行状态，而是变化作为变化单位所处的位置。

### 4.6 本轮结束后的下一步入口

Round 不只描述“这一轮发生了什么”，还必须承接：**这轮结束后从哪里继续。**

这与 StepRecord 都有 next，但层级不同：StepRecord 是局部下一步，Round 是整体变化下一步。

### 4.7 为什么暂不独立展开“完整产出列表”

“本轮产出了什么”当然重要，但当前阶段先不将其列为独立核心组成，因为：

1. 产出可先被包含在变化状态与后续入口中
2. 一旦独立展开，Round 会迅速膨胀成更细的设计层

### 4.8 为什么暂不独立展开“完整参与顺序”

当前阶段 Round 先要解决的是“本轮变化是什么”，不是“本轮内部具体先后顺序怎么排”。顺序更适合在流程和协同章节讨论。

### 4.9 四部分共同回答什么

* 变化目标：这轮在干什么
* Project 范围：这轮作用于哪些工作面
* 当前状态：这轮走到哪了
* 下一步入口：这轮之后从哪继续

四块组合起来后，Round 已足以承接目标、范围、过程位置和接续。

### 4.10 缺任一块会怎样

* 缺目标：退化成修改集合
* 缺范围：失去跨 Project 语义
* 缺状态：只能说明“存在过”，不能说明“现在在哪”
* 缺下一步入口：只能描述过去，不能承接继续

### 4.11 最小冻结版

> 当前 1.0 中，一个 Round 至少应承接四类内容：本轮变化目标、本轮涉及的 Project 范围、本轮当前状态、本轮结束后的下一步入口。这四部分共同构成 Round 的最小变化骨架。当前阶段不要求完整产出体系、完整参与顺序、完整字段表和完整状态机。

### 4.12 本章结论

Round 的最小组成首先是语义骨架；当前冻结为变化目标、Project 范围、当前状态、下一步入口；当前阶段暂不要求独立展开完整产出体系与完整参与顺序；只要这四块成立，Round 作为变化单位就已成立。

## 5. Round 的最小流程

### 5.1 本章目标

只有“定义”和“组成”还不够，还需要知道：一次 Round 从哪里开始，中间怎么承接变化，什么时候算结束，结束后怎么继续。本章只压出最小可用流程，不展开完整状态机。

### 5.2 最小流程判断

当前建议先压成 5 步：

1. 形成本轮变化目标
2. 确定本轮涉及的 Project 范围
3. 进入本轮焦点 Project 推进
4. 必要时顺序切换到其他相关 Project
5. 形成本轮断点或本轮结束，并给出下一步入口

### 5.3 第一步：形成本轮变化目标

Round 不能从“我先改着看”开始，必须先回答：**这轮变化到底要推动什么。**

### 5.4 第二步：确定本轮涉及的 Project 范围

在一个 Solution 中，很多 Project 可能都与当前目标有关，但不代表都应纳入本轮。所以要先区分：

* 本轮正式涉及的 Project
* 只作为背景存在的其他 Project

### 5.5 第三步：进入本轮焦点 Project 推进

虽然一个 Round 可涉及多个 Project，但你已经冻结了关键原则：**一次只推进一个 Project。**

因此，Round 确定范围后，必须落到某个当前焦点 Project 上推进。Round 承接变化，真正发生推进的仍是具体 Project。

### 5.6 第四步：必要时顺序切换到其他相关 Project

如果本轮涉及多个 Project，正确做法不是并发或交错推进，而是：

* 当前焦点 Project 形成明确断点
* 再显式切换到下一个相关 Project

这一步强调三点：

1. 切换必须显式
2. 切换必须顺序发生
3. 切换必须以本轮变化为上层依据

### 5.7 第五步：形成本轮断点或本轮结束，并给出下一步入口

Round 最终必须停在一个可承接的位置，结局有两种：

* 形成本轮断点：暂时停住，但后续可继续承接
* 本轮结束：当前变化完成，下一步进入新 Round 或新工作入口

无论哪种，都必须留下：**下一步从哪里接。**

### 5.8 为什么当前不写“自动创建 Round”

当前阶段 Round 先按显式变化单位来写，不引入自动识别开始、自动归并修改、自动补齐目标等机制，否则会过早滑向自动编排。

### 5.9 为什么当前不写“完整状态流转”

现在更重要的是先把 Round 的动作流程收住，而不是先把完整状态体系展开。所以只写最小流程，不写完整状态机。

### 5.10 与 Project 内部推进流程的关系

* Project 内部推进流程解决：Node 怎么推进、一轮怎么完成与沉淀
* Round 流程解决：一次变化怎么开始、涉及哪些 Project、怎样顺序纳入、最后停在哪个断点

所以：

* Round 流程是上层变化流程
* Project 流程是下层内容推进流程

### 5.11 最短顺序图

1. 明确本轮变化目标
2. 确定本轮涉及的 Project
3. 选定当前焦点 Project
4. 在该 Project 内执行当前推进
5. 如有必要，在形成断点后显式切换到下一个相关 Project
6. 当本轮形成整体断点或整体结束时，给出下一步入口

### 5.12 最小冻结版

> 当前 1.0 中，一个 Round 的最小流程为：先形成本轮变化目标，再确定本轮涉及的 Project 范围，然后进入当前焦点 Project 推进；若涉及多个 Project，则在当前 Project 形成明确断点后顺序切换到其他相关 Project；最终，当本轮形成整体断点或整体结束时，必须给出下一步入口。在此过程中，一个 Round 可以顺序涉及多个 Project，但任意实际推进时刻仍只推进一个 Project。

### 5.13 本章结论

当前阶段，Round 的最小流程冻结为目标形成、范围确定、焦点推进、必要时顺序切换、形成断点或结束并给出下一步入口；一个 Round 必须先有目标和范围；跨 Project 推进必须顺序发生；Project 切换必须显式；Round 流程是上层变化流程，不替代 Project 内部推进流程。

## 6. Round 与 Workspace 的关系

### 6.1 本章问题

Round 和 Workspace 都与“当前这次工作”有关，因此容易被误认为是一回事。但它们承接的对象不同。

### 6.2 Workspace 承接当前工作上下文

Workspace 是人进入某个 Solution 后当前干活时所处的工作上下文，至少承接：

* 当前焦点 Project
* 当前焦点入口
* 当前相关 Project
* 当前必要附加信息

它回答的是：**我现在在什么上下文里继续工作。**

### 6.3 Round 承接当前这次变化本身

Round 承接的是：

* 本轮变化目标
* 本轮涉及的 Project
* 本轮当前状态
* 本轮结束后的下一步入口

它回答的是：**这次变化作为一次正式变化，现在是什么。**

### 6.4 核心差异：承接对象不同

* Workspace 承接的是当前工作上下文
* Round 承接的是当前变化单位

更直白地说：

* Workspace 的对象是“当前怎么工作”
* Round 的对象是“当前这次变化是什么”

### 6.5 为什么它们会强关联

人之所以进入某个 Workspace，往往正因为当前有一轮变化正在推进；反过来，一次 Round 也总要落在某个 Workspace 中被实际工作承接。

所以：

* Round 提供变化承接
* Workspace 提供工作承接

### 6.6 Workspace 可承接 Round 相关信息，但不等于 Round

Workspace 当然可以挂着当前 Round 的信息，如：

* 当前承接哪个 Round
* 当前 Round 的目标
* 当前 Round 涉及哪些 Project
* 当前推进到哪一段

但这不等于 Workspace 就等于 Round。更准确地说：

* Round 是被承接的变化对象
* Workspace 是对该变化对象的当前工作视图

### 6.7 没有 Workspace，Round 仍成立

即使暂时没有 Workspace，你仍可承认：

* 存在一个 Solution
* 存在多个 Project
* 存在一次跨 Project 的正式变化
* 这次变化有目标、范围、状态、下一步入口

说明 Round 先是变化组织单位，而不是工作视图对象。

### 6.8 没有 Round，Workspace 也能存在，但会缺关键承接

即使不承认 Round，Workspace 仍可承接当前焦点、入口和背景。但它会失去一层关键内容：**当前这次变化本身。**

### 6.9 更准确的关系

* Round = 变化承接
* Workspace = 工作承接

### 6.10 最小例子

假设一个 Solution 为“整理 Ascend 1.0 的正式设计基础”，其中有三个 Project：

* 运行规则 Project
* 解决方案层 Project
* 实现规划 Project

当前发生一轮变化：

* 补齐解决方案层定义
* 同步校正运行规则口径
* 准备后续实现规划入口

此时：

* Round 承接的是这次变化的目标、范围、状态和下一步
* Workspace 承接的是当前焦点在哪个 Project、当前入口在哪、需要带哪些背景继续

这说明：

* Round 承接的是变化
* Workspace 承接的是工作上下文

### 6.11 两者不能互相替代

* Workspace 不能替代 Round，因为它只能告诉你现在在哪里工作，不能正式承接这次变化整体是什么
* Round 不能替代 Workspace，因为它不能告诉你当前具体看哪个 Project、从哪个入口继续、带哪些背景信息工作

### 6.12 最小冻结版

> Workspace 承接当前干活时的工作上下文，Round 承接当前这次变化本身。Workspace 可以承接当前 Round 的相关信息，但不等于 Round；Round 也不等于当前工作视图。两者分别属于工作承接层和变化承接层，彼此关联，但不能互相替代。

### 6.13 本章结论

Workspace 承接工作上下文，Round 承接变化本身；两者都与“当前”有关，但承接对象不同；Workspace 是使用层概念，Round 是变化层概念；Workspace 可挂着 Round，但不等于 Round；Round 与 Workspace 相互关联，但不可互相替代。

## 7. Round 与多 Project 协同的关系

### 7.1 多 Project 协同一定会出现

只要一个最终目标由多个 Project 共同承接，多 Project 协同就必然出现。问题不在于“有没有协同”，而在于：**协同如何被正式组织。**

### 7.2 没有 Round，协同会退化成隐性顺序

没有 Round 时，多 Project 当然仍可协同，但这种协同会退化成：

* 靠记忆维持的顺序
* 靠上下文暂时串起来的动作链
* 没有边界的一组相关修改

Round 的价值就在于把这种隐性协同变成显性变化组织。

### 7.3 Round 不是协同本身，而是协同的组织单位

更准确地说：

* 协同回答：多个 Project 如何围绕同一个目标互相作用
* Round 回答：当前这一次协同变化如何被承接

协同是内容，Round 是容器。Round 不等于整个多 Project 协同系统。

### 7.4 Round 承接“本轮协同”，不承接“所有协同规则”

一个 Solution 中，Project 之间可能长期存在很多关系。但 Round 承接的不是所有长期关系，而是：**这些关系在当前这一轮变化中如何被实际触发。**

所以：

* 长期协同关系 ≠ 某个 Round
* 某个 Round 只承接当前这次协同变化

### 7.5 协同第一原则：一次只推进一个 Project

一个 Round 可以涉及多个 Project，但任意实际推进时刻，仍然只推进一个 Project。这条原则把多 Project 协同从“并发乱跑”拉回到：**顺序协同。**

### 7.6 协同第二原则：通过顺序推进实现，不通过交错推进实现

正确方式是：

1. 当前焦点落在某个 Project
2. 在该 Project 中推进到明确断点
3. 如有必要，再显式切换到下一个相关 Project
4. 继续本轮变化

### 7.7 协同第三原则：长期关系不会自动进入当前 Round

某两个 Project 长期相关，不等于当前 Round 必须同时处理它们。只有当前变化明确涉及它们时，它们才进入本轮范围。

### 7.8 Round 在协同中的核心作用

Round 的作用可以压成一句话：

**Round 让多 Project 协同从“相关”变成“本轮正式变化”。**

至少体现在三点：

1. 圈出本轮协同范围
2. 组织本轮协同焦点与顺序
3. 把本轮协同结果接到下一轮

### 7.9 最小例子

假设当前有一个 Solution，承接目标“整理 Ascend 1.0 的正式设计基础”，其中有三个 Project：

* 运行规则 Project
* 解决方案层 Project
* 实现规划 Project

现发生一轮变化：

* 先补齐解决方案层定义
* 再同步修正运行规则口径
* 最后明确实现规划入口

此时：

* 协同关系：三个 Project 共同服务于同一目标，当前需顺序配合
* Round 的作用：把这次变化正式承接起来，明确涉及哪些 Project、当前焦点在哪、下一步切到哪里、结束后如何继续
* 实际推进方式：不是并发，而是先后顺序推进

### 7.10 Round 不能取代完整协同文档

本文只写到“Round 在协同中的角色”，不替代后续完整协同文档。后续仍需讨论关系类型、派生产物、长期依赖与当前变化的区分、不同生命周期 Project 如何协同等问题。

### 7.11 最小冻结版

> 多 Project 协同是 Solution 成立后的自然结果，而 Round 是承接本轮协同变化的正式单位。Round 不等于协同本身，而是把当前这次协同变化的范围、焦点、顺序与后续入口正式组织起来。在当前 1.0 中，一个 Round 可以涉及多个 Project，但任意一个实际推进时刻仍只推进一个 Project；多个 Project 的协同通过顺序推进实现，而不通过交错并发推进实现。

### 7.12 本章结论

多 Project 协同是 Solution 成立后的自然结果；没有 Round 时协同会退化成隐性顺序；Round 不是协同本身，而是承接本轮协同变化的组织单位；当前阶段协同通过顺序推进实现，且一次仍只推进一个 Project；长期相关关系不会自动进入当前 Round。

## 10. 最小例子

### 10.2 例子的目标

**整理 Ascend 1.0 当前的正式设计基础，并把“解决方案层”与“实现入口”同步接起来。**

这个最终目标不属于某一个 Round，而属于更上层的 Solution。Round 只承接围绕这个目标发生的某一次正式变化。

### 10.3 这个例子里的 Solution

可以有一个 Solution：

**Ascend 1.0 设计整理**

* 当前 Solution：Ascend 1.0 设计整理
* 当前焦点 Project：解决方案层 Project
* 当前焦点入口：正在编写《43-轮次.md》
* 当前相关 Project：运行规则 Project、实现规划 Project
* 当前附加信息：已冻结命名口径、运行规则结论、1.0 边界与未展开项

这回答的是：**我现在在什么上下文里继续干活。**

### 10.6 这个例子里的 Round

假设发生这样一轮变化：

* 先补齐《43-轮次.md》的核心章节
* 再确认它和《41-解决方案层与工作区.md》的边界关系
* 最后给后续实现规划 Project 留出明确入口

这时形成一个 Round，例如：

**整理并冻结 Solution 层之后的轮次定义**

它不等于 Solution，也不等于 Workspace，更不等于某条 StepRecord，而是：**这次跨 Project 变化的正式承接单位。**

### 10.7 这个例子里 Round 的最小骨架如何成立

1. 本轮变化目标
   补齐 Round 定义，并把它和 Solution 层、运行规则、实现规划之间的关系正式接起来。
2. 本轮涉及的 Project 范围
   可能包括解决方案层 Project、运行规则 Project、实现规划 Project。
3. 本轮当前状态
   例如：正在定义轮次，尚未完全收口，还需补后续实现入口。
4. 本轮结束后的下一步入口
   例如：进入《44-Project 的生命周期.md》，或回到实现规划 Project，或继续补《45-多Project协同与派生产物.md》。

这说明 Round 的四块最小骨架都可成立。

### 10.8 这个例子里 StepRecord 在哪里

在这轮变化过程中，某个具体 Project 内当然还会发生局部推进，例如某个 Node 在“轮次定义”“边界校正”“实现入口整理”等场景下完成一轮推进，并形成 StepRecord。

所以：

* StepRecord 仍然存在
* 仍然负责局部推进留痕
* 可能都与当前 Round 有关

但这不意味着 Round 等于这些 StepRecord 的总和，因为 StepRecord 不能说明：为什么这些局部推进属于同一轮变化，以及本轮整体下一步怎么继续。

### 10.9 这个例子里 Workspace 和 Round 的区别

* Workspace 回答：我现在怎么继续干活
* Round 回答：这次变化本身是什么

所以两者都出现，但职责不同。

### 10.10 这个例子里“一次只推进一个 Project”如何成立

虽然这一轮变化涉及多个 Project，但任意实际推进时刻，焦点仍然只有一个。例如：

* 现在先写《43-轮次.md》
* 写到明确断点后
* 再去补实现规划 Project
* 或再回头校正运行规则 Project

这说明：

* 一个 Round 可涉及多个 Project
* 但一次仍只推进一个 Project

### 10.11 如果没有 Round，这个例子会怎样

没有 Round，你当然仍可继续工作，但很快就会说不清：

* 为什么这一组动作属于同一次变化
* 哪些 Project 是这轮正式涉及的
* 这轮从哪里开始
* 结束后应怎么接

这说明没有 Round 时，系统对“这次变化”的正式承接会缺失。

### 10.12 最小图景

* 有一个最终目标 → 整理 Ascend 1.0 的正式设计基础
* 这个目标被一个 Solution 承接 → Ascend 1.0 设计整理
* 这个 Solution 内有多个 Project → 运行规则 / 解决方案层 / 实现规划
* 人通过 Workspace 进入这个 Solution → 当前焦点落在解决方案层 Project
* 当前正在发生一轮变化 → 补齐并冻结 Round 定义
* 这轮变化由 Round 正式承接 → 目标、涉及 Project、当前状态、下一步入口
* 任意时刻仍只推进一个焦点 Project

这说明：**Round 在上层结构中已获得明确位置。**

### 10.13 最小冻结版

> 例如，在“整理 Ascend 1.0 设计基础”这一最终目标下，可以存在一个 Solution，内部同时存在“运行规则 Project”“解决方案层 Project”“实现规划 Project”等多个独立工作面。人通过 Workspace 进入该 Solution 时，当前可聚焦其中一个 Project，而其他 Project 作为背景存在。当这一轮变化不仅涉及当前文档本身，还涉及与运行规则和实现规划的关系时，就形成了一个 Round。这个 Round 承接的是本轮变化的目标、涉及的 Project、当前状态与下一步入口；局部写作推进仍由 StepRecord 承接。于是 Solution 承接最终目标，Workspace 承接当前工作上下文，Project 承接独立工作面，Round 承接跨 Project 变化，StepRecord 承接局部推进留痕，各层边界保持清晰。

### 10.14 本章结论

最小例子证明：Round 放进完整上层结构后仍然成立；一个最终目标可由一个 Solution 承接，内部可存在多个 Project；Workspace 承接工作上下文；当一次变化同时涉及多个 Project 时，就可形成一个 Round；Round 的四块最小骨架在例子中都成立；StepRecord 仍负责局部留痕；一个 Round 可涉及多个 Project，但任意时刻仍只推进一个焦点 Project。

## 11. 本章结论

到这里，《轮次》正式建立以下内容：

### 11.1 关于 Round 的定位

Round 不是问题本身、不是最终目标本身、不是 Solution、不是 Project，也不是 StepRecord 或 Workspace 的同义词。Round 是：**围绕同一个最终目标而存在的一次跨 Project 变化组织单位。** 它属于变化承接层。

### 11.2 关于为什么需要 Round

单个 Project 只能承接局部变化；真实变化天然会同时影响多个 Project；没有 Round，跨 Project 变化会退化成散落修改；Round 的意义不是让系统更复杂，而是让变化获得正式承接和明确边界。

### 11.3 关于最小定义

Round 的最小定义已经成立：它承接本次变化涉及的工作面、变化边界、当前状态与后续入口。它回答的是：**这次变化整体是什么。**

### 11.4 关于最小骨架

当前 1.0 中，Round 的最小骨架冻结为：

* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮结束后的下一步入口

只要这四块成立，Round 就已可作为正式变化单位成立。

### 11.5 关于最小流程

当前 1.0 中，Round 的最小流程冻结为：

* 形成本轮变化目标
* 确定本轮涉及的 Project 范围
* 进入本轮焦点 Project 推进
* 必要时顺序切换到其他相关 Project
* 形成本轮断点或本轮结束，并给出下一步入口

### 11.6 关于 Round 与 StepRecord 的边界

StepRecord 记录局部推进沉淀；Round 记录跨 Project 变化整体承接；两者差异在层级而不只在大小；一个 Round 可关联多个 StepRecord，但不等于其集合；谁也不能替代谁。

### 11.7 关于 Round 与 Workspace 的边界

Workspace 承接当前工作上下文；Round 承接当前变化本身；Workspace 可挂着 Round，但不等于 Round；Round 也不等于当前工作视图。更准确地说：Round 负责变化承接，Workspace 负责工作承接。

### 11.8 关于 Round 与多 Project 协同

多 Project 协同是 Solution 成立后的自然结果；没有 Round，协同会退化成隐性顺序；Round 承接的是本轮协同变化，而不是所有协同规则；一个 Round 可涉及多个 Project，但任意时刻仍只推进一个焦点 Project；协同通过顺序推进实现。

### 11.9 关于当前 1.0 先冻结什么

当前 1.0 已正式承认 Round 存在，并冻结其最小定义、最小骨架、最小流程，以及它与 StepRecord、Workspace、多 Project 协同的边界；同时冻结“一次只推进一个 Project，协同通过顺序推进实现”；当前先按显式变化单位来写，先解决成立问题。

### 11.10 关于当前 1.0 暂不展开什么

当前 1.0 暂不展开 Round 的完整状态机、字段、存储、自动创建、自动结束与拆分、多 Round 并发、嵌套、跨 Solution、与派生产物系统的深度联动、自动优先级与自动路由，以及完整实现模型；这些问题都存在且重要，但当前只做记录。

### 11.11 关于最小例子的验证

最小例子已证明：Round 放进完整上层结构后仍然成立；当一次变化同时涉及多个 Project 时，Round 作为变化承接层是必要的；StepRecord 仍负责局部推进留痕；Workspace 仍负责工作上下文；一个 Round 可涉及多个 Project，但任意时刻仍只推进一个焦点 Project。

### 11.12 这份文档最终建立了什么

它正式建立了 Ascend 上层结构中的 **变化承接层** 。它没有推翻前面的单树推进规则，而是在其之上补上了“跨 Project 的变化如何被组织”这一层；它让 Solution、Workspace、Project、Round、StepRecord 之间获得稳定边界，并为后续的生命周期文档、协同文档和实现设计文档提供正式上游输入。

### 11.13 压缩版正式结论

> Ascend 在当前阶段，已正式承认 Round 作为围绕同一个最终目标而存在的一次跨 Project 变化组织单位。Round 不替代 Project 内部推进，也不替代 StepRecord、Workspace 或多 Project 协同规则本身；它承接的是这次变化的目标、范围、状态与后续入口。在当前 1.0 中，一个 Round 可以涉及多个 Project，但任意一个实际推进时刻仍然只推进一个焦点 Project；跨 Project 的协同通过 Round 组织，并通过顺序推进实现。当前阶段，Round 已以最小正确形态成立，但暂不展开其完整状态机、完整对象模型与自动组织机制。

## 0. 文档目标与边界

### 0.1 文档目标

本文档用于定义  **Ascend 在 Solution 层中，如何承接一次跨 Project 的变化** 。

更具体地说，这份文档只回答两个问题：

1. **什么是 Round**
2. **Round 如何作为跨 Project 的变化组织单位存在**

这份文档的重点，不是重新定义 Node 内部如何推进，也不是完整展开多 Project 协同机制，

而是先把“当一个变化不再只是某个 Project 内部的事时，系统用什么单位来承接”正式收住。

### 0.2 本文档要解决的问题

本文档只解决以下问题：

1. 为什么单个 Project 内部推进不足以承接一次真实变化
2. 为什么需要一个高于 Project 的变化组织单位
3. Round 的最小定义是什么
4. Round 和 StepRecord 的边界是什么
5. Round 和 Workspace 的边界是什么
6. 一个 Round 最小应承接哪些内容
7. 一个 Round 最小如何开始、推进和结束
8. Round 如何承接跨 Project 的顺序协同

也就是说，这份文档关心的是：

**一次跨 Project 变化如何被正式组织。**

### 0.3 本文档不解决的问题

本文档不负责以下内容：

1. 不重新定义 Project 内部的运行规则
2. 不展开 Node、StepRecord、Scheduler、Rescan 的内部机制
3. 不完整展开多 Project 协同的全部规则
4. 不完整展开 Project 生命周期
5. 不完整展开 Workspace 的 UI 与交互
6. 不定义 Round 的最终字段表、完整状态机和最终存储模型
7. 不讨论自动拆 Round、并发 Round、嵌套 Round 等高级机制

这些内容分别属于其他文档：

* Project 内部运行 → `运行规则.md`
* 上层目标容器与工作上下文 → `41-解决方案层与工作区.md`
* Project 生命周期 → `44-Project 的生命周期.md`
* 多 Project 协同与派生产物 → `45-多Project协同与派生产物.md`

### 0.4 本文档与其他文档的边界

#### 0.4.1 与《解决方案层与工作区》的边界

《解决方案层与工作区》回答的是：

* Solution 是什么
* Workspace 是什么
* Project 是什么
* 当前如何在多 Project 并存时工作

而本文档回答的是：

**当一次变化跨越多个 Project 时，用什么单位来组织它。**

也就是说：

* `41` 定义的是“空间”
* `43` 定义的是“变化单位”

#### 0.4.2 与《运行规则》的边界

《运行规则》回答的是：

* 一个 Node 如何推进
* 一轮如何完成
* StepRecord 如何生成
* 条件动作如何触发

这些都属于单个 Project 内部、乃至 Node 层的推进语义。

本文档不重新讨论这些内容，而只讨论：

**这些局部推进如何在更高层被组织成一次变化。**

#### 0.4.3 与 StepRecord 的边界

StepRecord 记录的是：

* 某个 Node 在某个场景下完成一轮推进后的结果

而 Round 要解决的不是“一个 Node 这轮发生了什么”，

而是：

**这一次跨 Project 的变化整体是什么。**

因此，StepRecord 是局部推进记录，Round 是跨 Project 变化单位。

两者相关，但不是一个层级的东西。

#### 0.4.4 与 Workspace 的边界

Workspace 承接的是：

**当前干活时的工作上下文。**

而 Round 承接的是：

**当前这次变化本身。**

所以：

* Workspace 解决“现在怎么继续工作”
* Round 解决“这次变化怎么被组织”

它们会互相引用，但不能写成同一个概念。

#### 0.4.5 与多 Project 协同文档的边界

多 Project 协同文档会更完整讨论：

* Project 之间如何顺序协作
* 派生产物如何出现
* 协同关系如何被理解

而本文档只先回答：

**Round 如何作为多 Project 协同的最小承接单位存在。**

也就是说，本文档触及协同，但不展开全部协同规则。

### 0.5 当前文档的最小任务

在 1.0 当前阶段，这份文档的最小任务只有四个：

1. 定义 Round 是什么
2. 定义 Round 与 StepRecord / Workspace / Project 的边界
3. 定义 Round 的最小组成
4. 定义 Round 的最小流程

只要这四件事写清，后面的多 Project 协同和实现规划就有了稳定上游输入。

### 0.6 当前文档的写作原则

本文档遵守以下原则：

1. **先定义变化单位，再讨论变化机制**

   先回答 Round 是什么，不急着讨论 Round 的高级玩法。

1. **先给最小可用边界，不给完整状态机**

   当前目标是让 Round 成立，不是把 Round 一次写成完整子系统。

1. **先承认显式变化，不假设自动组织**

   当前阶段优先把 Round 写成可理解、可承接、可实现的显式变化单位。

1. **不回到 Node 层细节，不提前吞并协同文档**

   本文档不重写运行规则，也不取代后续多 Project 协同文档。

### 0.7 当前名词口径

本章同时冻结以下名词口径：

* **问题** ：我要达成的最终目标
* **Solution** ：围绕同一个最终目标存在的最上层组织容器
* **Project** ：Solution 内部一级独立工作对象
* **Workspace** ：当前干活时的工作上下文
* **Round** ：一次跨 Project 的变化组织单位
* **StepRecord** ：某个 Node 在某个场景下完成一轮推进后的局部沉淀记录

这些名词之间的层级关系是：

* `Solution` 承接目标空间
* `Project` 承接独立工作面
* `Round` 承接一次变化
* `Workspace` 承接当前工作上下文
* `StepRecord` 承接局部推进留痕

### 0.8 本章结论

第 0 章到这里正式冻结以下内容：

1. 本文档是 **Round 的定义文档**
2. 它只解决“一次跨 Project 的变化如何被正式组织”
3. 它不负责 Project 内部运行规则，不负责完整多 Project 协同，不负责 Round 高级机制
4. 它与《解决方案层与工作区》的关系是：前者定义问题空间，本文定义变化单位
5. 它与 StepRecord 的边界是：StepRecord 记录局部推进，Round 承接跨 Project 变化
6. 它与 Workspace 的边界是：Workspace 承接当前工作上下文，Round 承接当前变化本身
7. 当前阶段，Round 先按“最小变化单位”来写，不按“完整系统”来写


## 1. 为什么需要轮次

### 1.1 单个 Project 内部推进，只能承接局部工作变化，不能自然承接一次完整变化

前面已经明确：

* `Project` 是一级独立工作对象
* `Node` 是最小推进对象
* 单个 Project 内部可以有完整推进闭环
* 一个 Project 当前默认可以采用 Tree 结构来承接内部推进

这说明，Project 内部推进本身是成立的。

但这并不等于：

**一次真实变化，就天然只会发生在一个 Project 内部。**

Project 内部推进解决的是：

* 某个独立工作面怎么继续
* 某个对象怎么推进
* 某一轮局部输入输出怎么沉淀

它并不天然解决：

**这次变化整体影响了什么。**

### 1.2 真实变化往往天然跨越多个 Project

在真实问题处理中，一次变化很少只是“我继续写某一个 Project”这么简单。

更常见的是：

* 主 Project 的结论变了
* 文档 Project 要同步调整
* 规则 Project 要同步补充
* AI 指令 Project 也要一起修改
* 有时还会新增新的派生 Project

也就是说，

你面对的往往不是“一个独立工作面继续推进”，

而是：

**一次变化同时影响多个工作面。**

这时，如果没有一个高于 Project 的组织单位，

系统虽然还能继续工作，但会逐渐出现一个问题：

**这次变化整体是什么，开始于哪里，结束于哪里，已经很难说清。**

### 1.3 如果没有 Round，跨 Project 变化会退化成“散落在各处的修改”

这一点非常重要。

如果没有 Round，

那你当然还是可以继续改：

* 一个 Project 改一点
* 另一个 Project 再改一点
* 规则补一点
* 文档再补一点

问题不在于“还能不能干”，而在于：

**这些修改之间缺少一个共同的变化承接单位。**

结果就是：

* 这次变化的边界不清
* 哪些 Project 属于同一轮变化不清
* 这一轮到底产出了什么不清
* 下次接着改时，很难知道是接哪一轮

也就是说，没有 Round 时，

跨 Project 的变化不会消失，

只是会退化成：

**散落在各处、靠记忆串起来的一组修改。**

### 1.4 StepRecord 不能替代 Round

这里要专门澄清一个非常容易混的点。

你前面已经把 StepRecord 收得很清楚了：

它记录的是某个 Node 在某个场景下完成一轮推进后的结果。

这已经足够支撑单个 Project 内部的推进留痕。

但 StepRecord 不能替代 Round，原因很简单：

* StepRecord 是**局部推进记录**
* Round 是**跨 Project 变化单位**

StepRecord 回答的是：

* 这个 Node 这一轮做了什么
* 这一轮留下了什么

Round 回答的是：

* 这次变化整体影响了哪些 Project
* 这次变化作为一个整体是什么
* 这次变化的当前状态是什么
* 这次变化之后下一步从哪里继续

所以不是 StepRecord 不够好，

而是：

**它解决的是更低层的问题。**

### 1.5 Workspace 也不能替代 Round

另一个容易混的点是 Workspace。

你前面已经把 Workspace 定义成：

当前干活时的工作上下文。

它承接的是：

* 当前焦点 Project
* 当前焦点入口
* 当前相关 Project
* 当前附加信息

这很重要，

但这仍然不能替代 Round。

因为 Workspace 解决的是：

**我现在在什么上下文里干活。**

Round 解决的是：

**这次变化作为一次正式变化，如何被承接。**

也就是说：

* Workspace 偏“当前使用状态”
* Round 偏“当前变化本身”

两者会相关，但不能合并。

### 1.6 Round 的出现，是为了让“变化”获得正式承接

到这里，其实原因已经清楚了。

当一个最终目标被拆成多个 Project 后，

系统会自然需要两种上层承接：

1. **问题空间承接**

   也就是 Solution

1. **变化过程承接**

   也就是 Round

Solution 解决的是：

* 这些 Project 为什么属于同一个最终目标

Round 解决的是：

* 这次变化为什么属于同一轮变化

所以 Round 的出现不是额外增加复杂度，

而是让“变化”这件事获得正式承接。

如果没有它，

你的上层只有“问题空间”，

但没有“变化单位”。

这样系统就会缺一层很关键的组织能力。

### 1.7 没有 Round，多 Project 协同就只能依赖隐性顺序

当前你已经非常明确地定下了一个好原则：

* 一个 Solution 中可以有多个 Project
* 一次只推进一个 Project
* 多 Project 协同通过顺序推进来实现
* 不在同一轮中交错推进多个 Project

这个原则非常重要。

但如果没有 Round，这个顺序协同很容易退化成一种隐性默认：

* 我先改这个
* 再去改那个
* 然后顺手补第三个
* 但这几个修改是不是同一轮，其实没有正式单位承接

这时协同虽然发生了，

却没有被正式组织起来。

所以 Round 的作用之一，就是把原本隐性的“这是一轮变化”变成显性的组织单位。

### 1.8 Round 不是为了做批处理，而是为了让一次变化有边界

“轮次”这个词很容易让人误解成：

* 批处理
* 阶段包
* 任务集合
* 一次大操作

这些理解都不完全错，

但如果只停留在这里，会把 Round 写得太表面。

Round 更本质的作用是：

**让一次变化有边界。**

这个边界至少回答四个问题：

1. 这次变化是围绕什么目标发生的
2. 这次变化涉及哪些 Project
3. 这次变化到哪里算结束
4. 这次变化结束后，下一步从哪里接

所以 Round 不是“把事情打包一下”那么简单，

而是：

**把原本容易散掉的跨 Project 变化，压成一个可承接、可记录、可继续的正式单位。**

### 1.9 Round 的存在，不会破坏“一次只推进一个 Project”

这里也要主动澄清一个潜在误解。

引入 Round 之后，

并不意味着你要在同一轮里同时推进多个 Project。

恰恰相反，Round 更适合你现在已经明确的那条原则：

**一次只推进一个 Project，但一轮变化可以顺序影响多个 Project。**

也就是说：

* Round 是上层组织单位
* Project 仍然是当前正式推进焦点单位
* 一个 Round 中可以先后涉及多个 Project
* 但在任何具体推进时刻，仍然只有一个焦点 Project

这样，Round 和 Workspace / Project 的边界反而更清晰了。

### 1.10 当前阶段为什么必须先承认 Round

如果你现在不承认 Round，

后面会出现一个很明显的问题：

你已经有了：

* Solution
* Workspace
* Project
* 单点推进原则

但你还没有一个正式概念来承接：

**“这次变化本身”。**

也就是说，系统会有：

* 目标空间
* 工作对象
* 当前上下文
* 局部推进记录

却没有：

* 一次变化的正式承接层

这会让你的上层结构缺一层非常关键的组织能力。

所以当前阶段必须先承认 Round，

即使暂时还不细化它的全部状态机和字段设计，

它作为概念层也必须先成立。

### 1.11 本章结论

第 1 章到这里正式冻结以下内容：

1. 单个 Project 内部推进可以承接局部工作变化，但不足以自然承接一次完整跨 Project 变化
2. 真实变化往往天然会同时影响多个 Project
3. 如果没有 Round，跨 Project 变化会退化成散落在各处、靠记忆串起来的一组修改
4. StepRecord 只能记录局部推进，不能替代跨 Project 的变化单位
5. Workspace 只能承接当前工作上下文，不能替代变化单位
6. Solution 承接问题空间，Round 承接变化过程，两者不是同一层东西
7. Round 的出现，是为了让“变化”获得正式承接
8. Round 的核心意义，不是做批处理，而是让一次变化拥有明确边界
9. 引入 Round 不会破坏“一次只推进一个 Project”的原则，反而让这条原则在跨 Project 协同中更稳
10. 当前阶段必须先承认 Round 作为正式概念存在，即使暂不展开其完整机制


## 2. Round 的最小定义

### 2.1 Round 不是某个 Project 的内部概念，而是高于 Project 的变化单位

在当前阶段，Round 首先应被理解为：

**围绕同一个最终目标而发生的一次跨 Project 变化组织单位。**

这里的关键点有两个：

第一，它不是某个 Project 内部的一轮。

第二，它不是抽象的“阶段感觉”，而是一次正式的变化单位。

也就是说，Round 所承接的不是：

* 某个 Node 的本轮推进
* 某个 Project 的单次局部修改

而是：

**一组围绕同一个目标、并且在本次变化中彼此相关的 Project 级变化。**

### 2.2 Round 解决的是“这次变化是什么”，不是“这个问题是什么”

这一点必须先分开。

前面已经冻结：

* `问题` 是我要达成的最终目标
* `Solution` 承接这个最终目标
* `Project` 承接围绕该目标展开的独立工作面

那么 Round 在这里的地位就应该非常明确：

**Round 承接的是“这次变化”。**

也就是说：

* 问题回答：最终要达成什么
* Solution 回答：这个目标的上层问题空间是什么
* Project 回答：有哪些独立工作面存在
* Round 回答：**这一次变化本身是什么**

所以，Round 不是问题本身，

也不是目标空间本身，

它是目标推进过程中某一次正式变化的承接单位。

### 2.3 Round 的核心职责，不是推进内容，而是组织变化

Round 很容易被误写成“又一个推进对象”。

但如果这样写，它会和 Project、Node 层继续打架。

更准确地说：

**Round 不直接负责推进内容，它负责组织变化。**

也就是说，Round 不直接做这些事：

* 不直接替代 Node 推进
* 不直接替代 Project 内部运行
* 不直接替代 Scheduler 选节点
* 不直接替代 StepRecord 留痕

它真正做的是：

* 承接这次变化的边界
* 承接这次变化涉及哪些 Project
* 承接这次变化当前处在哪个阶段
* 承接这次变化结束后下一步怎么继续

所以，Round 首先是 **变化承接对象** ，而不是内容执行对象。

### 2.4 Round 的最小定义

在当前阶段，我建议把 Round 的最小定义冻结成下面这句话：

> **Round 是围绕同一个最终目标而存在的一次跨 Project 变化组织单位，用于承接本次变化涉及的工作面、变化边界、当前状态与后续入口。**

这里有四个关键词：

#### 2.4.1 一次

Round 不是长期存在的目标空间，

而是某一次正式变化。

#### 2.4.2 跨 Project

它的意义在于承接超出单个 Project 的变化。

即使这次变化最后只影响了一个 Project，

Round 的概念本身仍然站在“可能跨 Project”的上层。

#### 2.4.3 变化组织单位

Round 的作用不是替内容执行，而是把这次变化组织起来。

#### 2.4.4 后续入口

Round 不是变化结束即消失的描述标签，

它还要承接：

**这次变化之后，下一步从哪里继续。**

### 2.5 Round 和 Project 的关系

Round 和 Project 的关系，不能理解成包含或替代。

#### 2.5.1 Round 不是更大的 Project

Round 不是新的工作面。

它不直接去承接“分析”“文档”“规则”“AI 指令”这些具体工作。

这些仍然由 Project 承接。

#### 2.5.2 Project 也不是 Round 的子步骤

Project 是长期或阶段性的独立工作对象，

而 Round 是某次变化对这些工作对象的组织承接。

所以，Project 不是 Round 的“内部步骤”。

#### 2.5.3 两者关系

更准确地说：

* Project 承接“工作对象”
* Round 承接“本次变化如何作用于这些工作对象”

所以，两者是两条不同维度：

* 一个是对象维度
* 一个是变化维度

### 2.6 Round 和 StepRecord 的关系

这一组边界也必须在定义章里直接压清。

StepRecord 记录的是：

* 某个 Node 在某个场景下完成一轮推进后的结果

Round 记录的是：

* 这次变化整体涉及了哪些 Project
* 这次变化整体推动了什么
* 这次变化整体现在处在哪

所以两者关系不是上下包含，而是：

* StepRecord 是局部推进留痕
* Round 是跨 Project 变化承接

这意味着：

**一个 Round 可以关联很多局部推进痕迹，但它不等于这些痕迹的简单堆叠。**

### 2.7 Round 和 Workspace 的关系

这一组关系也要提前钉住。

Workspace 承接的是：

* 当前干活的上下文

Round 承接的是：

* 当前这次变化本身

所以它们的关系更像是：

* Workspace 让人知道“现在在哪个上下文里工作”
* Round 让系统知道“当前这次变化是什么”

这意味着：

* Workspace 可以承接当前 Round 的相关信息
* 但 Workspace 不等于 Round
* Round 也不等于当前工作视图

### 2.8 Round 的最小职责

在当前阶段，我建议把 Round 的职责先收成下面四条。

#### 2.8.1 承接本次变化的目标边界

也就是回答：

**这次变化到底是围绕什么发生的。**

它不是重新定义最终目标，

而是把最终目标在当前这次变化中的有效边界收住。

#### 2.8.2 承接本次变化涉及的 Project 范围

也就是回答：

**这一轮变化涉及了哪些 Project。**

没有这层，变化会散落在多个 Project 中，

但没有上层统一承接。

#### 2.8.3 承接本次变化的当前状态

也就是回答：

**这次变化现在进行到哪了。**

注意，这里的“状态”不是 Node 那种细粒度运行状态，

而是这次变化作为一个变化单位所处的位置。

#### 2.8.4 承接本次变化结束后的下一步入口

Round 不应只是“描述这次改动”的标签，

它还要能把这次变化和下一次变化接起来。

所以 Round 必须承接：

**这次变化结束后，下一步从哪里继续。**

### 2.9 Round 的最小成立条件

不是任何修改集合都值得叫一个 Round。

在当前阶段，我建议把 Round 的最小成立条件冻结成下面三条：

#### 2.9.1 它围绕同一个当前变化目标

也就是说，这些变化在当前这次动作里，属于同一个变化方向，而不是只是碰巧一起做了。

#### 2.9.2 它涉及至少一个明确工作对象

也就是说，Round 不能只是一句空计划。

它至少要能够落到某个或某组 Project 上。

#### 2.9.3 它具有可继续承接的意义

如果这次变化完全没有边界、没有状态、没有下一步入口，

那它就还不够资格成为正式 Round。

它顶多只是临时操作痕迹。

### 2.10 当前阶段 Round 的最小骨架

在当前 1.0 阶段，我建议先把 Round 的最小骨架理解成下面四块：

1. 本轮变化目标
2. 本轮涉及的 Project
3. 本轮当前状态
4. 本轮结束后的下一步入口

只要这四块成立，Round 这个概念就已经可用。

至于更细的字段、关系、状态机，可以后面再补。

### 2.11 Round 当前不是什么

为了防止它继续膨胀，这里也要反向钉死。

当前阶段，Round 不是：

* 不是最终目标本身
* 不是 Solution 本身
* 不是某个 Project 本身
* 不是某个 Node 的一轮推进
* 不是 StepRecord 的上位同义词
* 不是 Workspace 的别名
* 不是完整任务系统
* 不是自动调度器

一句话：

**Round 是变化单位，不是万能容器。**

### 2.12 当前 1.0 对 Round 的最小冻结版本

如果把这一章压到最小，可以冻结成下面这段话：

> Round 是围绕同一个最终目标而存在的一次跨 Project 变化组织单位。
>
> 它不直接替代 Project 内部推进，而是承接本次变化的目标边界、涉及的 Project 范围、当前状态与下一步入口。
>
> Round 不是问题本身，不是 Solution 本身，不是 Project 本身，也不是 StepRecord 或 Workspace 的同义词。
>
> 它属于“变化承接层”，用于让跨 Project 的正式变化获得明确边界和持续承接。

### 2.13 本章结论

第 2 章到这里正式冻结以下内容：

1. Round 是一次跨 Project 的变化组织单位
2. Round 承接的是“这次变化是什么”，而不是“最终目标是什么”
3. Round 的核心职责不是推进内容，而是组织变化
4. Round 的最小定义已经成立：承接本次变化的边界、涉及的 Project、当前状态与后续入口
5. Round 与 Project 的关系，不是包含关系，而是“工作对象维度”和“变化维度”的关系
6. Round 与 StepRecord 的关系，不是上下替代关系，而是“局部推进留痕”和“跨 Project 变化承接”的关系
7. Round 与 Workspace 的关系，不是同义关系，而是“变化承接”和“当前工作上下文承接”的关系
8. 当前阶段，Round 的最小骨架先冻结为：变化目标、涉及 Project、当前状态、下一步入口
9. 当前阶段，Round 不是问题、不是 Solution、不是 Project、不是 StepRecord、不是 Workspace，也不是万能容器
10. Round 当前已经可以作为正式概念成立，即使其完整字段和状态机暂不展开


## 3. Round 与 StepRecord 的边界

### 3.1 这一章要解决的问题

Round 和 StepRecord 都和“变化”有关，

也都和“记录”有关，

所以它们天然容易被混成一类东西。

但它们真正承接的不是同一层级的变化。

因此，这一章要回答的核心问题是：

1. StepRecord 记录的到底是什么
2. Round 记录的到底是什么
3. 为什么 StepRecord 不能替代 Round
4. 为什么 Round 也不能吞并 StepRecord

也就是说，这一章不是讲字段，而是讲：

**层级边界。**

### 3.2 StepRecord 记录的是局部推进完成后的沉淀

前面已经冻结过：

StepRecord 记录的是：

**某个 Node 在某个场景下完成一轮推进后的结果。**

所以 StepRecord 的核心特点是：

* 它依附于 Node
* 它依附于某一轮局部推进
* 它记录的是这一轮局部输入、输出、变化和下一步入口
* 它属于局部推进留痕

因此，StepRecord 回答的是：

**这个 Node 这一轮发生了什么。**

它的视角是微观的、局部的、推进内核层的。

### 3.3 Round 记录的是一次跨 Project 变化的整体承接

而 Round 记录的不是某个 Node 的一轮推进，

而是：

**一次跨 Project 的变化整体是什么。**

所以 Round 的核心特点是：

* 它不依附于单个 Node
* 它不依附于单个局部推进
* 它承接的是本次变化涉及哪些 Project、变化边界是什么、当前状态是什么、下一步从哪里继续
* 它属于变化组织层

因此，Round 回答的是：

**这次变化整体是什么。**

它的视角是更高层的、组织性的、跨 Project 的。

### 3.4 两者的核心差异，不在“大小”，而在“层级”

很多人第一反应会觉得：

* StepRecord 比较小
* Round 比较大

这个理解不算错，但不够准。

更准确的说法是：

**它们的区别不只是大小，而是层级不同。**

StepRecord 所在层级是：

* Node 内部推进层
* 局部轮次沉淀层

Round 所在层级是：

* Project 之上的变化组织层
* 跨 Project 承接层

所以，Round 不是“大一点的 StepRecord”，

StepRecord 也不是“小一点的 Round”。

它们首先是不同层级的对象。

### 3.5 StepRecord 回答“局部这轮”，Round 回答“整体这次”

如果把两者压成最简单的对照，可以写成：

* StepRecord 回答：**这个 Node 这一轮怎么样了**
* Round 回答：**这次变化整体怎么样了**

这两个问题看起来相似，

但本质完全不同。

例如：

一个分析 Project 中某个 Node 完成了一轮判断，

生成了一条 StepRecord。

这说明这个 Node 的一轮推进成立了。

但这并不自动说明：

* 本次跨 Project 变化已经成立
* 本次变化已经结束
* 本次变化涉及哪些其他 Project
* 本次变化下一步应该转向哪里

这些问题，仍然需要 Round 来承接。

### 3.6 一个 Round 可以关联多个 StepRecord，但不等于多个 StepRecord 的集合

这是最关键的一条边界。

一个 Round 中，当然可能出现很多局部推进：

* 某个 Project 中一个 Node 推进了一轮
* 另一个 Project 中两个 Node 也分别推进了一轮
* 还有一个派生产物 Project 中补了一轮

这些都可能各自产生 StepRecord。

所以从关系上说：

**一个 Round 可以关联多个 StepRecord。**

但这里不能直接推出：

**Round = 多个 StepRecord 的集合。**

原因是：

StepRecord 只告诉你：

* 各个局部推进分别发生了什么

但 Round 还要告诉你：

* 为什么这些局部推进属于同一轮变化
* 这次变化整体边界是什么
* 这次变化当前处于什么状态
* 这次变化之后下一步怎么继续

也就是说，Round 比 StepRecord 集合多出来的，不只是“更多记录”，而是：

**变化整体的组织语义。**

### 3.7 StepRecord 无法回答“这次变化为什么是同一次变化”

这是 StepRecord 不能替代 Round 的根本原因。

即使你收集了很多 StepRecord，

你仍然可能说不清：

* 为什么这几条记录属于同一次变化
* 这次变化的开始边界在哪里
* 这次变化的结束边界在哪里
* 这几条记录在整体变化中各自处于什么位置

StepRecord 记录的是“局部已经发生了什么”，

但不天然提供“它们为什么属于同一轮变化”的上层解释。

所以：

**StepRecord 有留痕能力，但没有变化组织能力。**

而 Round 的意义，恰恰就在于补上这一层。

### 3.8 Round 也不能替代 StepRecord

边界不是单向的。

不能说 StepRecord 不够，就让 Round 去把局部推进全吞掉。

如果这样做，Round 会立刻变成一个巨大的混合物：

* 既要记录每个 Node 的局部输入输出
* 又要记录每轮的局部变化
* 又要记录每个场景下的推进结果
* 同时还要承接整体变化

这样做的结果是：

* Round 会过重
* 局部推进粒度会被污染
* Node 层沉淀会失去独立性
* 你前面已经冻住的运行规则会被反向破坏

所以必须明确：

**Round 不能替代 StepRecord。**

局部推进留痕仍然必须由 StepRecord 承接。

### 3.9 两者关系更准确的描述：局部沉淀 与 变化承接

如果不用“谁更大”来描述，

那更准确的关系应该是：

* **StepRecord = 局部沉淀**
* **Round = 变化承接**

局部沉淀解决的是：

* 这个局部推进现在留下了什么

变化承接解决的是：

* 这一整次变化如何被正式组织起来

这两个层级既不能混为一谈，

也不能互相吞并。

### 3.10 从“记录对象”角度看两者差异

从“记录对象”的角度来看，两者差异会更清楚。

#### 3.10.1 StepRecord 的记录对象

StepRecord 记录的是：

**Node 在某个场景下完成的一轮推进结果。**

它的天然对象是：

* Node
* 场景
* 局部轮次

#### 3.10.2 Round 的记录对象

Round 记录的是：

**围绕同一个目标发生的一次跨 Project 变化。**

它的天然对象是：

* 当前变化
* 涉及的 Project
* 整体变化边界
* 后续变化入口

所以，

StepRecord 面对的是“推进对象的一轮”，

Round 面对的是“变化本身”。

### 3.11 从“恢复与继续”的角度看两者差异

这也是一个非常实用的对比方式。

#### 3.11.1 StepRecord 支持局部恢复

看 StepRecord，你能知道：

* 某个 Node 上一轮做到哪了
* 这一轮留下了什么
* 这个局部下一步怎么接

它支持的是：

**局部推进恢复。**

#### 3.11.2 Round 支持整体变化恢复

看 Round，你能知道：

* 当前这次变化整体在干什么
* 它已经涉及了哪些 Project
* 当前变化的边界是什么
* 下一次变化应从哪里接

它支持的是：

**整体变化恢复。**

所以，两者的“可继续性”也不是一个层级。

### 3.12 当前 1.0 对两者关系的最小冻结版本

如果把这一章再压到最小，可以冻结成下面这段话：

> StepRecord 记录的是某个 Node 在某个场景下完成一轮推进后的局部沉淀结果；Round 记录的是围绕同一个最终目标而发生的一次跨 Project 变化的整体承接。
>
> 一个 Round 可以关联多个 StepRecord，但 Round 不等于多个 StepRecord 的集合。
>
> StepRecord 负责局部推进留痕，Round 负责变化整体组织。
>
> 两者相关，但处于不同层级，不能互相替代。

### 3.13 本章结论

第 3 章到这里正式冻结以下内容：

1. StepRecord 记录的是某个 Node 在某个场景下完成一轮推进后的局部沉淀
2. Round 记录的是一次跨 Project 变化的整体承接
3. 两者的差异不只是大小，而是层级不同
4. StepRecord 回答“局部这轮怎么样了”，Round 回答“整体这次变化怎么样了”
5. 一个 Round 可以关联多个 StepRecord
6. 但 Round 不等于多个 StepRecord 的简单集合
7. StepRecord 无法回答“这次变化为什么属于同一次变化”，因此不能替代 Round
8. Round 也不能吞并 StepRecord，否则会破坏局部推进留痕层
9. StepRecord 属于局部沉淀层，Round 属于变化承接层
10. StepRecord 支持局部恢复，Round 支持整体变化恢复
11. 当前 1.0 已经可以正式把两者的边界冻结下来，不必再混用


## 4. Round 的最小组成

### 4.1 这一章的目标

当前阶段，Round 还不适合直接进入完整字段表、状态机和存储模型。
但如果连最小组成都说不清，
那 Round 仍然只是一个抽象词。

所以这一章的目标就是：

**先把 Round 最少必须承接的组成部分压出来。**

这里强调的是“最少必须有”，
不是“未来可能还会有”。

### 4.2 Round 的最小组成，不是对象堆叠，而是变化骨架

先给一个总判断。

Round 的最小组成，不应理解成：

* 有几个字段
* 有几个对象
* 有几个列表

它更应该理解成：

**一轮变化至少要能回答哪几类问题。**

也就是说，Round 的骨架首先是语义骨架，
然后才有可能进一步落成字段结构。

在当前阶段，我建议把 Round 的最小组成收成 4 块：

1. 本轮变化目标
2. 本轮涉及的 Project 范围
3. 本轮当前状态
4. 本轮结束后的下一步入口

只要这 4 块成立，Round 作为变化单位就已经成立。

### 4.3 第一部分：本轮变化目标

一个 Round 首先必须承接：

**这次变化到底是在干什么。**

注意，这里的“目标”不是最终目标本身。
最终目标属于 Solution 层。
Round 这里承接的是：

**最终目标在这一次变化中的具体推进目标。**

例如：

* 本轮要整理哪些规则
* 本轮要把哪些上层定义补齐
* 本轮要把哪几个相关 Project 同步推进到某个断点

如果这一层没有，Round 就会退化成：

* 一堆修改
* 一组动作
* 一次模糊操作痕迹

所以，Round 的第一组成部分必须是：

**本轮变化目标。**

### 4.4 第二部分：本轮涉及的 Project 范围

只有目标还不够。
Round 还必须承接：

**这次变化涉及哪些 Project。**

这是 Round 之所以高于单个 Project 的核心原因。
如果不记录这一层，
那你就无法明确：

* 这次变化到底跨没跨 Project
* 这次变化具体作用于哪些工作面
* 哪些 Project 是本轮正式参与对象
* 哪些 Project 只是背景，不属于本轮实际变化范围

所以，Round 的第二组成部分必须是：

**本轮涉及的 Project 范围。**

这一层至少要能区分两类东西：

* 本轮正式涉及的 Project
* 当前存在但不属于本轮范围的其他 Project

### 4.5 第三部分：本轮当前状态

Round 不能只是“变化的标签”，
它还必须承接：

**这次变化当前走到哪了。**

这里的“状态”不是 Node 那种局部状态，
也不是 Project 内部的运行状态。
它是：

**这次变化作为变化单位，现在处在什么位置。**

当前阶段先不用展开完整状态机，
但概念上必须承认这一层存在。
否则 Round 无法回答：

* 本轮是否已经开始
* 本轮是否仍在进行
* 本轮是否已经形成明确断点
* 本轮是否已经结束

所以，Round 的第三组成部分必须是：

**本轮当前状态。**

### 4.6 第四部分：本轮结束后的下一步入口

Round 还有一个很重要的组成部分，
就是它不能只描述“这轮发生了什么”，
还必须承接：

**这轮结束后下一步从哪里继续。**

这一点和 StepRecord 有点像，
但层级不同。

StepRecord 的 `next` 是：

* 某个 Node 的局部下一步入口

Round 这里承接的是：

* 这一整次变化结束后，系统从哪个变化入口继续

如果这一层没有，
Round 就只能解释“过去”，不能真正承接“继续”。

所以，Round 的第四组成部分必须是：

**本轮结束后的下一步入口。**

### 4.7 为什么当前最小组成里还不急着放“完整产出列表”

很多人会觉得：
Round 不是还应该有“本轮产出了什么”吗？

这个方向没有错，
但在当前阶段，我不建议把它直接列成独立的第五块核心组成，原因有两个：

#### 4.7.1 当前产出可以先被包含在变化状态与后续入口中

在当前最小版本下，
“本轮产出了什么”还可以先作为：

* 变化状态的一部分
* 后续入口的一部分
  来理解。

也就是说，
只要你知道：

* 这轮推进到哪了
* 这轮后面从哪接

很多产出信息其实已经能被承接。

#### 4.7.2 一旦独立展开“完整产出”，Round 会很快开始膨胀

因为你马上就会继续问：

* 产出分哪几类
* 文档算不算产出
* StepRecord 算不算产出
* Project 新增算不算产出
* 规则变更算不算产出

这会立刻把 Round 拉向更细的设计层。

所以当前阶段我建议先克制一点：
Round 的最小组成先冻结为 4 块，
而不是一下长出很完整的产出系统。

### 4.8 为什么当前最小组成里还不急着放“完整参与顺序”

另一个自然会想到的东西是：

* 本轮先做哪个 Project
* 再做哪个 Project
* 这些顺序要不要写进 Round

我认为这个问题要先压住。

因为当前阶段，Round 先要解决的是：

**本轮变化是什么。**

至于“本轮内部具体先后顺序怎么排”，
那是后面 Round 流程和多 Project 协同章节更适合讨论的问题。

也就是说：

* `涉及哪些 Project` 是最小组成的一部分
* `这些 Project 怎么排序推进` 还不是当前最小组成必须写死的部分

否则这一章会过早滑向“流程设计”。

### 4.9 Round 的最小组成之间的关系

把前面四部分放在一起后，
可以得到一个很清晰的骨架：

#### 4.9.1 本轮变化目标

回答：
**这轮变化在干什么。**

#### 4.9.2 本轮涉及的 Project 范围

回答：
**这轮变化作用于哪些工作面。**

#### 4.9.3 本轮当前状态

回答：
**这轮变化现在走到哪了。**

#### 4.9.4 本轮结束后的下一步入口

回答：
**这轮变化结束后，从哪继续。**

这四块组合起来后，Round 就已经能够同时承接：

* 目标
* 范围
* 过程位置
* 后续接续

这已经足以让它成为一个正式变化单位。

### 4.10 如果缺少其中一块，会发生什么

这一节很有助于验证这四块是不是足够必要。

#### 4.10.1 没有“本轮变化目标”

Round 会退化成一堆修改集合，
但说不清这次变化到底想推进什么。

#### 4.10.2 没有“涉及的 Project 范围”

Round 会失去跨 Project 语义，
最后和普通局部修改没区别。

#### 4.10.3 没有“本轮当前状态”

Round 只能说明“这次变化存在过”，
但不能说明它现在处在哪。

#### 4.10.4 没有“下一步入口”

Round 只能描述已经发生的事，
不能真正承接继续。

所以，这四块不是随便列的，
它们都是最小必要组成。

### 4.11 当前 1.0 的最小组成冻结版本

如果把这一章压到最小，可以冻结成下面这段话：

> 一个 Round 在当前 1.0 阶段，至少应承接四类内容：本轮变化目标、本轮涉及的 Project 范围、本轮当前状态、本轮结束后的下一步入口。
> 这四部分共同构成 Round 的最小变化骨架。
> 当前阶段，Round 暂不要求完整产出体系、完整参与顺序、完整字段表和完整状态机，只要求它作为变化单位能够回答：这轮在干什么、作用于哪些 Project、现在走到哪了、之后从哪继续。

### 4.12 本章结论

第 4 章到这里正式冻结以下内容：

1. Round 的最小组成首先是语义骨架，而不是完整字段堆叠
2. 当前 1.0 阶段，Round 的最小组成先冻结为四部分：
   * 本轮变化目标
   * 本轮涉及的 Project 范围
   * 本轮当前状态
   * 本轮结束后的下一步入口
3. 本轮变化目标承接的是“这次变化在干什么”，而不是最终目标本身
4. 本轮涉及的 Project 范围承接的是“这次变化作用于哪些工作面”
5. 本轮当前状态承接的是“这次变化作为变化单位现在走到哪了”
6. 本轮结束后的下一步入口承接的是“这次变化之后从哪里继续”
7. 当前阶段，Round 暂不要求把完整产出体系独立展开
8. 当前阶段，Round 暂不要求把完整参与顺序写成最小组成的一部分
9. 这四块共同构成了 Round 当前最小可成立的变化骨架
10. 只要这四块成立，Round 作为正式变化单位就已经成立


## 5. Round 的最小流程

### 5.1 这一章的目标

当前阶段，Round 已经不是空概念了。

但如果只有“定义”和“组成”，仍然还不够。

因为你还会自然追问：

* 一次 Round 是从哪里开始的
* 它中间怎么承接变化
* 它什么时候算结束
* 结束之后如何继续

所以这一章的目标很明确：

**把 Round 的最小生命周期压成一条最短可用流程。**

注意，是 **最小流程** ，不是完整状态机。

### 5.2 Round 最小流程的基本判断

在当前阶段，我建议把 Round 的最小流程先压成下面 5 步：

1. 形成本轮变化目标
2. 确定本轮涉及的 Project 范围
3. 进入本轮焦点 Project 推进
4. 必要时顺序切换到其他相关 Project
5. 形成本轮断点或本轮结束，并给出下一步入口

这 5 步就足以让一个 Round 作为变化单位成立。

它不是最终系统流程，

但已经足以承接：

* 一次变化从何开始
* 如何在多个 Project 间被组织
* 如何在某个时点形成可继续的断点

### 5.3 第一步：形成本轮变化目标

一个 Round 不能从“我先改着看”开始。

它至少要有一个明确的本轮变化目标。

也就是说，在 Round 开始时，系统或人必须先回答：

**这轮变化到底要推动什么。**

这个目标不需要像最终目标那样宏大，

但必须足够清楚，能够说明：

* 这轮为什么存在
* 这轮和最终目标是什么关系
* 这轮大致想推进到什么断点

没有这一步，Round 会退化成临时修改集合，

而不是正式变化单位。

所以，Round 最小流程的第一步必须是：

**形成本轮变化目标。**

### 5.4 第二步：确定本轮涉及的 Project 范围

有了目标之后，还不够。

Round 还必须确定：

**这轮变化正式涉及哪些 Project。**

这一步的作用，是把“可能相关”和“本轮正式纳入”区分开。

因为在一个 Solution 中，

很多 Project 都可能和当前目标有关，

但不代表它们都应该被纳入本轮。

所以在这一步，至少要区分两类东西：

* 本轮正式涉及的 Project
* 当前存在但只作为背景存在的其他 Project

这一步一旦不做清，

后面 Round 就会越跑越散，

最后谁都能被临时拉进来。

因此，Round 最小流程的第二步必须是：

**确定本轮涉及的 Project 范围。**

### 5.5 第三步：进入本轮焦点 Project 推进

虽然一个 Round 可以涉及多个 Project，

但你已经明确冻结了一条关键原则：

**一次只推进一个 Project。**

所以在确定本轮范围后，

Round 不会同时把多个 Project 一起推进，

而是必须进入：

**当前焦点 Project 的正式推进。**

这意味着：

* Round 承接的是变化
* 但真正发生推进的，仍然是某个具体 Project
* Round 并不替代 Project 内部推进规则

所以这一步的本质是：

**Round 把变化落到一个当前焦点 Project 上。**

这也是为什么 Round 必须和 Workspace 配合：

Workspace 承接的是当前工作上下文，

而 Round 需要在这个上下文中明确当前焦点。

### 5.6 第四步：必要时顺序切换到其他相关 Project

如果这一轮变化只涉及一个 Project，

那第三步之后可能就已经足够。

但真实情况下，Round 往往会影响多个 Project。

这时，正确的做法不是并发推进，

也不是交错推进，

而是：

**在当前焦点 Project 形成明确断点后，再显式切换到下一个相关 Project。**

这一步要特别强调三个点：

#### 5.6.1 切换必须显式

不能在当前 Project 中途，悄悄把另一个 Project 的推进混进来。

#### 5.6.2 切换必须顺序发生

多个 Project 的推进在一个 Round 中可以先后发生，

但不能交错并发。

#### 5.6.3 切换必须以“本轮变化”为上层依据

也就是说，不是随便切换，

而是因为这个 Project 已在第二步中被纳入本轮正式范围。

所以，Round 最小流程的第四步是：

**必要时顺序切换到其他相关 Project。**

### 5.7 第五步：形成本轮断点或本轮结束，并给出下一步入口

Round 最后不能停在“已经做了很多事”的模糊状态。

它必须走到一个正式可承接的位置。

当前阶段，我建议把这一点压成两个可接受结局：

#### 5.7.1 形成本轮断点

也就是说：

* 本轮变化暂时停住了
* 当前已有可继续承接的位置
* 下一轮可以从这个断点继续

#### 5.7.2 本轮结束

也就是说：

* 当前这次变化已经完成
* 本轮不再继续扩展
* 下一步将进入新的 Round 或新的工作入口

这两种情况都必须满足一件事：

**Round 必须给出下一步入口。**

也就是说，本轮不能只留下“做过了”，

还必须留下：

* 后面从哪里接
* 是继续当前变化
* 还是进入下一轮变化
* 还是切换到新的焦点 Project

所以，Round 最小流程的第五步是：

**形成本轮断点或本轮结束，并给出下一步入口。**

### 5.8 为什么当前最小流程里不写“自动创建 Round”

这一点要单独压一下。

当前阶段，我们不把 Round 写成自动系统。

也就是说，这个最小流程默认仍然偏向：

**显式承认一轮变化已经开始。**

原因很简单：

* 现在你还在概念与边界冻结阶段
* 如果现在就引入“自动识别一轮变化开始”，会立刻把问题拉向自动路由和自动编排
* 那会超出当前 1.0 边界

所以当前最小流程，不写：

* 自动创建 Round
* 自动结束 Round
* 自动拆分 Round

这些都留到后续层再处理。

### 5.9 为什么当前最小流程里不写“完整状态流转”

你自然会继续问：

* Round 是不是也应该有“未开始 / 进行中 / 已完成 / 已冻结”
* Round 是否也要有正式状态机

这些问题都合理，

但当前阶段最好先压住。

因为现在更重要的是先把：

**Round 的动作流程**

收住，而不是先把：

**Round 的完整状态体系**

展开。

所以这一章只写最小流程，不写完整状态机。

### 5.10 Round 最小流程和 Project 内部推进流程的关系

这一节必须明确，否则会继续混。

Project 内部推进流程解决的是：

* 某个 Node 怎么进入推进
* 一轮怎么完成
* 一轮怎么沉淀
* 条件动作怎么发生

Round 最小流程解决的是：

* 一次变化怎么开始
* 这次变化涉及哪些 Project
* 这些 Project 如何被顺序纳入
* 这次变化最后停在哪个断点

所以两者关系不是：

* 谁包含谁

而是：

* Round 流程是上层变化流程
* Project 流程是下层内容推进流程

更直白一点说：

**Round 负责“这一轮变化怎么走”，Project 负责“这次落到我这里后怎么推进”。**

### 5.11 Round 最小流程中的最小顺序图

如果把这一章压成一条最短顺序，可以写成：

1. 明确本轮变化目标
2. 确定本轮涉及的 Project
3. 选定当前焦点 Project
4. 在该 Project 内执行当前推进
5. 如有必要，在形成断点后显式切换到下一个相关 Project
6. 当本轮形成整体断点或整体结束时，给出下一步入口

这条顺序已经足以作为当前 Round 的最小流程。

### 5.12 当前 1.0 对 Round 最小流程的冻结版本

如果把这一章再压成一段正式冻结语句，可以写成：

> 一个 Round 在当前 1.0 阶段的最小流程为：先形成本轮变化目标，再确定本轮涉及的 Project 范围，然后进入当前焦点 Project 推进；若本轮涉及多个 Project，则在当前 Project 形成明确断点后，顺序切换到其他相关 Project；最终，当本轮形成整体断点或整体结束时，必须给出下一步入口。
>
> 在此过程中，一个 Round 可以顺序涉及多个 Project，但任意一个实际推进时刻仍然只推进一个 Project。
>
> 当前阶段，Round 的最小流程不展开自动创建、自动结束、自动拆分，也不展开完整状态机。

### 5.13 本章结论

第 5 章到这里正式冻结以下内容：

1. 当前阶段，Round 的最小流程先冻结为 5 步：

* 形成本轮变化目标
* 确定本轮涉及的 Project 范围
* 进入本轮焦点 Project 推进
* 必要时顺序切换到其他相关 Project
* 形成本轮断点或本轮结束，并给出下一步入口

1. 一个 Round 不能从模糊修改开始，必须先有本轮变化目标
2. 一个 Round 不能无限扩散，必须先确定本轮正式涉及的 Project 范围
3. 虽然一个 Round 可涉及多个 Project，但任意一个实际推进时刻仍然只推进一个 Project
4. 跨 Project 的推进必须顺序发生，不能交错并发
5. Project 切换必须是显式动作
6. Round 最终必须形成可继续承接的断点或正式结束，并给出下一步入口
7. 当前阶段，Round 不展开自动创建、自动结束、自动拆分
8. 当前阶段，Round 不展开完整状态机
9. Round 最小流程是上层变化流程，不替代下层 Project 内部推进流程


## 6. Round 与 Workspace 的关系

### 6.1 这一章要解决的问题

Round 和 Workspace 之所以容易混，是因为它们都与“当前这次工作”有关。

* Workspace 承接的是当前干活时的上下文
* Round 承接的是当前这次变化本身

它们都跟“当前”有关，
也都可能同时出现在同一个 Solution 中。
因此很容易让人误以为：

* Workspace 就是当前 Round 的另一种说法
* Round 就是 Workspace 当前状态的一部分

这两种理解都不准确。

所以这一章的核心问题是：

1. Workspace 到底承接什么
2. Round 到底承接什么
3. 两者为什么会关联
4. 两者为什么又不能合并

### 6.2 Workspace 承接的是“当前干活时的上下文”

前面已经冻结过：

**Workspace 是人进入某个 Solution 后，当前干活时所处的工作上下文。**

它至少承接：

* 当前焦点 Project
* 当前焦点入口
* 当前相关 Project
* 当前必要附加信息

所以，Workspace 回答的是：

**我现在在什么上下文里继续工作。**

它天然偏向的是：

* 使用状态
* 焦点状态
* 当前入口
* 当前背景

也就是说，Workspace 首先是一个 **使用层概念** 。

### 6.3 Round 承接的是“当前这次变化本身”

而 Round 承接的不是工作上下文，
而是：

**这次变化本身。**

它至少承接：

* 本轮变化目标
* 本轮涉及的 Project
* 本轮当前状态
* 本轮结束后的下一步入口

所以，Round 回答的是：

**这次变化作为一次正式变化，现在是什么。**

它天然偏向的是：

* 变化边界
* 变化范围
* 变化状态
* 变化接续

也就是说，Round 首先是一个 **变化层概念** 。

### 6.4 两者的核心差异，不在“当前”，而在“承接对象”

两者都与“当前”有关，
但它们承接的“当前”不是同一种东西。

* Workspace 承接的是：**当前工作上下文**
* Round 承接的是：**当前变化单位**

所以它们最根本的差异不在于：

* 谁更大
* 谁更重要
* 谁更抽象

而在于：

**它们承接的对象不是同一个。**

更准确地说：

* Workspace 的对象是“当前怎么工作”
* Round 的对象是“当前这次变化是什么”

这条边界一旦钉死，很多混乱会立刻消失。

### 6.5 为什么 Round 和 Workspace 会强关联

虽然两者不同，但它们会天然强关联。

原因很简单：

当前人之所以进入某个 Workspace 干活，
往往就是因为当前有一轮变化正在推进。
反过来，一次 Round 要真正被推进，也总会落在某个 Workspace 里被实际工作承接。

所以它们之间会自然形成这种关系：

* Round 给出“当前这次变化是什么”
* Workspace 给出“人在这个变化里现在怎么干活”

也就是说：

**Round 提供变化承接，Workspace 提供工作承接。**

这也是为什么两者总会一起出现，
但又不该被合并。

### 6.6 Workspace 可以承接当前 Round 的相关信息，但不等于 Round

这一条要单独写清。

既然 Workspace 是当前工作上下文，
那它当然可以承接一些当前 Round 的相关信息，例如：

* 当前正在承接哪个 Round
* 当前 Round 的目标是什么
* 当前 Round 涉及哪些 Project
* 当前 Round 目前推进到了哪一段

这些都可以被 Workspace 承接。
因为 Workspace 本来就应该承接继续工作所需的必要背景。

但是：

**Workspace 承接 Round 相关信息，不等于 Workspace 就等于 Round。**

两者的关系更像是：

* Round 是被承接的变化对象
* Workspace 是承接当前工作时对这个变化对象的上下文视图

所以，Workspace 里可以“挂着”一个当前 Round，
但 Workspace 不是 Round 本身。

### 6.7 如果没有 Workspace，Round 也仍然成立

这是一个很好的检验方式。

假设你暂时没有 Workspace 这个概念，
你仍然可以在概念上承认：

* 存在一个 Solution
* 存在多个 Project
* 存在一次跨 Project 的正式变化
* 这次变化有目标、有范围、有状态、有下一步入口

这说明：

**Round 的成立，不依赖 Workspace。**

它首先是一个变化组织单位，
而不是一个工作视图对象。

所以 Workspace 不是 Round 的必要定义前提。
它更多是：

* 使用层承接
* 工作时承接
* 当前状态承接

### 6.8 如果没有 Round，Workspace 仍然存在，但会失去一层关键承接

反过来也一样。

即使不承认 Round，
你仍然可以说：

* 当前有一个 Solution
* 当前有多个 Project
* 当前 Workspace 聚焦某个 Project
* 当前继续在这个上下文里工作

这说明：

**Workspace 的存在，也不依赖 Round 作为定义前提。**

但是如果没有 Round，
Workspace 会少一层非常关键的东西：

**当前这次变化到底是什么。**

也就是说，Workspace 还能存在，
但它承接的只是：

* 当前焦点
* 当前入口
* 当前背景

而不能正式承接：

* 当前这轮变化的边界
* 当前这轮变化为什么同时牵涉多个 Project
* 当前这轮变化是如何继续的

这说明两者虽然独立成立，
但组合起来时会互相增强。

### 6.9 两者的关系更准确的描述：变化承接 与 工作承接

如果不用“哪个更高一级”来描述，
更准确的说法应该是：

* **Round = 变化承接**
* **Workspace = 工作承接**

变化承接解决的是：

* 这次变化是什么
* 这次变化涉及什么
* 这次变化怎么继续

工作承接解决的是：

* 人当前在哪个上下文里继续
* 现在焦点是什么
* 现在从哪里接
* 现在需要带着哪些背景信息

这两个层级彼此咬合，
但不能互相吞并。

### 6.10 一个最小例子

用一个很小的例子就能看清两者区别。

假设当前有一个 Solution：
“整理 Ascend 1.0 的正式设计基础”

当前存在三个 Project：

* 运行规则 Project
* 解决方案层 Project
* 实现规划 Project

现在发生一轮变化：

* 补齐解决方案层定义
* 同步对运行规则口径做必要校正
* 准备后续实现规划入口

那么此时：

#### Round 承接的是：

* 这次变化的目标是什么
* 涉及了哪几个 Project
* 当前变化现在走到哪了
* 下一步准备转到哪里

#### Workspace 承接的是：

* 当前焦点在哪个 Project
* 当前从哪个入口继续
* 当前相关的其他 Project 是什么
* 当前需要一起带着看的背景信息是什么

这个例子一对照就很明显：

* Round 承接的是“变化”
* Workspace 承接的是“工作上下文”

### 6.11 Round 与 Workspace 不能相互替代

到这里可以把边界彻底钉死。

#### 6.11.1 Workspace 不能替代 Round

因为 Workspace 只能告诉你：

* 现在在哪里工作
* 现在看什么
* 现在从哪里继续

但它不天然告诉你：

* 这次变化作为一个整体是什么
* 为什么这些 Project 属于同一轮变化
* 这轮变化现在整体走到哪了

#### 6.11.2 Round 不能替代 Workspace

因为 Round 只能告诉你：

* 这次变化是什么
* 涉及哪些 Project
* 当前变化状态是什么

但它不天然告诉你：

* 当前人真正正在看哪个 Project
* 当前入口具体落在哪里
* 当前附加背景是什么
* 当前如何在使用层继续工作

所以：

**Round 不能替代 Workspace，Workspace 也不能替代 Round。**

### 6.12 当前 1.0 的最小冻结版本

如果把这一章再压到最小，可以冻结成下面这段话：

> Workspace 承接的是当前干活时的工作上下文，Round 承接的是当前这次变化本身。
> Workspace 可以承接当前 Round 的相关信息，但不等于 Round；Round 也不等于当前工作视图。
> 两者分别属于“工作承接层”和“变化承接层”，彼此关联，但不能互相替代。
> 在当前 1.0 中，当前工作可以在 Workspace 中进行，而当前变化则通过 Round 获得正式边界和持续承接。

### 6.13 本章结论

第 6 章到这里正式冻结以下内容：

1. Workspace 承接的是当前工作上下文，Round 承接的是当前这次变化本身
2. 两者都与“当前”有关，但承接对象不同
3. Workspace 是使用层概念，Round 是变化层概念
4. Workspace 可以承接当前 Round 的相关信息，但不等于 Round
5. Round 的成立不依赖 Workspace；Workspace 的成立也不依赖 Round
6. 如果没有 Workspace，Round 仍然可以作为变化单位成立
7. 如果没有 Round，Workspace 仍然可以作为当前工作上下文存在，但会失去对“当前变化本身”的正式承接
8. 两者关系更准确的描述是：Round 负责变化承接，Workspace 负责工作承接
9. Round 不能替代 Workspace，Workspace 也不能替代 Round
10. 当前 1.0 已经可以正式冻结两者的边界关系

## 7. Round 与多 Project 协同的关系

### 7.1 多 Project 协同为什么一定会出现

前面已经冻结过：

* 一个最终目标往往需要多个 Project 共同承接
* 一个 Solution 中可以并存多个 Project
* 这些 Project 虽然各自独立，但共同服务于同一个最终目标

这意味着，多 Project 协同不是后面“可选加上的高级能力”，

而是：

**只要 Solution 层成立，多 Project 协同就一定会自然出现。**

因为只要多个 Project 真正服务于同一个目标，

它们之间就一定会在某些时刻发生：

* 信息传递
* 结果引用
* 顺序接力
* 派生关系
* 变化影响

所以，多 Project 协同不是“有没有”的问题，

而是“如何被正式组织”的问题。

### 7.2 如果没有 Round，多 Project 协同会退化成隐性顺序

这一点其实和前面“为什么需要 Round”是连着的，

但这里要专门从协同角度再压一次。

如果没有 Round，

多 Project 当然还是可以协同。

你仍然可以：

* 先改一个 Project
* 再改另一个 Project
* 再回到第一个 Project 补一点
* 然后顺手开第三个 Project

表面上这也是协同。

但问题在于：

**这种协同没有正式的变化单位承接。**

于是它会退化成：

* 靠记忆维持的顺序
* 靠上下文暂时串起来的动作链
* 没有边界的一组相关修改

这样一来，多 Project 虽然协同了，

但系统并没有真正承接“这一次协同本身”。

而 Round 的价值，就在于把这种隐性协同变成显性变化组织。

### 7.3 Round 不是协同本身，而是协同的组织单位

这里必须把边界先钉死。

Round 很重要，但它不是“多 Project 协同系统”的全部。

更准确地说：

**多 Project 协同是行为关系，Round 是承接这种行为关系的一次变化单位。**

也就是说：

* 协同回答的是：多个 Project 如何围绕同一个目标互相作用
* Round 回答的是：这一次具体协同变化如何被承接

所以两者关系不是：

* 谁替代谁

而是：

* 协同是内容
* Round 是容器

如果把 Round 直接写成协同本身，

它会立刻过重。

### 7.4 Round 承接的是“本轮协同”，不是“所有协同规则”

这一条非常关键。

一个 Solution 中多个 Project 之间，

可以存在很多长期关系，例如：

* 某个 Project 的结果长期会影响另一个 Project
* 某类产物长期由某个主 Project 派生
* 某个 Project 一直是另一个 Project 的背景支撑

这些都属于 **长期协同关系** 。

但它们不应全部被写进某个 Round 里。

Round 承接的是：

**这些协同关系在当前这一次变化中如何被实际触发。**

所以：

* 长期协同关系，不等于某个 Round
* 某个 Round 只承接当前这次协同变化
* Round 是协同关系的一次实际发生，不是全部协同规则的总和

这条边界非常重要，

否则 Round 会变成“多 Project 所有关联关系的大仓库”。

### 7.5 多 Project 协同的第一原则：一次只推进一个 Project

这一条必须在这里再次正式落下来。

既然多 Project 协同是必然存在的，

那最重要的问题就变成：

**协同是否意味着同时推进多个 Project。**

当前阶段，你已经明确给出了一个非常好的约束：

**不意味着。**

也就是说：

* 一个 Round 可以涉及多个 Project
* 但在任意一个实际推进时刻，仍然只推进一个 Project

这条原则非常关键。

因为它把多 Project 协同从“并发乱跑”拉回到了：

**顺序协同。**

所以，多 Project 协同的第一原则可以正式冻结为：

**一个 Round 可以组织多个 Project，但实际推进始终保持单点焦点。**

### 7.6 多 Project 协同的第二原则：协同通过顺序推进实现，不通过交错推进实现

当前你已经很明确地意识到：

* 多个 Project 可以相关
* 多个 Project 可以属于同一个 Round
* 多个 Project 可以被同一轮变化影响

但这不代表它们应该在同一轮中交错推进。

正确的方式是：

1. 当前焦点落在某个 Project
2. 在该 Project 中推进到明确断点
3. 如有必要，再显式切换到下一个相关 Project
4. 继续本轮变化

也就是说：

**多 Project 协同在当前阶段，首先是一种顺序协同，而不是交错协同。**

这条规则极大地降低了复杂度，

也保证了 Workspace、Project、Round 三层关系不会混乱。

### 7.7 多 Project 协同的第三原则：Project 之间的关系不会自动进入当前 Round

一个 Solution 中，

Project 之间当然可能长期相关。

但不是所有相关关系都会自动进入当前这轮变化。

所以这里还必须钉死一条：

**Project 之间存在关系，不等于这些关系自动成为当前 Round 的正式内容。**

也就是说：

* 某两个 Project 长期相关
* 并不等于当前 Round 必须同时处理它们
* 只有当这次变化明确涉及它们时，它们才进入当前 Round 范围

这一条很重要，

因为它防止 Round 不断膨胀。

### 7.8 Round 在多 Project 协同中的核心作用

到这里，其实可以把 Round 的角色压成一句话：

**Round 让多 Project 协同从“相关”变成“本轮正式变化”。**

更具体地说，它至少完成三件事：

#### 7.8.1 把本轮协同范围圈出来

也就是：

* 本轮正式涉及哪些 Project
* 哪些 Project 只是背景，不进入本轮

#### 7.8.2 把本轮协同顺序组织起来

虽然当前不展开完整顺序系统，

但至少承认：

* 本轮当前焦点在哪
* 后续可能顺序进入哪些 Project

#### 7.8.3 把本轮协同结果接到下一轮

Round 不只是承接“这轮做了什么”，

还要承接：

* 这轮之后从哪里继续
* 哪个 Project 成为下一步焦点
* 这轮变化有没有形成新的协同入口

这就是 Round 在协同中的不可替代性。

### 7.9 一个最小例子

用一个最小例子来看会更清楚。

假设当前有一个 Solution，

承接的最终目标是：

**整理 Ascend 1.0 的正式设计基础**

其中存在三个 Project：

* 运行规则 Project
* 解决方案层 Project
* 实现规划 Project

现在发生一轮变化：

* 先补齐解决方案层定义
* 再同步修正运行规则口径
* 最后明确实现规划入口

这时：

#### 协同关系是什么

这三个 Project 共同服务于同一个目标，

并且当前这次变化需要它们顺序配合。

#### Round 在做什么

Round 把这次变化正式承接起来，

明确：

* 本轮涉及这三个 Project
* 当前先聚焦哪一个
* 下一步如何顺序切到另一个
* 本轮结束后从哪里继续

#### 实际推进怎么发生

不是三个 Project 一起并发推进，

而是：

* 先推进解决方案层 Project
* 到明确断点后，再切到运行规则 Project
* 最后再切到实现规划 Project

这个例子直接说明：

**协同是 Project 之间的关系，Round 是当前这次协同变化的组织单位。**

### 7.10 Round 不能取代多 Project 协同文档本身

这一条也要反向钉死。

虽然这一章已经把 Round 和协同关系说清楚了，

但这并不意味着：

**Round 文档已经等于多 Project 协同文档。**

因为多 Project 协同后面还会继续涉及：

* Project 之间有哪些关系类型
* 派生产物是怎样形成的
* 长期依赖与当前变化怎么区分
* 不同生命周期 Project 怎么协同

这些都属于更完整的协同问题。

Round 这里只承接：

**本轮协同变化。**

所以这一章只写到“Round 在协同中的角色”，

不替代后面的完整协同文档。

### 7.11 当前 1.0 的最小冻结版本

如果把这一章再压到最小，可以冻结成下面这段话：

> 多 Project 协同是 Solution 成立后的自然结果，而 Round 是承接“本轮协同变化”的正式单位。
>
> Round 不等于多 Project 协同本身，而是把当前这次协同变化的范围、焦点、顺序与后续入口正式组织起来。
>
> 在当前 1.0 中，一个 Round 可以涉及多个 Project，但任意一个实际推进时刻仍然只推进一个 Project；多个 Project 的协同通过顺序推进实现，而不通过交错并发推进实现。
>
> Project 之间的长期相关关系不会自动进入当前 Round，只有当本轮变化明确涉及它们时，它们才进入当前 Round 范围。

### 7.12 本章结论

第 7 章到这里正式冻结以下内容：

1. 多 Project 协同是 Solution 成立后的自然结果
2. 如果没有 Round，多 Project 协同会退化成隐性顺序和散落修改
3. Round 不是协同本身，而是协同的变化组织单位
4. Round 承接的是“本轮协同变化”，而不是“所有协同规则”
5. 一个 Round 可以涉及多个 Project，但实际推进始终保持单点焦点
6. 多 Project 协同在当前阶段通过顺序推进实现，而不通过交错并发推进实现
7. Project 之间的长期相关关系不会自动进入当前 Round
8. Round 的核心作用，是把本轮协同范围、焦点、顺序与后续入口正式组织起来
9. Round 不能替代后续完整的多 Project 协同文档


## 8. 当前 1.0 先冻结什么

### 8.1 这一章的目标

到目前为止，你已经把这些内容都触碰到了：

* Round 为什么存在
* Round 的最小定义
* Round 与 StepRecord 的边界
* Round 的最小组成
* Round 的最小流程
* Round 与 Workspace 的关系
* Round 与多 Project 协同的关系

如果这时不做一次收口，
后面 Round 很容易自然膨胀成：

* 上层任务系统
* 完整协同系统
* 自动调度系统
* 变化存储系统
* 组织层大脑

所以这一章的目标只有一个：

**给 Round 在 1.0 当前阶段划出一个最小冻结边界。**

### 8.2 当前 1.0 先冻结的第一件事：正式承认 Round 作为变化单位存在

这一条必须先钉死。

当前阶段，1.0 正式承认：

**Round 是围绕同一个最终目标而存在的一次跨 Project 变化组织单位。**

这意味着：

* Round 不再只是临时说法
* Round 不再只是口头上的“一轮”
* Round 已经进入正式概念体系

从这一刻开始，
当变化超出单个 Project 内部范围时，
系统就不再只依赖：

* Project
* Workspace
* StepRecord

而是正式承认还有一层：

**变化承接层。**

### 8.3 当前 1.0 先冻结的第二件事：Round 的最小定义

当前阶段，Round 的最小定义已经可以正式冻结为：

> Round 是围绕同一个最终目标而存在的一次跨 Project 变化组织单位，用于承接本次变化涉及的工作面、变化边界、当前状态与后续入口。

这一条非常关键。
因为它决定了 Round 不是：

* 问题本身
* Solution 本身
* Project 本身
* StepRecord 的上位同义词
* Workspace 的别名

而是：

**变化单位。**

### 8.4 当前 1.0 先冻结的第三件事：Round 的最小骨架

当前阶段，Round 的最小骨架先冻结为四部分：

1. 本轮变化目标
2. 本轮涉及的 Project 范围
3. 本轮当前状态
4. 本轮结束后的下一步入口

这一条的意义在于：

当前先不要求 Round 长成完整对象模型，
但至少必须保证它已经能够回答：

* 这轮在干什么
* 这轮影响哪些 Project
* 这轮现在走到哪了
* 这轮后面从哪接

只要这四块成立，
Round 就已经可以作为正式变化单位存在。

### 8.5 当前 1.0 先冻结的第四件事：Round 的最小流程

当前阶段，Round 的最小流程已经可以正式冻结为：

1. 形成本轮变化目标
2. 确定本轮涉及的 Project 范围
3. 进入本轮焦点 Project 推进
4. 必要时顺序切换到其他相关 Project
5. 形成本轮断点或本轮结束，并给出下一步入口

这条流程已经足够支撑：

* 一次变化怎么开始
* 它怎么落到具体 Project 上
* 多个 Project 如何被顺序承接
* 变化怎么形成断点并继续

当前阶段不要求它成为完整状态机，
但这条最小流程已经足以冻结。

### 8.6 当前 1.0 先冻结的第五件事：Round 与 StepRecord 的边界

这一条必须冻结，
否则后面实现和文档都会反复打架。

当前阶段正式冻结：

* StepRecord 记录的是局部推进沉淀
* Round 记录的是跨 Project 变化承接
* 一个 Round 可以关联多个 StepRecord
* 但 Round 不等于多个 StepRecord 的集合

这一条的意义是：

**局部推进留痕层，不能上浮替代变化承接层。**

同时也意味着：

**变化承接层，不能反过来吞掉局部推进留痕层。**

### 8.7 当前 1.0 先冻结的第六件事：Round 与 Workspace 的边界

当前阶段也应正式冻结：

* Workspace 承接当前工作上下文
* Round 承接当前变化本身
* Workspace 可以挂着当前 Round 的相关信息
* 但 Workspace 不等于 Round
* Round 也不等于当前工作视图

这一条的意义是：

**当前干活状态** 和 **当前变化单位**
在 1.0 中已经必须被明确拆开。

否则你后面很容易把：

* 焦点
* 入口
* 当前变化
* 当前背景

混成一个概念。

### 8.8 当前 1.0 先冻结的第七件事：Round 是多 Project 协同的组织单位

当前阶段应正式承认：

**Round 是多 Project 协同的变化组织单位。**

这意味着：

* 多 Project 协同通过 Round 组织
* 一个 Round 可以涉及多个 Project
* 但任意一个实际推进时刻，仍然只推进一个 Project
* 协同通过顺序推进实现，而不是交错并发推进

这一条很关键。
因为它把 Round 正式放进了：

* Solution
* Workspace
* Project

这套上层结构里，
并且明确了它和协同的关系。

### 8.9 当前 1.0 先冻结的第八件事：Round 先按显式变化单位来写

当前阶段，我建议把一个重要实现口径也先冻结下来：

**Round 先按显式变化单位来写。**

也就是说，在当前 1.0 中，优先承认：

* 这是一次正式变化
* 这轮变化现在开始
* 这轮变化涉及哪些 Project
* 这轮变化现在推进到哪了

而不是先假设：

* 系统能自动识别 Round 开始
* 系统能自动拆出 Round
* 系统能自动结束 Round

这样做的好处是：

* 概念更稳
* 实现更简单
* 边界更清晰
* 不会过早滑向自动编排

### 8.10 当前 1.0 先冻结的第九件事：Round 当前先解决“成立”，不解决“完备”

这一条要单独写出来。

当前你对 Round 的任务，不是一次把它写成完整系统，
而是先让它以最小正确形态成立。

所以当前阶段先冻结的，是：

* Round 为什么存在
* Round 是什么
* Round 最少承接什么
* Round 最少怎么流动
* Round 和其他对象的边界是什么

而不是：

* Round 的最终对象模型
* Round 的最终状态机
* Round 的最终 UI
* Round 的自动调度与自动组织能力

这一条本质上是在防止 Round 一上来就膨胀。

### 8.11 当前 1.0 的最小冻结范围

如果把这一章再压成最小冻结范围，我建议写成下面这组：

#### 概念层冻结

* 1.0 正式承认 Round 存在
* Round 是跨 Project 的变化组织单位
* Round 不等于 StepRecord，不等于 Workspace，不等于 Project

#### 骨架层冻结

* Round 最小骨架包含：
  * 变化目标
  * Project 范围
  * 当前状态
  * 下一步入口

#### 流程层冻结

* Round 最小流程包含：
  * 目标形成
  * 范围确定
  * 焦点 Project 推进
  * 必要时顺序切换
  * 形成断点或结束并给出下一步入口

#### 协同层冻结

* 多 Project 协同通过 Round 组织
* 一个 Round 可涉及多个 Project
* 但一次只推进一个 Project
* 协同通过顺序推进实现

#### 实现口径冻结

* Round 当前先按显式变化单位来写
* 当前先解决成立问题，不解决完备问题

### 8.12 当前冻结这些内容的意义

这一章的冻结不是为了“保守”，
而是为了让 Round 不在 1.0 当前阶段失控。

冻结这些内容，有三个直接作用：

#### 8.12.1 让 Round 先从概念层正式成立

## 9. 当前 1.0 暂不展开什么

### 9.1 这一章的目标

当前阶段，Round 已经触碰到很多后续方向，例如：

* 状态机
* 字段模型
* 自动创建
* 自动结束
* 多 Round 并发
* 跨 Solution 变化
* 与产物系统的深度联动

这些方向都是真的，

也都值得后续继续讨论。

但当前 1.0 不能一口气把它们全部吃进去。

所以这一章的目标，不是否定这些问题，

而是正式声明：

**它们存在，但当前只做记录，不进入正式冻结范围。**

### 9.2 暂不展开：Round 的完整状态机

前面你已经承认：

* Round 有当前状态
* Round 有开始、推进、断点、结束的概念

这已经足够支撑它作为变化单位成立。

但当前 1.0 不适合继续展开完整状态机，例如：

* `未开始 / 进行中 / 暂停 / 已完成 / 已归档`
* 各状态之间如何严格流转
* 哪些状态允许回退
* 哪些状态允许重开
* 状态变化的触发条件

这些都属于更细的系统化设计。

当前阶段只需要承认：

**Round 有状态，但暂不展开完整状态机。**

### 9.3 暂不展开：Round 的完整字段设计

前面已经把 Round 的最小骨架冻结为：

* 本轮变化目标
* 涉及的 Project 范围
* 当前状态
* 下一步入口

这已经足够。

当前 1.0 不适合继续细化成完整字段系统，例如：

* 唯一标识
* 创建时间
* 修改时间
* 发起来源
* 参与者
* 优先级
* 标签
* 关联产物列表
* 关联 StepRecord 列表
* 依赖关系字段

这些东西最终都可能需要，

但现在如果直接展开，会让 Round 迅速从概念层滑向完整对象建模阶段。

所以当前阶段：

**冻结最小骨架，不展开完整字段表。**

### 9.4 暂不展开：Round 的最终存储模型

一旦 Round 被承认为正式变化单位，

你自然会继续问：

* Round 是数据库对象吗
* 是内存对象吗
* 是日志对象吗
* 是事件对象吗
* 是不是需要长期持久化
* 是否需要和 Solution / Project 分开存储

这些问题都很真实。

但当前 1.0 不适合继续展开：

* 最终存储形态
* 存储层级
* 持久化策略
* 查询方式
* 与 StepRecord 的存储关系

因为现在你还在冻结概念层和最小流程层。

当前阶段只需要先承认：

**Round 需要被正式承接，但暂不展开最终存储模型。**

### 9.5 暂不展开：自动创建 Round

当前阶段，我已经建议你把 Round 先按**显式变化单位**来写。

所以当前 1.0 不适合继续展开：

* 系统自动识别一轮变化开始
* 自动判断哪些修改属于同一个 Round
* 自动把多个 Project 改动归并到同一个 Round
* 自动补齐 Round 目标

这些都属于更高阶的自动组织能力。

一旦展开，Round 会立刻从“概念成立”进入“自治系统设计”。

这不符合当前边界。

所以当前阶段明确：

**Round 暂不自动创建，先按显式承认来处理。**

### 9.6 暂不展开：自动结束 / 自动拆分 Round

和自动创建一样，

你自然还会继续问：

* Round 什么时候自动结束
* 什么时候一轮变化应该被拆成两轮
* 什么时候多个连续动作其实属于同一个 Round
* 什么时候 Round 应该被强制截断

这些问题都非常关键，

但也都明显属于下一层问题。

因为一旦展开，你就要继续定义：

* 断点判定
* 结束判定
* 拆分条件
* 合并条件

这会直接把当前讨论拉进“完整变化管理系统”。

所以当前阶段只冻结：

* Round 可以开始
* Round 可以形成断点或结束

但不展开：

* 自动结束
* 自动拆分
* 自动合并

### 9.7 暂不展开：多 Round 并发

当前你已经给多 Project 协同定下了一个很稳的原则：

* 一次只推进一个 Project
* 多 Project 协同通过顺序推进实现

在这个阶段，再引入“多个 Round 并发”会迅速把复杂度拉爆。

因为你马上就会面对：

* 两个 Round 是否能同时作用于同一个 Solution
* 一个 Project 是否能同时属于两个活跃 Round
* 当前 Workspace 里焦点 Round 怎么确定
* 多个 Round 的优先级如何处理

这些都太早了。

所以当前 1.0 明确不展开：

**多 Round 并发。**

当前阶段默认更稳的口径是：

**一个当前工作上下文中，只显式承接一个当前 Round。**

### 9.8 暂不展开：Round 嵌套

另一个很自然会冒出来的问题是：

* 一个大 Round 里面能不能有小 Round
* 某个局部变化是不是可以再独立成子 Round
* 子 Round 和父 Round 怎么同步

这个方向不是错，

但它会迅速引入新的层级复杂度。

而你现在还在把：

* Solution
* Workspace
* Project
* Round

这四层关系先收稳。

这时再引入 Round 嵌套，会让整个结构一下多出一层“变化里的变化”。

所以当前阶段：

**不展开 Round 嵌套。**

### 9.9 暂不展开：跨 Solution 的 Round

当前阶段你还只是刚把：

* Solution 作为问题空间
* Round 作为变化单位

这两层关系建立起来。

所以现在最稳的边界应该是：

**Round 只讨论单个 Solution 内部的变化组织。**

当前 1.0 暂不展开：

* 一个 Round 影响多个 Solution
* Solution 之间共享同一个 Round
* 跨 Solution 的全局变化空间
* Solution 间迁移与协同变化

这些问题一定会来，

### 9.10 暂不展开：Round 与派生产物系统的深度联动

当前阶段，你已经承认：

* 派生产物可以升格为独立 Project
* 多 Project 协同通过 Round 组织

这已经足够。

但当前 1.0 不适合继续展开：

* 哪类产物自动挂到当前 Round
* 产物是否必须归属某个 Round
* 一个产物能否跨多个 Round
* Round 是否需要维护完整产物清单
* Round 与派生产物的统一建模

这些问题如果继续往下走，

Round 会很快从“变化单位”膨胀成“产物追踪系统”。

所以当前阶段只冻结：

* Round 可以涉及派生产物 Project
* 但不展开深度联动规则

### 9.11 暂不展开：Round 的自动优先级与自动路由

当前你已经有：

* Solution：目标空间
* Workspace：当前工作上下文
* Project：独立工作面
* Round：变化单位

这已经够了。

当前 1.0 不适合继续引入：

* 哪个 Round 应自动优先
* 当前该自动切到哪个 Round
* 哪个 Project 应自动进入本轮

* Round 如何自动与 Scheduler 形成上层联动

这些问题一旦进来，

这会破坏当前很清楚的边界：

* Scheduler 解决局部推进秩序
* Round 解决变化承接
* Workspace 解决工作上下文

所以当前阶段：

**不展开 Round 的自动优先级与自动路由。**

### 9.12 暂不展开：Round 的完整实现模型

到这里为止，Round 已经有了：

* 是什么

## 10. 最小例子

### 10.1 为什么需要最小例子

前面几章已经冻结了这些内容：

* 为什么需要 Round
* Round 的最小定义
* Round 与 StepRecord 的边界
* Round 的最小骨架
* Round 的最小流程
* Round 与 Workspace 的关系
* Round 与多 Project 协同的关系
* 当前 1.0 先冻结什么
* 当前 1.0 暂不展开什么

这些内容单独看都成立。

但真正的问题是：

**放在一起之后，Round 到底是怎么工作的。**

所以这一章的作用，就是用一个最小场景验证：

* Round 不是空概念
* Round 不会和 Workspace、StepRecord、Project 混掉
* Round 的“变化单位”定位确实能跑通

### 10.2 例子的目标

我们用这样一个最小目标来举例：

**整理 Ascend 1.0 当前的正式设计基础，并把“解决方案层”与“实现入口”同步接起来。**

注意，这里的最终目标不是某一个 Round。

它属于更上层的 Solution，

因为它是一个跨时间、跨阶段、需要多个独立工作面共同服务的目标。

Round 在这个例子里承接的，只是：

**围绕这个目标而发生的某一次正式变化。**

### 10.3 这个例子里的 Solution

在这个例子里，可以有一个 Solution，名字可以理解为：

**Ascend 1.0 设计整理**

这个 Solution 承接的不是单次修改，

而是一个更大的最终目标：

* 把当前已经形成的设计内容整理成正式结构
* 让上层组织定义、运行规则和后续实现入口能够接起来

也就是说，

Solution 承接的是整个问题空间，

而不是某一轮变化。

### 10.4 这个例子里的 Project

在这个例子里，当前至少可能存在三个 Project：

#### 10.4.1 运行规则 Project

它承接的是：

* Tree 结构下 Node 如何推进
* 一轮如何沉淀
* 条件动作如何触发
* 局部运行规则如何冻结

#### 10.4.2 解决方案层 Project

它承接的是：

* Solution 是什么
* Workspace 是什么
* Project 是什么
* 上层组织边界是什么

#### 10.4.3 实现规划 Project

它承接的是：

* 最小实现范围
* 实现顺序
* AI 编码输入物
* 后续验证用例入口

这三个 Project 都围绕同一个最终目标服务，

但显然不是同一种工作面。

这就说明，单个 Project 已不足以自然承接这一类问题。

### 10.5 这个例子里的 Workspace

当人进入这个 Solution 时，面对的不是抽象目标本身，

而是一个当前工作上下文。

例如当前 Workspace 中可能承接的是：

* 当前 Solution：`Ascend 1.0 设计整理`
* 当前焦点 Project：`解决方案层 Project`
* 当前焦点入口：正在编写《43-轮次.md》
* 当前相关 Project：
* 运行规则 Project
* 实现规划 Project
* 当前附加信息：
* 已冻结的命名口径
* 已冻结的运行规则结论
* 当前 1.0 的边界与未展开项

这个 Workspace 回答的是：

**我现在在什么上下文里继续干活。**

它不是变化单位，

它只是承接这次工作时的当前上下文。

### 10.6 这个例子里的 Round 是什么

现在，假设发生这样一次变化：

* 先补齐《43-轮次.md》的核心章节
* 再确认它和前面《41-解决方案层与工作区.md》的边界关系
* 最后给后续实现规划 Project 留出明确入口

这时，

就不再只是“某个 Project 内部的一点局部推进”了，

而是一轮明确的跨 Project 变化。

在这个例子里，可以认为存在一个 Round：

**Round：整理并冻结 Solution 层之后的轮次定义**

这就是这次变化本身。

它不等于 Solution，

也不等于当前 Workspace，

更不等于某条 StepRecord。

它是：

**这次跨 Project 变化的正式承接单位。**

### 10.7 这个例子里 Round 的最小骨架如何成立

现在来看，前面冻结的 Round 最小骨架，是否在这个例子里真的成立。

#### 10.7.1 本轮变化目标

本轮目标可以是：

**补齐 Round 定义，并把它和 Solution 层、运行规则、实现规划之间的关系正式接起来。**

这说明，Round 的第一块——变化目标——成立。

#### 10.7.2 本轮涉及的 Project 范围

这一轮正式涉及的 Project 可能包括：

* 解决方案层 Project
* 运行规则 Project
* 实现规划 Project

其中：

* 当前焦点可能是“解决方案层 Project”下的轮次文档
* 运行规则 Project 和实现规划 Project 当前可能只是正式涉及对象，但不一定同时进入推进

这说明，Round 的第二块——Project 范围——成立。

#### 10.7.3 本轮当前状态

这轮变化当前可能处于：

* 正在定义轮次
* 尚未完全收口
* 还需要补一个后续实现入口

虽然我们没有展开完整状态机，

但“本轮当前状态”这个骨架在例子中是能成立的。

#### 10.7.4 本轮结束后的下一步入口

这轮变化结束后，下一步可能是：

* 进入 `44-Project 的生命周期.md`
* 或回到实现规划 Project
* 或继续补 `45-多Project协同与派生产物.md`

这说明，Round 的第四块——下一步入口——也成立。

所以，这个例子已经说明：

**Round 的四块最小骨架并不是空设。**

### 10.8 这个例子里 StepRecord 在哪里

现在来看 StepRecord。

在这轮变化过程中，

某个具体 Project 内部当然可能发生局部推进。

例如：

* 某个 Node 在“轮次定义”场景下完成一轮写作推进
* 某个 Node 在“边界校正”场景下完成一轮判断
* 某个 Node 在“实现入口整理”场景下完成一轮总结

这些都可能各自产生 StepRecord。

所以：

* StepRecord 仍然存在
* StepRecord 仍然记录局部推进留痕
* 它们可能都和当前 Round 有关

但这并不意味着：

**Round 就等于这些 StepRecord 的总和。**

因为 StepRecord 只能说明：

* 某个 Node 这一轮做了什么

而不能说明：

* 这次跨 Project 变化整体是什么
* 为什么这些局部推进属于同一轮变化
* 本轮变化整体下一步怎么继续

这个例子很好地证明了两者边界成立。

### 10.9 这个例子里 Workspace 和 Round 的区别

现在再看 Workspace。

当前 Workspace 承接的是：

* 当前焦点 Project 是什么
* 当前入口是什么
* 当前相关 Project 是什么
* 当前需要带着什么背景继续工作

它回答的是：

**我现在怎么继续干活。**

而当前 Round 承接的是：

* 这次变化的目标是什么
* 这次变化涉及哪些 Project
* 这次变化当前走到哪
* 这次变化结束后从哪继续

它回答的是：

**这次变化本身是什么。**

这个例子里两者都出现了，

但功能完全不同。

这正好说明：

* Workspace 不是 Round
* Round 也不是 Workspace

### 10.10 这个例子里“一次只推进一个 Project”如何成立

虽然这一轮变化涉及多个 Project，

但在任意一个实际推进时刻，当前焦点仍然只有一个。

例如：

* 现在先写 `《43-轮次.md》`
* 写到明确断点之后
* 再去补实现规划 Project
* 或再回头校正运行规则 Project

这说明：

* 一个 Round 可以涉及多个 Project
* 但一次仍然只推进一个 Project

所以，Round 并没有破坏你前面已经冻结的使用原则，

反而让这条原则在多 Project 变化中变得更稳。

### 10.11 如果没有 Round，这个例子会变成什么样

这个例子还有一个反向验证作用。

如果没有 Round，

你当然还是可以继续工作。

你也可以：

* 写一段轮次定义
* 去改一点运行规则
* 再去补实现规划
* 最后回到解决方案层

但问题会立刻出现：

* 这一组动作为什么属于同一次变化，说不清
* 哪些 Project 是这轮正式涉及的，说不清
* 这轮变化是从哪里开始的，说不清
* 这轮变化结束后应该怎么接，说不清

这说明，如果没有 Round，

你仍然能做事，

但系统对“这次变化”的正式承接会缺失。

### 10.12 这个例子告诉我们的最小图景

如果把这个例子再压一下，可以得到一个非常清楚的最小图景：

* 有一个最终目标

  → 整理 Ascend 1.0 的正式设计基础

* 这个最终目标被一个 Solution 承接

  → `Ascend 1.0 设计整理`

* 这个 Solution 内有多个 Project

  → 运行规则 / 解决方案层 / 实现规划

* 人通过 Workspace 进入这个 Solution

  → 当前焦点落在 `解决方案层 Project`

* 当前正在发生一轮变化

  → `补齐并冻结 Round 定义`

* 这轮变化由 Round 正式承接

  → 它定义了本轮目标、涉及 Project、当前状态和下一步入口

* 在任意一个时刻

  → 仍然只推进一个焦点 Project

这个最小图景说明：

**Round 在上层结构中已经获得了明确位置。**

### 10.13 当前 1.0 的最小例子冻结版

如果把这一章再压成一段话，可以冻结成下面这样：

> 例如，在“整理 Ascend 1.0 设计基础”这一最终目标下，可以存在一个 Solution，内部同时存在“运行规则 Project”“解决方案层 Project”“实现规划 Project”等多个独立工作面。

> 人通过 Workspace 进入该 Solution 时，当前可以聚焦其中一个 Project，例如正在编写《43-轮次.md》，而其他 Project 作为背景存在。

> 当这一轮变化不仅涉及当前文档本身，还涉及与运行规则和实现规划的关系时，就形成了一个 Round。
>
> 这个 Round 承接的是本轮变化的目标、涉及的 Project、当前状态与下一步入口；而局部写作推进仍由 StepRecord 承接。

> 这样，Solution 承接最终目标，Workspace 承接当前工作上下文，Project 承接独立工作面，Round 承接跨 Project 变化，StepRecord 承接局部推进留痕，各层边界保持清晰。

## 11. 本章结论

到这里为止，《轮次》这一份文档，正式冻结以下内容。

### 11.1 关于 Round 的定位

1. Round 不是问题本身，也不是最终目标本身。
2. Round 不是 Solution，本身也不是 Project。
3. Round 不是 StepRecord 的放大版，也不是 Workspace 的别名。
4. Round 是：**围绕同一个最终目标而存在的一次跨 Project 变化组织单位。**
5. Round 属于 **变化承接层** ，而不是局部推进层或当前工作上下文层。

### 11.2 关于为什么需要 Round

6. 单个 Project 内部推进可以承接局部工作变化，但不足以自然承接一次完整跨 Project 变化。
7. 真实变化往往天然会同时影响多个 Project。
8. 如果没有 Round，跨 Project 变化会退化成散落在各处、靠记忆串起来的一组修改。
9. Round 的出现，是为了让“变化”获得正式承接，而不是让系统更复杂。
10. Round 的核心意义，不是做批处理，而是让一次变化拥有明确边界。

### 11.3 关于 Round 的最小定义

11. 当前阶段，Round 的最小定义已经正式成立：

    **Round 是围绕同一个最终目标而存在的一次跨 Project 变化组织单位，用于承接本次变化涉及的工作面、变化边界、当前状态与后续入口。**
11.  Round 的核心职责不是推进内容，而是组织变化。
11.  Round 回答的是：**这次变化整体是什么。**
11.  Round 首先是变化承接对象，而不是内容执行对象。

### 11.4 关于 Round 的最小骨架

15. 当前 1.0 阶段，Round 的最小骨架先冻结为四部分：

* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮结束后的下一步入口

16. 这四部分共同构成了 Round 当前最小可成立的变化骨架。
17. 只要这四块成立，Round 作为正式变化单位就已经成立。
18. 当前阶段，Round 暂不要求完整字段表、完整状态机和完整对象模型。

### 11.5 关于 Round 的最小流程

19. 当前阶段，Round 的最小流程先冻结为五步：

* 形成本轮变化目标
* 确定本轮涉及的 Project 范围
* 进入本轮焦点 Project 推进
* 必要时顺序切换到其他相关 Project
* 形成本轮断点或本轮结束，并给出下一步入口

20. 一个 Round 不能从模糊修改开始，必须先有本轮变化目标。
21. 一个 Round 不能无限扩散，必须先有正式涉及的 Project 范围。
22. 一个 Round 最终必须形成可继续承接的断点或正式结束，并给出下一步入口。

### 11.6 关于 Round 与 StepRecord 的边界

23. StepRecord 记录的是某个 Node 在某个场景下完成一轮推进后的局部沉淀。
24. Round 记录的是一次跨 Project 变化的整体承接。
25. 两者的区别不只是大小，而是层级不同。
26. StepRecord 回答“局部这轮怎么样了”，Round 回答“整体这次变化怎么样了”。
27. 一个 Round 可以关联多个 StepRecord。
28. 但 Round 不等于多个 StepRecord 的集合。
29. StepRecord 无法替代 Round，Round 也不能吞并 StepRecord。
30. StepRecord 属于局部沉淀层，Round 属于变化承接层。

### 11.7 关于 Round 与 Workspace 的边界

31. Workspace 承接的是当前干活时的工作上下文。
32. Round 承接的是当前这次变化本身。
33. Workspace 是使用层概念，Round 是变化层概念。
34. Workspace 可以承接当前 Round 的相关信息，但不等于 Round。
35. Round 也不等于当前工作视图。
36. Round 和 Workspace 的关系更准确的描述是：

* Round 负责变化承接
* Workspace 负责工作承接

37. 两者相关，但不能互相替代。

### 11.8 关于 Round 与多 Project 协同的关系

38. 多 Project 协同是 Solution 成立后的自然结果。
39. 如果没有 Round，多 Project 协同会退化成隐性顺序和散落修改。
40. Round 不是协同本身，而是协同的变化组织单位。
41. Round 承接的是“本轮协同变化”，而不是“所有协同规则”。
42. 一个 Round 可以涉及多个 Project，但实际推进始终保持单点焦点。
43. 多 Project 协同在当前阶段通过顺序推进实现，而不通过交错并发推进实现。
44. Project 之间的长期相关关系不会自动进入当前 Round。
45. Round 的核心作用，是把本轮协同范围、焦点、顺序与后续入口正式组织起来。

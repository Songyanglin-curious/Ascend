
## 0. 文档目标与边界

### 0.1 文档目标

本文档用于定义：

**Ascend 1.0 当前最小实现范围的正式验证用例集。**

它的作用不是继续补充设计，不是继续讨论架构，也不是发现新需求。

它只负责一件事：

**验证《51-最小实现范围.md》中定义的最小实现边界是否真的被实现。**

因此，本文档是：

**施工结果的验收清单。**

不是：

* 方案说明书
* 架构讨论稿
* 未来规划文档
* 扩展能力建议清单

### 0.2 本文档的判定地位

本文档通过与否，是判定：

**《51-最小实现范围.md》第 7 章总验收句是否成立的唯一依据。**

也就是说：

* 《51》定义“本次该做什么”
* 《54》负责判断“本次是否真的做到了”

如果《54》中的核心用例未通过，

则无论实现看起来多完整、多漂亮，

本次实现都应判定为：

**不通过。**

### 0.3 本文档只验证什么

本文档只验证以下内容：

1. 《51》定义的最小对象模型是否成立
2. 《51》定义的最小闭环是否跑通
3. 《51》冻结的上层组织边界是否在实现中保持清晰
4. 《51》明确不实现的内容是否确实没有被做进去
5. 《51》的总验收句是否可被正式判定为成立

换句话说，本文档只验证：

**当前 1.0 的最小正确形态是否成立。**

### 0.4 本文档不验证什么

本文档不验证以下内容：

1. 未来版本能力
2. 当前明确不实现的扩展项
3. 架构是否“更优雅”
4. 代码是否“更通用”
5. 是否已经具备完整产品能力
6. 是否已经具备完整自动化与自治能力
7. 是否已经具备完整 UI 与完整对象体系

也就是说，本文档不负责回答：

* 以后还能不能扩
* 还有哪些地方可以做得更强
* 有没有提前做未来能力

它只回答：

**当前范围内，最小实现有没有真的跑通。**

### 0.5 本文档与其他文档的边界

#### 0.5.1 与《51-最小实现范围.md》的边界

《51》负责定义：

* 本次必须实现什么
* 本次明确不实现什么
* 最小对象模型是什么
* 最小闭环是什么

本文档负责：

* 把这些内容翻译成正式验收用例
* 判断它们是否真的成立

因此：

* `51` 是施工范围单
* `54` 是施工验收单

#### 0.5.2 与方案类文档的边界

如：

* 方案总览
* `41-解决方案层与工作区.md`
* `43-轮次.md`
* `44-Project 的生命周期.md`
* `45-多Project协同与派生产物.md`

这些文档负责冻结概念、边界与上层结构。

本文档不重写它们，

只检查实现是否遵守了它们已经冻结的口径。

### 0.6 本文档的使用方式

使用本文档时，遵守以下规则：

1. 所有用例都必须可判断、可观察、可验证
2. 任何模糊表述均不得作为“通过依据”
3. 所有用例必须优先对齐《51》的明确要求
4. 任何超出《51》的实现内容，不作为加分项
5. 若实现包含《51》明确不实现的内容，应作为风险或直接不通过项处理

### 0.7 本章结论

第 0 章到这里正式冻结以下内容：

1. 本文档是 Ascend 1.0 当前最小实现范围的正式验证用例集
2. 本文档通过与否，是判定《51》第 7 章总验收句是否成立的唯一依据
3. 本文档只验证当前最小正确形态是否成立
4. 本文档不补设计、不扩需求、不谈未来能力
5. 本文档与《51》的关系是：`51` 定义范围，`54` 定义验收
6. 所有后续用例必须可判断、可观察、可验证

## 1. 验证总原则

### 1.1 总原则一：所有验证必须严格对齐《51-最小实现范围.md》

本文档中所有验证用例，必须严格映射到《51》中已经明确冻结的内容。

不得出现以下情况：

* 用例验证内容超出《51》
* 用例擅自补新需求
* 用例把未来能力提前拉入当前验证范围

也就是说：

**《54》只能验证《51》已经明确要求的内容。**

### 1.2 总原则二：正向验证与反向验证必须并行

当前阶段的验证不能只做正向验证。

也就是说，不能只问：

* 该做的做了没有

还必须同时问：

* 明确不该做的，有没有被偷偷做进去

因此，本文档后续用例必须同时覆盖两类内容：

#### 1.2.1 正向验证

用于确认：

* 最小对象模型是否成立
* 最小闭环是否跑通
* 上层边界是否被正确实现

#### 1.2.2 反向验证

用于确认：

* 当前明确不实现的内容是否确实没有实现
* AI 或实现过程是否顺手做进了未来能力
* 边界是否因“补全”而被破坏

这两类验证同等重要，

任何一类缺失，当前阶段的验收都不完整。

### 1.3 总原则三：所有用例必须可判断、可观察、可验证

后续每个用例都必须满足：

* 有清晰前置条件
* 有明确执行步骤
* 有明确预期结果
* 有明确失败判定

不接受以下表述作为验收结果：

* 差不多可用
* 看起来正确
* 基本成立
* 大体符合
* 应该没问题

所有结论都必须能落成：

* 成立 / 不成立
* 有 / 没有
* 能 / 不能

这是当前阶段最严格、也最必要的原则之一。

### 1.4 总原则四：最小闭环是第一优先级

虽然本文档会包含对象、边界、反向验证等内容，

但当前验证的第一优先级始终是：

**《51》第 5 章定义的最小闭环是否真的跑通。**

也就是说，后续所有用例都应服务于这一点：

* Solution 是否成立
* Workspace 是否成立
* Project 是否成立
* 最小推进是否成立
* StepRecord 是否成立
* 必要时 Round 是否成立
* 显式切换是否成立
* 下一步入口是否成立

如果最小闭环没跑通，

其他验证即使再漂亮，也不能判定本次实现通过。

### 1.5 总原则五：边界验证是当前阶段的高优先级内容

当前 Ascend 1.0 最大的实现风险，不是“对象少了”，

而是：

**层级边界被写混。**

因此，本文档必须把以下边界作为高优先级验证点：

* Workspace 不等于 Round
* Project 不等于 Tree
* Tree 只作为 Project 默认内部结构
* 生命周期不等于 Node.status
* 生命周期不等于 Round 状态
* 生命周期不等于 Workspace 当前焦点
* StepRecord 不等于 Round

也就是说，当前阶段不仅要验证“功能有”，

还必须验证“层级没混”。

### 1.6 总原则六：当前明确不实现项必须作为一等验证对象

《51》第 3 章已经明确列出了当前不实现的内容。

这些内容不是“以后再说”，而是：

**当前必须确认没有被实现。**

因此，本文档后续必须对以下方向设置反向验证：

* 多 Round 并发
* 自动协同
* 自动升格
* 完整 UI
* 完整状态机
* 跨 Solution 关系
* 多结构类型支持
* 完整生命周期自动迁移

如果这些内容被实现，

则当前实现不是“更完整”，而是：

**越界。**

### 1.7 总原则七：任何验证都不得把“未来能力”当作当前加分项

当前阶段，所有未来方向都不应作为“实现加分项”。

例如：

* 自动路由
* 自动判定该升格
* 自动创建 Round
* 自动结束 Round
* 复杂依赖关系系统
* 完整协同图谱

如果这些内容提前做了，

本文档不会将其视为“做得更多”，

而会视为：

**偏离当前最小实现范围。**

### 1.8 总原则八：最终结论必须非黑即白

本次验收结论不允许模糊。

最终只能有两种结果：

* 通过
* 不通过

不允许：

* 基本通过
* 大部分通过
* 只差一点
* 结构上通过但实现上还差一点

因此，后续所有章节都必须服务于最后形成一条明确结论：

**当前实现是否满足《51》的总验收句。**

### 1.9 后续用例统一写法

从下一章开始，所有具体验证用例统一使用下面结构：

1. 用例名称
2. 验证目标
3. 前置条件
4. 执行步骤
5. 预期结果
6. 失败判定

这套结构从现在开始固定，不再变化。

### 1.10 本章结论

第 1 章到这里正式冻结以下内容：

1. 所有验证必须严格对齐《51-最小实现范围.md》
2. 所有验证必须同时包含正向验证与反向验证
3. 所有验证项都必须可判断、可观察、可验证
4. 最小闭环是当前阶段的第一优先级
5. 边界验证是当前阶段的高优先级内容
6. 当前明确不实现项必须作为一等验证对象
7. 所有未来能力都不得被当作当前加分项
8. 最终验收结论必须非黑即白
9. 后续用例统一采用固定结构书写

## 2. 核心闭环验证用例

### 2.1 本章目标

本章用于验证：

**《51》第 5 章定义的最小闭环是否真的跑通。**

本章中的用例，不验证未来能力，

不验证扩展能力，

只验证：

**当前 1.0 的最小正确形态能否形成一条完整可继续的链路。**

### 2.2 用例总说明

本章所有用例共同服务于一条总链路：

1. 创建 Solution
2. 在 Solution 下创建 Project
3. 建立 Workspace
4. 选中当前焦点 Project
5. 在当前 Project 内创建或进入 Node
6. 完成一次最小推进
7. 生成 StepRecord
8. 更新 Node / Tree / Project
9. 必要时创建最小 Round
10. 必要时显式切换到另一个 Project
11. 留下下一步入口

后续所有用例都必须围绕这条链路展开，

不得脱离该链路自行发散。

---

### 用例 2-1：创建 Solution

#### 验证目标

验证系统能够创建一个最小 Solution，作为当前问题空间容器。

#### 前置条件

无。

#### 执行步骤

1. 发起一个新的最终目标
2. 基于该目标创建一个 Solution

#### 预期结果

必须同时满足：

1. 系统中存在一个明确的 Solution 实体
2. 该 Solution 承接一个最终目标语义
3. 该 Solution 处于可继续挂接 Project 的状态

#### 失败判定

出现以下任一情况即判定失败：

1. 不能创建 Solution
2. 创建出的对象不是 Solution，而只是普通容器或临时上下文
3. Solution 无法承接最终目标语义
4. Solution 创建后不能继续挂接 Project

---

### 用例 2-2：在 Solution 下创建 Project

#### 验证目标

验证系统能够在某个 Solution 下创建至少一个 Project。

#### 前置条件

* 已通过用例 2-1
* 已存在一个有效 Solution

#### 执行步骤

1. 在已创建的 Solution 下创建一个 Project
2. 指定该 Project 为某一独立工作面

#### 预期结果

必须同时满足：

1. 该 Project 明确挂接于某个 Solution 下
2. 该 Project 被承认为一级独立工作对象
3. 当前默认采用 Tree 作为内部组织结构
4. 该 Project 可被后续 Workspace 选中为焦点

#### 失败判定

出现以下任一情况即判定失败：

1. 无法在 Solution 下创建 Project
2. Project 创建后未挂接到 Solution
3. 系统仍将 Tree 误当作一级单位
4. Project 创建后不能被后续工作上下文引用

---

### 用例 2-3：建立 Workspace

#### 验证目标

验证系统能够建立一个 Workspace，承接当前工作上下文。

#### 前置条件

* 已通过用例 2-1
* 已通过用例 2-2
* 已存在一个 Solution 和至少一个 Project

#### 执行步骤

1. 创建或进入一个 Workspace
2. 将该 Workspace 绑定到当前 Solution
3. 让 Workspace 准备承接当前焦点与当前入口

#### 预期结果

必须同时满足：

1. Workspace 明确绑定当前 Solution
2. Workspace 不是 Solution 本身，也不是 Project 本身
3. Workspace 具备承接当前焦点与当前入口的能力

#### 失败判定

出现以下任一情况即判定失败：

1. 无法建立 Workspace
2. Workspace 未绑定到当前 Solution
3. Workspace 被实现成 Solution 的别名
4. Workspace 无法承接当前焦点或当前入口

---

### 用例 2-4：选中当前焦点 Project

#### 验证目标

验证 Workspace 能明确选中一个当前焦点 Project。

#### 前置条件

* 已通过用例 2-3
* Workspace 已建立
* Solution 下至少存在一个 Project

#### 执行步骤

1. 在 Workspace 中选择一个当前焦点 Project
2. 将该 Project 设定为当前正式推进对象

#### 预期结果

必须同时满足：

1. Workspace 中存在唯一明确的当前焦点 Project
2. 当前焦点 Project 属于当前 Solution
3. 当前焦点选择结果可被后续推进直接使用

#### 失败判定

出现以下任一情况即判定失败：

1. Workspace 中没有焦点 Project
2. Workspace 中同时存在多个正式焦点
3. 焦点 Project 不属于当前 Solution
4. 焦点选择后无法继续推进

---

### 用例 2-5：在当前 Project 内创建或进入 Node

#### 验证目标

验证系统能够在当前焦点 Project 内创建或进入一个可推进的 Node。

#### 前置条件

* 已通过用例 2-4
* 已存在焦点 Project

#### 执行步骤

1. 在当前焦点 Project 内创建一个 Node，或进入一个已有 Node
2. 为该 Node 填充最小内容语义

#### 预期结果

必须同时满足：

1. 当前 Project 内存在一个明确 Node
2. Node 至少能承接：

* 原始内容
* 总结内容
* 当前结论
* 下一步入口
* 当前状态

1. Node 能被后续最小推进直接使用

#### 失败判定

出现以下任一情况即判定失败：

1. Project 内无法创建或进入 Node
2. Node 不具备最小内容承接能力
3. Node 只是空占位，无法进入后续推进
4. Node 语义和 Project / Round 混层

---

### 用例 2-6：完成一次最小推进

#### 验证目标

验证当前 Node 能完成一次符合统一推进契约的最小推进。

#### 前置条件

* 已通过用例 2-5
* 已存在可推进 Node

#### 执行步骤

1. 对当前 Node 发起一次最小推进
2. 执行本轮动作
3. 生成本轮结果

#### 预期结果

必须同时满足：

1. 本轮推进存在明确输入状态
2. 本轮推进存在明确本轮动作
3. 本轮推进存在明确输出结果
4. 本轮推进导致明确状态变化
5. 本轮推进形成明确下一步入口

注意：

不能只写“推进成功”，

必须能观察到上述五项推进契约。

#### 失败判定

出现以下任一情况即判定失败：

1. 只能执行动作，不能说明输入状态
2. 只能得到结果，不能说明状态变化
3. 推进后没有下一步入口
4. 所谓“推进成功”只是模糊过程，没有形成完整推进契约
5. 推进语义被错误上浮成 Round 或 Workspace 行为

---

### 用例 2-7：生成 StepRecord

#### 验证目标

验证每次局部推进后都能生成对应 StepRecord。

#### 前置条件

* 已通过用例 2-6
* 已完成一次最小推进

#### 执行步骤

1. 在当前 Node 推进完成后生成一条 StepRecord
2. 将该记录挂接到当前 Node

#### 预期结果

必须同时满足：

1. 每次最小推进后存在一条对应 StepRecord
2. StepRecord 明确挂到当前 Node
3. StepRecord 至少能表达：

* 本轮动作
* 本轮结果
* 本轮下一步入口

#### 失败判定

出现以下任一情况即判定失败：

1. 推进后没有 StepRecord
2. StepRecord 未挂接到 Node
3. StepRecord 不能表达本轮动作 / 结果 / 下一步入口
4. StepRecord 被错误实现为 Round 或 Round 的子结构

---

### 用例 2-8：更新 Node / Tree / Project

#### 验证目标

验证一次局部推进之后，Node / Tree / Project 三层能够形成最小回写。

#### 前置条件

* 已通过用例 2-7
* 已存在 StepRecord

#### 执行步骤

1. 将本轮推进结果回写到 Node
2. 保持 Tree 的最小结构承接有效
3. 让 Project 保持可继续推进状态

#### 预期结果

必须同时满足：

1. Node 已完成最小更新
2. Tree 仍然能承接当前 Node 所在的最小结构关系
3. Project 仍然处于可继续承接状态
4. 局部推进结束后，系统没有丢失继续入口

#### 失败判定

出现以下任一情况即判定失败：

1. StepRecord 生成了，但 Node 未更新
2. 推进后 Tree 结构失效或断裂
3. Project 失去可继续承接能力
4. 局部推进结束后无法找到继续入口

---

### 用例 2-9：必要时创建最小 Round

#### 验证目标

验证当变化超出单 Project 内部时，系统能够显式创建一个最小 Round。

#### 前置条件

* 已通过用例 2-8
* 当前变化已不再只是单 Project 内局部推进

#### 执行步骤

1. 显式声明当前变化进入跨 Project 承接
2. 创建一个最小 Round
3. 为该 Round 填入最小骨架内容

#### 预期结果

必须同时满足：

1. 系统能显式创建 Round
2. Round 至少承接：

* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮下一步入口

1. Round 不等于 StepRecord
2. Round 不等于 Workspace

#### 失败判定

出现以下任一情况即判定失败：

1. 无法创建 Round
2. 创建出的 Round 不具备最小骨架
3. Round 被直接实现为 StepRecord 集合
4. Round 被直接实现为 Workspace 当前状态的一部分

**高优先级边界验证。**

### 用例 3-1：Workspace 不等于 Round

#### 验证目标

验证 Workspace 和 Round 在实现中被严格区分。

#### 前置条件

* 已存在 Solution
* 已存在至少一个 Project
* 已建立 Workspace
* 必要时已创建 Round

#### 执行步骤

1. 检查 Workspace 的职责与数据承接内容
2. 检查 Round 的职责与数据承接内容
3. 对照当前实现，确认二者字段与行为边界

#### 预期结果

必须同时满足：

1. Workspace 承接的是当前工作上下文
2. Round 承接的是当前这次变化本身
3. Workspace 可以挂接当前 Round 的相关信息
4. 但 Workspace 本体不承接 Round 的最小骨架四项：

* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态

1. Round 不承接 Workspace 的焦点语义：

* 当前焦点 Project

1. Round 的最小骨架字段被直接实现为 Workspace 自身字段
2. Workspace 的当前焦点语义被直接存入 Round 作为核心职责
3. 实现中把 Round 当作“当前工作上下文对象”
4. 实现中把 Workspace 当作“当前变化对象”
5. Round 和 Workspace 在代码中没有独立对象边界，只是名字不同

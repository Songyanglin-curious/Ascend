

# Ascend 1.0 方案总览

## 1. 版本定位

Ascend 1.0 是  **探索性编码 Agent 阶段** 。

它不是完整产品，也不是最终架构。
它要验证的是：

**复杂任务能否脱离大段 prompt 的人工硬控，转而通过统一推进骨架与上层组织结构，被稳定承接、稳定推进、稳定接续。**

Ascend 1.0 当前关注的，不只是“单个对象怎么推进”，而是：

**围绕一个真实问题，多个工作对象能否在同一套系统中被组织、被推进、被记录、被接续，而不互相打架。**

---

## 2. 核心判断

Ascend 1.0 不是思考框架，而是  **任务推进框架** ；
并且它已经不再只处理单个对象推进，而开始承认 **问题空间、工作上下文、独立工作对象与变化单位** 这几层上层结构。

Ascend 1.0 的共性不在任务内容里，而在推进契约里。
它不要求所有任务共享同一种内容步骤，
它要求的是：

1. 有输入状态
2. 有本轮动作
3. 有输出结果
4. 有状态变化
5. 有下一步入口

这五项，是 Ascend 1.0 在不同任务、不同对象、不同层级之间的最小共性。

也就是说：

* 写文章和评审不一样
* 分析和改写不一样
* 学习和规则整理不一样
* 运行层和组织层也不一样

但它们都应能被压进同一种最小推进契约中。

---

## 3. 1.0 当前要解决的核心问题

Ascend 1.0 当前主要解决六件事：

1. 上下文不再依赖平铺聊天历史，而是形成正式承接结构
2. 单个工作对象不再承担全部复杂度，真实问题开始被上层组织容器承接
3. 不同任务不再混在同一次输出里，而是按 Project、Mode、Scenario、Round 分层推进
4. 每次推进都有局部记录，每次变化也有上层承接，而不是只留下最后结果
5. 任务可以形成清晰的下一步入口，而不是每次重新起头
6. 上位变化后，相关内容可以重新纳入推进，多个 Project 的协同也能被正式组织

---

## 4. Ascend 1.0 的总体结构

Ascend 1.0 现在应理解成  **两层结构共同成立** ：

1. **上层组织结构**
2. **Project 内部推进内核**

### 4.1 上层组织结构

这是当前新增、也是最关键的升层部分。
它回答的不是“Node 怎么推进”，而是：

**围绕一个真实问题，多个工作对象如何被组织起来。**

当前最小结构为：

* **Problem** ：我要达成的最终目标
* **Solution** ：围绕同一个最终目标存在的最上层组织容器
* **Workspace** ：人在某个 Solution 中当前干活时的工作上下文
* **Project** ：Solution 内部一级独立工作对象
* **Round** ：一次跨 Project 的变化组织单位

这套结构解决的是：

* 问题空间如何成立
* 当前工作上下文如何承接
* 多个独立工作面如何并存
* 一次变化如何跨 Project 被正式组织

### 4.2 Project 内部推进内核

Project 作为一级独立工作对象，内部仍然需要一套统一推进骨架。
这一套骨架保留你原来已经明确的三层结构：

#### 4.2.1 运行骨架层

它定义统一推进契约：

* 输入状态
* 本轮动作
* 输出结果
* 状态变化
* 下一步入口

这一层回答的是：

**任何推进对象在系统里，最小一次推进应该长什么样。**

#### 4.2.2 模式层

这一层定义不同类型的推进方式。
例如：

* Explore
* Select
* Write
* Review
* Revise
* Freeze

模式层回答的是：

**这一轮到底以什么方式推进。**

#### 4.2.3 场景层

这一层定义不同任务如何组织模式。
例如：

* 思考场景
* 写作场景
* 学习场景
* 规则整理场景
* 文档整理场景

场景层回答的是：

**一类任务通常如何组合推进模式。**

---

## 5. Project 内部的支撑结构

在 Project 内部推进内核之外，Ascend 1.0 还需要一组支撑结构，使默认采用 Tree 结构的 Project 能够真正落地运行。

这些支撑结构当前主要服务于：

**Project 默认采用 Tree 结构时的内部承接。**

### 5.1 Tree

Tree 不再是 Solution 内部一级单位。
它现在的定位是：

**Project 当前默认可采用的一种内部组织结构。**

它主要解决的是：

* 局部内容如何形成结构
* 父子关系如何表达
* 分支如何挂接
* 局部上下文位置如何确定

可以理解为：

**Tree 管 Project 内部结构，不再承担上层一级组织单位职责。**

### 5.2 Node

Node 是最小推进对象的内容承载体。
它主要解决的问题是：

* 当前在推进什么
* 原始内容如何保留
* 总结内容如何承接
* 当前结论如何挂住
* 下一步入口如何保留
* 当前状态如何表达

可以理解为：

**Node 管最小推进内容。**

### 5.3 StepRecord

StepRecord 负责记录某个 Node 在某个场景下完成一轮推进后的结果。
它主要解决的问题是：

* 这一轮围绕哪个对象展开
* 这一轮做了什么
* 这一轮产出了什么
* 这一轮让对象发生了什么变化
* 这一轮下一步从哪里继续

可以理解为：

**StepRecord 管局部推进留痕。**

### 5.4 Scheduler / Rescan

Scheduler 和 Rescan 负责维持 Project 内部的推进秩序。

其中：

* **Scheduler** ：负责局部推进对象的选择与继续
* **Rescan** ：负责在上位变化后识别受影响内容并重新纳入推进

可以理解为：

**Scheduler / Rescan 管局部推进秩序。**

---

## 6. 上层组织侧的新增承接内容

随着单树推进内核逐步明确，Ascend 1.0 已经额外长出了三类上层问题。
它们不是 Project 内部运行规则，但已经是 1.0 必须承认的结构。

### 6.1 Project 生命周期

Project 作为一级独立工作对象，具有自己的生命周期。
生命周期不是 Node 状态，也不是 Round 状态，而是：

**Project 作为工作对象整体如何存在。**

当前 1.0 先冻结为四段：

* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档

同时，当前正式承认不同 Project 生命周期存在差异：

* 长期承接型
* 临时型
* 派生型

### 6.2 多 Project 协同

只要一个 Solution 中有多个 Project，共同服务于同一个最终目标，协同就会自然出现。
当前 1.0 冻结的最小协同原则是：

* 多 Project 协同是正式问题
* 协同不等于并发推进
* 一次只推进一个 Project
* 协同通过顺序推进实现
* 当前这次协同变化由 Round 正式承接

### 6.3 派生产物升格

某个 Project 的结果，并不天然自动升格为新的 Project。
当前 1.0 冻结的最小判断是：

**当某个结果已经形成新的独立工作面，并且继续留在原 Project 中会造成混层时，它应升格为新的 Project。**

这意味着，Ascend 1.0 已经正式承认：

* 结果可以继续留在原 Project 内
* 结果也可以升格为新的 Project
* 升格判断的核心不在“是不是新内容”，而在“是不是新的独立工作面”

---

## 7. Ascend 1.0 的统一运行方式

现在 Ascend 1.0 的统一运行方式，已经不能只压成一句“对象挂在上下文中推进”。
更完整的理解应该是：

**围绕一个最终目标，多个 Project 被组织在 Solution 中；人在 Workspace 中以当前工作上下文进入某个焦点 Project；Project 内部再通过统一推进契约完成局部推进，留下 StepRecord，必要时形成新的 Round、触发协同、派生新的 Project，并持续形成下一步入口。**

把它展开，可以写成：

1. 当前存在一个最终目标
2. 该目标由一个 Solution 承接
3. Solution 内存在多个 Project
4. 人通过 Workspace 进入当前工作上下文
5. 当前焦点落在某个 Project 上
6. Project 内部根据当前状态、场景与模式继续推进
7. 推进产生局部结果与 StepRecord
8. 若变化跨 Project，则由 Round 正式承接
9. 若结果形成新的独立工作面，则可升格为新的 Project
10. 若上位变化影响既有内容，则通过 Rescan 等机制重新纳入推进
11. 最终持续形成下一步入口，而不是每次重新起头

---

## 8. Ascend 1.0 对任务差异的处理方式

Ascend 1.0 仍然不要求所有任务共享同一种内容步骤。
它要求的是：

* **共享同一种推进契约**
* **通过 Mode 处理推进方式差异**
* **通过 Scenario 组织具体推进路径**
* **通过 Project 区分独立工作面**
* **通过 Round 承接跨 Project 变化**
* **通过 Solution 承接同一个最终目标**

因此：

* 思考任务可以偏探索、选择、冻结
* 写作任务可以偏组织、生成、修订
* 评审任务可以偏检查与反馈
* 学习任务可以偏理解、提炼、校验
* 文档、规则、AI 指令等结果也可以在必要时升格成独立 Project

这样系统既有共性，也保留了层级化扩展性。

---

## 9. Ascend 1.0 的边界

Ascend 1.0 当前不做这些事：

1. 不追求完整自治
2. 不追求覆盖所有任务类型
3. 不追求复杂多 Agent 协同
4. 不追求一次性做成最终产品
5. 不追求完整的 Project 结构类型体系
6. 不追求完整的 Round 状态机与自动组织机制
7. 不追求完整的生命周期自动迁移与自动归档
8. 不追求完整的多 Project 自动编排机制
9. 不追求完整的派生产物分类学
10. 不追求完整的 Workspace UI 设计

Ascend 1.0 当前只验证一件事：

**统一推进骨架加上最小上层组织结构，是否足以把复杂任务从纯 prompt 阶段推进到可持续承接、可持续接续的编码阶段。**

---

## 10. 1.0 当前阶段目标

### 阶段一：Project 内部推进内核成立

确认统一推进契约、Mode、Scenario、Node、StepRecord、Scheduler / Rescan 能支撑单个 Project 的持续推进。

### 阶段二：上层组织结构成立

确认 Solution、Workspace、Project、Round 这几层已经形成稳定边界。

### 阶段三：Project 生命周期成立

确认 Project 不再只是“创建后一直存在”的对象，而是具有最小生命周期骨架。

### 阶段四：多 Project 协同与派生成立

确认多个 Project 可以围绕同一目标顺序协同，且结果在必要时可升格为新的 Project。

### 阶段五：形成实现输入

将上述结构压成：

* 最小实现范围
* 类型冻结
* 实现顺序
* AI 编码输入物
* 最小验证用例

---

## 11. 一句话定义

**Ascend 1.0 是一套围绕最终目标组织多个 Project 的探索性编码方案：它以 Solution 承接问题空间，以 Workspace 承接当前工作上下文，以 Project 承接独立工作面，以 Round 承接跨 Project 变化，以统一推进契约、Mode、Scenario 驱动 Project 内部推进，并以 Tree / Node / StepRecord / Scheduler / Rescan 支撑默认 Tree 结构下的局部运行。**

先只收  **Scheduler 在 1.0 里承担哪些具体功能** ，不展开实现。

我建议它先只承担 5 个功能。

## 1. 候选过滤

先判断哪些 Node 有资格进入本轮候选。

它至少看这些条件：

* `activeStatus = 启用`
* `status != 已完成`
* 必要时排除 `已冻结`

也就是说，Scheduler 第一件事不是“选谁”，而是先把 **不该碰的节点排除掉** 。

## 2. 当前节点选择

在候选节点里，选出 **当前要推进的那个 Node** 。

这就是它最核心的职责。
它解决的是：

**现在先讨论谁。**

注意，这里是“首选选择”，不是一次把所有节点排好长期计划。

## 3. 模式选择

在当前 Node 已知 `scenario` 的前提下，选择本轮 `mode`。

例如：

* `scenario = 思考`，更可能选 `Explore / Select / Freeze`
* `scenario = 写作`，更可能选 `Write / Review / Revise`

所以它第二个核心职责是：

**现在用什么方式推进这个节点。**

## 4. 人工介入判断

Scheduler 还要判断：

**这一轮能不能直接推进，还是必须交给人。**

例如这些情况就该触发人工：

* 候选节点并列，规则无法明显区分
* 当前 Node 的 `next` 不明确
* 当前场景下可选 mode 不止一个，而且差异很大
* 涉及冻结、切换方向、重新激活停用节点

所以它不只是“自动选”，还要负责：

**什么时候不该自动选。**

## 5. 重新纳管入口

当 Rescan 或人工操作把某些节点重新送回来时，Scheduler 要负责把它们重新纳入当前候选。

也就是说它还承担一个很轻的职责：

**把新进入运行范围的节点，重新接入推进流。**

---

## 不该它负责的事

为了边界清楚，也一起定一下它 **不负责什么** ：

* 不负责承载内容，那是 Node
* 不负责关系组织，那是 NodeTree
* 不负责记录推进，那是 StepRecord
* 不负责定义模式语义，那是 Mode
* 不负责定义场景语义，那是 Scenario
* 不负责真正执行内容生成，它只是选，不是做

---

## 一句话压住

**Scheduler 在 1.0 里负责：过滤候选节点、选当前推进对象、选本轮模式、判断是否需要人工介入、接收重新纳管的节点。**

如果按最短版本压成 3 句话，就是：

* 选谁
* 怎么推进
* 什么时候别自动选

下一小步最自然的是：
只继续讨论  **Scheduler 选当前 Node 时，优先依据哪些信息** 。

这一轮只回答：

**Scheduler 选当前 Node 时，优先依据哪些信息。**

我建议 1.0 先只看  **6 类信息** ，而且分主次。

## 第一优先级：是否可进入候选

这是门槛，不是排序。

先看：

* `activeStatus` 是否为 **启用**
* `status` 是否不是 **已完成**
* 必要时，`已冻结` 默认不进入，除非被重新打开

也就是说：

**先判有没有资格被选。**

## 第二优先级：节点推进状态

在有资格的节点里，先看 `status`。

我建议优先顺序先这样：

1. `进行中`
2. `未开始`
3. `已冻结`（仅在被重新纳管时）
4. `已完成`（不选）

原因很简单：

**先收口，再开新口。**

已经在推进中的节点，通常比新开节点更适合优先处理。

## 第三优先级：`next` 是否明确

再看这个节点有没有清晰的下一步入口。

因为：

* `next` 明确，说明这个节点更容易低摩擦继续
* `next` 不明确，说明还缺承接条件，或者需要先人工判断

所以：

**有明确 `next` 的节点，优先于没有明确 `next` 的节点。**

## 第四优先级：`scenario`

再看它属于什么场景。

不是说哪个场景永远更高，而是：

**当前系统/当前会话正在处理什么类型的任务，就优先同类场景节点。**

比如你当前正在处理“架构设计”，那：

* `scenario = 思考`
* `scenario = 设计`
* `scenario = 写作（方案整理）`

这些会比“学习某个新概念”的节点更近。

所以 `scenario` 的作用是：

**判断这个节点和当前任务上下文是不是同路。**

## 第五优先级：NodeTree 位置

再看它在树里的位置。

这里 NodeTree 提供两个信息：

* 它离当前焦点节点远不远
* 它在同级里的 `order`

优先原则可以先很朴素：

* 当前焦点附近的节点优先
* 同级冲突时按 `order`

所以：

**NodeTree 提供位置与顺序，帮助 Scheduler 做最后排序。**

## 第六优先级：人工指定 / 外部触发

如果有这些情况，可以直接提高优先级：

* 用户刚点了某个节点
* 某个节点刚被人工启用
* Rescan 刚把某个节点重新送回候选池

也就是说：

**人工显式关注 > 普通自动排序。**

---

## 压成一个最小顺序

Scheduler 选当前 Node 时，先看：

1. 能不能进候选池
2. 是不是进行中
3. `next` 是否明确
4. `scenario` 是否贴近当前任务
5. 在树里离当前焦点是否更近
6. 并列时按 `order`
7. 有人工指定时优先人工指定

---

## 最短一句话

**Scheduler 先依据启用状态和推进状态过滤候选，再优先选择“正在进行、next 明确、场景贴近当前任务、位置更接近当前焦点”的节点。**

下一条如果继续，最自然的是只做一个小点：

**这些依据里，哪些必须写死成规则，哪些可以让人工覆盖。**

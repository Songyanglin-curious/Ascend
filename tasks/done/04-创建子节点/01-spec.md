# 01-spec：节点结束后的候选子节点提取与确认创建

## 摘要

- 本 spec 只定义一个新的独立后处理阶段：当一个 `Node` 的场景执行结束后，系统如何从其原始对话记录中提取候选子节点，如何交给人确认，以及如何在确认后正式创建真实子节点并维护树关系。
- 本 spec 不改 `advance` 场景内部 A/B/C 推进逻辑，不改现有 `Node / Tree` 的最小承载原则，只在其外层新增“候选子节点提取与确认创建”能力。
- 本 spec 中的“子节点提取 Agent”必须与场景工作流解耦。它不是 `advance` graph 内部节点，也不属于 `TreeStore` 的职责。
- 本批只冻结最小契约：候选子节点数据结构、提取阶段、人工确认阶段、真实子节点创建阶段、异常边界与验收场景。具体文件拆分和函数命名留到 `02-plan.md`。

## 目标与范围

本批目标只有 2 个：

1. 在父节点场景结束后，基于该节点返回的原始对话内容提取候选子节点
2. 将候选子节点交给人确认；确认通过后创建真实子节点，并挂接到现有树关系上

本批范围内：

- 基于已完成父节点的原始对话记录提取候选子节点
- 提取结果必须是严格可解析的 JSON
- 提取结果必须经过人确认
- 人确认后创建真实子节点
- 维护父节点与新子节点的树关系

本批明确不做：

- 不改 `advance` 场景内部 workflow 行为
- 不做 UI
- 不做自动确认
- 不做自动执行新子节点
- 不做复杂树操作，例如移动节点、删除子树、重排
- 不做图结构扩展，当前仍只支持树
- 不做回扫关系
- 不做总结生成

## 事实基础

- 当前仓库已经存在一个可运行的 `advance` 场景工作流，并且可以在结束时返回场景原始结果
- 当前仓库已经存在最小 `NodeStore / TreeStore / TreeService`
- 当前 `TreeStore` 只保存父子关系，不保存节点业务内容
- 当前 `executeSceneNode(...)` 只负责“进入节点 -> 执行场景 -> 返回原始结果 -> 节点结束”
- 因此，本批正确方向不是把“子节点提取”塞进场景内部，也不是把“候选子节点”塞进树结构，而是新增一个独立的后处理阶段

## 核心概念

### 1. Parent Node

- `Parent Node` 指刚刚完成场景执行并已拿到原始结果的节点
- 本批所有候选子节点都来源于某个 `Parent Node`

### 2. Child Candidate Extractor

- `Child Candidate Extractor` 是一个独立 Agent / 独立处理单元
- 它的唯一任务是：从父节点的原始对话记录中提取“值得成为子节点的候选分支”
- 它不负责：
  - 执行场景
  - 创建真实节点
  - 写树关系
  - 自动决定是否采用候选子节点

### 3. Child Candidate

- `Child Candidate` 是“候选子节点”，不是实际节点
- 它只是从父节点原始对话中提取出来的结构化候选分支
- 在经过人确认前，它不能进入 `NodeStore`，也不能进入 `TreeStore`

### 4. Human Confirmation

- `Human Confirmation` 是候选子节点进入真实树结构前的强制门禁
- 没有人确认，系统不得自动创建真实子节点

### 5. Real Child Node

- `Real Child Node` 是确认通过后正式创建的节点
- 它必须进入 `NodeStore`
- 它必须通过 `TreeService` 连接到对应父节点

## 提取原则

`Child Candidate Extractor` 必须遵守以下硬约束：

1. 只提取“可独立推进”的分支
2. 优先提取三类分支：
   - 新问题
   - 分支方向
   - 关键约束
3. 不得改写原意
4. 不得补充模型自己的新想法
5. 不得把“总结”“重述”“细节补充”误提为子节点
6. 语义重复的候选必须合并
7. 默认提取 3 到 5 个；不足则少给，不强凑

## 数据契约

### 1. 候选子节点原始输出

提取 Agent 的原始输出必须是严格 JSON 数组，数组项至少表达以下语义：

```ts
type ChildCandidateType = "question" | "direction" | "constraint";

interface ChildCandidateRawItem {
  title: string;
  summary: string;
  type: ChildCandidateType;
  reason: string;
  evidence: string;
}
```

约束：

- `title` 必须是一句话级别的候选子节点名称
- `summary` 必须贴近原对话语义
- `type` 只允许 `question | direction | constraint`
- `reason` 必须说明为何值得成为子节点
- `evidence` 必须对应原对话中的依据
- 输出必须是合法 JSON；不得输出 markdown 包裹、额外说明文或自然语言前后缀

### 2. 规范化后的候选子节点

为便于后续人工确认与创建真实节点，系统层必须把原始输出规范化为运行时候选对象。

spec 层冻结其语义，不强钉最终字段命名；它至少必须能表达：

- 候选自身的稳定标识
- 来源父节点 id
- `title`
- `summary`
- `type`
- `reason`
- `evidence`

说明：

- 提取 Agent 的原始 JSON 中不要求自带稳定 `candidateId`
- 系统可以在解析成功后为候选生成运行时 id，供人工确认时引用

### 3. 真实子节点最小内容

确认通过后创建的真实子节点，不能只是“一个空 id”。

spec 层要求：真实子节点至少必须保留以下语义之一的等价表达：

- 它来源于哪个父节点
- 它对应哪个已确认候选
- 它的 `title`
- 它的 `summary`
- 它的候选类型

spec 层此处只冻结“必须保留这些语义”，不强制具体字段名，也不强制这些信息一定落在 `sceneInput` 还是节点元数据中。

### 4. Tree 契约不变

- `TreeStore` 继续只存父子关系
- 真实子节点创建后，树层只新增关系，不保存候选内容
- 候选子节点本身不进入 `TreeStore`

## 最小时序

本批冻结的最小时序为：

1. 父节点执行结束  
   条件：父节点已经获得场景原始结果

2. 独立调用候选子节点提取 Agent  
   输入：父节点的原始对话记录  
   输出：严格 JSON 的候选子节点数组

3. 系统解析并校验候选子节点  
   结果：
   - 合法：进入人工确认阶段
   - 不合法：提取阶段失败，不创建子节点

4. 人工确认  
   人可以：
   - 确认某个候选子节点
   - 拒绝全部候选子节点

5. 创建真实子节点  
   仅对已确认候选执行：
   - 创建真实 `Node`
   - 将确认候选语义写入该节点

6. 维护树关系  
   使用现有树服务将新节点挂到父节点下

7. 本次后处理结束  
   说明：
   - 新子节点默认只创建，不自动执行
   - 本批不递归触发孙节点生成

## 人工确认契约

### 1. 确认是强制步骤

- 没有人工确认，不得创建真实子节点

### 2. v1 的最小确认能力

为控制复杂度，v1 只冻结最小能力：

- 系统必须能把候选子节点展示给人
- 人必须能明确选择“添加”或“不添加”

是否支持一次确认多个候选、是否支持编辑候选文案，留到 `02-plan.md` 决定。

### 3. 拒绝全部候选时

- 不创建任何新节点
- 不改树关系
- 父节点原有状态保持不变

## 成功与失败路径

### 1. 提取成功但没有候选

- 允许返回空数组
- 空数组不是错误
- 后续不进入节点创建

### 2. 提取结果不是合法 JSON

- 视为提取阶段失败
- 不创建任何子节点
- 不得静默 fallback 成空数组

### 3. 提取结果字段不合法

例如：

- 缺少必要字段
- `type` 不在允许枚举内
- 字段为空且无法继续使用

处理要求：

- 视为提取阶段失败
- 不创建任何子节点

### 4. 人工拒绝

- 不是错误
- 只是“不新增子节点”

### 5. 创建真实子节点或挂树关系失败

- 视为后处理失败
- 错误必须显式抛出或返回明确失败结果
- 不得伪造“创建成功”

## 模块边界

### 1. advance Scene

继续负责：

- 场景内部推进
- 场景原始结果

不负责：

- 提取候选子节点
- 人工确认
- 创建子节点
- 写树关系

### 2. Child Candidate Extractor

负责：

- 读取父节点原始对话
- 输出候选子节点 JSON

不负责：

- 执行场景
- 管理节点 id
- 管理树关系
- 决定是否正式创建子节点

### 3. Node / Tree 模块

负责：

- 创建真实节点
- 保存节点内容
- 维护父子关系

不负责：

- 提取候选分支
- 自动批准候选

## 最小公共接口语义

本批 spec 至少冻结以下公共接口语义：

```ts
extractChildCandidates(...)
confirmChildCandidate(...)
createChildNodeFromCandidate(...)
createChild(...)
```

说明：

- 最终函数名可在 `02-plan.md` 调整
- 但 4 类行为必须存在：
  - 候选提取
  - 人工确认
  - 从候选创建真实节点
  - 建立父子关系

## 验收场景

### 1. 父节点结束后成功提取候选子节点

- 能从父节点原始对话中提取出候选子节点数组
- 提取结果是合法 JSON

### 2. 候选子节点为空

- 系统接受空数组
- 不报错
- 不创建真实子节点

### 3. 候选子节点经过人工确认后创建真实节点

- 真实节点被成功创建
- 节点能按 id 读取

### 4. 真实子节点被正确挂到父节点下

- 父节点的 `childrenIds` 包含新子节点
- 新子节点的 `parentId` 指向父节点

### 5. 人工拒绝全部候选

- 不创建任何子节点
- 树关系不变

### 6. 提取输出非法

- 非法 JSON 或非法字段都应被识别为失败
- 不得偷偷回退为空数组
- 不得创建节点

### 7. 子节点提取逻辑与场景工作流解耦

- 不需要侵入 `advance` graph 内部节点职责
- 提取阶段作为独立逻辑单元存在

## 默认假设

- v1 中候选子节点提取发生在父节点已拿到完整场景原始结果之后
- v1 中提取输入以“原始对话记录”为准，不要求依赖 `advance` 内部状态字段
- v1 中真实子节点仍挂在当前树结构之下，不扩展成 DAG 或图
- v1 中新建子节点默认不自动执行
- 本 spec 只冻结行为与契约；具体文件名、函数签名、CLI 交互细节、测试命令留到 `02-plan.md`

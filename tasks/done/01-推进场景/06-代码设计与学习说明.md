# 代码设计与学习说明

## 先看结论

- 这套代码不是把“所有逻辑都塞进 LangGraph”，而是把**适合做状态流转的部分**交给 LangGraph，把**适合做终端交互和进程控制的部分**留在 Node.js/CLI 层。
- 如果你先抓住这条主线，再回头看每个文件，会容易很多：
  - `index.ts`：程序入口，只负责装配
  - `model.ts`：模型适配层，只负责“怎么跟 LLM 说话”
  - `prompts.ts`：提示词与 prompt 拼装，只负责“给模型什么输入”
  - `nodes.ts`：节点逻辑，只负责“每个节点做什么”
  - `graph.ts`：工作流路由，只负责“节点之间怎么跳”
  - `cli.ts`：终端交互，只负责“每轮怎么收输入、怎么决定要不要进图、什么时候结束”
  - `types.ts`：统一状态与公共类型

---

## 一、整体调用链

程序真正跑起来时，链路是这样的：

1. `pnpm dev`
2. Node.js 用 `tsx` 直接执行 [src/index.ts](D:/code/Ascend/src/index.ts)
3. [src/index.ts](D:/code/Ascend/src/index.ts) 先加载环境变量，再创建模型、创建 LangGraph、启动 CLI
4. [cli.ts](D:/code/Ascend/src/workflows/advance/cli.ts) 进入循环，每次读取一行输入
5. CLI 先判断：
   - 是不是显式退出
   - 是不是 `await_c_intent` 下的 filler 输入
   - 如果都不是，再进入 graph
6. [graph.ts](D:/code/Ascend/src/workflows/advance/graph.ts) 根据当前 `phase` 决定从哪个节点开始
7. [nodes.ts](D:/code/Ascend/src/workflows/advance/nodes.ts) 调模型，返回局部状态更新
8. LangGraph 把这些局部更新合并回总状态
9. CLI 再决定：
   - 是否结束工作流
   - 是否提示 `EMPTY`
   - 是否继续下一轮

你可以把它理解成：

- **CLI** 是“回合驱动器”
- **LangGraph** 是“回合内部状态机”
- **LLM** 是“节点里的判断/生成引擎”

## 二、为什么这样拆文件

### 1. `index.ts` 只做装配

[src/index.ts](D:/code/Ascend/src/index.ts) 很短，这是故意的。

原因：

- 入口文件最怕一上来就混进业务细节
- 入口应该像“组装总开关”，而不是“实现总开关”
- 以后不管你换 CLI、换 Web、换 API server，业务内核都尽量不动

所以它只做三件事：

1. 读环境变量
2. 创建模型
3. 创建图并运行 CLI

这是一种很典型的 Node.js 分层思路。

### 2. `types.ts` 单独存在，是为了让“状态定义”先于“逻辑实现”

[src/workflows/advance/types.ts](D:/code/Ascend/src/workflows/advance/types.ts) 里放了：

- `AgentState`
- `HandoffRecord`
- `ProblemState`
- `Phase`
- `WorkflowEndReason`
- `AdvanceStateAnnotation`

这样做的原因是：

- 工作流代码最核心的不是“某个函数怎么写”，而是“系统状态到底长什么样”
- 如果状态不先冻结，后面的 CLI、graph、nodes 很容易各写各的

也就是说，这里先定义“这个系统的真相”，后面的文件都只能围绕这个真相工作。

### 3. `model.ts` 单独抽象，是为了让图和测试脱离真实网络

[src/workflows/advance/model.ts](D:/code/Ascend/src/workflows/advance/model.ts) 里最重要的不是 DeepSeek 适配本身，而是这句接口：

```ts
interface WorkflowModel {
  complete(messages: PromptMessage[]): Promise<string>;
}
```

这句接口的意义非常大：

- 对 graph 来说，它不用知道 DeepSeek、OpenAI SDK、API key 是什么
- 对测试来说，它可以塞一个假的 model stub
- 对未来来说，你要换模型，只要保证 `complete()` 行为不变，其他地方可以不改

这就是“面向接口编程”在这里的最实际价值。

这里还有一个这次重构后的关键变化：

- 旧写法：`systemPrompt + userPrompt`，本质上是把历史对话拍平成普通字符串
- 新写法：`PromptMessage[]`，显式保留 `system / user / assistant` 的角色结构

为什么这一步值得做：

- 模型更容易分清“规则”“历史上下文”“当前这轮用户输入”
- `evaluate / action` 这类多轮分析节点，天然更适合吃结构化历史消息
- `recognizeIntent` 可以只喂 3 条消息：上一轮 C 输出、当前用户回复、节点自己的 system 规则
- 测试可以直接断言 prompt 结构，而不只是断言最后产出的文本

### 4. `prompts.ts` 单独抽出，是为了让“节点职责”和“提示词内容”分离

如果 prompt 直接写在 `nodes.ts` 里，会有两个问题：

- 节点代码会很长，业务控制流不清楚
- 以后改 prompt 时，很容易误碰节点逻辑

现在拆开以后：

- `nodes.ts` 负责“什么时候调模型、调完怎么解释结果”
- `prompts.ts` 负责“给模型看什么文字”

这对后续调 prompt 很有帮助。

### 5. `nodes.ts` 和 `graph.ts` 分开，是为了区分“节点做什么”和“节点怎么连”

这是 LangGraph 特别值得掌握的一点。

很多初学者会把这两件事混在一起：

- 一个节点里既做业务，又顺手决定下一步去哪

这样写短期看着快，长期非常容易乱。

我们这里刻意拆开：

- [nodes.ts](D:/code/Ascend/src/workflows/advance/nodes.ts) 只负责**节点内部逻辑**
- [graph.ts](D:/code/Ascend/src/workflows/advance/graph.ts) 只负责**节点之间的路由**

这样你读代码时会更清楚：

- “这个节点返回了什么”
- “图根据这个状态跳到哪里”

### 6. `cli.ts` 单独存在，是因为 CLI 不等于工作流

这是这套代码里最容易忽略、但最关键的设计点之一。

CLI 负责的是：

- 读终端输入
- 打印输出
- 判断显式退出
- 判断 filler 输入
- 在结束时生成 `HandoffRecord`

这些事都**不是 LangGraph 节点本身的职责**。

如果把它们也塞进图里，会出现两个坏处：

- 图会承担太多“环境相关”的东西
- 测试和迁移到别的入口会更难

所以我们把它放在图外，CLI 像一层“壳”，LangGraph 像“内核”。

## 三、Node.js 相关：这段代码到底依赖了什么环境能力

你说自己对 JS 有基础，但对 Node.js 不熟，这里我按“本项目实际用到的东西”来讲。

### 1. Node.js 在这里不是“语言”，而是“运行环境”

JavaScript 是语言。
Node.js 是让 JavaScript 能在本地机器上跑起来的运行环境。

在这个项目里，Node.js 主要提供了几类能力：

- 运行 TypeScript 编译后的 JavaScript
- 读环境变量 `process.env`
- 跟终端交互
- 退出进程
- 跑测试

也就是说，这里不是浏览器环境，而是服务端/命令行环境。

### 2. `import "dotenv/config"` 在做什么

在 [src/index.ts](D:/code/Ascend/src/index.ts) 顶部有：

```ts
import "dotenv/config";
```

它的作用是：

- 在程序一启动时就读取项目根目录下的 `.env`
- 把里面的键值放进 `process.env`

这样后面 `model.ts` 里就能直接读：

```ts
process.env.DEEPSEEK_API_KEY
```

如果没有这句：

- 你本地 `.env` 里的 key 不会自动进入运行时

### 3. `process.env` 是什么

`process` 是 Node.js 提供的全局对象。

你可以把它理解成“当前 Node 进程的信息和控制面板”。

这里主要用了两块：

- `process.env`：环境变量
- `process.exit(1)`：异常退出进程

为什么只允许在入口文件里 `process.exit(1)`？

因为如果底层模块也直接退出进程：

- 测试会很难写
- CLI 以外的调用方会被突然终止
- 模块复用性会变差

所以底层只抛错，顶层决定是否退出。

### 4. `readline/promises` 在做什么

[cli.ts](D:/code/Ascend/src/workflows/advance/cli.ts) 里用了：

```ts
import { createInterface } from "node:readline/promises";
```

它的作用是：

- 在终端里显示 prompt
- 等用户输入一行
- 以 Promise 方式拿到结果

为什么用 `readline/promises`，而不是老式回调？

因为我们的主流程本来就是 `async/await` 风格，用 Promise 版会更顺。

### 5. `pnpm dev / build / test` 分别在做什么

#### `pnpm dev`

执行的是：

```json
"dev": "tsx src/index.ts"
```

意思是：

- 用 `tsx` 直接执行 TypeScript 文件
- 不需要你先手动编译到 `dist`

这个最适合开发期调试。

#### `pnpm build`

执行的是：

```json
"build": "tsc -p tsconfig.json"
```

意思是：

- 用 TypeScript 编译器把 `src/**/*.ts` 编译到 `dist`

这一步主要验证“代码是否能被正式编译”。

#### `pnpm typecheck`

执行的是：

```json
"typecheck": "tsc --noEmit"
```

意思是：

- 只做类型检查
- 不产出编译文件

它比 `build` 更适合快速发现类型错误。

#### `pnpm test`

执行的是：

```json
node --import tsx --test src/workflows/advance/workflow.test.ts
```

意思是：

- 用 Node 自带 test runner 跑测试
- 通过 `--import tsx` 让 Node 能直接理解 `.ts`

这是一个比较“Node 原生”的测试方式，不依赖 Jest / Vitest。

## 四、LangGraph 相关：把这套实现对应回概念

如果你第一次看 LangGraph，最容易糊的是几个概念：

- 状态是什么
- 节点是什么
- 边是什么
- 为什么节点只返回局部更新

我按这套代码来讲。

### 1. `Annotation.Root` 是“状态 schema + 合并规则”

在 [types.ts](D:/code/Ascend/src/workflows/advance/types.ts) 里：

```ts
export const AdvanceStateAnnotation = Annotation.Root({
  ...
});
```

你可以把它理解成：

- 先告诉 LangGraph：这张图维护哪些状态字段
- 再告诉 LangGraph：当节点返回更新时，这些字段怎么合并

这里最关键的是 `messages`：

```ts
messages: Annotation<BaseMessage[]>({
  reducer: appendMessages,
  default: () => [],
})
```

意思是：

- 默认值是空数组
- 节点如果返回新的 `messages`，不是覆盖，而是追加

其他字段则用 `replaceWithLatest`：

- 谁最后返回，谁覆盖当前值

这正好符合我们的业务：

- `messages` 是日志，要累积
- `phase/currentState/rawInput/...` 是当前状态，要覆盖

### 2. `StateGraph` 是“围绕一个共享状态运行的有向图”

在 [graph.ts](D:/code/Ascend/src/workflows/advance/graph.ts) 里：

```ts
new StateGraph(AdvanceStateAnnotation)
```

这表示：

- 这张图里所有节点共享同一个状态对象
- 每个节点拿到的是当前状态
- 每个节点返回的是局部更新
- LangGraph 负责把这些更新合并回总状态

### 3. `START` / `END` 是保留节点名

在 LangGraph 里：

- `START` 表示入口
- `END` 表示当前 invocation 结束

注意这里的 `END` 很重要：

**它结束的是这次 graph invocation，不一定结束整个工作流。**

这也是为什么：

- `normalize=EMPTY` 时图会走到 `END`
- 但 CLI 不会结束，而是继续等待下一轮输入

这个区别你一定要记住：

- **图结束**
- **工作流结束**

不是一回事。

### 4. 节点为什么只返回局部更新

比如 `actionCNode` 返回：

```ts
{
  messages: [new AIMessage(normalized)],
  lastAssistantOutput: normalized,
  phase: "await_c_intent"
}
```

而不是返回整个完整 `AgentState`。

原因有两个：

1. 这样节点更专注  
   节点只管自己改动的字段。

2. 这样更适合图组合  
   LangGraph 会按照 Annotation 规则把局部更新合并起来。

这和 React 里“只更新自己关心的状态片段”有一点像，但这里是工作流状态，不是 UI state。

### 5. 条件边在这里的真实作用

比如：

```ts
.addConditionalEdges("evaluateStateNode", routeAfterEvaluate, [
  "actionANode",
  "actionBNode",
  "actionCNode",
])
```

它的含义是：

- `evaluateStateNode` 先跑
- 然后 `routeAfterEvaluate()` 读状态
- 决定下一跳是 A、B 还是 C

这就是为什么我们说：

- evaluate 只判态
- graph 负责分流

如果把分流逻辑放回节点，图的价值就会被削弱很多。

### 6. 为什么 `reject` 不是直接结束，而是“同轮回到 normalize”

这是这套工作流最关键的设计之一。

用户在 C 后说：

- “我觉得还差一点，再看看成本”

这句话不是退出，也不是确认。
它其实是一条**新的业务输入**。

所以 `recognizeIntentNode` 做完二选一以后：

- `confirm`：`phase=ended`
- `reject`：`phase=normal`、`currentState=null`

然后图从 `normalizeInputNode` 重新开始，继续使用同一条 `rawInput`。

这样做的好处是：

- 不需要用户再重复输入一次
- “打回继续推进”是一个真正闭环

## 五、为什么 `messages` 写入责任要卡这么死

这是整个实现里最容易“看起来小，实际上很关键”的点。

如果不限制写入责任，会出现两个典型 bug：

1. 同一条用户输入被记两次
2. 同一条 assistant 输出被 CLI 和节点各写一次

所以现在的规则是：

- CLI 写 user message
- `actionA/B/C` 写业务 assistant message
- `normalize/evaluate/recognizeIntent` 不写 message
- CLI 只在两种固定提醒时写 assistant message

这套规则的目的不是“形式整齐”，而是为了保证：

- 转录能真实反映用户与系统的对话
- `reject` 同轮重评不会产生重复消息

这也是为什么 `recognizeIntentNode` 虽然是一个节点，但它不写 assistant message。

因为它的职责只是做控制判断，不是对用户说话。

## 六、为什么 `EMPTY` 不直接结束整个工作流

因为 `EMPTY` 表示的是：

- 这次输入没法进入有效分析

它不表示：

- 用户不想继续了
- 工作流已经完成了

所以这里必须区分两层：

### 图内语义

- `normalizeInputNode` 输出 `EMPTY`
- graph 走到 `END`
- 本次 invocation 结束

### CLI 语义

- 给用户一条固定提醒
- 保持 `phase` 不变
- 等下一轮输入

如果把 `EMPTY` 直接做成工作流结束，会有两个问题：

- 用户只是不小心输空了，流程却直接没了
- `HandoffRecord` 会混进很多不该结束的情况

---

## 七、为什么 `HandoffRecord` 要统一从 CLI 出口生成

结束路径有两条：

- 显式退出
- confirm 结束

如果这两条路分别在不同地方自己拼记录，很容易产生：

- 字段不一致
- 记录时机不一致
- 某一条路漏掉最新状态

所以现在统一约定：

- graph 只负责把 `phase` 变成 `ended`
- CLI 看到结束后，统一调用 `buildHandoffRecord()`

这是一种“单一出口”设计。

好处是：

- 结束记录规则更稳定
- 后面你要扩字段，只改一个地方

比如：

- 并行分支

这些现在还不是这套代码的重点，先别急着上。

## 十、你可以怎么自己动手练

如果你想拿这套代码练手，我建议按这个顺序：

3. 把 CLI 的固定提示文案抽成单独常量文件
4. 尝试增加一个“调试模式”，打印每轮进入了哪个节点
5. 最后再考虑把 CLI 换成 Web API，而保持 graph/nodes 不变

这个练习顺序的目的，是让你体会：

- 好的分层能让入口形式变化，但核心工作流不跟着散架

## 最后的理解框架

你可以先把这套代码压缩成一句话：

**Node.js 负责把程序跑起来并和终端交互，LangGraph 负责维护工作流状态和节点路由，LLM 负责在节点内部做判断或生成。**

只要这句话你已经真正吃透，后面再读这套代码，就不会只是在看语法了。

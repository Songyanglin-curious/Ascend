
## 0. 文档目标与边界

### 0.1 文档目标

本文档用于定义：

**Ascend 1.0 当前最小实现范围的实际推进顺序与阶段拆分。**

它不负责重新讨论：

* 方案是什么
* 为什么这么设计
* 最小实现范围是什么
* 验收标准是什么

它只负责回答：

1. 当前这次实现按什么顺序推进
2. 应拆成几个阶段
3. 每一阶段先做什么、后做什么
4. 哪些东西当前不能抢跑

也就是说，这份文档的作用是：

**把《51》的施工边界，翻译成实际的推进顺序。**

### 0.2 本文档在整个执行文档组中的位置

当前执行文档组分工如下：

* **《51-最小实现范围.md》** ：定义本次做什么 / 不做什么
* **《54-验证用例.md》** ：定义做到什么算通过 / 不通过
* **《52-实现计划.md》** ：定义这次按什么顺序做

所以本文档既不是范围文档，也不是验收文档，

而是：

**推进顺序文档。**

### 0.3 本文档只解决什么

本文档只解决以下问题：

1. 当前实现应该拆成几个阶段
2. 这些阶段的先后顺序是什么
3. 每个阶段的主要目标是什么
4. 哪些能力必须在前置阶段完成后才能进入下一阶段
5. 当前有哪些内容严禁提前实现

换句话说，本文档只关心：

**当前实现的依赖顺序。**

### 0.4 本文档不解决什么

本文档不负责以下内容：

1. 不重新定义最小对象模型
2. 不重新定义最小闭环
3. 不重写验证用例
4. 不展开具体代码设计
5. 不展开完整实现细节
6. 不给未来能力做路线图
7. 不新增当前范围外的能力

也就是说：

* **《51》决定边界**
* **《54》决定裁决**
* **《52》决定推进顺序**

当前不得把三者写混。

### 0.5 本文档的使用方式

执行本文档时，必须遵守以下规则：

1. 以《51》中的范围为前提
2. 以《54》中的验收标准为终点
3. 本文档只负责把中间推进过程排顺
4. 本文档未列入当前阶段的内容，不得抢跑
5. 若某项能力尚未成为前置阶段的必要条件，则不得提前实现

### 0.6 本文档的核心目标

本文档当前核心目标只有一个：

**让实现不再靠感觉推进，而是按依赖顺序，分阶段跑通最小正确形态。**

这里强调的是：

* 不是先写“最想写的”
* 不是先写“看起来最厉害的”
* 不是先写“未来最值钱的”
* 而是先写**最依赖、最基础、最能支撑闭环的部分**

### 0.7 本章结论

第 0 章到这里正式冻结以下内容：

1. 本文档是当前 1.0 的实现顺序文档
2. 本文档不定义范围，不定义验收，只定义推进顺序
3. 本文档只解决阶段拆分、依赖顺序和禁止抢跑项
4. 当前执行顺序必须以《51》为边界，以《54》为终点
5. 本文档目标是让当前实现按阶段、按依赖、按闭环推进

## 1. 计划总原则

### 1.1 总原则一：按依赖顺序推进，不按文档顺序推进

当前实现顺序不能按文档编号、讨论顺序或书写顺序推进。

只能按一条原则推进：

**谁是前置依赖，谁先做。**

这意味着：

* 不是因为某个文档先写完，就先实现它对应的所有东西
* 不是因为某个概念更上层，就一定先实现它的全部能力
* 不是因为某个模块更“显眼”，就优先做它

而是：

**先做支撑最小闭环成立的最小依赖。**

### 1.2 总原则二：先跑通最小闭环，再补上层语义

当前实现的第一目标，不是对象齐全，

而是：

**最小闭环跑通。**

所以实现顺序必须遵守：

1. 先让最小链路工作
2. 再让上层语义更完整
3. 再让边界表达更清楚

不能反过来。

也就是说，不允许出现这种顺序：

* 先做很多上层解释性结构
* 先补很多对象字段
* 先做很多未来预留
* 但最小闭环还没跑通

当前阶段，闭环优先级高于对象丰满度。

### 1.3 总原则三：先做最小承接，再做最小协同

当前上层系统里有两类问题：

1. **对象如何被承接**
2. **多个对象如何协同**

当前阶段必须先解决第一类，

再进入第二类。

也就是说，顺序必须是：

* 先让 Solution / Workspace / Project / Node / StepRecord / Tree / Round 这些对象以最小形式成立
* 再让多个 Project 之间发生最小协同
* 再承认派生产物升格

不能先做协同，再补对象承接层。

因为协同没有对象基础就会变成空转。

### 1.4 总原则四：先做显式机制，不做自动机制

当前阶段一切实现都优先采用：

**显式机制。**

也就是说：

* Round 显式创建
* Project 显式切换
* 升格显式发生
* 生命周期先显式表达
* 协同先显式顺序推进

当前不允许因为“未来更智能”而提前引入：

* 自动协同
* 自动升格
* 自动创建 Round
* 自动结束 Round
* 自动生命周期迁移

因为一旦自动机制提前进入，

当前阶段最小正确形态会立刻膨胀。

### 1.5 总原则五：先做当前冻结边界，不做未来扩展准备

当前实现不是为未来搭一个无限扩展平台，

而是先让 1.0 当前边界成立。

所以实现时必须坚持：

* 不为未来多结构类型先做通用框架
* 不为未来完整状态机先做完整引擎
* 不为未来自动编排先做全局调度层
* 不为未来完整 UI 先做重型前端结构

当前允许：

* 适度留注释
* 适度留接口位置
* 适度留 TODO

但不允许：

* 未来能力提前落代码主体

### 1.6 总原则六：阶段结束必须能被验证，不允许“模糊完成”

当前计划中的每个阶段，都必须满足：

* 有明确开始条件
* 有明确完成目标
* 有明确下一阶段入口

不允许以下情况作为阶段完成：

* 差不多写完了
* 基本能用了
* 之后再补几下就行
* 概念上已经成立

当前阶段结束的唯一标准只能是：

**该阶段对应的最小目标是否已经可验证成立。**

### 1.7 总原则七：任何阶段都不得破坏前面已冻结的边界

实现过程中，哪怕当前阶段目标完成了，

如果它破坏了前面已经冻结的边界，也视为失败。

尤其不得破坏以下边界：

* Project 不能退回成 Tree 一级单位
* Workspace 不能被写成 Round
* StepRecord 不能被写成 Round
* 生命周期不能被写成 Node.status 或 Round 状态
* 协同不能被写成并发推进

也就是说：

**计划推进不能以牺牲边界为代价。**

### 1.8 总原则八：当前阶段只追求“最小正确”，不追求“完整漂亮”

这一条必须明确写出来。

因为 AI 和人都很容易被“完整性冲动”带偏，

例如自然想去补：

* 更完整对象模型
* 更漂亮结构分层
* 更智能自动机制
* 更完整 UI
* 更完整未来接口

当前这些都不是目标。

当前目标只有：

**最小正确形态成立。**

所以优先级始终是：

* 正确
* 收敛
* 可跑通
* 可验证

而不是：

* 完整
* 华丽
* 超前

### 1.9 本章结论

第 1 章到这里正式冻结以下内容：

1. 当前实现必须按依赖顺序推进，不按文档顺序推进
2. 当前实现必须先跑通最小闭环，再补上层语义
3. 当前实现必须先做最小承接，再做最小协同
4. 当前实现必须先做显式机制，不做自动机制
5. 当前实现必须先做当前冻结边界，不做未来扩展准备
6. 当前每个阶段都必须可验证完成，不允许模糊完成
7. 当前任何阶段都不得破坏前面已冻结的边界
8. 当前阶段只追求最小正确，不追求完整漂亮


## 2. 实现阶段拆分

### 2.1 总体拆分原则

当前 1.0 的实现，不按“对象多寡”拆，也不按“概念层级”拆。

当前拆分只遵守一条原则：

**每一阶段都必须为下一阶段提供明确前置依赖，并且每一阶段结束后都应形成一个更完整的可运行状态。**

也就是说：

* 阶段不是主题分组
* 阶段不是文档目录映射
* 阶段是施工顺序

当前建议固定拆成  **5 个阶段** ：

1. Project 内部最小内核
2. 上层组织外壳
3. Round 最小承接
4. 最小协同与升格
5. 生命周期最小语义补齐

这 5 个阶段已经足够覆盖当前 1.0 的最小正确形态，

也不会把未来复杂度提前拖进来。

---

### 2.2 第一阶段：Project 内部最小内核

#### 2.2.1 阶段目标

先让单个 Project 内部的最小推进能力成立。

这一阶段要解决的是：

**如果没有上层 Solution / Workspace / Round，仅在单个 Project 内，能否完成一次最小推进并留下记录。**

#### 2.2.2 本阶段必须完成的对象

本阶段只实现以下最小对象：

* Tree
* Node
* StepRecord
* Scheduler（最小语义）
* Rescan（最小语义）

#### 2.2.3 本阶段必须完成的能力

必须至少成立：

1. Project 内部可存在 Tree
2. Tree 中可创建或进入 Node
3. Node 能承接最小内容语义
4. Node 能完成一次最小推进
5. 推进后能生成 StepRecord
6. 推进后能更新 Node / Tree
7. 能留下下一步入口

#### 2.2.4 本阶段不做什么

当前阶段不做：

* Solution
* Workspace
* Round
* 多 Project 协同
* 升格
* 生命周期完整表达

#### 2.2.5 阶段完成标志

当下面条件同时成立时，第一阶段完成：

* 单个 Project 内部最小推进闭环成立
* StepRecord 可以正确生成
* Node / Tree 可继续承接下一步入口

可以直接压成一句话：

**先把 Project 内部最小推进做成一个能独立工作的内核。**

---

### 2.3 第二阶段：上层组织外壳

#### 2.3.1 阶段目标

在第一阶段成立的基础上，补上最小上层组织容器。

这一阶段要解决的是：

**Project 内部最小推进已经成立之后，它如何被正式放进一个问题空间和当前工作上下文中。**

#### 2.3.2 本阶段必须完成的对象

本阶段实现以下最小对象：

* Solution
* Workspace
* Project（上层对象定位）

注意：

* 这里不是重新实现 Project 内部内核
* 而是把 Project 作为一级独立工作对象正式放进上层组织中

#### 2.3.3 本阶段必须完成的能力

必须至少成立：

1. 能创建 Solution
2. 能在 Solution 下创建 Project
3. Workspace 能绑定当前 Solution
4. Workspace 能选中当前焦点 Project
5. 当前焦点 Project 能连接到第一阶段已成立的内部最小内核

#### 2.3.4 本阶段不做什么

当前阶段不做：

* Round
* 多 Project 协同
* 升格
* 生命周期完整表达
* 完整 UI

#### 2.3.5 阶段完成标志

当下面条件同时成立时，第二阶段完成：

* Solution / Workspace / Project 的最小组织关系成立
* 焦点 Project 可被 Workspace 正式承接
* 焦点 Project 内部能继续调用第一阶段内核

可以直接压成一句话：

**让已经能工作的 Project，有正式的上层容器与当前工作上下文。**

---

### 2.4 第三阶段：Round 最小承接

#### 2.4.1 阶段目标

在上层组织外壳成立后，补上跨 Project 变化承接层。

这一阶段要解决的是：

**系统不再只知道“当前在做什么 Project”，还要知道“当前这次变化是什么”。**

#### 2.4.2 本阶段必须完成的对象

本阶段实现：

* Round（最小版）

#### 2.4.3 本阶段必须完成的能力

必须至少成立：

1. 当变化超出单 Project 内部时，可以显式创建 Round
2. Round 至少承接：

* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮下一步入口

1. Round 能与当前 Workspace / Project 形成最小挂接
2. Round 与 StepRecord / Workspace / Project 的边界不被写混

#### 2.4.4 本阶段不做什么

当前阶段不做：

* 完整 Round 状态机
* 自动创建 / 自动结束 / 自动拆分
* 多 Round 并发
* Round 嵌套

#### 2.4.5 阶段完成标志

当下面条件同时成立时，第三阶段完成：

* 系统可以显式创建并承接一个最小 Round
* Round 能和当前 Workspace / Project 配合
* Round 不与 StepRecord 或 Workspace 混层

可以直接压成一句话：

**让系统正式拥有“这次变化”的承接能力。**

---

### 2.5 第四阶段：最小协同与升格

#### 2.5.1 阶段目标

在 Round 成立后，补上最小多 Project 顺序协同与最小派生升格能力。

这一阶段要解决的是：

**多个 Project 已经存在、当前这次变化也已成立之后，它们如何顺序协同，以及结果何时成为新的 Project。**

#### 2.5.2 本阶段必须完成的能力

必须至少成立：

1. 一个 Round 可以涉及多个 Project
2. 当前 Project 推进到明确断点后，能显式切换到另一个 Project
3. 切换后 Workspace / Round / Project 三层语义保持清楚
4. 某个结果在满足独立工作面条件后，可以显式升格为新的 Project
5. 新 Project 能挂回当前 Solution，并可被 Workspace 选中

#### 2.5.3 本阶段不做什么

当前阶段不做：

* 自动协同编排
* 自动升格
* 完整协同关系图谱
* 完整派生产物分类体系

#### 2.5.4 阶段完成标志

当下面条件同时成立时，第四阶段完成：

* 多 Project 协同能够通过顺序推进发生
* Project 切换是显式动作
* 最小升格语义成立
* 新 Project 能被正式纳入当前 Solution

可以直接压成一句话：

**让多个 Project 开始被正式组织起来，并允许结果长成新的工作面。**

---

### 2.6 第五阶段：生命周期最小语义补齐

#### 2.6.1 阶段目标

在对象、变化、协同都已成立后，补上 Project 作为工作对象的最小存续语义。

这一阶段要解决的是：

**Project 不再只是“创建了就一直挂着”，而是具有最小生命周期表达。**

#### 2.6.2 本阶段必须完成的能力

必须至少成立：

1. Project 能表达：

* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档

1. 生命周期语义独立于：

* Node.status
* Round 状态
* Workspace 焦点

1. 生命周期语义能被当前系统正式承认，而不是注释性说明

#### 2.6.3 本阶段不做什么

当前阶段不做：

* 完整生命周期状态机
* 自动迁移
* 自动归档
* 完整记忆 / 保留策略系统

#### 2.6.4 阶段完成标志

当下面条件同时成立时，第五阶段完成：

* Project 生命周期四段最小语义成立
* 生命周期和其他状态层边界清楚
* 生命周期已能作为正式语义进入系统

可以直接压成一句话：

**让 Project 作为工作对象，不只是能被创建和推进，还能被正式表达其整体存续状态。**

---

### 2.7 五阶段之间的依赖关系

当前五个阶段之间的依赖关系固定如下：

#### 第一阶段 → 第二阶段

因为没有 Project 内部最小推进内核，

上层组织外壳会变成空容器。

#### 第二阶段 → 第三阶段

因为没有 Solution / Workspace / Project，

Round 没有落点。

#### 第三阶段 → 第四阶段

因为没有 Round，

跨 Project 的正式协同变化无法被承接。

#### 第四阶段 → 第五阶段

因为没有最小协同与升格，

生命周期的补齐会缺少真实工作对象关系背景。

也就是说，当前顺序不是可交换的，

至少核心方向上不可逆。

---

### 2.8 当前阶段拆分的压缩版

如果把这一章压成一句正式执行结论，可以写成：

> 当前 1.0 的实现固定拆分为五个阶段：先完成 Project 内部最小推进内核，再补上 Solution / Workspace / Project 的上层组织外壳，然后补上 Round 的最小变化承接，再实现最小多 Project 顺序协同与结果升格，最后补上 Project 生命周期的最小语义。
>
> 这五个阶段按依赖顺序推进，不允许跳阶段抢跑。

---

### 2.9 本章结论

第 2 章到这里正式冻结以下内容：

1. 当前 1.0 的实现固定拆分为 5 个阶段
2. 第一阶段：Project 内部最小内核
3. 第二阶段：上层组织外壳
4. 第三阶段：Round 最小承接
5. 第四阶段：最小协同与升格
6. 第五阶段：生命周期最小语义补齐
7. 五个阶段之间存在明确依赖关系，不允许跳阶段推进
8. 每个阶段都必须在完成前一阶段最小目标后再进入下一阶段
9. 当前阶段拆分只服务于最小正确形态成立，不服务于未来能力扩展

2. 上层组织外壳
3. Round 最小承接
4. 最小协同与升格
5. 生命周期最小语义补齐

这 5 个阶段已经足够覆盖当前 1.0 的最小正确形态，

也不会把未来复杂度提前拖进来。

---

### 2.2 第一阶段：Project 内部最小内核

#### 2.2.1 阶段目标

先让单个 Project 内部的最小推进能力成立。

这一阶段要解决的是：

**如果没有上层 Solution / Workspace / Round，仅在单个 Project 内，能否完成一次最小推进并留下记录。**

#### 2.2.2 本阶段必须完成的对象

本阶段只实现以下最小对象：

* Tree
* Node
* StepRecord
* Scheduler（最小语义）
* Rescan（最小语义）

#### 2.2.3 本阶段必须完成的能力

必须至少成立：

1. Project 内部可存在 Tree
2. Tree 中可创建或进入 Node
3. Node 能承接最小内容语义
4. Node 能完成一次最小推进
5. 推进后能生成 StepRecord
6. 推进后能更新 Node / Tree
7. 能留下下一步入口

#### 2.2.4 本阶段不做什么

当前阶段不做：

* Solution
* Workspace
* Round
* 多 Project 协同
* 升格
* 生命周期完整表达

#### 2.2.5 阶段完成标志

当下面条件同时成立时，第一阶段完成：

* 单个 Project 内部最小推进闭环成立
* StepRecord 可以正确生成
* Node / Tree 可继续承接下一步入口

可以直接压成一句话：

**先把 Project 内部最小推进做成一个能独立工作的内核。**

---

### 2.3 第二阶段：上层组织外壳

#### 2.3.1 阶段目标

在第一阶段成立的基础上，补上最小上层组织容器。

这一阶段要解决的是：

**Project 内部最小推进已经成立之后，它如何被正式放进一个问题空间和当前工作上下文中。**

#### 2.3.2 本阶段必须完成的对象

本阶段实现以下最小对象：

* Solution
* Workspace
* Project（上层对象定位）

注意：

* 这里不是重新实现 Project 内部内核
* 而是把 Project 作为一级独立工作对象正式放进上层组织中

#### 2.3.3 本阶段必须完成的能力

必须至少成立：

1. 能创建 Solution
2. 能在 Solution 下创建 Project
3. Workspace 能绑定当前 Solution
4. Workspace 能选中当前焦点 Project
5. 当前焦点 Project 能连接到第一阶段已成立的内部最小内核

#### 2.3.4 本阶段不做什么

当前阶段不做：

* Round
* 多 Project 协同
* 升格
* 生命周期完整表达
* 完整 UI

#### 2.3.5 阶段完成标志

当下面条件同时成立时，第二阶段完成：

* Solution / Workspace / Project 的最小组织关系成立
* 焦点 Project 可被 Workspace 正式承接
* 焦点 Project 内部能继续调用第一阶段内核

可以直接压成一句话：

**让已经能工作的 Project，有正式的上层容器与当前工作上下文。**

---

### 2.4 第三阶段：Round 最小承接

#### 2.4.1 阶段目标

在上层组织外壳成立后，补上跨 Project 变化承接层。

这一阶段要解决的是：

**系统不再只知道“当前在做什么 Project”，还要知道“当前这次变化是什么”。**

#### 2.4.2 本阶段必须完成的对象

本阶段实现：

* Round（最小版）

#### 2.4.3 本阶段必须完成的能力

必须至少成立：

1. 当变化超出单 Project 内部时，可以显式创建 Round
2. Round 至少承接：

* 本轮变化目标
* 本轮涉及的 Project 范围
* 本轮当前状态
* 本轮下一步入口

1. Round 能与当前 Workspace / Project 形成最小挂接
2. Round 与 StepRecord / Workspace / Project 的边界不被写混

#### 2.4.4 本阶段不做什么

当前阶段不做：

* 完整 Round 状态机
* 自动创建 / 自动结束 / 自动拆分
* 多 Round 并发
* Round 嵌套

#### 2.4.5 阶段完成标志

当下面条件同时成立时，第三阶段完成：

* 系统可以显式创建并承接一个最小 Round
* Round 能和当前 Workspace / Project 配合
* Round 不与 StepRecord 或 Workspace 混层

可以直接压成一句话：

**让系统正式拥有“这次变化”的承接能力。**

---

### 2.5 第四阶段：最小协同与升格

#### 2.5.1 阶段目标

在 Round 成立后，补上最小多 Project 顺序协同与最小派生升格能力。

这一阶段要解决的是：

**多个 Project 已经存在、当前这次变化也已成立之后，它们如何顺序协同，以及结果何时成为新的 Project。**

#### 2.5.2 本阶段必须完成的能力

必须至少成立：

1. 一个 Round 可以涉及多个 Project
2. 当前 Project 推进到明确断点后，能显式切换到另一个 Project
3. 切换后 Workspace / Round / Project 三层语义保持清楚
4. 某个结果在满足独立工作面条件后，可以显式升格为新的 Project
5. 新 Project 能挂回当前 Solution，并可被 Workspace 选中

#### 2.5.3 本阶段不做什么

当前阶段不做：

* 自动协同编排
* 自动升格
* 完整协同关系图谱
* 完整派生产物分类体系

#### 2.5.4 阶段完成标志

当下面条件同时成立时，第四阶段完成：

* 多 Project 协同能够通过顺序推进发生
* Project 切换是显式动作
* 最小升格语义成立
* 新 Project 能被正式纳入当前 Solution

可以直接压成一句话：

**让多个 Project 开始被正式组织起来，并允许结果长成新的工作面。**

---

### 2.6 第五阶段：生命周期最小语义补齐

#### 2.6.1 阶段目标

在对象、变化、协同都已成立后，补上 Project 作为工作对象的最小存续语义。

这一阶段要解决的是：

**Project 不再只是“创建了就一直挂着”，而是具有最小生命周期表达。**

#### 2.6.2 本阶段必须完成的能力

必须至少成立：

1. Project 能表达：

* 创建
* 活跃
* 暂停 / 封存
* 结束 / 归档

1. 生命周期语义独立于：

* Node.status
* Round 状态
* Workspace 焦点

1. 生命周期语义能被当前系统正式承认，而不是注释性说明

#### 2.6.3 本阶段不做什么

当前阶段不做：

* 完整生命周期状态机
* 自动迁移
* 自动归档
* 完整记忆 / 保留策略系统

#### 2.6.4 阶段完成标志

当下面条件同时成立时，第五阶段完成：

* Project 生命周期四段最小语义成立
* 生命周期和其他状态层边界清楚
* 生命周期已能作为正式语义进入系统

可以直接压成一句话：

**让 Project 作为工作对象，不只是能被创建和推进，还能被正式表达其整体存续状态。**

---

### 2.7 五阶段之间的依赖关系

当前五个阶段之间的依赖关系固定如下：

#### 第一阶段 → 第二阶段

因为没有 Project 内部最小推进内核，

上层组织外壳会变成空容器。

#### 第二阶段 → 第三阶段

因为没有 Solution / Workspace / Project，

Round 没有落点。

#### 第三阶段 → 第四阶段

因为没有 Round，

跨 Project 的正式协同变化无法被承接。

#### 第四阶段 → 第五阶段

因为没有最小协同与升格，

生命周期的补齐会缺少真实工作对象关系背景。

也就是说，当前顺序不是可交换的，

至少核心方向上不可逆。

---

### 2.8 当前阶段拆分的压缩版

如果把这一章压成一句正式执行结论，可以写成：

> 当前 1.0 的实现固定拆分为五个阶段：先完成 Project 内部最小推进内核，再补上 Solution / Workspace / Project 的上层组织外壳，然后补上 Round 的最小变化承接，再实现最小多 Project 顺序协同与结果升格，最后补上 Project 生命周期的最小语义。
>
> 这五个阶段按依赖顺序推进，不允许跳阶段抢跑。

### 2.9 本章结论

第 2 章到这里正式冻结以下内容：

1. 当前 1.0 的实现固定拆分为 5 个阶段
2. 第一阶段：Project 内部最小内核
3. 第二阶段：上层组织外壳
4. 第三阶段：Round 最小承接
5. 第四阶段：最小协同与升格
6. 第五阶段：生命周期最小语义补齐
7. 五个阶段之间存在明确依赖关系，不允许跳阶段推进
8. 每个阶段都必须在完成前一阶段最小目标后再进入下一阶段
9. 当前阶段拆分只服务于最小正确形态成立，不服务于未来能力扩展

## 4. 当前实现顺序中的禁止事项

### 4.1 本章目标

前面三章已经明确了：

* 这份文档只负责实现顺序
* 当前必须按依赖顺序推进
* 当前实现已经拆成 5 个阶段
* 每个阶段都有输入、输出和完成条件

如果这时不明确“禁止事项”，

AI 和人都会自然出现一种倾向：

**明明当前阶段还没完成，却顺手把后面更复杂、更完整、更未来的东西提前做进去。**

所以本章的目标是：

**卡住抢跑。**

---

### 4.2 禁止跳过第一阶段直接做上层对象

当前明确禁止：

* 在 Project 内部最小推进内核未成立前，先去实现完整 Solution / Workspace / Round 逻辑
* 在 Node / Tree / StepRecord 最小闭环未成立前，先去实现多 Project 组织关系

原因很简单：

如果第一阶段没完成，

后面的 Solution / Workspace / Project / Round 都会失去实际落点，

最后只能变成：

* 空壳对象
* 伪上层结构
* 只有概念没有承接能力的容器

所以当前明确禁止：

**跳过 Project 内部最小内核，直接做上层。**

---

### 4.3 禁止在第二阶段提前做完整 UI

当前明确禁止：

* 在上层组织外壳刚成立时，就开始实现完整 Workspace 页面
* 提前实现多面板布局、标签系统、交互系统、可视化结构界面

原因是：

当前第二阶段只要求：

* Solution 成立
* Workspace 成立
* Project 作为一级对象挂接进去
* 焦点 Project 能被正式承接

它不要求：

* 完整产品界面
* 完整可视化交互

所以当前明确禁止：

**把 Workspace 的语义成立，误做成完整 UI 设计。**

---

### 4.4 禁止在第三阶段提前做完整 Round 状态机

当前明确禁止：

* 在 Round 最小承接刚成立时，就开始实现完整状态机
* 提前补：
* 自动开始
* 自动结束
* 自动拆分
* 自动合并
* 回退 / 重开
* 多状态流转表

当前第三阶段只要求：

* Round 最小对象成立
* Round 最小骨架成立
* Round 能承接当前变化

它不要求：

* 完整变化管理系统

所以当前明确禁止：

**用完整 Round 系统替代最小 Round 承接。**

---

### 4.5 禁止在第四阶段提前做自动协同与自动升格

当前明确禁止：

* 自动判断哪些 Project 进入当前 Round
* 自动排列协同顺序
* 自动切换当前焦点 Project
* 自动判断某个结果是否应升格为新 Project
* 自动创建派生 Project

当前第四阶段只要求：

* 顺序协同成立
* 显式切换成立
* 显式升格成立

也就是说，这一阶段必须先验证：

**人或系统在显式边界下，最小协同与升格是否成立。**

而不是去做自动化版本。

所以当前明确禁止：

**在最小协同刚成立时，就把它升级成自动协同系统。**

---

### 4.6 禁止在第五阶段提前做完整生命周期系统

当前明确禁止：

* 自动生命周期迁移
* 自动归档
* 自动升格 / 降级
* 完整生命周期状态机
* 完整记忆裁剪 / 保留策略系统

当前第五阶段只要求：

* Project 能表达四段最小生命周期语义
* 生命周期和其他状态轴边界清楚

它不要求：

* 自动运行的生命周期引擎

所以当前明确禁止：

**用完整生命周期系统替代最小生命周期语义补齐。**

---

### 4.7 禁止提前引入未来结构类型

当前明确禁止：

* 在当前默认 Tree 结构未跑通前，提前引入：
* Linear
* Hybrid
* Graph
* 多结构切换机制
* 结构兼容抽象层

当前版本已经明确：

**Project 当前默认采用 Tree 结构。**

所以当前禁止：

* 为未来结构扩展做正式落地实现
* 为未来泛化而牺牲当前收敛性

允许：

* 在注释中提及后续可能扩展

不允许：

* 把未来结构先写进当前系统主体

---

### 4.8 禁止为了“更通用”而重做当前冻结边界

当前明确禁止以下行为：

* 把 Project 改写回 Tree 一级单位
* 把 Workspace 做成 Round 的附属对象
* 把 StepRecord 上浮为 Round 的替代物
* 把生命周期写成 Node.status 或 Round 状态的派生
* 把协同写成并发推进

原因是：

这些都不是“更通用”，

而是直接破坏了已经冻结的边界。

所以当前明确禁止：

**以“为了更优雅 / 更统一 / 更抽象”为理由，重写已冻结边界。**

---

### 4.9 禁止在任何阶段引入新的核心对象层

当前明确禁止：

* 在实现过程中擅自新增新的核心对象层

  例如：

* GlobalOrchestrator
* ProjectManager
* RoundEngine
* LifecycleEngine
* DependencyGraph
* PromptCompiler

除非它们只是：

* 实现细节中的局部辅助类
* 且不改变当前对象边界

也就是说：

**可以有辅助实现，不可以增加新的核心概念层。**

---

### 4.10 禁止以“先做一点”名义落地明确不实现项

当前明确禁止这种行为：

* 虽然《51》里写了不实现，但先做一个最小版
* 虽然现在不需要，但先留个正式能力入口
* 虽然不验收，但先把主体逻辑写了

这些都属于：

**借“最小版”之名，行越界实现之实。**

当前规则非常明确：

* 不实现 = 当前不做
* 不验收 = 当前不写
* 不冻结 = 当前不落地

---

### 4.11 禁止脱离《54》写“阶段完成”

当前还必须禁止一种常见错误：

**只根据实现感觉宣布某阶段完成。**

当前阶段完成必须同时满足：

1. 本文档第 3 章中的完成条件成立
2. 后续《54-验证用例.md》中对应验证能够通过

所以禁止出现以下说法：

* 这一阶段差不多完成了
* 逻辑上已经有了
* 还没验证但应该问题不大
* 先进入下一阶段，后面再测

当前规则是：

**阶段完成必须能被验证，不接受凭感觉推进。**

---

### 4.12 本章结论

第 4 章到这里正式冻结以下内容：

1. 禁止跳过第一阶段直接做上层对象
2. 禁止在第二阶段提前做完整 UI
3. 禁止在第三阶段提前做完整 Round 状态机
4. 禁止在第四阶段提前做自动协同与自动升格
5. 禁止在第五阶段提前做完整生命周期系统
6. 禁止提前引入未来结构类型
7. 禁止以“更通用”为理由重写已冻结边界
8. 禁止在任何阶段擅自新增新的核心对象层
9. 禁止以“先做一点”为理由落地明确不实现项
10. 禁止脱离《54》仅凭感觉宣布某阶段完成

## 5. 本次实现计划结论

### 5.1 本章目标

本章用于把整份《52-实现计划.md》压成一组可以直接执行的正式结论。

它不再补新信息，

而是把前面 0–4 章已经冻结的内容收成：

* 当前实现怎么推进
* 当前不允许怎么推进
* 当前到底先做到哪里

---

### 5.2 当前实现的总顺序

当前 1.0 的实现总顺序固定为：

1. **Project 内部最小内核**
2. **上层组织外壳**
3. **Round 最小承接**
4. **最小协同与升格**
5. **生命周期最小语义补齐**

这 5 个阶段就是当前实现计划的正式主顺序。

后续执行不得改写为：

* 先做 UI
* 先做自动化
* 先做未来能力
* 先做完整状态机

---

### 5.3 当前实现的核心目标

当前实现计划的核心目标只有一个：

**按依赖顺序，把 Ascend 1.0 的最小正确形态做成可运行、可继续、可验证的系统。**

这个目标可以再压成三条：

1. 让单个 Project 内部最小推进成立
2. 让上层 Solution / Workspace / Project / Round 成立
3. 让最小协同、最小升格、最小生命周期语义成立

当前不要求：

* 完整系统
* 完整产品
* 完整自动化平台

---

### 5.4 当前每阶段的正式完成定义

当前阶段的正式完成定义如下：

#### 第一阶段完成

当单个 Project 内部最小推进闭环成立时完成。

#### 第二阶段完成

当 Solution / Workspace / Project 的最小组织关系成立时完成。

#### 第三阶段完成

当最小 Round 变化承接能力成立时完成。

#### 第四阶段完成

当最小协同与最小升格能力成立时完成。

#### 第五阶段完成

当 Project 生命周期四段最小语义成立时完成。

只有这五个完成定义依次成立，

当前 1.0 的实现计划才算真正执行完成。

---

### 5.5 当前实现的最终推进规则

当前实现推进时，必须同时遵守以下规则：

1. 按依赖顺序推进
2. 不跳阶段
3. 不抢跑未来能力
4. 不重写冻结边界
5. 不提前实现明确不实现项
6. 每阶段完成都必须能被《54》验证

也就是说，当前推进规则不是：

* 先做最想做的
* 先做最完整的
* 先做未来最值钱的

而是：

**先做最依赖、最基础、最能支撑闭环成立的部分。**

---

### 5.6 当前实现的禁止性结论

为了防止歧义，本次实现计划还需要明确一组禁止性结论：

* 不得以 UI 替代上层语义成立
* 不得以完整状态机替代最小对象承接
* 不得以自动机制替代显式机制
* 不得以未来扩展准备替代当前最小实现
* 不得以“更通用”名义破坏冻结边界
* 不得以“做得更多”作为越界实现的理由

当前 1.0 的判断标准不是“功能更多”，

而是：

**是否严格按最小正确形态成立。**
